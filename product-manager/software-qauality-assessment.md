## Software Quality Assessment based on Lifecycle Expectations
> Оценка качества программного обеспечения на основе ожиданий жизненного цикла

**Software Quality Assessment based on Lifecycle Expectations** — это оценка качества ПО не «вообще», а **в привязке к этапу жизненного цикла** (требования, разработка, тестирование, релиз, поддержка) и к тем ожиданиям, которые для этого этапа важны.

**Суть**

На каждом этапе у качества «своё лицо»:

- **На этапе требований**: качество = полнота, непротиворечивость, тестируемость.
- **На этапе разработки**: качество = соответствие стандартам (Checkstyle), отсутствие критических уязвимостей (SonarQube), покрытие тестами.
- **Перед релизом**: качество = стабильность, отсутствие дефектов высокого приоритета, соответствие комплаенс‑правилам.
- **В поддержке**: качество = скорость исправления багов, предсказуемость патчей, стабильность на проде.

То есть метрики и критерии успеха меняются: то, что критично на этапе релиза (например, отсутствие уязвимостей CVE), не обязательно должно быть главным на этапе прототипирования.

---

### Качество на практике

| Этап | Ожидания от качества | Инструменты/практики |
| --- | --- | --- |
| **Требования / дизайн** | Чёткие use case, согласованные статусы и переходы, понятная архитектура (C4) | Use Case Diagram, C4‑диаграммы, согласования в Jira |
| **Разработка** | Чистый код, стиль, отсутствие «запахов» | Checkstyle, SonarQube, ревью кода |
| **CI / сборка** | Стабильные сборки, воспроизводимость, соответствие политикам | Maven, CI‑пайплайны, правила веток, запрет force push на release |
| **Тестирование** | Покрытие юнит‑ и интеграционными тестами, проверка граничных случаев | JUnit, Testcontainers, сценарии по альтернативным потокам use case |
| **Релиз** | Отсутствие критических дефектов, подтверждённая версия (тег), changelog | Git‑теги, Argo CD, отчёты SonarQube |
| **Поддержка** | Скорость реакции на инциденты, контролируемые хотфиксы | Jira SLA, хотфикс‑теги, откат по тегу |

---

### Практическая значимость

- **Комплаенс и аудит**: проверяющие смотрят не «сколько всего ошибок», а «соответствуют ли критерии качества ожиданиям этапа» (например, «на релизе не должно быть уязвимостей High/Critical»).
- **CI/CD**: пайплайн можно строить как последовательность «ворот качества» (quality gates) для каждого этапа: не прошёл этап — не идёт дальше.
- **Разные этапы требуют разных проверок**: на коммите достаточно Checkstyle, на PR — SonarQube и тесты, на теге — полная сборка и сканирование уязвимостей.
- **Документация (C4)**: диаграммы и спецификации тоже оцениваются по «этапной зрелости»: на уровне C1 достаточно контекста, на уровне C3 — детальных activity/sequence диаграмм и use case.
