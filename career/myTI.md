## Java: В чём разница между fail-fast и fail-safe итераторами?
| Характеристика                | fail-fast                                   | fail-safe                                   |
| ----------------------------- | ------------------------------------------- | ------------------------------------------- |
| **Поведение при модификации** | Бросает `ConcurrentModificationException`   | Продолжает итерацию по снапшоту             |
| **Механизм**                  | Проверяет `modCount` при каждом вызове      | Итерирует по копии коллекции                |
| **Примеры**                   | `ArrayList`, `HashSet`, `HashMap`           | `CopyOnWriteArrayList`, `ConcurrentHashMap` |
| **Оверхед**                   | Низкий                                      | Высокий (копирование данных)                |
| **Актуальность данных**       | Всегда актуальные                           | Данные на момент создания снапшота          |
| **Потокобезопасность**        | Нет (один поток)                            | Да (для чтения)                             |
| **Использование**             | Однопоточный код, раннее обнаружение ошибок | Многопоточное чтение с редкими записями     |

## Spring: Что такое ApplicationContext? Отличие от BeanFactory?

**ApplicationContext** — расширенный контейнер Spring, управляющий бинами и предоставляющий enterprise-функции.  
**BeanFactory** — базовый DI-контейнер с минимальной функциональностью.

**Отличия:**

| Характеристика                 | BeanFactory                   | ApplicationContext         |
| ------------------------------ | ----------------------------- | -------------------------- |
| Инициализация синглтонов       | Ленивая (при getBean)         | Eager (при старте)         |
| Интернационализация ([[i18n]]) | Нет                           | Да (MessageSource)         |
| События (ApplicationEvent)     | Нет                           | Да (@EventListener)        |
| AOP / проксирование            | Вручную                       | Автоматически              |
| Загрузка ресурсов              | Нет                           | Да (ResourceLoader)        |
| Поддержка веб                  | Нет                           | Да (WebApplicationContext) |
| Использование по умолчанию     | Редко (в legacy или embedded) | Всегда в Spring Boot       |

**Итог:** `ApplicationContext` — надстройка над `BeanFactory`, используется в 99% случаев.

## Spring: Какие типы сделать инжект бина существуют? Когда какой использовать?

**Типы инжекции бинов в Spring:**

| Тип                 | Синтаксис                                              | Когда использовать                                                                      |
| ------------------- | ------------------------------------------------------ | --------------------------------------------------------------------------------------- |
| **Конструктор**     | `public MyBean(Dependency dep) {}`                     | **По умолчанию** — иммутабельность, final поля, обязательные зависимости, тестируемость |
| **Сеттер**          | `@Autowired public void setDep(Dependency dep) {}`     | Опциональные зависимости, зависимости, которые можно менять после создания              |
| **Поле**            | `@Autowired private Dependency dep;`                   | Прототипы, быстрые прототипы (минус: сложно тестировать, нет final)                     |
| **Параметр метода** | `@Autowired public void register(Dep1 d1, Dep2 d2) {}` | Обработчики, слушатели, специфичные сценарии                                            |

**Рекомендации:**

| Сценарий                                        | Рекомендуемый тип                                                       |
| ----------------------------------------------- | ----------------------------------------------------------------------- |
| Обязательные зависимости (сервисы, репозитории) | **Конструктор** (без `@Autowired` при одном конструкторе в Spring 4.3+) |
| Опциональные (логирование, метрики)             | **Сеттер** с `required=false`                                           |
| Зависимости с циклическими ссылками             | **Сеттер** или `@Lazy` (конструктор не разрешит)                        |
| Тестируемость                                   | **Конструктор** (легко передать моки)                                   |
| Immutable классы                                | **Конструктор** (final поля)                                            |

## Паттерны: В чём разница между Factory, Abstract Factory и Builder?

**Factory, Abstract Factory, Builder** — порождающие паттерны. Разница — в уровне абстракции и назначении.

**Сравнение:**

| Характеристика         | Factory Method                                 | Abstract Factory                                          | Builder                                                        |
| ---------------------- | ---------------------------------------------- | --------------------------------------------------------- | -------------------------------------------------------------- |
| **Назначение**         | Создание одного продукта                       | Создание семейства связанных продуктов                    | Пошаговое создание сложного объекта                            |
| **Возвращает**         | Один объект                                    | Группа объектов (семейство)                               | Один объект (часто с состоянием)                               |
| **Способ**             | Один метод (фабричный)                         | Интерфейс с несколькими методами                          | Цепочка методов (fluent)                                       |
| **Когда использовать** | Иерархия продуктов, неизвестный конкретный тип | Нужно обеспечить совместимость продуктов одного семейства | Много параметров, невалидные промежуточные состояния, вариации |
| **Пример в Java**      | `Collection.iterator()`                        | `DocumentBuilderFactory`                                  | `StringBuilder`, `Stream.builder()`                            |

## Паттерны: Объясните Proxy vs Decorator. Примеры в Spring.

**Proxy** и **Decorator** — структурные паттерны, оба оборачивают объект, но цели разные.

**Сравнение:**

| Характеристика                  | Proxy                                                          | Decorator                                      |
| ------------------------------- | -------------------------------------------------------------- | ---------------------------------------------- |
| **Назначение**                  | Контроль доступа, ленивая инициализация, логирование, security | Динамическое добавление новой функциональности |
| **Изменяет интерфейс**          | Нет (тот же интерфейс)                                         | Нет (тот же интерфейс)                         |
| **Создаёт ли новый функционал** | Нет (управляет существующим)                                   | Да (расширяет поведение)                       |
| **Отношение к оригиналу**       | Контролирует доступ                                            | Обогащает поведение                            |
| **Время жизни**                 | Создаётся один раз, переиспользуется                           | Можно оборачивать несколько раз (композиция)   |


**Примеры в Spring:**

| Паттерн | Пример в Spring |
|---------|----------------|
| **Proxy** | `@Transactional` — прокси управляет транзакцией (открытие/коммит/откат) |
| **Proxy** | `@Cacheable` — проверяет кэш до вызова метода |
| **Proxy** | `@Async` — выполняет метод в отдельном потоке |
| **Proxy** | Spring Security — проверяет роли до вызова |
| **Decorator** | `BufferedInputStream` (Java IO, не Spring) — добавляет буферизацию |
| **Decorator** | `HttpServletRequestWrapper` в Spring Security — добавляет методы для безопасности |
| **Decorator** | Декораторы бинов через `@Primary` + композицию |

**Кодовая разница:**

```java
// Proxy — контролирует доступ
class TransactionProxy implements Service {
    private Service target;
    public void execute() {
        beginTx();
        target.execute();
        commitTx();
    }
}

// Decorator — добавляет функционал
class LoggingDecorator implements Service {
    private Service wrapped;
    public void execute() {
        log("start");
        wrapped.execute();
        log("end");
    }
}
```

**Итог:** Proxy управляет доступом (транзакции, кэш, lazy loading), Decorator расширяет поведение (добавляет логирование, сжатие, шифрование).

## Архитектура: Чем CQRS отличается от Event Sourcing? Могут ли быть без друг друга?

**CQRS** (Command Query Responsibility Segregation) и **Event Sourcing** — разные паттерны, часто используются вместе, но могут существовать независимо.

**Сравнение:**

| Характеристика     | CQRS                                  | Event Sourcing                                    |
| ------------------ | ------------------------------------- | ------------------------------------------------- |
| **Суть**           | Разделение моделей на чтение и запись | Хранение состояния как последовательности событий |
| **Хранит**         | Текущее состояние (обычно)            | Все события (аудит, полная история)               |
| **Запись**         | Обновляет текущее состояние           | Добавляет события в неизменяемый журнал           |
| **Чтение**         | Изолированная модель чтения           | Восстанавливается из событий (snapshot + replay)  |
| **Главная выгода** | Масштабирование, независимые модели   | Полный аудит, time travel, replay                 |

**Могут ли быть без друг друга?**

| Комбинация                | Возможна? | Пример                                                                             |
| ------------------------- | --------- | ---------------------------------------------------------------------------------- |
| **Только CQRS**           | ✅ Да      | Обычное приложение с разделением команд/запросов, но хранит текущее состояние в БД |
| **Только Event Sourcing** | ✅ Да      | Система с событиями, но единая модель для команд и запросов                        |
| **CQRS + Event Sourcing** | ✅ Да      | Команды → события → обновление read-моделей (классика)                             |

**Примеры:**

```java
// Только CQRS
class UserService {
    // Command
    void updateEmail(userId, email) → обновить строку в users_table
    
    // Query
    UserDto getUser(userId) → SELECT * FROM users_table
}

// Только Event Sourcing (без CQRS)
class UserAccount {
    void updateEmail(email) → append Event{EmailChanged}
    String getEmail() → rebuild from events
}

// CQRS + Event Sourcing
class UserCommands {
    void updateEmail(userId, email) → append Event → update read-db
}
class UserQueries {
    UserDto get(userId) → query read-db (не восстанавливает из событий!)
}
```

**Итог:** Паттерны ортогональны. CQRS про разделение ответственности, Event Sourcing про хранение истории. Вместе дают максимальную гибкость, но сложность выше.

## Архитектура: Какие проблемы решает Circuit Breaker? Пример в микросервисах.

**Circuit Breaker** — паттерн для защиты системы от каскадных отказов при вызовах удалённых сервисов.

**Проблемы, которые решает:**

| Проблема | Описание |
|----------|----------|
| **Таймауты без ответа** | Ждать каждый раз → блокировка потоков |
| **Каскадные отказы** | Сервис A падает → B ждёт → C ждёт → вся система виснет |
| **Перегрузка больного сервиса** | Неудачные вызовы только ухудшают его состояние |
| **Пустая трата ресурсов** | Вызовы, которые всё равно упадут |

**Состояния Circuit Breaker:**

| Состояние | Поведение |
|-----------|-----------|
| **Closed** (норма) | Выполняются запросы, ошибки подсчитываются |
| **Open** (разомкнут) | Запросы блокируются мгновенно (fail fast) |
| **Half-Open** (проверка) | Пропускается пробный запрос, если успех → Closed, если нет → Open |

**Пример в микросервисах (Resilience4j + Spring Boot):**

```java
@Service
public class PaymentService {
    
    @CircuitBreaker(name = "paymentService", fallbackMethod = "fallback")
    public PaymentResult processPayment(PaymentRequest request) {
        return paymentClient.call(request);  // удалённый вызов
    }
    
    private PaymentResult fallback(PaymentRequest request, Exception e) {
        return new PaymentResult("PENDING", "Сервис недоступен, оплата позже");
    }
}
```

**Конфигурация (application.yml):**
```yaml
resilience4j.circuitbreaker:
  instances:
    paymentService:
      slidingWindowSize: 10          # окно запросов
      failureRateThreshold: 50       # 50% ошибок → Open
      waitDurationInOpenState: 5s    # время в Open
      permittedNumberOfCallsInHalfOpenState: 3
```

**Пример сценария:**
```
1. payment-service начинает падать
2. Circuit Breaker насчитывает 5 ошибок из 10 (50%)
3. Переходит в Open → все вызовы падают мгновенно
4. Через 5 секунд → Half-Open → пробный запрос
5. Успех → Closed (восстановление)
```

**В реальном стеке:** Resilience4j (Spring Cloud Circuit Breaker), Hystrix (legacy), Istio (sidecar), или ручная реализация.

# Graceful Shutdown в Kubernetes + Spring Boot

## Основные механизмы

### 1. **Spring Boot встроенный graceful shutdown**
- Настроить `server.shutdown=graceful` в application.properties
- Задать `spring.lifecycle.timeout-per-shutdown-phase=30s`
- Spring перестает принимать новые запросы, но дообрабатывает текущие

### 2. **Kubernetes настройки**

**PreStop hook** – выполняется перед отправкой SIGTERM:
- Дает приложению команду на подготовку к остановке
- Задержка перед отправкой SIGTERM

**terminationGracePeriodSeconds** – общее время на завершение:
- Дефолт 30 секунд, для тяжелых приложений увеличивать до 60-90

**readinessProbe** – критически важен:
- При shutdown первым делом отключаем readiness probe
- Pod перестает получать трафик из Service

### 3. **Правильный порядок событий**

1. Pod получает SIGTERM (или PreStop hook срабатывает раньше)
2. Readiness probe начинает возвращать fail
3. Service исключает Pod из endpoint'ов
4. Spring Boot перестает принимать новые запросы
5. Текущие запросы дообрабатываются (timeout)
6. После завершения – Pod удаляется

### 4. **Подводные камни**

- **Readiness probe настроен агрессивно** – при задержках Pod могут преждевременно исключить из ротации
- **Короткий terminationGracePeriodSeconds** – не успевают дообработаться запросы
- **Отсутствие PreStop hook** – приложение не успевает подготовиться
- **Long-running запросы** – нужно уменьшить `spring.lifecycle.timeout-per-shutdown-phase`
- **@Async задачи** – отдельный пул потоков, их тоже нужно завершать
- **Kafka consumers** – нужно закрыть сессии и закоммитить offset'ы

### 5. **Минимальная конфигурация**

```yaml
# deployment.yaml
spec:
  template:
    spec:
      terminationGracePeriodSeconds: 60
      containers:
      - name: app
        lifecycle:
          preStop:
            exec:
              command: ["sh", "-c", "sleep 5"]
        readinessProbe:
          initialDelaySeconds: 5
          periodSeconds: 5
```

```properties
# application.properties
server.shutdown=graceful
spring.lifecycle.timeout-per-shutdown-phase=30s
```

### 6. **Дополнительные рекомендации**

- Использовать `management.health.readiness-state.enabled=true`
- Настроить `spring.datasource.hikari.connection-timeout` меньше чем shutdown timeout
- Для очередей (RabbitMQ, Kafka) добавить слушатели на закрытие
- Мониторить метрики времени завершения
- Тестировать сценарии отказа (Chaos engineering)

**Ключевой принцип**: сначала отключаем readiness, потом даем время дообработать, только потом убиваем процесс.
