Разница между `javax` и `jakarta` — это не просто изменение названия, а **исторический сдвиг в экосистеме Java**, который затронул миллионы проектов.

Если коротко: **`javax` — это прошлое (Java EE), а `jakarta` — это будущее (Jakarta EE).** Это одно и то же с технической точки зрения (те же API), но разные пространства имен (package names).

Вот подробный разбор ситуации.

---

### 1. Почему это произошло? (История)

**До 2017 года:**
Технологии для Enterprise (Servlets, JSP, JPA, EJB и т.д.) разрабатывались компанией Oracle под названием **Java EE** (Java Enterprise Edition). Все классы этих технологий жили в пакетах, начинающихся с `javax.*`.

**После 2017 года:**
Oracle решила передать Enterprise-технологии сообществу и фонду **Eclipse Foundation**.
Фонд Eclipse не мог дальше использовать торговую марку "Java" (права остались у Oracle). Поэтому:
1.  Название платформы сменили на **Jakarta EE**.
2.  Но самое важное: Oracle запретила фонду менять код внутри пакетов `javax.*`. То есть Eclipse не могли развивать технологии, оставляя их в старых пакетах.

**Решение:**
Чтобы продолжить развитие и внедрение новых фич, сообщество приняло волевое решение: в версии **Jakarta EE 9** (вышла в 2020 году) все пакеты были массово переименованы с `javax.*` на `jakarta.*`.

### 2. Техническая разница

Это буквально «поиск и замена» текста в коде, но на глобальном уровне.

| Характеристика | `javax.*` | `jakarta.*` |
| :--- | :--- | :--- |
| **Эра** | Java EE 8 и старше | Jakarta EE 9, 10, 11 и новее |
| **Пример пакета** | `javax.servlet.http.HttpServlet` | `jakarta.servlet.http.HttpServlet` |
| **Пример (JPA)** | `javax.persistence.Entity` | `jakarta.persistence.Entity` |
| **Совместимость** | Старые библиотеки и серверы (Tomcat 9, Spring Boot 2) | Новые библиотеки и серверы (Tomcat 10+, Spring Boot 3+) |

### 3. Как это влияет на разработчика?

Это влияние вы почувствуете сразу, как только обновите версию фреймворка или сервера приложений.

#### Сценарий 1: Spring Boot (Самый частый кейс)
*   **Spring Boot 2.x:** Использует Java EE. Импорты в коде: `import javax.*`.
*   **Spring Boot 3.x:** Переехал на Jakarta EE. Импорты в коде: `import jakarta.*`.

Если вы обновляете проект со Spring Boot 2 на Spring Boot 3, ваш код перестанет компилироваться, пока вы вручную или через IDE не замените все `javax` на `jakarta` в аннотациях и классах.

#### Сценарий 2: Серверы приложений (Tomcat, Jetty, WildFly)
Серверы приложений делятся на две категории:
1.  **Старые (javax):** Tomcat 9, WildFly 20-26, Payara 5. Они работают с пакетами `javax`.
2.  **Новые (jakarta):** Tomcat 10+, WildFly 27+, Payara 6+. Они работают с пакетами `jakarta`.

**Нюанс:** Войный файл (WAR), собранный под `javax`, **не запустится** на сервере Tomcat 10+, потому что сервер ожидает классы из пакетов `jakarta.*`.

### 4. Почему это вызывает боль? (Зависимости)

Главная проблема — транзитивные зависимости.
Представьте, что вы перешли на Spring Boot 3 (jakarta), но подключили старую библиотеку для работы с PDF, которая внутри себя использует `javax.servlet`. При запуске вы получите ошибку `ClassNotFoundException` или конфликт бинов, потому что сервер предоставляет `jakarta.servlet`, а библиотека ищет `javax.servlet`.

Решения:
1.  Использовать инструменты автоматической миграции (например, **Eclipse Transformer**).
2.  Искать обновленные версии библиотек, поддерживающие `jakarta`.

### Итог

*   Если вы поддерживаете **старый проект** (Java 8, Spring Boot 2, старые серверы) — используйте **`javax`**. Это стабильная, завершенная ветка развития.
*   Если вы начинаете **новый проект** или обновляетесь на **Java 17/21 и Spring Boot 3** — используйте только **`jakarta`**. Это стандарт будущего.

**Важное примечание про Java SE:**
Пакеты `javax.*` остались в самой Java (Standard Edition). Например, `javax.swing`, `javax.sql` (JDBC) и `javax.crypto`. Переименование коснулось **только** Enterprise-слоя (Web, Persistence, Transactions и т.д.).
