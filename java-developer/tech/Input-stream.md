## Когда следует использовать `InputStream`

`InputStream` — это абстракция для **последовательного чтения байтов**. Его стоит использовать, когда:

- **Данные не помещаются в память целиком.** Например, файл на 5 ГБ, большой дамп, поток логов. Вместо загрузки в `byte[]` или `String` ты читаешь его кусками.
- **Источник — поток, а не файл.** Сетевой ответ (`java.net.http`), сокет, канал, сжатый архив, конвейер в Linux. Такие данные по своей природе «текут» и не хранятся целиком.
- **Нужна потоковая обработка.** Парсинг XML/JSON через SAX/StAX, чтение CSV построчно, конвертация форматов «на лету», фильтрация/трансформация потока.
- **Требуется экономия памяти и предсказуемое потребление кучи.** В CI/Docker-контейнерах с лимитами памяти (например, 256–512 МБ) загрузка больших файлов в `byte[]` может вызвать `OutOfMemoryError`.
- **Нужно начать обработку до получения всех данных.** Например, отдавать первые байты ответа клиенту, пока сервер ещё досылает остаток.

## Как `InputStream` связан с буферизацией

Сам по себе `InputStream` (например, `FileInputStream`, `SocketInputStream`) часто **не буферизован**: он может читать по 1 байту за вызов `read()`, что очень медленно из‑за частых системных вызовов.

### Роль `BufferedInputStream`

Чтобы ускорить чтение, поток оборачивают в `BufferedInputStream`:

**Что происходит:**

- `BufferedInputStream` держит в памяти небольшой буфер (обычно 8 КБ).
- При вызове `read()` он старается заполнить буфер одним системным вызовом.
- Последующие байты отдаются из буфера, без обращения к ОС.
- Это резко снижает количество системных вызовов и повышает пропускную способность.

### Практические советы по размеру буфера

- **8–16 КБ** — хороший универсальный выбор для файлов и сети.
- Для последовательного чтения больших файлов иногда лучше **64–128 КБ**, чтобы лучше использовать дисковые кэши ОС и контроллеров.
- Слишком маленький буфер (1–2 КБ) увеличивает накладные расходы на вызовы.
- Слишком большой буфер (мегабайты) бесполезно тратит кучу и может ухудшить общую производительность при множестве параллельных потоков.

> Для твоего стека (Maven, CI, Docker): в скриптах и утилитах используй `BufferedInputStream` с фиксированным размером буфера (например, 32 КБ), чтобы поведение было предсказуемым на разных раннерах и в контейнерах.

## Связь с размером кучи (heap) и OOM

|Подход|Потребление памяти|Риск OOM|Когда уместно|
|---|---|---|---|
|`InputStream` + буферизация|**O(1)** относительно размера данных: только размер буфера (несколько КБ)|Низкий|Большие файлы, сетевые потоки, стриминг|
|Чтение в `byte[]` целиком|**O(N)**: весь файл в памяти|Высокий при больших N|Маленькие файлы (KB–единицы MB), когда нужен случайный доступ или многократное чтение|
|Чтение в `String` целиком|**O(N) + кодировка**: строка в UTF‑16 занимает больше, чем исходные байты|Высокий|Небольшие текстовые файлы, конфиги, короткие ответы API|
|SAX/StAX поверх `InputStream`|**O(1) по данным**, только состояние парсера|Низкий|XML любого размера, в т. ч. для SBOM/POM‑файлов|

## Нюансы, важные для твоего контекста (Maven, CI, Checkstyle, Docker)

- **Checkstyle и качество кода.** Избегай `Files.readAllBytes` / `Files.readString` для потенциально больших файлов. В правилах качества кода это часто помечается как «риск OOM».
- **Docker и CI.** Контейнеры часто запускаются с жёсткими лимитами памяти. Потоковый подход делает сборку более стабильной и переносимой между раннерами.
- **Maven‑плагины и утилиты.** Если пишешь плагин, который читает POM‑файлы модулей, используй `InputStream` и буферизацию: в многомодульных проектах суммарный объём XML может быть большим.
- **SBOM‑генерация.** При сборе лицензий и зависимостей ты можешь обрабатывать сотни POM‑файлов. Потоковое чтение и SAX‑парсинг позволяют держать потребление памяти низким и прогнозируемым.

## Частые ошибки и как их избежать

|Ошибка|Как правильно|
|---|---|
|Читать по 1 байту без буферизации|Оберни в `BufferedInputStream`|
|Загружать большой файл целиком в `String`|Читай через `InputStream` → SAX/StAX или копируй в файл/другой поток|
|Игнорировать закрытие потоков|Всегда `try-with-resources`|
|Думать, что `InputStream` сам по себе буферизирован|Помни: буферизация — отдельная обёртка|
|Использовать гигантские буферы «на всякий случай»|Держи буфер в разумных пределах (8–64 КБ)|
