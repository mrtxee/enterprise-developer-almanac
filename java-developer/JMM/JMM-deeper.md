# проблема кэш лайнов

- **[[Cache-Line]]** — это блок памяти, с которым работает CPU для ускорения доступа.
- **False Sharing** — частая проблема в многопоточности, когда потоки борются за одну cache line.
- **Оптимизация:** Выравнивание данных, минимизация shared-переменных, использование `@Contended`.

**[[Cache-Line]]** (кэш-линия) — это минимальный блок данных, который процессор загружает из оперативной памяти (RAM) в кэш (CPU Cache) при чтении или записи. 
* Обычно **64 байта** (на современных x86/x64 CPU), но может быть 32, 128 байт (зависит от архитектуры).

**Как работает:**
- Когда процессор обращается к ячейке памяти, в кэш загружается **целая cache line**, содержащая эту ячейку.
- Последующие обращения к соседним данным происходят быстрее, так как они уже в кэше.
- Если два ядра CPU работают с разными переменными, но они попадают в **одну cache line**, это вызывает конфликты:
	* Ядро 1 меняет `переменную A` → кэш-линия помечается как "грязная".
	- Ядро 2 читает `переменную B` из той же строки → вынуждено загружать обновлённые данные из кэша Ядра 1, хотя `B` не изменилась. 
	- **Результат:** Производительность падает из-за избыточной синхронизации.

### Как оптимизировать работу с Cache Line?
1. **Выравнивание данных** (Padding)  
    Добавление "пустых" байтов, чтобы разные потоки работали с разными cache lines.

# Как работает JMM
1. JMM строит все возможные пути исполнения программы
    1. Вначале действия структурируются в PO, SO
        1. Synchronization Order = Program Order + Synchronization Actions
    2. Потом действия различных потоков связываются через SW
    3. В результате чего Happens-Before отношение порядка выполнения
2. JMM отбрасывает запрещенные исполнения
    4. на основе структурных ограничений, проверок и валидаций
3. Оставшиеся варианты исполнения — разрешены
    5. таких вариантов много, и в некоторхы могут возникать сайдэффекты.


# SC-DRF — Sequential Consistency-Data Race Free

**SC-DRF: Executions**

Execution: $E = \langle P, A, \xrightarrow{po}, \xrightarrow{so}, W, V, \xrightarrow{sw}, \xrightarrow{hb} \rangle$

- **$E$** — выполнение (execution)
- $P$ — программа (program)
- $A$ — множество действий программы (actions)
- $\xrightarrow{po}$ — program order, порядок программного кода
- $\xrightarrow{so}$ — synchronization order, порядок синхронизации
- $W(r)$ — «write seen function», возвращает запись, которую видит данное чтение $r$
- $V(r)$ — значение, которое прочитало конкретное чтением $r$
- $\xrightarrow{sw}$ — synchronizes-with order, отношение "synchronizes-with"
- $\xrightarrow{hb}$ — happens-before order, отношение "happens-before"

> 💬 _“SC-DRF is the formal model for sequential consistency in concurrent programming.”_

Модель `SC-DRF` гарантирует `Sequential Consistency`, но только в том случае, если мы избавимся от всех гонок данных `data race`
Модель `SC-DRF` через последовательность `локальных трансформаций` стоит HB-очередность выполнения операций программы.

## data race — состояние гонки данных
Состояние **гонка данных** `data race` возникает, когда два или более потока пытаются получить доступ к одной и той же не финальной переменной без синхронизации.
В состоянии гонки данных могут возникнуть изменения, которые не будут видны другим потокам. Что повлечет чтение устаревших данных, бесконечным циклам, поврежденным структурам данных или неточным вычислениям.
## SC — Sequential Consistency
Принцип который говорит, что результат выполнения паралельного кода должен быть не отличим, как если бы все операции выполнены согласно последовательностью кода заданной разработчиком.
# PO — Program Order
порядок действий внутри одного потока
- PO связывает порядок действий только внутри одного потока и его не хватает, чтобы обеспечить SC
Из-за того, что PO является отношение частичного порядка (не обеспечивает полный порядок), java предлагает использовать `Synchronization Actions` для связывания порядка выполнения тасков между разными потоками.  
  
**$Program Order + Synchronization Actions = Synchronization Order$**
# SO — Synchronization Order
`Synchronization Actions` образуют `Synchronization Order` — Полный порядок.
`Synchronization Order` — это нужная надстройка, которая получается из `Program Order + Synchronization Actions`
# SA — Synchronization Actions
- volatile read/write
- lock monitor, unlock monitor
- первое (синтетические) и последнее действие в потоке, действия, запускающие поток
- операции, обнаруживающие завершение потока (`Thread.join()`, `Thread.isInterrupted()` и т.п.)
# SW — Synchronization With Order
Некоторый порядок выполнения операций в многопоточке, который связывает порядок выполнения операций между параллельными потоками
## Roach motel «ловушка для таракана»
принцип оптимизации Стека выполнения JMM, который позволяет заменить вызовы одной сущности в разных потоках и вернуть один объект всем потокам, вместо того, чтобы повторно делать одинаковую работу в разных потоках
# Happens-Before Order
Порядок следования, который объединяет `Synchronization With Order` с `Program Order`.
- PO — дает семантику внутри потока
- SW — дает связь между потоками

Happens-Before `HB` — отношение `частичного порядока`. Наделен свойствами:
- отсутствуют циклы
- Happens-Before Consistency `HBC`
