## fail-fast vs fail-safe итераторы

| Характеристика                | fail-fast                                   | fail-safe                                   |
| ----------------------------- | ------------------------------------------- | ------------------------------------------- |
| **Поведение при модификации** | Бросает `ConcurrentModificationException`   | Продолжает итерацию по снапшоту             |
| **Механизм**                  | Проверяет `modCount` при каждом вызове      | Итерирует по копии коллекции                |
| **Примеры**                   | `ArrayList`, `HashSet`, `HashMap`           | `CopyOnWriteArrayList`, `ConcurrentHashMap` |
| **Оверхед**                   | Низкий                                      | Высокий (копирование данных)                |
| **Актуальность данных**       | Всегда актуальные                           | Данные на момент создания снапшота          |
| **Потокобезопасность**        | Нет (один поток)                            | Да (для чтения)                             |
| **Использование**             | Однопоточный код, раннее обнаружение ошибок | Многопоточное чтение с редкими записями     |

## ApplicationContext vs BeanFactory

**ApplicationContext** — расширенный контейнер Spring, управляющий бинами и предоставляющий enterprise-функции.  
**BeanFactory** — базовый DI-контейнер с минимальной функциональностью.

| Характеристика                 | BeanFactory                   | ApplicationContext         |
| ------------------------------ | ----------------------------- | -------------------------- |
| Инициализация синглтонов       | Ленивая (при getBean)         | Eager (при старте)         |
| Интернационализация ([[i18n]]) | Нет                           | Да (MessageSource)         |
| События (ApplicationEvent)     | Нет                           | Да (@EventListener)        |
| AOP / проксирование            | Вручную                       | Автоматически              |
| Загрузка ресурсов              | Нет                           | Да (ResourceLoader)        |
| Поддержка веб                  | Нет                           | Да (WebApplicationContext) |
| Использование по умолчанию     | Редко (в legacy или embedded) | Всегда в Spring Boot       |

**Итог:** `ApplicationContext` — надстройка над `BeanFactory`, используется в 99% случаев.

## Proxy vs Decorator with Spring

**Proxy** и **Decorator** — структурные паттерны, оба оборачивают объект, но цели разные.

**Сравнение:**

| Характеристика                  | Proxy                                                          | Decorator                                      |
| ------------------------------- | -------------------------------------------------------------- | ---------------------------------------------- |
| **Назначение**                  | Контроль доступа, ленивая инициализация, логирование, security | Динамическое добавление новой функциональности |
| **Изменяет интерфейс**          | Нет (тот же интерфейс)                                         | Нет (тот же интерфейс)                         |
| **Создаёт ли новый функционал** | Нет (управляет существующим)                                   | Да (расширяет поведение)                       |
| **Отношение к оригиналу**       | Контролирует доступ                                            | Обогащает поведение                            |
| **Время жизни**                 | Создаётся один раз, переиспользуется                           | Можно оборачивать несколько раз (композиция)   |


**Примеры в Spring:**

| Паттерн | Пример в Spring |
|---------|----------------|
| **Proxy** | `@Transactional` — прокси управляет транзакцией (открытие/коммит/откат) |
| **Proxy** | `@Cacheable` — проверяет кэш до вызова метода |
| **Proxy** | `@Async` — выполняет метод в отдельном потоке |
| **Proxy** | Spring Security — проверяет роли до вызова |
| **Decorator** | `BufferedInputStream` (Java IO, не Spring) — добавляет буферизацию |
| **Decorator** | `HttpServletRequestWrapper` в Spring Security — добавляет методы для безопасности |
| **Decorator** | Декораторы бинов через `@Primary` + композицию |

**Кодовая разница:**

```java
// Proxy — контролирует доступ
class TransactionProxy implements Service {
    private Service target;
    public void execute() {
        beginTx();
        target.execute();
        commitTx();
    }
}

// Decorator — добавляет функционал
class LoggingDecorator implements Service {
    private Service wrapped;
    public void execute() {
        log("start");
        wrapped.execute();
        log("end");
    }
}
```

**Итог:** Proxy управляет доступом (транзакции, кэш, lazy loading), Decorator расширяет поведение (добавляет логирование, сжатие, шифрование).

## Circuit Breaker

**Circuit Breaker** — паттерн для защиты системы от каскадных отказов при вызовах удалённых сервисов.

**Проблемы, которые решает:**

| Проблема | Описание |
|----------|----------|
| **Таймауты без ответа** | Ждать каждый раз → блокировка потоков |
| **Каскадные отказы** | Сервис A падает → B ждёт → C ждёт → вся система виснет |
| **Перегрузка больного сервиса** | Неудачные вызовы только ухудшают его состояние |
| **Пустая трата ресурсов** | Вызовы, которые всё равно упадут |

**Состояния Circuit Breaker:**

| Состояние                | Поведение                                                         |
| ------------------------ | ----------------------------------------------------------------- |
| **Closed** (норма)       | Выполняются запросы, ошибки подсчитываются                        |
| **Open** (разомкнут)     | Запросы блокируются мгновенно (fail fast)                         |
| **Half-Open** (проверка) | Пропускается пробный запрос, если успех → Closed, если нет → Open |

## Graceful Shutdown в Kubernetes + Spring Boot

1. **Spring Boot встроенный graceful shutdown**
	- Настроить `server.shutdown=graceful` в application.properties
	- Задать `spring.lifecycle.timeout-per-shutdown-phase=30s`
	- Spring перестает принимать новые запросы, но дообрабатывает текущие

2. **Kubernetes настройки**
	**PreStop hook** – выполняется перед отправкой SIGTERM:
	- Дает приложению команду на подготовку к остановке
	- Задержка перед отправкой SIGTERM

	**terminationGracePeriodSeconds** – общее время на завершение:
	- Дефолт 30 секунд, для тяжелых приложений увеличивать до 60-90
	
	**readinessProbe** – критически важен:
	- При shutdown первым делом отключаем readiness probe
	- Pod перестает получать трафик из Service

3. **Правильный порядок событий**
	1. Pod получает SIGTERM (или PreStop hook срабатывает раньше)
	2. Readiness probe начинает возвращать fail
	3. Service исключает Pod из endpoint'ов
	4. Spring Boot перестает принимать новые запросы
	5. Текущие запросы дообрабатываются (timeout)
	6. После завершения – Pod удаляется

4. **Подводные камни**
	- **Readiness probe настроен агрессивно** – при задержках Pod могут преждевременно исключить из ротации
	- **Короткий terminationGracePeriodSeconds** – не успевают дообработаться запросы
	- **Отсутствие PreStop hook** – приложение не успевает подготовиться
	- **Long-running запросы** – нужно уменьшить `spring.lifecycle.timeout-per-shutdown-phase`
	- **@Async задачи** – отдельный пул потоков, их тоже нужно завершать
	- **Kafka consumers** – нужно закрыть сессии и закоммитить offset'ы
