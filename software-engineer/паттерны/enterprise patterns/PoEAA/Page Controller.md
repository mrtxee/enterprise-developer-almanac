Разберу сравнение паттернов **Page Controller**, **Front Controller** и **Application Controller** — их суть, отличия, плюсы/минусы и сценарии применения.


## 1. Page Controller

**Суть:** для каждой веб‑страницы (или группы похожих страниц) создаётся отдельный контроллер.


**Как работает:**
* URL напрямую сопоставляется с классом/методом контроллера;
* контроллер обрабатывает запрос: загружает данные, выполняет бизнес‑логику, выбирает View;
* каждый контроллер самодостаточен и обычно не зависит от других.


**Пример:**
* `/user/profile` → `UserProfileController`;
* `/orders` → `OrderListController`.

**Плюсы:**
* простота реализации и понимания;
* прямая связь между URL и контроллером;
* подходит для небольших и средних приложений;
* быстрая разработка прототипов.

**Минусы:**
* дублирование кода (аутентификация, логирование, валидация);
* сложность поддержки при росте числа страниц;
* слабая централизация конфигурации.

**Примеры реализаций:** классические PHP‑приложения, ASP.NET Web Forms.

---


## 2. Front Controller

**Суть:** единый обработчик всех HTTP‑запросов приложения, который маршрутизирует их к соответствующим командам/обработчикам.

**Компоненты:**
* **Front Controller** — главный обработчик запросов;
* **Dispatcher** — маршрутизатор, определяющий, какой обработчик вызвать;
* **Commands/Handlers** — выполняют конкретную логику (мелкие контроллеры).

**Как работает:**
1. Все запросы проходят через единый вход (например, `index.php`).
2. Диспетчер анализирует URL и выбирает нужный обработчик.
3. Обработчик выполняет бизнес‑логику.
4. Front Controller рендерит View или возвращает ответ.

**Плюсы:**
* централизация общих задач (аутентификация, локализация, кэширование);
* единая точка конфигурации и обработки ошибок;
* масштабируемость (легко добавлять новые маршруты);
* стандартизация обработки запросов.

**Минусы:**
* выше порог входа для новичков;
* риск превращения в «монолит» с избыточной логикой;
* требует продуманной архитектуры команд/обработчиков.

**Примеры реализаций:** Laravel, Symfony, Spring MVC, ASP.NET MVC.

---

## 3. Application Controller

**Суть:** расширение Front Controller для управления **бизнес‑workflow** и навигацией (последовательностью шагов).

**Ключевые функции:**
* управление многошаговыми процессами (мастер оформления заказа, анкета, процесс одобрения);
* хранение состояния workflow;
* динамическое определение следующего шага на основе условий;
* централизация правил переходов между шагами.

**Как работает:**
1. Front Controller получает запрос.
2. Application Controller определяет текущий шаг workflow.
3. Выполняется логика шага.
4. Application Controller решает, куда перейти дальше (следующий шаг, ошибка, завершение).

**Плюсы:**
* поддержка сложных сценариев с условными переходами;
* гибкая навигация (разные пути для разных ролей/условий);
* централизация бизнес‑правил workflow;
* возможность возобновления прерванного процесса.

**Минусы:**
* высокая сложность реализации;
* избыточность для простых CRUD‑приложений;
* необходимость управления состоянием workflow.

**Примеры реализаций:** системы бронирования, банковские приложения, CMS с workflow‑редакторами.

## Сравнительная таблица

| Критерий                    | Page Controller                      | Front Controller                   | Application Controller                        |
| --------------------------- | ------------------------------------ | ---------------------------------- | --------------------------------------------- |
| **Основная цель**           | Обработка отдельных страниц          | Централизация обработки запросов   | Управление бизнес‑процессами (workflow)       |
| **Количество контроллеров** | Много (по одному на страницу/группу) | Один главный + команды/обработчики | Один главный + логика workflow                |
| **Связь URL → контроллер**  | Прямая (1:1)                         | Через маршрутизатор                | Через маршрутизатор + состояние workflow      |
| **Дублирование кода**       | Высокое (общая логика копируется)    | Низкое (централизована)            | Низкое (правила workflow централизованы)      |
| **Сложность**               | Низкая                               | Средняя                            | Высокая                                       |
| **Масштабируемость**        | Ограниченная                         | Отличная                           | Отличная (для workflow)                       |
| **Тестируемость**           | Простая (изолированные контроллеры)  | Хорошая (модульные команды)        | Средняя/сложная (зависит от состояния)        |
| **Типичное применение**     | Простые сайты, CRUD, прототипы       | Крупные веб‑приложения, API        | Мастера, процессы с шагами, сложные workflows |
| **Гибкость навигации**      | Жёсткая (страница = контроллер)      | Гибкая (маршрутизация)             | Очень гибкая (динамические переходы)          |
| **Поддержка состояний**     | Нет                                  | Частично (через сессии)            | Встроена (состояние workflow)                 |

## Взаимосвязь паттернов


Паттерны могут **комбинироваться** в рамках одного приложения:
* **Front Controller** часто служит основой для всей системы;
* внутри него могут работать **Page Controllers** как обработчики отдельных страниц;
* **Application Controller** может надстраиваться над Front Controller для управления сложными процессами.


**Пример комбинации:**
* Front Controller обрабатывает все запросы;
* для простых страниц (профиль пользователя, список заказов) используются Page Controllers;
* для оформления заказа запускается Application Controller, управляющий шагами: корзина → доставка → оплата → подтверждение.


---

## Когда что выбирать?

* **Page Controller:**
    * небольшое приложение или прототип;
    * простые CRUD‑операции;
    * команда с небольшим опытом в веб‑разработке;
    * жёсткая связь URL и страницы.
* **Front Controller:**
    * крупное веб‑приложение или API;
    * нужна централизация аутентификации, логирования, кэширования;
    * планируется масштабирование;
    * требуется гибкая маршрутизация.
* **Application Controller:**
    * бизнес‑процесс состоит из нескольких шагов с условиями;
    * нужно сохранять и возобновлять состояние процесса;
    * разные роли/условия ведут к разным путям в workflow;
    * сложная навигация (мастера, анкеты, одобрения).

---

## Краткий итог

* **Page Controller** — простота для отдельных страниц.
* **Front Controller** — централизация и масштабируемость запросов.
* **Application Controller** — управление сложными бизнес‑процессами с шагами и состояниями.

Выбор паттерна зависит от **масштаба**, **сложности бизнес‑логики** и **требований к навигации**. В крупных системах часто используют комбинацию этих подходов.
