### Паттерн Backpressure («обратное давление»)


**Суть**: механизм контроля потока данных, предотвращающий перегрузку системы путём «сигнализации» источнику о невозможности обработать текущий объём входящих данных. Система не просто отбрасывает запросы при перегрузке, а **регулирует скорость приёма**, сообщая потребителю/источнику: *«Я не успеваю, замедлись»*.


### Зачем нужен

Без backpressure:
- буфер заполняется, запросы накапливаются;
- растёт latency, потребляется память;
- возможны сбои (OOM, таймауты);
- система становится неотзывчивой.


Backpressure решает это, сохраняя стабильность за счёт **управляемого снижения пропускной способности**.

### Как работает

1. **Система‑приёмник** (например, сервис, очередь, БД) отслеживает свои ресурсы:  
   - длину очереди;  
   - загрузку CPU/памяти;  
   - время обработки запроса.  
2. При приближении к лимитам она **сигнализирует источнику**:  
   - явным сообщением (например, HTTP 429 Too Many Requests);  
   - неявным замедлением (не принимает новые пакеты);  
   - протокольными механизмами (TCP flow control).  
3. **Источник** реагирует:  
   - снижает частоту отправки запросов;  
   - ставит запросы в локальную очередь;  
   - применяет троттлинг/повторные попытки.  
4. Когда нагрузка спадает, система снимает ограничение, и поток восстанавливается.

### Ключевые механизмы реализации

1. **Ограничение размера буфера**  
   - Фиксированный размер очереди (например, 1 000 элементов).  
   - При переполнении — отказ в приёме или сигнал backpressure.  

2. **Протокольные средства**  
   - **TCP window scaling**: получатель сообщает, сколько данных может принять.  
   - **HTTP/2 flow control**: клиент и сервер регулируют скорость передачи.  
3. **Алгоритмы троттлинга**  
   - Token Bucket: «ведро» с токенами, ограничивающее скорость.  
   - Leaky Bucket: фиксированная скорость обработки.  
4. **Явные коды ошибок/заголовки**  
   - HTTP 429 Too Many Requests + `Retry-After`.  
   - gRPC `RESOURCE_EXHAUSTED`.  
5. **Асинхронные очереди с контролем**  
   - RabbitMQ/Kafka: настройка max‑inflight‑messages, ack‑тайм‑аутов.  
6. **Реактивные фреймворки**  
   - RxJava, Project Reactor, Akka: встроенные операторы backpressure (например, `onBackpressureBuffer`, `onBackpressureDrop`).

### Примеры применения

1. **Веб‑сервис под нагрузкой**  
   - Клиент шлёт 1 000 RPS, сервер может обработать 500 RPS.  
   - Сервер отвечает 429 + `Retry-After: 2`, клиент снижает частоту.  

2. **Поток данных в Kafka**  
   - Потребитель не успевает читать сообщения.  
   - Kafka ограничивает выдачу новых сообщений, пока потребитель не «продвинется».  

3. **Микросервисная архитектура**  
   - Сервис A вызывает сервис B, который тормозит.  
   - B отвечает 429, A ставит запросы в очередь и повторяет с задержкой.  

4. **Фронтенд‑бэкенд**  
   - Пользователь быстро кликает кнопку «Отправить».  
   - Фронтенд применяет debounce/throttle, не шлёт лишние запросы.  

5. **БД под нагрузкой**  
   - Пул соединений исчерпан.  
   - БД отклоняет новые подключения, приложение ждёт освобождения соединения.


### Плюсы
- **Стабильность**: предотвращает каскадные сбои.  
- **Предсказуемость**: система работает в границах своих возможностей.  
- **Эластичность**: автоматически адаптируется к нагрузке.  
- **Сохранение данных**: минимизирует потери (в отличие от простого отбрасывания).  


### Минусы
- **Задержка**: запросы могут ждать в очереди.  
- **Сложность**: требует настройки буферов, стратегий реакции.  
- **Зависимость от протокола**: не все системы поддерживают backpressure «из коробки».  


### Лучшие практики
1. **Задавайте явные лимиты**  
   - Размер буфера, max RPS, время ожидания.  
2. **Используйте стандартные коды/заголовки**  
   - 429 Too Many Requests, `Retry-After`, gRPC коды.  
3. **Реализуйте повторные попытки с задержкой**  
   - Экспоненциальный откат (exponential backoff).  
4. **Мониторинг и алерты**  
   - Отслеживайте длину очередей, частоту 429, latency.  
5. **Тестируйте под нагрузкой**  
   - Проверяйте, как система реагирует на переполнение буфера.  
6. **Комбируйте с другими паттернами**  
   - [[Circuit Breaker]] (отключайте перегруженный сервис).  
   - [[Resilience Patterns|Rate Limiting]] (ограничивайте вход).  
   - [[Resilience Patterns|Bulkhead]] (изолируйте компоненты).  


### Вывод


Backpressure — не просто «отбрасывание запросов», а **интеллектуальное управление потоком** для сохранения работоспособности системы. Он критически важен для:
- высоконагруженных сервисов;
- распределённых систем;
- потоковой обработки данных.

**Ключевой принцип**: лучше обработать меньше, но стабильно, чем попытаться обработать всё и упасть.



## Backpressure в Reactive Streams

**Backpressure** (обратное давление) в контексте Reactive Streams — это **механизм управления потоком данных**, позволяющий потребителю (subscriber) сигнализировать производителю (publisher) о своей текущей пропускной способности. Цель — не допустить перегрузки потребителя, когда производитель генерирует данные быстрее, чем потребитель успевает их обрабатывать.


### Почему это важно

Без backpressure:
- потребитель может исчерпать память из‑за буферизации неподъёмного объёма данных;
- система рискует «зависнуть» или упасть из‑за перегрузки;
- задержки обработки растут, ухудшается отзывчивость.

Backpressure решает эту проблему, **согласовывая скорости производителя и потребителя**.


### Как работает (на уровне спецификации Reactive Streams)

Ключевые элементы:
1. **`Publisher`** — источник данных (производитель).  
2. **`Subscriber`** — обработчик данных (потребитель).  
3. **`Subscription`** — связь между ними, через которую управляется поток.  
4. **`request(n)`** — метод, которым потребитель запрашивает у производителя ровно `n` элементов.  
5. **`onNext()`** — метод, через который производитель передаёт элементы потребителю.


**Базовый сценарий:**
1. Подscriber подписывается на Publisher и получает объект `Subscription`.  
2. Подscriber вызывает `subscription.request(10)`, запрашивая 10 элементов.  
3. Publisher отправляет ровно 10 элементов через `onNext()`.  
4. После обработки этих 10 элементов подписчик может вызвать `request()` снова, запрашивая следующую порцию.  
5. Если подписчик не вызывает `request()`, производитель приостанавливает отправку.

Таким образом, потребитель **сам контролирует темп получения данных**.


### Стратегии обработки backpressure


1. **Буферизация**  
   - Данные временно складируются в буфере, пока потребитель не сможет их обработать.  
   - *Риск:* переполнение буфера, если данные поступают слишком быстро.  
   - *Решение:* ограничение размера буфера и политика вытеснения (например, отбрасывание старых/новых элементов).


2. **Отбрасывание (dropping)**  
   - Новые данные игнорируются, если потребитель не готов.  
   - Подходит для сценариев, где потеря части данных допустима (например, мониторинг).

3. **Ограничение скорости (throttling)**  
   - Производитель замедляется, чтобы соответствовать скорости потребителя.  
   - Реализуется через `request()` с малым `n`.
4. **Остановка производителя**  
   - Потребитель сигнализирует о полной неготовности, и производитель приостанавливает генерацию.  
1. **Масштабирование потребителя**
   - Запуск дополнительных экземпляров потребителя для увеличения пропускной способности.


### Примеры в реальных библиотеках


- **Project Reactor (Java)**  
  ```java
  Flux.range(1, 1000)
      .onBackpressureBuffer(100)  // буфер на 100 элементов
      .subscribe(System.out::println);
  ```
- **RxJava**  
  ```java
  Flowable.range(1, 1000)
      .onBackpressureDrop()  // отбрасывать новые элементы при перегрузке
      .subscribe(System.out::println);
  ```

### Плюсы backpressure

- **Предотвращение перегрузки** памяти и CPU.  
- **Стабильность системы** при пиковых нагрузках.  
- **Гибкость** — можно выбирать стратегию под конкретный сценарий.  
- **Асинхронность** — потребитель не блокируется, а управляет потоком через запросы.


### Когда backpressure особенно важен
- Потоковая обработка больших данных (Kafka, Flink, Spark Streaming).  
- Высоконагруженные API, где клиенты могут отправлять запросы быстрее, чем сервер обрабатывает.  
- Системы реального времени (чаты, биржевые тикеры), где задержки критичны.


### Итог


Backpressure в Reactive Streams — **это механизм обратной связи**, позволяющий:
- потребителю контролировать объём получаемых данных;  
- производителю адаптироваться к скорости потребителя;  
- системе оставаться устойчивой при неравномерной нагрузке.


Ключевой принцип: **«потребитель запрашивает — производитель отправляет»**, а не наоборот. Это делает реактивные системы масштабируемыми и надёжными.
