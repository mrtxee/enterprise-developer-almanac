
**Aggregate Root (Корень агрегата)** — это **ключевое понятие в DDD ([[Domain-Driven Design]])**, которое помогает управлять сложностью и обеспечивать целостность бизнес-объектов.

---

## ✅ Что такое **Aggregate Root**?

> **Aggregate Root** — это **главный объект в группе связанных сущностей**, который:
> - Является **единственной точкой входа** в агрегат
> - Отвечает за **целостность всех объектов внутри агрегата**
> - Обеспечивает **инварианты** (бизнес-правила)

### 💡 Пример: Заказ (`Order`) как Aggregate Root

```plaintext
Order (Aggregate Root)
├── OrderLine (содержит товары)
├── OrderLine
└── PaymentStatus
```

- Вы можете **только через `Order`** добавить/удалить строку заказа.
- Правило: *"Общая сумма заказа не может быть отрицательной"* → проверяется в `Order`.
- Если кто-то попробует изменить `OrderLine` напрямую — нарушится инвариант.

---

## 🔍 Почему нужен Aggregate Root?

Без него:

- Сущности могут быть изменены из любого места → **нарушение бизнес-правил**
- Нет контроля над жизненным циклом группы объектов
- Транзакции становятся непредсказуемыми

С Aggregate Root:

✅ Все изменения проходят **через корень** → можно контролировать бизнес-логику.  
✅ Гарантируется **согласованность** всей группы.  
✅ Упрощается **сохранение в базу**: вся группа сохраняется как единое целое.  
✅ Легко реализовать **Event Sourcing**: событие `OrderPlaced` = всё состояние корня + дочерних.

---

## ✅ Основные характеристики

| Характеристика | Объяснение |
|----------------|------------|
| **Единственная точка входа** | Только Aggregate Root может создавать/изменять свои дочерние сущности |
| **Инварианты** | Корень отвечает за соблюдение правил: <br>• "Заказ не может быть больше 100 позиций"<br>• "Платёж должен соответствовать сумме" |
| **Транзакционная граница** | Всё, что входит в агрегат, должно обновляться одной транзакцией |
| **Сохраняется целиком** | При сохранении `Order` → сохраняются все `OrderLine` |
| **Не зависит от ORM** | Даже если вы используете JPA/Hibernate — корень должен управлять изменениями |

## 🧩 Пример: Aggregate Root в коде (Java)

```java
public class Order {
    private final String id;
    private List<OrderLine> lines = new ArrayList<>();
    private OrderStatus status;
    private BigDecimal total;

    // Единственный способ добавить товар — через метод корня
    public void addItem(Product product, int quantity) {
        if (lines.size() >= 100) {
            throw new BusinessException("Максимум 100 товаров");
        }

        OrderLine line = new OrderLine(product, quantity);
        this.lines.add(line);
        recalculateTotal();
    }

    public void confirm() {
        if (this.total.compareTo(BigDecimal.ZERO) <= 0) {
            throw new BusinessException("Нулевой заказ нельзя подтверждать");
        }
        this.status = OrderStatus.CONFIRMED;
    }

    private void recalculateTotal() {
        this.total = lines.stream()
                         .map(OrderLine::getPrice)
                         .reduce(BigDecimal.ZERO, BigDecimal::add);
    }
}
```

> ✅ **Никакие внешние объекты не могут напрямую менять `OrderLine`.**  
> ✅ **Все изменения — только через `Order.addItem()` → инварианты защищены.**

## ✅ Когда создавать Aggregate Root?

| Да, создайте AR | Нет, не нужно |
|------------------|----------------|
| Есть группа связанных сущностей | Одиночные сущности (User, Product) |
| Есть бизнес-правила между ними | Нет зависимостей |
| Нужна транзакционная согласованность | Не критично |
| Используется Event Sourcing / CQRS | Простые CRUD-операции |

## 🔁 Как работает с другими паттернами?

| Паттерн                        | Связь                                                          |
| ------------------------------ | -------------------------------------------------------------- |
| **Entity**                     | Сущности внутри агрегата (например, `OrderLine`)               |
| **Value Object**               | Часть агрегата (например, `Address`, `Money`)                  |
| **Repository**                 | Работает с **целым агрегатом** (`OrderRepository.save(order)`) |
| **[[Event Sourcing]]**         | События создаются от корня (`OrderPlaced`, `OrderCancelled`)   |
| **[[CQRS]]**                   | Команды работают с корнем, Query — с проекциями                |
| **DDD (Domain-Driven Design)** | Агрегаты — фундамент моделирования домена                      |

## ❌ Частые ошибки

| Ошибка | Последствия |
|--------|-------------|
| ❌ Слишком большой агрегат | Медленно, конфликты при записи |
| ❌ Разрешить прямой доступ к дочерним сущностям | Нарушаются инварианты |
| ❌ Несколько корней в одном агрегате | Потеря ясности |
| ❌ Игнорировать размер агрегата | Блокировки, проблемы с масштабированием |

---

## ✅ Лучшие практики

| Правило | Объяснение |
|--------|------------|
| ✅ **AR должен быть маленьким** | ≤ 5–7 сущностей — иначе проблемы с производительностью |
| ✅ **Сохраняйте только корень** | `OrderRepository.save(order)` — не `orderLineRepository.save(...)` |
| ✅ **Используйте ID для связи между агрегатами** | `Order` ссылается на `Customer` по `customerId`, но **не содержит** его |
| ✅ **AR — это транзакционная граница** | Внутри одного агрегата — одна транзакция |
| ✅ **Избегайте глубоких вложенности** | `Order → OrderLine → DiscountRule → AuditLog` — плохо. Упростите. |

# Aggregate  vs Aggregate Root

**Aggregate Root (корень агрегата)** и **Aggregate (агрегат)** — это **тесно связанные, но не одинаковые понятия** в **[[Domain-Driven Design]] (DDD)**.

Разберём чётко: **в чём разница**, **как они работают**, **почему это важно**.

---

## ✅ Краткий ответ:

| Понятие | Что это? | Пример |
|--------|----------|--------|
| **Aggregate (Агрегат)** | Группа **связанных сущностей и value objects**, которые должны быть согласованы вместе. Это **логическая группа**. | `Order` + `OrderLine` + `Discount` → одна транзакция |
| **Aggregate Root (AR)** | **Один объект** в агрегате, который является **единственной точкой входа**. Все изменения проходят через него. | `Order` — корень; `OrderLine` нельзя менять напрямую |

> 🔑 **Aggregate = команда футболистов**  
> **Aggregate Root = капитан команды**  
> Вы можете говорить только с капитаном. Он решает, что делать остальным.

---

## ✅ Подробное объяснение

### 1. **Что такое Aggregate?**

> **Aggregate** — это **паттерн моделирования домена**, при котором:
> - Несколько объектов (сущности, value objects) образуют **единицу целостности**
> - Вся группа должна **сохраняться одной транзакцией**
> - Внутри агрегата есть **бизнес-инварианты**, которые нельзя нарушать

#### 💡 Пример агрегата: Заказ
```plaintext
Aggregate: Order
├── Aggregate Root: Order
│   ├── OrderLine: "iPhone", кол-во=1
│   ├── OrderLine: "Чехол", кол-во=2
│   ├── Discount: "Скидка 10%"
│   └── PaymentStatus: "Оплачено"
```

→ Это **один агрегат**: все эти данные должны быть согласованы.  
Если добавляете товар — нужно пересчитывать скидку и проверять оплату.

---

### 2. **Что такое Aggregate Root?**

> **Aggregate Root** — это **главная сущность** внутри агрегата, которая:
> - Является **единственным способом доступа** к агрегату
> - Отвечает за **соблюдение бизнес-правил**
> - Управляет **жизненным циклом дочерних объектов**
> - Обеспечивает **целостность данных**

#### 🧩 Пример: Как правильно

```java
// ✅ Только через корень можно изменить заказ
order.addItem(product, 1);
order.applyDiscount("PROMO10");
order.confirm();
```

#### ❌ Как неправильно

```java
// ❌ Нельзя напрямую создавать OrderLine без Order
OrderLine line = new OrderLine(...);
orderLineRepository.save(line); // Ломает инвариант!
```

> ✅ **Только `Order` может создавать/удалять `OrderLine`**

---

## 🆚 Сравнение: Aggregate vs Aggregate Root

| Критерий | **Aggregate** | **Aggregate Root** |
|----------|----------------|--------------------|
| **Тип** | Группа объектов | Один объект (Entity) |
| **Цель** | Гарантирует **целостность группы** | Является **шлюзом** для этой группы |
| **Где используется** | При проектировании доменной модели | В коде, как главный объект |
| **Пример** | `Order` + `OrderLines` + `PaymentInfo` | Объект `Order` |
| **Транзакционная граница** | Да — весь агрегат в одной транзакции | Да — только он может начать сохранение |
| **Можно ли менять дочерние объекты напрямую?** | ❌ Нет — только через корень | ✅ Только он управляет ими |
| **ORM / JPA** | Целый агрегат — одна запись или связанная структура | Часто аннотируется как `@Entity`, `@AggregateRoot` |

---

## ✅ Зачем нужен Aggregate Root?

Без AR:

- Другие сервисы могут изменять `OrderLine` напрямую → обойдут бизнес-проверки
- Инварианты ломаются: *"Заказ подтверждён, но нет товаров"*
- Транзакции становятся хаотичными

С AR:

✅ Все изменения контролируются.  
✅ Можно гарантировать:  
> _«Перед тем как подтвердить заказ — я проверю, что он не пустой»_  
> _«Нельзя добавить больше 100 товаров»_

---

## ✅ Правила DDD про Aggregates

| Правило | Объяснение |
|--------|------------|
| **1. Меняйте агрегат только через его корень** | Никаких `repository.save(child)` |
| **2. Ссылайтесь на другие агрегаты по ID** | `Order.customerId`, а не `Order.customer` |
| **3. Минимизируйте размер агрегата** | Не делайте `User` → `Orders` → `Payments` → `Invoices` — это монолит |
| **4. Агрегат — единица транзакции** | Всё сохраняется вместе или ничего |
| **5. Агрегат — источник событий** | `OrderPlaced`, `OrderCancelled` — от корня |

---

## ✅ Пример: Банковский счёт

```plaintext
Aggregate: BankAccount
└── Aggregate Root: BankAccount
    ├── Transaction[] (Value Objects)
    ├── Balance: Money
    ├── OverdraftPolicy: Value Object
    └── Status: ACTIVE/BLOCKED
```

- Только `BankAccount` может:
  - Добавить транзакцию
  - Проверить овердрафт
  - Заблокировать счёт
- `Transaction` — нельзя менять напрямую
- `BankAccount` — корень, управляющий всем

## ✅ Как выглядит в коде (Java)

```java
@Entity
public class Order {
    @Id
    private String id;
    
    @OneToMany(cascade = CascadeType.ALL, mappedBy = "order")
    private List<OrderLine> lines;

    public void addItem(Product product, int qty) {
        if (lines.size() >= 100) 
            throw new BusinessRuleException("Too many items");

        lines.add(new OrderLine(this, product, qty));
        recalculateTotal();
    }

    public void confirm() {
        if (total.isZero()) 
            throw new BusinessRuleException("Can't confirm empty order");

        status = CONFIRMED;
    }
}
```

> ✅ `Order` — **Aggregate Root**  
> ✅ Весь класс — **Aggregate**

## ✅ Финальный вывод: Главное отличие

| Вопрос | Ответ |
|--------|-------|
| **Что такое Aggregate?** | Это **группа объектов**, которые должны быть согласованы |
| **Что такое Aggregate Root?** | Это **единственный объект**, через который можно изменять эту группу |
| **Может ли быть Aggregate без Root?** | ❌ Нет — корень — часть агрегата |
| **Может ли быть несколько корней в одном агрегате?** | ❌ Нет — только один корень |
| **Какова цель?** | Защитить бизнес-инварианты, избежать ошибок |
