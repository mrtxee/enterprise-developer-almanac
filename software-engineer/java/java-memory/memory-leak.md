## Примеры ситуаций утечки памяти в Java

**Статические коллекции, растущие без ограничения**

Статические поля живут всё время работы приложения. Если коллекция постоянно пополняется и не очищается, память будет накапливаться.

```java
public class MemoryLeakExample {
    private static Set<Object> cache = new HashSet<>();

    public void addToCache(Object obj) {
        cache.add(obj); // Объекты никогда не удаляются
    }
}
```

**Слушатели (listeners) без отписки**

Если объект зарегистрирован как слушатель, но не отписывается при уничтожении, он остаётся в памяти, пока жив источник событий.

```java
button.addActionListener(new ActionListener() {
    @Override
    void actionPerformed(ActionEvent e) { /* ... */ }
});
// Слушатель не удаляется — утечка
```

**Незакрытые ресурсы (соединения, потоки)**

Незакрытые соединения с БД, файлы, сетевые сокеты удерживают память и системные ресурсы.

```java
Connection conn = DriverManager.getConnection(url, user, password);
Statement stmt = conn.createStatement();
// conn и stmt не закрываются — утечка ресурсов
```

**Использование `ThreadLocal` без очистки**

`ThreadLocal` хранит данные для каждого потока. Если поток долгоживущий (из пула), данные не очистятся автоматически.

```java
private static ThreadLocal<Map<String, Object>> threadLocalMap =
    new ThreadLocal<>();

void doSomething() {
    threadLocalMap.set(new HashMap<>());
    // threadLocalMap.remove() не вызывается — утечка
}
```

**Кэши без политики вытеснения**

Кэш, который только растёт, без лимита размера или времени жизни элементов.

```java
Map<String, BigObject> cache = new HashMap<>();
void cacheData(String key, BigObject obj) {
    cache.put(key, obj); // Нет механизма очистки — утечка
}
```

**Замыкания в лямбда‑выражениях захватывают внешние объекты**

Лямбда‑выражение может неявно захватывать ссылку на внешний объект, удерживая его в памяти.

```java
class Service {
    private BigObject data;

    void registerHandler() {
        eventBus.register(event -> process(data)); // data не освобождается
    }
}
```

**Внутренние классы удерживают ссылку на внешний класс**

Нестатический внутренний класс содержит неявную ссылку на внешний класс. Если внутренний объект сохраняется надолго, внешний класс тоже не освободится.

```java
class Outer {
    private byte[] bigData = new byte[1024 * 1024];

    class Inner {
        void useBigData() { /* использует bigData */ }
    }
}
// Если экземпляр Inner сохраняется, Outer тоже остаётся в памяти
```

**Некорректное использование `WeakReference` / `SoftReference`**

Ошибочное применение слабых/мягких ссылок может привести к тому, что объекты не освобождаются вовремя или слишком рано.

**Кеширование строк через `String.intern()`**

Строки, добавленные в пул через `intern()`, хранятся в [[jmm|Metaspace]] и не освобождаются до конца работы JVM.

```java
String largeString = readHugeFile();
largeString.intern(); // Может заполнить Metaspace
```

**Утечки в сторонних библиотеках**

Некоторые библиотеки (например, логирование, ORM) могут кэшировать объекты без должной очистки. Пример: [[hibernate|Hibernate]] без настройки кэша второго уровня.

**Краткий итог**

- **Статические поля** с коллекциями или кэшами.
- **Неотписанные слушатели** (listeners, callbacks).
- **Незакрытые ресурсы** (соединения, потоки).
- **ThreadLocal** без вызова `remove()`.
- **Кэши** без политики вытеснения (LRU, TTL).
- **Захваты объектов** в лямбдах и внутренних классах.
- **Пул строк** (`String.intern()`).
- **Ошибки в библиотеках** и фреймворках.

Для диагностики используют профилировщики памяти (VisualVM, Eclipse MAT, JProfiler) и анализ дампов кучи (`hprof`).

## Инструменты для визуализации и анализа утечек памяти в Java

### Встроенные инструменты JDK

- **VisualVM (jvisualvm)**
  - бесплатный инструмент, включён в [[jdk-jls-jni|JDK]];
  - мониторинг использования памяти в реальном времени;
  - анализ heap dump (снимков кучи);
  - визуализация объектов и их взаимосвязей;
  - поддержка плагинов для расширения функциональности.
- **Java Flight Recorder (JFR) + Java Mission Control (JMC)**
  - JFR: сбор низкоуровневых данных о работе [[jvm|JVM]] с минимальными накладными расходами;
  - JMC: графический интерфейс для анализа данных JFR;
  - детальный анализ памяти, сборки мусора, выделений объектов;
  - подходит для использования в production‑средах.

### Коммерческие профилировщики

- **YourKit**
  - детальная визуализация использования памяти;
  - сравнение heap dump;
  - отслеживание аллокаций в реальном времени;
  - удобный интерфейс для поиска утечек.
- **JProfiler**
  - комплексный анализ производительности и памяти;
  - графики распределения памяти;
  - дерево ссылок (reference tree) для поиска удерживающих объектов;
  - интеграция с IDE.
- **Eclipse Memory Analyzer (MAT)**
  - мощный анализатор heap dump;
  - отчёт *Leak Suspects* — автоматически выявляет вероятные утечки;
  - гистограмма объектов (показывает, какие классы занимают больше всего памяти);
  - граф объектов (визуализация цепочек ссылок).

### Специализированные инструменты

- **GCViewer**
  - анализ логов [[jmm-gc|сборщика мусора]] (GC logs);
  - визуализация: рост памяти, паузы GC, эффективность очистки;
  - помогает выявить: частые Full GC, рост старого поколения (Old Gen), неэффективную сборку мусора.
- **HeapHero**
  - онлайн‑анализатор heap dump;
  - выдаёт рекомендации по устранению утечек;
  - показывает «стоимость» объектов в памяти (с учётом ссылок).

### Инструменты для Android

- **LeakCanary**
  - библиотека для автоматического обнаружения утечек в Android‑приложениях;
  - создаёт уведомления при обнаружении утечки;
  - генерирует отчёты с указанием цепочки ссылок.

### Системы мониторинга production‑среды (APM)

- **New Relic**
- **Dynatrace**
- **AppDynamics**
  - непрерывный мониторинг использования памяти;
  - автоматическое обнаружение аномалий (например, рост потребления памяти со временем);
  - корреляция с бизнес‑транзакциями и пользовательскими действиями.

## Краткий сравнительный обзор

| Инструмент | Тип | Основное назначение | Плюсы | Минусы |
|----------|------|-------------------|------|-------|
| VisualVM | Бесплатный | Базовый анализ памяти и CPU | Простота, встроен в JDK | Менее детализирован, чем коммерческие решения |
| JMC + JFR | Бесплатный/Коммерческий | Глубокий анализ JVM | Низкие накладные расходы, подходит для production | Требует настройки JFR, менее интуитивен |
| Eclipse MAT | Бесплатный | Анализ heap dump | Мощный анализ утечек, отчёт Leak Suspects | Требуется ручной сбор heap dump |
| YourKit | Коммерческий | Комплексный профилировщик | Удобный интерфейс, детальная визуализация | Платный |
| JProfiler | Коммерческий | Комплексный профилировщик | Гибкость, интеграция с IDE | Платный |
| GCViewer | Бесплатный | Анализ логов GC | Простота, наглядная визуализация GC | Только анализ логов, не находит объекты‑источники утечек |
| LeakCanary | Бесплатный | Утечки в Android | Автоматическое обнаружение, простота | Только для Android |
| New Relic/Dynatrace | Коммерческий | Мониторинг production | Автоматическое обнаружение аномалий | Высокая стоимость, требует настройки |

## Как выбрать инструмент

- **Локальная разработка / отладка:** VisualVM, Eclipse MAT, JProfiler, YourKit.
- **Глубокий анализ в production:** JFR + JMC, YourKit, Dynatrace.
- **Анализ логов GC:** GCViewer.
- **Android‑разработка:** LeakCanary.
- **Непрерывный мониторинг production:** New Relic, Dynatrace, AppDynamics.

**Общий подход к диагностике:**

1. Зафиксировать рост потребления памяти (через VisualVM, JMC или APM).
2. Сделать heap dump (или собрать данные JFR).
3. Проанализировать heap dump в MAT/YourKit/JProfiler: найти объекты, занимающие много памяти, и цепочки ссылок, удерживающие их.
4. При необходимости — отследить аллокации в реальном времени (YourKit, JProfiler).
