**Reactive Streams** — это **международный стандарт** для асинхронной обработки потоков данных с **управлением обратным давлением ([[Backpressure]])**. Он лежит в основе всех современных реактивных систем: Spring [[WebFlux]], Project [[Reactor]], RxJava, Akka Streams, Vert.x и др.

---

## 🎯 Главная цель Reactive Streams

> **Дать возможность компонентам обмениваться потоками данных асинхронно, без переполнения памяти и с контролем скорости.**

Проблема, которую решает стандарт:
- **Источник данных** (например, база) может генерировать данные **быстрее**, чем **потребитель** (например, HTTP-клиент) может их обработать.
- Без контроля — потребитель получит **OutOfMemoryError** или упадёт под нагрузкой.

Reactive Streams решает это через **динамическое управление скоростью передачи данных** — это и есть **backpressure**.

---

## 🔑 Четыре интерфейса (всего 4!)

Стандарт определяет **только 4 интерфейса** (в пакете `org.reactivestreams`):

| Интерфейс             | Назначение                                                                                  |
| --------------------- | ------------------------------------------------------------------------------------------- |
| **`Publisher<T>`**    | Источник данных. Может отправлять элементы подписчикам.                                     |
| **`Subscriber<T>`**   | Потребитель данных. Подписывается на издателя и получает данные.                            |
| **`Subscription`**    | Связь между издателем и подписчиком. Управляет потоком данных (запрос/отмена).              |
| **`Processor<T, R>`** | (необязательный) И одновременно `Publisher<R>`, и `Subscriber<T>` — фильтр/преобразователь. |

> 💡 Вся мощь реактивных систем строится на этих 4 простых интерфейсах.

## 🔄 Как это работает: пошагово

### 1. Подписка
```java
Publisher<String> publisher = ...;
Subscriber<String> subscriber = ...;

publisher.subscribe(subscriber); // ← запускает процесс
```

### 2. Издатель создаёт `Subscription` и отправляет его подписчику
```java
// Внутри Subscriber:
@Override
public void onSubscribe(Subscription subscription) {
    this.subscription = subscription;
    subscription.request(1); // ← ЗАПРОСИТЬ 1 элемент!
}
```

### 3. Издатель отправляет данные (но **не больше**, чем запрошено!)
```java
// Внутри Publisher:
@Override
public void subscribe(Subscriber<? super String> subscriber) {
    subscriber.onSubscribe(new MySubscription());
    // Позже, когда есть данные:
    if (requested > 0) {
        subscriber.onNext("данные");
        requested--;
    }
}
```

### 4. Потребитель обрабатывает данные и запрашивает следующие
```java
@Override
public void onNext(String item) {
    System.out.println("Получил: " + item);
    subscription.request(1); // ← Готов к следующему!
}
```

### 5. Завершение или ошибка
```java
subscriber.onComplete();   // Успешное завершение
// или
subscriber.onError(ex);    // Ошибка
```

## ⚖️ [[Backpressure]] — сердце Reactive Streams

> **Потребитель сам решает, сколько данных он готов принять.**

Это **инверсия управления**:  
- В обычных коллекциях (`List`, `Stream`) — потребитель **забирает** данные.  
- В Reactive Streams — потребитель **запрашивает** данные.

### Пример без backpressure:
```java
// База выдаёт 1 млн записей → клиент падает с OutOfMemory
List<User> all = userRepository.findAll(); // 💥
```

### С backpressure:
```java
// Клиент запрашивает по 10 записей за раз
Flux<User> users = userRepository.findAll(); // ленивый поток
users.subscribe(user -> {
    process(user);
    // Spring/R2DBC автоматически управляет request()
});
```

→ Память не переполняется, система устойчива.

## 🌐 Почему это стандарт, а не просто библиотека?

До Reactive Streams каждая библиотека (RxJava, Akka, Reactor) имела **свой формат потоков** → они **не могли работать вместе**.

**Reactive Streams (2015)** утвердил **единый контракт**, и теперь:

| Библиотека | Реализует `Publisher<T>`? |
|------------|---------------------------|
| Project Reactor (`Flux`, `Mono`) | ✅ |
| RxJava 2+ (`Flowable`) | ✅ |
| Akka Streams | ✅ |
| Spring WebFlux | ✅ |
| R2DBC | ✅ |

→ Вы можете **подключить любой `Publisher` к любому `Subscriber`**, даже из разных экосистем!

```java
// RxJava → Reactor
Flux<String> flux = Flux.from(rxJavaFlowable);

// Reactor → R2DBC
repository.saveAll(flux); // saveAll принимает Publisher<T>
```

| Библиотека | Назначение |
|-----------|-----------|
| **Project Reactor** | Основа Spring WebFlux (`Flux`, `Mono`) |
| **RxJava** | Реактивное программирование с богатым набором операторов |
| **Akka Streams** | Распределённые потоки данных в системах на Akka |
| **Vert.x** | Реактивные приложения на основе event loop |

Все они **совместимы**, потому что реализуют `org.reactivestreams.Publisher`.

## 🧠 Простая аналогия

Представьте **водопровод с краном**:

- **Издатель** = водонапорная башня
- **Подписчик** = вы с ведром
- **Subscription** = кран
- **Backpressure** = вы **сами открываете кран**, когда ведро не полное

> 💧 Вода не хлынет внезапно — вы контролируете поток!

---

## ⚠️ Важные ограничения (правила стандарта)

1. **`onNext` не должен вызываться после `onComplete`/`onError`**
2. **`onNext` не должен вызываться больше, чем запрошено через `request(n)`**
3. **Подписка должна быть отменена при ошибке или завершении**
4. **`request(n)` должен быть вызван хотя бы один раз, иначе данные не пойдут**

> Нарушение этих правил → неопределённое поведение.

## 🎯 Зачем это знать разработчику?

1. **Понимать, как работает WebFlux, R2DBC, WebClient** под капотом.
2. **Отлаживать проблемы с backpressure** (например, "висящие" запросы).
3. **Писать совместимые реактивные компоненты**.
4. **Избегать ошибок** вроде:
   - Забыл вызвать `request()` → данные не идут
   - Вызвал `onNext` без учёта backpressure → переполнение

## 🌟 Итог

> **Reactive Streams — это не фреймворк, а контракт.**  
> Он обеспечивает:
> - **Безопасную асинхронную передачу данных**
> - **Управление скоростью (backpressure)**
> - **Совместимость между библиотеками**

Без этого стандарта не было бы единой реактивной экосистемы в Java.  
Spring WebFlux, R2DBC, Netty — всё это **работает вместе именно благодаря Reactive Streams**.
