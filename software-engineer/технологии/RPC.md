## RPC

🔹 Определение:
**RPC (Remote Procedure Call)** — это **парадигма программирования**, при которой программа может вызвать функцию или процедуру на удалённом сервере **так же, как если бы она была локальной**.

> 💡 Смысл: *«Вызови функцию `getUser(id)` — и система сама отправит запрос по сети, получит ответ и вернёт результат».*

🔹 Принцип работы (упрощённо):
```plaintext
Клиент → [сериализует аргументы] → [отправляет по сети] → Сервер
                     ← [возвращает результат] ← [десериализует ответ]
```

🔹 Исторические примеры RPC:
- **Sun RPC / ONC RPC** — из Unix-эпохи (1980s)
- **CORBA** — попытка стандартизации в 90-х
- **DCOM** — Microsoft-овская реализация
- **XML-RPC** — через HTTP + XML
- **JSON-RPC** — через HTTP + JSON

🔹 Особенности классического RPC:

| Характеристика                    | Описание                                                 |
| --------------------------------- | -------------------------------------------------------- |
| **Протокол**                      | Может быть любым: TCP, UDP, HTTP, собственный бинарный   |
| **Формат данных**                 | Бинарный, XML, JSON — зависит от реализации              |
| **Сервис-дискавери**              | Обычно нет — клиент должен знать IP/порт сервера         |
| **Типизация**                     | Часто слабая или неявная                                 |
| **Производительность**            | Зависит от реализации — часто низкая (например, XML-RPC) |
| **Поддержка потоков / стриминга** | Редко                                                    |
| **Безопасность**                  | Нужно добавлять вручную (TLS, аутентификация)            |

> ⚠️ Классический RPC — это **не стандарт**, а **паттерн**. Реализаций — множество, и они **несовместимы** между собой.

## gRPC

🔹 Определение:
**gRPC** — это **современная, открытая, высокопроизводительная реализация RPC**, разработанная **Google** и выпущенная как **открытый фреймворк** в 2015 году.

> 💡 gRPC — это **не просто RPC**, а **полноценная платформа для построения распределённых систем** с чёткой спецификацией, инструментами и поддержкой множества языков.

🔹 Основные технологии, лежащие в основе gRPC:

| Компонент                       | Описание                                                                                          |
| ------------------------------- | ------------------------------------------------------------------------------------------------- |
| **Protocol Buffers (protobuf)** | Стандартный способ описания структур данных и API (`.proto` файлы).                               |
| **HTTP/2**                      | Транспортный протокол — мультиплексирование, двунаправленный стриминг, заголовки в бинарном виде. |
| **gRPC Core**                   | C-языковое ядро, на котором построены все остальные реализации.                                   |
| **Платформенная поддержка**     | Поддерживает 10+ языков: Go, Java, Python, C#, Node.js, Rust, PHP, Ruby и др.                     |

🔹 Как работает gRPC (пример):

Шаг 1: Определяете `.proto`-интерфейс
```protobuf
// user.proto
syntax = "proto3";
package user;

service UserService {
  rpc GetUser (UserRequest) returns (UserResponse);
  rpc ListUsers (Empty) returns (stream UserResponse); // Server streaming
  rpc UpdateUser (stream UserUpdate) returns (UserSummary); // Client streaming
  rpc Chat (stream UserMessage) returns (stream UserMessage); // Bidirectional streaming
}

message UserRequest { int32 id = 1; }
message UserResponse { string name = 1; string email = 2; }
message Empty {}
message UserUpdate { int32 id = 1; string name = 2; }
message UserMessage { string text = 1; }
```

Шаг 2: Генерируете код на нужном языке
```bash
protoc --grpc_out=. --plugin=protoc-gen-grpc=/usr/local/bin/grpc_cpp_plugin user.proto
```

Шаг 3: Пишете сервер и клиент — и всё готово!
```go
// Go: клиент вызывает метод так же, как локальную функцию
user, err := client.GetUser(context.Background(), &pb.UserRequest{Id: 123})
```

## 🆚 RPC vs gRPC

| Критерий                       | **Обычный RPC**                       | **gRPC**                                                                                                                   |
| ------------------------------ | ------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| **Тип**                        | Паттерн / концепция                   | Конкретная реализация (фреймворк)                                                                                          |
| **Стандартизация**             | ❌ Нет единого стандарта               | ✅ Чёткий стандарт (Google, CNCF)                                                                                           |
| **Транспорт**                  | TCP, HTTP, UDP, собственные протоколы | ✅ Только **HTTP/2**                                                                                                        |
| **Формат сериализации**        | XML, JSON, бинарный — произвольный    | ✅ **Protocol Buffers (protobuf)** — бинарный, эффективный, типизированный                                                  |
| **Производительность**         | Низкая (XML-RPC), средняя (JSON-RPC)  | ✅ **Очень высокая** — бинарный формат + HTTP/2                                                                             |
| **Мультиплексирование**        | ❌ Обычно нет                          | ✅ Да — один TCP-соединение = много параллельных вызовов                                                                    |
| **Стриминг**                   | ❌ Редко поддерживается                | ✅ Полная поддержка: <br> • Unary (1:1)<br> • Server streaming (1:N)<br> • Client streaming (N:1)<br> • Bidirectional (N:N) |
| **Типизация**                  | Слабая или отсутствует                | ✅ **Строгая типизация** через `.proto` — компилятор проверяет всё                                                          |
| **Генерация кода**             | Часто ручная                          | ✅ Автоматическая генерация клиентов/серверов на 10+ языках                                                                 |
| **Аутентификация / TLS**       | Нужно делать вручную                  | ✅ Встроенная поддержка **mTLS**, OAuth2, JWT                                                                               |
| **Инструменты**                | Минимальные                           | ✅ **gRPC Gateway** (REST ↔ gRPC), **Prometheus метрики**, **Tracing**, **Health Checks**, **Load Balancing**               |
| **Экосистема**                 | Фрагментированная                     | ✅ Интеграция с Kubernetes, Istio, Envoy, OpenTelemetry, Cloud Native                                                       |
| **Использование в продакшене** | Устаревает                            | ✅ **Стандарт де-факто** в микросервисах (Netflix, Docker, Uber, Square, etc.)                                              |
# Инструменты RPC

gRPC — это высокопроизводительный фреймворк RPC, разработанный Google. Он использует **Protocol Buffers ([[Avro|Protobuf]])** для сериализации данных и HTTP/2 для транспортировки.

Apache Thrift — это фреймворк для разработки и реализации межъязыковых RPC-сервисов. Он был разработан в Facebook и поддерживает множество языков программирования.

Apache [[Avro|Avro]] — это фреймворк для сериализации данных и RPC, разработанный в рамках проекта Hadoop. Он использует JSON для определения схем данных и бинарный формат для их сериализации. Бинарная сериализация обеспечивает высокую производительность и малый размер данных.

ZeroC ICE (Internet Communications Engine) — это довольно сложный в изучении фреймворк для построения распределённых систем. Однако поддерживает множество языков программирования, различные типы транспорта и протоколов, SSL/TLS и аутентификацию.

JSON-RPC — простой в использовании протокол для удалённого вызова процедур (RPC), использующий JSON для кодирования сообщений. Он поддерживает как однонаправленные вызовы, так и нотификации.
