Разберу подробно разницу между **UUID** и **RqUID** — несмотря на возможную схожесть формата, это разные концепции с разными целями.


## UUID (Universally Unique Identifier)

**UUID** — стандарт уникальной идентификации ([[RFC 4122 UUID|RFC 4122]]), 128‑битное значение с крайне малой вероятностью коллизии.


**Ключевые характеристики:**
* **Назначение:** глобальная уникальная идентификация объектов (пользователей, заказов, файлов и т. д.).
* **Формат:** 36 символов в виде `xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx` (8‑4‑4‑4‑12).
* **Версии:**
    * **v1:** на основе времени и MAC‑адреса;
    * **v3/v5:** хеширование с пространством имён;
    * **v4:** полностью случайный (наиболее распространён);
    * **v6/v7:** новые версии с улучшенной сортируемостью.
* **Где используется:**
    * первичные ключи в БД;
    * идентификаторы сущностей в API;
    * ID файлов, сессий, транзакций;
    * распределённые системы (где нет центрального генератора ID).
* **Кто генерирует:** любая сторона (клиент, сервер, сервис) — децентрализованная генерация.
* **Срок жизни:** постоянный (на весь жизненный цикл сущности).

**Примеры:**
* `user_id: 123e4567-e89b-12d3-a456-426614174000`;
* `order_id: a1b2c3d4-e5f6-7890-1234-56789abcdef0`.

## RqUID (Request Unique Identifier)


**RqUID** — не самостоятельный стандарт, а **практика использования UUID для идентификации HTTP‑запросов**.


**Ключевые характеристики:**
* **Назначение:** идентификация конкретного HTTP‑запроса для:
    * обеспечения идемпотентности (повторный запрос с тем же RqUID не выполняет операцию заново);
    * трассировки запроса в логах (от клиента до сервера и обратно);
    * аудита и отладки.
* **Формат:** обычно [[UUID]] v4 (но технически может быть любой уникальный ID).
* **Где используется:** исключительно в заголовках HTTP‑запросов (например, `RqUID: a1b2c3d4-...`).
* **Кто генерирует:** всегда **клиент** перед отправкой запроса.
* **Срок жизни:** временный (часы/дни), затем удаляется из хранилища.
* **Бизнес‑значение:** отсутствует — это технический идентификатор операции, а не сущности.

**Пример запроса:**
```http
POST /api/v1/orders
RqUID: a1b2c3d4-e5f6-7890-1234-56789abcdef0
Content-Type: application/json

{
  "product_id": "P12345",
  "quantity": 2
}
```

## Сравнительная таблица

| Параметр                 | UUID                                      | RqUID                                                             |
| ------------------------ | ----------------------------------------- | ----------------------------------------------------------------- |
| **Что это**              | Стандарт идентификации (RFC 4122)         | Практика использования UUID в заголовке HTTP‑запроса              |
| **Цель**                 | Уникально идентифицировать объект         | Уникально идентифицировать запрос                                 |
| **Где применяется**      | БД, API, файлы, сессии, транзакции        | Только в заголовках HTTP‑запросов (`RqUID: ...`)                  |
| **Кто генерирует**       | Любая сторона (сервер, клиент, сервис)    | Всегда клиент (перед отправкой запроса)                           |
| **Формат**               | Строго по RFC 4122 (128 бит, 36 символов) | Обычно UUID v4, но может быть и другой уникальный ID              |
| **Срок жизни**           | Постоянный (пока существует объект)       | Временный (часы/дни для логирования и проверки дубликатов)        |
| **Сохранение**           | Да, как атрибут сущности (в БД, кэше)     | Да, временно (для проверки дубликатов и трассировки)              |
| **Уникальность**         | Глобальная (в рамках стандарта)           | Глобальная для запросов (не должен повторяться в период хранения) |
| **Бизнес‑смысл**         | Имеет (идентифицирует сущность)           | Отсутствует (технический идентификатор операции)                  |
| **Пример использования** | `user_id`, `order_id`, `file_id`          | Заголовок `RqUID` в POST/PUT‑запросах                             |

## Практические сценарии


**Сценарий 1. Создание заказа**
* **UUID:** сервер генерирует `order_id=a1b2c3d4-...` и сохраняет в БД.
* **RqUID:** клиент генерирует `RqUID=uuid-for-create-request` для POST‑запроса. Если запрос повторится, сервер вернёт тот же `order_id` без создания нового заказа.

**Сценарий 2. Обновление баланса**
* **UUID:** `account_id=acc456` — идентификатор счёта.
* **RqUID:** `RqUID=uuid-for-update-balance` — гарантирует, что повторная отправка запроса не спишет деньги дважды.


**Сценарий 3. Отладка**
* По **UUID** находят все операции с объектом (например, все изменения заказа `a1b2c3d4-...`).
* По **RqUID** находят конкретный запрос в логах сервера (время, IP, статус, тело запроса).

## Краткий итог


* **UUID** — **что это?** (идентифицирует объект). Аналогия: номер паспорта человека.
* **RqUID** — **что было сделано?** (идентифицирует действие). Аналогия: номер квитанции в банке.

**Связь:** RqUID часто *реализуется через* UUID (обычно v4), но это не обязательное требование. Главное отличие — в **целевом назначении** и **контексте использования**.


**Когда что использовать:**
* Используйте **UUID**, если нужно уникально идентифицировать сущность (пользователя, заказ, файл).
* Используйте **RqUID**, если нужно обеспечить идемпотентность запросов или трассировать их в логах.
