# Avro

**Avro**, **[[Protobuf]]** и **[[Distributed Tracing]]** — это три критически важных технологий в современных распределённых системах, особенно в архитектурах на основе **Event-Driven (EDA)**, **microservices** и **cloud-native**. Они решают фундаментальные проблемы: **совместимость данных, производительность и отладка сложных систем**.

Разберём их по порядку — с примерами, сравнением и практическими рекомендациями.

---

## ✅ 1. Что такое **Avro** и **Protobuf**?

Это **форматы сериализации данных** — то есть, способы **преобразовать структурированные данные (например, объекты Python/Java/Go) в бинарный или текстовый формат для передачи по сети или хранения**.

Они используются вместо JSON/XML, когда нужно:

- Экономить место (меньший размер)
- Увеличить скорость (быстрее кодирование/декодирование)
- Гарантировать совместимость между сервисами
- Поддерживать строгую типизацию

---
### 🔹 **Apache Avro** — от Apache (Hadoop-экосистема)

#### 📌 Определение:
> **Avro** — это система сериализации, которая **хранит схему вместе с данными** (в отличие от Protobuf, где схема — отдельно).

#### ✅ Пример схемы (JSON):
```json
{
  "type": "record",
  "name": "User",
  "fields": [
    {"name": "id", "type": "int"},
    {"name": "name", "type": "string"},
    {"name": "email", "type": "string"},
    {"name": "is_active", "type": "boolean"}
  ]
}
```

→ Данные в бинарном виде:
```binary
[0x80, 0x7F, 0x61, 0x6C, 0x69, 0x63, 0x65, 0x40, 0x65, 0x78, 0x61, 0x6D, 0x70, 0x6C, 0x65, 0x2E, 0x63, 0x6F, 0x6D, 0x01]
```

#### 💡 Как работает:
- Схема **хранится отдельно** (в Schema Registry — например, Confluent Schema Registry)
- При отправке события — только **бинарные данные**
- При получении — система **загружает схему по ID** и восстанавливает объект

#### ✅ Преимущества Avro:
| Плюс | Объяснение |
|------|------------|
| **Схема + данные** | Схема может меняться — Avro умеет читать старые данные с новой схемой |
| **Поддержка динамической схемы** | Можно читать данные без предварительной генерации кода |
| **Отлично интегрируется с Hadoop / Spark** | Стандарт для Big Data |
| **Маленький размер** | Похож на Protobuf — очень компактный |
| **Поддержка рекурсии и сложных типов** | Массивы, карты, юнионы |

#### ⚠️ Недостатки:
- Сложнее в использовании (нужен Schema Registry)
- Медленнее сериализации, чем Protobuf (но всё равно быстрее JSON)
- Менее популярна в микросервисах, чем Protobuf

> ✅ **Идеален для потоковой обработки (Kafka), больших данных, ETL-систем.**

## 🆚 Сравнение: Avro vs Protobuf

| Критерий | **Protobuf** | **Avro** |
|----------|--------------|----------|
| **Схема** | Отдельно (в `.proto`) | Встроена в данные или в Schema Registry |
| **Человекочитаемость** | ❌ Нет | ❌ Нет (но схема — JSON) |
| **Скорость** | ✅ Лучше | ✅ Хорошая (немного медленнее) |
| **Размер данных** | ✅ Самый маленький | ✅ Очень маленький |
| **Обратная совместимость** | ✅ Да (через номера полей) | ✅ Да (через схему) |
| **Типизация** | ✅ Строгая, на этапе компиляции | ✅ Строгая, на этапе чтения |
| **Генерация кода** | ✅ Обязательна | ❌ Необязательна (можно динамически) |
| **Schema Registry** | ❌ Не требуется | ✅ Рекомендуется (Confluent) |
| **Лучшее применение** | gRPC, микросервисы, высокопроизводительные системы | Kafka, Hadoop, Spark, Big Data, ETL |
| **Популярность в microservices** | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ |

> 💬 **Если вы используете gRPC — выбирайте Protobuf.  
> Если вы пишете Kafka-приложение с большим количеством потребителей — выбирайте Avro + Schema Registry.**

## ✅ Когда что использовать?

| Сценарий | Рекомендация |
|----------|--------------|
| ✅ Вы используете **gRPC** | → **Protobuf** — стандарт |
| ✅ Вы используете **Kafka** для событий | → **Avro + Schema Registry** — лучший выбор для совместимости |
| ✅ Вам нужны **большие данные / Hadoop / Spark** | → **Avro** — стандартный формат |
| ✅ Вам нужна **максимальная скорость и минимальный размер** | → **Protobuf** |
| ✅ Вам нужно **отслеживать путь запроса через 10+ сервисов** | → **OpenTelemetry + Jaeger** |
| ✅ Вы строите **микросервисную систему в облаке** | → **Все три технологии вместе** |
| ✅ Вы делаете **MVP с 2 сервисами** | → JSON + логи — достаточно |

## 📚 Лучшие практики

| Практика | Объяснение |
|---------|------------|
| **Всегда используйте Schema Registry с Avro** | Без него — потеряете совместимость при изменении схемы |
| **Используйте OpenTelemetry** | Он заменил OpenTracing/OpenCensus — будущее трассировки |
| **Настройте sampling** | Не трассируйте 100% запросов — 1–10% достаточно для анализа |
| **Добавляйте теги в спаны** | `user_id`, `order_id`, `region` — чтобы фильтровать в UI |
| **Интегрируйте трассировку с логами** | OpenTelemetry позволяет связывать trace_id с логами |
| **Документируйте схемы** | Используйте Confluent Schema Registry UI — все могут видеть, как меняются события |

## 💬 Финальный вывод

| Технология | Это... | Ваша цель |
|------------|--------|------------|
| **Protobuf** | Супербыстрый, компактный способ **передавать структурированные данные** | Сделать ваш API/IPC **быстрым и надёжным** |
| **Avro** | Гибкий, совместимый способ **хранить и передавать события** с поддержкой схем | Сделать ваши **Kafka-потоки устойчивыми к изменениям** |
| **Distributed Tracing** | GPS-трекер для вашего **распределённого запроса** | Увидеть, **где и почему** система ломается — без логов в 1000 файлов |

> ✅ **Protobuf/Avro — это «что» вы передаёте.  
> Distributed Tracing — это «как» вы его отслеживаете.  
> Без них вы строите систему в темноте.  
> С ними — вы видите, как она дышит.**
