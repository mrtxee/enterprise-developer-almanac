## 🌟 Три механизма масштабирования в Kubernetes

| Механизм                      | Сокращение | Что масштабирует?                     | Когда использовать?                                    |
| ----------------------------- | ---------- | ------------------------------------- | ------------------------------------------------------ |
| **Horizontal Pod Autoscaler** | **HPA**    | Количество **Pod’ов** (реплик)        | Приложение получает больше/меньше трафика              |
| **Vertical Pod Autoscaler**   | **VPA**    | Ресурсы **одного Pod’а** (CPU, RAM)   | Pod’ы постоянно перегружены или недоиспользуют ресурсы |
| **Cluster Autoscaler**        | **CA**     | Количество **узлов (нод)** в кластере | Нет места на узлах — новые Pod’ы не могут запуститься  |

> ✅ **Их можно использовать вместе** — это **идеальная комбинация** для продакшена.

## ✅ 1. Horizontal Pod Autoscaler (HPA) — масштабируем **количество Pod’ов**

### 🎯 Что делает?
> Автоматически **увеличивает или уменьшает количество реплик Deployment’а (или StatefulSet’а)** на основе **метрик** (обычно CPU или память).

### 🔧 Как работает?
- Вы задаёте:
  - Минимальное количество Pod’ов (`minReplicas`)
  - Максимальное количество Pod’ов (`maxReplicas`)
  - Целевую нагрузку (например: `CPU 70%`)

- HPA **постоянно смотрит** на метрики (через `metrics-server`)
- Если CPU > 70% → **добавляет Pod’ы**
- Если CPU < 30% → **убирает Pod’ы**

### 📌 Пример: HPA для `events-service`

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
meta
  name: events-service-hpa
  namespace: cinemaabyss
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: events-service
  minReplicas: 2
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70   # ← Цель: 70% CPU
```

### 🔍 Что произойдёт?
| Ситуация | Действие HPA |
|----------|--------------|
| Средняя нагрузка CPU = 85% | ✅ Увеличит реплики до 3, 4, ... (до 10) |
| Средняя нагрузка CPU = 20% | ✅ Уменьшит реплики до 2 (минимум) |
| Нагрузка = 70% | ✅ Ничего не меняет — идеально |

### ✅ Проверить статус:
```bash
kubectl -n cinemaabyss get hpa
```

Вывод:
```
NAME               REFERENCE                 TARGETS         MINPODS   MAXPODS   REPLICAS   AGE
events-service-hpa Deployment/events-service  65%/70%         2         10        3          10m
```

> ✅ `TARGETS: 65%/70%` — значит, **нагрузка ниже цели** — HPA может уменьшить реплики.

## ✅ 2. Vertical Pod Autoscaler (VPA) — масштабируем **ресурсы одного Pod’а**

### 🎯 Что делает?
> Автоматически **изменяет `requests` и `limits` CPU/RAM** для Pod’ов — **без перезапуска** (в новых версиях).

> ❗ **Важно**:  
> VPA **не меняет ресурсы «на лету»** — он **перезапускает Pod’ы**, чтобы применить новые значения.

### 🔧 Как работает?
- VPA **анализирует историю использования** CPU и памяти Pod’ов
- Рекомендует новые значения
- **Перезапускает Pod’ы** с новыми `requests/limits`

### 📌 Пример: VPA для `events-service`

```yaml
apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
meta
  name: events-service-vpa
  namespace: cinemaabyss
spec:
  targetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: events-service
  updatePolicy:
    updateMode: "Auto"   # ← Автоматически применяет изменения
  resourcePolicy:
    containerPolicies:
    - containerName: events-service
      mode: "Auto"
```

### 🔍 Что происходит?
| Ситуация | Действие VPA |
|----------|--------------|
| Pod использует 800m CPU, но имеет `requests: 200m` | ✅ Увеличит `requests` до 800m–1000m |
| Pod использует 50Mi RAM, но имеет `limits: 1Gi` | ✅ Уменьшит `limits` до 256Mi |
| Pod перегружен — падает из-за OOM | ✅ Увеличит `limits` и `requests` |

### ✅ Проверить рекомендации:
```bash
kubectl -n cinemaabyss get vpa events-service-vpa -o yaml
```

Найдите в выводе:
```yaml
recommendation:
  containerRecommendations:
  - containerName: events-service
    lowerBound:
      cpu: 500m
      memory: 256Mi
    target:
      cpu: 800m
      memory: 512Mi
    upperBound:
      cpu: 1000m
      memory: 1Gi
```

> 💡 VPA **не меняет Deployment** — он **только рекомендует**.  
> Чтобы применить — нужно **перезапустить Pod’ы** (VPA делает это автоматически, если `updateMode: Auto`).

## ✅ 3. Cluster Autoscaler (CA) — масштабируем **узлы кластера**

### 🎯 Что делает?
> Автоматически **добавляет или удаляет физические/виртуальные машины (узлы)** в кластере, когда:
> - **Нет места** для новых Pod’ов → **добавляет ноду**
> - **Узлы недоиспользуются** → **удаляет ноду**

> ✅ Это **важно для облака (EKS, GKE, AKS)** — экономит деньги!

### 🔧 Как работает?
- CA **смотрит на Pod’ы, которые не могут быть запущены** (из-за нехватки CPU/RAM)
- Если есть **Pending Pod’ы** → CA **запрашивает новую ноду** у провайдера (AWS, GCP и т.д.)
- Если нода **не используется > 10 минут** → CA **удаляет её**

### 📌 Пример: Cluster Autoscaler в AWS EKS

> CA **не устанавливается вручную** — он **встроен** в EKS / GKE / AKS.

Если вы используете **Minikube** или **Docker Desktop** — CA **не работает** (нет физических нод для масштабирования).

### 🔍 Когда CA срабатывает?

| Ситуация | Действие CA |
|----------|-------------|
| У вас 3 ноды, все загружены на 90% → новый Pod не может запуститься | ✅ CA запрашивает **новую ноду** |
| У вас 5 нод, одна из них используется на 10% → другие Pod’и пересажены | ✅ CA удаляет **ненужную ноду** через 10 минут |
| У вас есть **Pod с `nodeSelector`** или **taint/toleration** | CA **учитывает** — добавит только подходящую ноду |

### ✅ Проверить, работает ли CA (в облаке):

```bash
kubectl -n kube-system get pods -l app=cluster-autoscaler
```

Если есть Pod — **CA работает**.

## 🆚 Сравнение: HPA vs VPA vs CA

| Критерий | **HPA** | **VPA** | **Cluster Autoscaler** |
|----------|---------|---------|------------------------|
| **Что масштабирует** | Количество Pod’ов | CPU/RAM одного Pod’а | Количество узлов (нод) |
| **Скорость реакции** | Быстро (секунды) | Средняя (минуты — перезапуск Pod’ов) | Медленная (2–5 минут — запуск ноды) |
| **Зависит от** | Metrics Server | VPA-аддон | Облачный провайдер (AWS, GCP...) |
| **Требует** | `metrics-server` | `vpa-admission-controller` | Поддержка CA в кластере (EKS/GKE) |
| **Повторный запуск Pod’ов** | ❌ Нет | ✅ Да | ✅ Да (если Pod переносится на новую ноду) |
| **Экономия ресурсов** | ✅ Хорошая | ✅ Отличная | ✅ Лучшая (уменьшает стоимость нод) |
| **Подходит для** | Веб-сервисы, API | Приложения с неравномерной нагрузкой | Все, особенно в облаке |

## ✅ Как они работают вместе? (Пример из реальной жизни)

Представьте сервис `events-service`:

### 📈 Сценарий: Пик трафика (например, выход фильма)

| Этап | Что происходит |
|------|----------------|
| 1. В 18:00 — всплеск трафика → CPU Pod’ов = 90% | ✅ **HPA** → добавляет Pod’ы: 2 → 5 → 8 |
| 2. Новые Pod’ы не могут запуститься — не хватает CPU на нодах | ✅ **Cluster Autoscaler** → запрашивает новую ноду (например, `t3.large`) |
| 3. Новая нода появляется → Pod’ы запускаются | ✅ **VPA** анализирует — замечает, что Pod’ы используют 800m CPU, а у них `requests: 200m` → рекомендует увеличить |
| 4. Через 10 минут — VPA перезапускает Pod’ы с `requests: 800m` | ✅ Теперь Pod’ы более стабильны |
| 5. В 22:00 — трафик падает → CPU = 20% | ✅ HPA → уменьшает Pod’ы до 2 |
| 6. Одна из нод не используется > 10 минут | ✅ Cluster Autoscaler → удаляет её → **экономия денег!** |

> ✅ **Идеальная комбинация**:
> - **HPA** — масштабирует **горизонтально**
> - **VPA** — оптимизирует **вертикально**
> - **CA** — масштабирует **инфраструктуру**

## ✅ Рекомендации по настройке

| Механизм | Рекомендация |
|----------|--------------|
| ✅ **HPA** | Используйте **CPU и память** — `averageUtilization: 60–70%`<br>Для HTTP-запросов — можно использовать **пользовательские метрики** (например, запросы в секунду через Prometheus) |
| ✅ **VPA** | Используйте `updateMode: "Auto"` — но **тестируйте в dev**<br>Не используйте для **StatefulSet’ов с базами данных** — может повредить данные |
| ✅ **Cluster Autoscaler** | Всегда включайте в **облачных кластерах**<br>Настройте **минимальный и максимальный размер кластера** (например: 2–10 нод) |
| ✅ **Все три** | Включайте **все вместе** — это **стандарт продакшена** |

## ✅ Как включить HPA и VPA в Minikube / Docker Desktop?

### 🔧 HPA — нужен `metrics-server`

```bash
# В Minikube:
minikube addons enable metrics-server

# В Docker Desktop — включён по умолчанию (проверьте):
kubectl get pods -n kube-system | grep metrics-server
```

### 🔧 VPA — устанавливается вручную

```bash
# Установите VPA (все компоненты)
kubectl apply -f https://github.com/kubernetes/autoscaler/releases/download/v0.12.0/vpa-release.yaml
```

> ⚠️ **Не используйте VPA в Minikube/Docker Desktop для продакшена** — он нестабилен и не масштабируется.

## ✅ Проверка: Как убедиться, что всё работает?

| Команда | Что проверяет |
|---------|---------------|
| `kubectl get hpa` | Есть ли HPA и какие цели |
| `kubectl get vpa` | Есть ли VPA и какие рекомендации |
| `kubectl get nodes` | Сколько нод — и меняется ли при нагрузке |
| `kubectl top pods` | Какие Pod’ы используют CPU/RAM |
| `kubectl top nodes` | Какие ноды загружены |
| `kubectl get pods --all-namespaces -o wide` | Есть ли Pending Pod’ы → значит, CA должен сработать |

## ✅ Финальный совет: Когда что использовать?

| Ваша цель | Рекомендация |
|-----------|--------------|
| 📈 Приложение получает **пиковые нагрузки** (например, 18:00 — 22:00) | ✅ **HPA** |
| 💡 Pod’ы **постоянно перегружены** или **много ресурсов пропадают** | ✅ **VPA** |
| 💰 Вы используете **облачный кластер (EKS, GKE)** и хотите **экономить** | ✅ **Cluster Autoscaler** |
| 🏗️ Вы строите **продакшен-систему** | ✅ **Все три вместе** — это **золотой стандарт** |
| 🧪 Вы тестируете локально | ✅ Только **HPA** (с `metrics-server`) — VPA и CA не нужны |

## ✅ Резюме: Масштабирование в Kubernetes — шпаргалка

| Механизм | Что масштабирует | Как? | Когда? |
|----------|------------------|------|--------|
| **HPA** | Количество Pod’ов | Увеличивает/уменьшает реплики | При изменении нагрузки (трафик, запросы) |
| **VPA** | CPU/RAM одного Pod’а | Перезапускает Pod’ы с новыми лимитами | Когда Pod’ы слишком мало или слишком много ресурсов |
| **Cluster Autoscaler** | Количество узлов (нод) | Добавляет/удаляет машины | Когда не хватает места — или ноды не используются |

> ✅ **Лучшая практика**:  
> **HPA + VPA + CA = идеальная, экономичная, отказоустойчивая система.**
