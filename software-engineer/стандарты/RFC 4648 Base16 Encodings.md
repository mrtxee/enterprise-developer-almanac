# RFC 4648: The Base16, Base32, and Base64 Data Encodings

**RFC 4648** — это стандарт [[IETF]] (Internet Engineering Task Force), опубликованный в октябре 2006 года. Он описывает **методы кодирования бинарных данных в текстовом формате** — то есть преобразования последовательности байтов в строку символов, безопасную для передачи через текстовые протоколы (например, HTTP, email, JSON).


## Основные схемы кодирования в RFC 4648

Стандарт формализует три популярные схемы:


1. **Base64**
   * Алфавит: 64 символа — `A–Z`, `a–z`, `0–9`, `+`, `/`.
   * Для выравнивания длины строки используется символ `=` (паддинг).
   * Широко применяется для встраивания бинарных данных (изображений, файлов) в JSON, XML, веб‑токены (JWT).
   * Пример: `Hello` → `SGVsbG8=`.

2. **Base32**
   * Алфавит: 32 символа — заглавные буквы `A–Z` и цифры `2–7`.
   * Исключает символы, похожие друг на друга (`0`, `1`, `8`, `9`, строчные буквы), поэтому менее подвержен ошибкам при ручном вводе.
   * Также использует паддинг (`=`).
   * Применяется в OTP (одноразовых паролях), QR‑кодах, системах, где важна читаемость.
   * Пример: `Hello` → `JBSWY3DP`.

3. **Base16** (шестнадцатеричное кодирование, hex)
   * Алфавит: 16 символов — цифры `0–9` и буквы `A–F` (или `a–f`).
   * Паддинг не требуется.
   * Используется повсеместно: контрольные суммы (MD5, SHA), цвета в CSS, дампы памяти, отладка.
   * Пример: `Hello` → `48656C6C6F`.

## Ключевые положения стандарта


RFC 4648 чётко определяет:
* **Алфавиты** для каждой схемы — какие символы и в каком порядке использовать.
* **Правила паддинга** — когда и как добавлять символы `=` для выравнивания длины строки.
* **Обратимость** — алгоритм должен позволять однозначно декодировать строку обратно в исходные бинарные данные.
* **Обработку ошибок** — как реагировать на недопустимые символы или некорректную длину.
* **Регистрозависимость** — например, Base16 допускает и `A–F`, и `a–f`, а Base32 использует только заглавные.
* **Ограничения на пробелы и переносы строк** — стандарт допускает их игнорирование при декодировании (удобно для форматирования длинных строк).

## Зачем нужен RFC 4648

До публикации документа разные реализации Base64 (и других схем) могли:
* использовать разные алфавиты (менять местами `+` и `/`, добавлять иные спецсимволы);
* по‑разному обрабатывать паддинг или ошибки;
* не согласовываться между системами.

**RFC 4648 унифицировал эти правила**, обеспечив:
* совместимость между библиотеками и языками программирования;
* надёжность передачи данных через текстовые каналы;
* однозначность интерпретации закодированных строк.

## Краткий итог


**RFC 4648** — это нормативный документ, который:
* стандартизирует кодирование Base16, Base32 и Base64;
* задаёт чёткие правила алфавита, паддинга и декодирования;
* устраняет разночтения между реализациями;
* делает обмен бинарными данными через текст предсказуемым и безопасным.
