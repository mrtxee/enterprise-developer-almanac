## 📋 Ключевые стандарты IETF для разработки ПО и облачных решений

**IETF (Internet Engineering Task Force)** — организация, разрабатывающая добровольные стандарты для интернета. Многие RFC стали **де-факто обязательными** для построения надёжных, безопасных и масштабируемых систем.

# RFC

**RFC** расшифровывается как **Request for Comments** (в переводе с английского — **«Запрос на комментарии»** или «Предложение для обсуждения»).

### 📜 Немного истории и смысла:
Хотя название звучит скромно («просто запрос на мнение»), на практике RFC являются **официальными стандартами и спецификациями**, регулирующими работу интернета.

1.  **Происхождение:** Термин появился в 1969 году в рамках проекта ARPANET (предтеча интернета). Инженеры публиковали технические идеи в виде документов, чтобы коллеги могли их обсудить, покритиковать и доработать.
2.  **Эволюция:** Со временем процесс стал формализованным. Документ проходит стадии черновика (Draft), обсуждения, исправления и, если он одобрен сообществом IETF (Internet Engineering Task Force), получает статус **Standard** (Стандарт) или **Best Current Practice** (Лучшая текущая практика).
3.  **Неизменность:** После публикации RFC получает уникальный номер (например, RFC 793 для TCP) и **никогда не изменяется**. Если нужно что-то исправить или дополнить, публикуется новый RFC, который может устаревать (obsoletes) предыдущий.

### 💡 Почему это важно?
Когда вы видите ссылку на **RFC 2616** (HTTP/1.1) или **RFC 8446** (TLS 1.3), это означает, что вы читаете **канонический источник истины** о том, как должен работать этот протокол. Все браузеры, серверы и сетевое оборудование обязаны следовать этим документам для обеспечения совместимости.


Ниже — отобранные стандарты, сгруппированные по областям применения.

## 🌐 Сетевые протоколы и транспорт

| Стандарт | Краткое описание | Зачем нужен в облаке |
|----------|-----------------|---------------------|
| **RFC 793 TCP** | Transmission Control Protocol | Надёжная доставка, контроль перегрузок, основа большинства сервисов |
| **RFC 2460 IPv6** | Интернет-протокол версии 6 | Будущее адресации, необходимо для масштабирования и IoT |
| **RFC 6298 TCP RTO** | Алгоритм расчёта таймаута повторной передачи | Критичен для настройки таймаутов в микросервисах |
| **RFC 8996 TLS 1.3** | Современная версия TLS | Безопасность по умолчанию, 0-RTT, улучшенная производительность |
| **RFC 8446 QUIC** | Транспорт поверх UDP с встроенным TLS | Низкая задержка для мобильных и веб-приложений (HTTP/3) |
| **RFC 7540 HTTP/2** | Мультиплексирование, сжатие заголовков, server push | Ускорение веб-запросов, снижение latency |
| **RFC 9110–9114 HTTP/3** | HTTP поверх QUIC | Устойчивость к потере пакетов, быстрый хендшейк |

> 💡 **Практический совет**: Используйте **TLS 1.3 + HTTP/2** как минимальный стандарт для новых сервисов.

## 🔐 Безопасность и аутентификация

| Стандарт | Краткое описание | Зачем нужен в облаке |
|----------|-----------------|---------------------|
| **RFC 6749 OAuth 2.0** | Фреймворк авторизации | Делегирование доступа между сервисами, SSO |
| **RFC 7519 JWT** | JSON Web Token | Stateless-аутентификация в микросервисах |
| **RFC 8414 OAuth 2.0 Authorization Server Metadata** | Авто-обнаружение конфигурации авторизации | Упрощение интеграции с OIDC-провайдерами |
| **RFC 8705 OAuth 2.0 Mutual TLS** | mTLS для защиты токенов | Zero Trust-архитектуры, защита от утечки токенов |
| **RFC 8445 ICE** | Установление соединений через NAT | P2P-коммуникации, WebRTC, голос/видео в облаке |
| **RFC 2104 HMAC** | keyed-Hash Message Authentication Code | Подпись запросов между сервисами, вебхуки |

> 💡 **Практический совет**: Реализуйте **OAuth 2.0 + JWT + mTLS** для сервис-сервис аутентификации в Zero Trust.

## 🌍 HTTP, API и веб-архитектура

| Стандарт                                                                        | Краткое описание                                         | Зачем нужен в облаке                            |
| ------------------------------------------------------------------------------- | -------------------------------------------------------- | ----------------------------------------------- |
| **RFC 7230–7237 HTTP/1.1**                                                      | Базовая спецификация HTTP                                | Понимание кэширования, заголовков, методов      |
| **RFC 7807 Problem Details for HTTP APIs**                                      | Стандартизация ошибок в API                              | Единый формат ошибок для клиентов и мониторинга |
| **RFC 6585 Additional HTTP Status Codes**                                       | 429 Too Many Requests, 451 Unavailable For Legal Reasons | Rate limiting, compliance                       |
| **RFC 7694 Hypertext Transfer Protocol (HTTP) Client-Initiated Content Upload** | Загрузка больших файлов                                  | Chunked upload, resumable transfers             |
| **RFC 8288 Web Linking**                                                        | Link headers для пагинации, версионирования              | HATEOAS, навигация по ресурсам в REST API       |
| **RFC 9110 HTTP Semantics**                                                     | Обновлённая семантика методов, кэширования               | Корректная реализация кэшей, прокси, CDN        |

> 💡 **Практический совет**: Всегда возвращайте ошибки в формате **RFC 7807]** — это упрощает отладку и автоматическую обработку.

## ☁️ Облачные и распределённые системы

| Стандарт | Краткое описание | Зачем нужен в облаке |
|----------|-----------------|---------------------|
| **RFC 7542 The "alt-svc" HTTP Header Field** | Альтернативные сервисы (например, HTTP/3) | Плавный переход на новые протоколы без разрыва |
| **RFC 8613 Object Security for Constrained RESTful Environments (OSCORE)** | Защита CoAP на уровне сообщений | IoT, edge-устройства с ограниченным ресурсом |
| **RFC 8323 CoAP over TCP, TLS, and WebSockets** | Адаптация CoAP для надёжных транспортов | Гибридные архитектуры: IoT → облако |
| **RFC 8949 Concise Binary Object Representation (CBOR)** | Бинарный аналог JSON для ограниченных сред | Эффективная сериализация в микросервисах и IoT |
| **RFC 9116 A File Format to Report Security Vulnerabilities** | security.txt | Стандартизация процесса disclosure для облачных сервисов |

> 💡 **Практический совет**: Используйте **CBOR** вместо JSON для внутренних сервисов с высокой нагрузкой — экономия 20–40% трафика и CPU.

| ------------------------------------------------- | ----------------------------------------- | ------------------------------------------------------------ |
| **[[RFC 2782 DNS SRV Records]]**                  | Записи для указания хоста и порта сервиса | Service discovery без дополнительного компонента             |

> 💡 **Практический совет**: Используйте **DNS SRV + DNS-SD** для service discovery в гибридных средах (on-premise + cloud).

## 🧰 Инструменты и практики внедрения

### 1. Валидация соответствия стандартам
```yaml
# .github/workflows/rfc-compliance.yml
- name: Check HTTP headers compliance
  run: |
    curl -sI https://api.example.com/health | \
      grep -E "^(HTTP|Content-Type|Cache-Control):" | \
      ./validate-rfc7234.sh
```

### 2. Генерация клиентов по спецификациям
```bash
# OpenAPI + RFC 7807 ошибки
openapi-generator generate \
  -i api.yaml \
  -g typescript-fetch \
  --additional-properties=useRFC7807Errors=true
```

### 3. Тестирование устойчивости к стандартам
```python
# Тест: корректная обработка 429 по RFC 6585
def test_rate_limiting():
    for _ in range(101):  # лимит 100 req/min
        resp = client.get("/api/data")
    assert resp.status_code == 429
    assert resp.headers["Retry-After"  # по RFC 7231
```

## ✅ Чек-лист соответствия стандартам для нового сервиса

- [ ] Все внешние API используют **HTTPS (TLS 1.3)** и возвращают заголовки безопасности (HSTS, CSP)
- [ ] Ошибки возвращаются в формате **RFC 7807]** с машиночитаемым `type`
- [ ] Временные метки в логах и ответах — **RFC 3339 (UTC)**
- [ ] Аутентификация реализована через **OAuth 2.0 / JWT (RFC 6749], RFC 7519])**
- [ ] Поддерживается **HTTP/2** (или HTTP/3) для снижения latency
- [ ] Rate limiting возвращает **429 + Retry-After (RFC 6585])**
- [ ] Кэширование настроено согласно **RFC 7234]** (Cache-Control, ETag)
- [ ] Service discovery использует **DNS SRV / DNS-SD (RFC 2782, RFC 6763)** при отсутствии service mesh
