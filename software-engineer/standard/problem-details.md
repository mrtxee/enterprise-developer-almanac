## RFC 9457 Problem Details for HTTP API

**RFC 9457** («Problem Details for HTTP APIs») — стандарт, опубликованный в августе 2023 года рабочей группой [[org-ietf|IETF]] (Internet Engineering Task Force). Он обновляет и заменяет RFC 7807, уточняя формат описания ошибок в HTTP-API.

Цель стандарта — унифицировать, как веб-сервисы сообщают клиентам о проблемах: вместо разнородных ответов с кодами состояния и «сырыми» сообщениями — структурированные JSON-объекты с чёткими полями.

### Зачем нужен RFC 9457

Без единого формата ошибки API выглядят так:

- разные сервисы используют свои ключи (`error`, `message`, `err`, `details` и т. д.);
- текст сообщений не стандартизирован — сложно парсить автоматически;
- нет ссылок на документацию или способы исправить ошибку;
- клиенты вынуждены писать много кода для обработки частных случаев.

RFC 9457 решает эти проблемы, задавая **минимальный набор полей** и правила их заполнения.

### Ключевые поля объекта ошибки

Ответ об ошибке — JSON-объект с опциональными и обязательными полями:

| Поле | Обязательность | Описание |
|---|---|---|
| `type` | опционально | URI, указывающий на тип проблемы (например, `https://example.com/problems/invalid-input`). Может быть ссылкой на документацию. |
| `title` | **обязательно** | Краткое, читаемое человеком описание типа ошибки, не зависит от конкретного запроса. Примеры: `"Bad Request"`, `"Forbidden"`. |
| `status` | **обязательно** | HTTP-статус-код ответа (целое число). Примеры: 400, 401, 404, 500. |
| `detail` | опционально | Подробное, конкретное сообщение об ошибке для этого запроса. Пример: `"Email address is not valid"`. |
| `instance` | опционально | URI, идентифицирующий конкретный экземпляр ошибки (например, лог или трассировку). Пример: `/logs/error-12345`. |

### Примеры ответов

**Неверный ввод (400 Bad Request)**

```http
HTTP/1.1 400 Bad Request
Content-Type: application/problem+json
```

```json
{
  "type": "https://example.com/problems/validation-error",
  "title": "Invalid Input",
  "status": 400,
  "detail": "The 'email' field must be a valid email address.",
  "instance": "/api/v1/users/registration"
}
```

**Доступ запрещён (403 Forbidden)**

```http
HTTP/1.1 403 Forbidden
Content-Type: application/problem+json
```

```json
{
  "type": "https://example.com/problems/insufficient-rights",
  "title": "Forbidden",
  "status": 403,
  "detail": "You do not have permission to access this resource.",
  "instance": "/api/v1/admin/dashboard"
}
```

**Ресурс не найден (404 Not Found)**

```http
HTTP/1.1 404 Not Found
Content-Type: application/problem+json
```

```json
{
  "type": "https://tools.ietf.org/html/rfc9110#section-15.5.5",
  "title": "Not Found",
  "status": 404,
  "detail": "The requested user ID '123' does not exist.",
  "instance": "/api/v1/users/123"
}
```

### Важные технические детали

1. **Content-Type**: для ответов по RFC 9457 используется `application/problem+json`. Это чётко сигнализирует клиенту, что тело ответа — структурированная ошибка.
2. **HTTP-статус**: поле `status` должно совпадать с кодом состояния HTTP. Это упрощает обработку на стороне клиента.
3. **Локализация**: стандарт не регулирует перевод `title` и `detail`. Если API поддерживает несколько языков, можно использовать заголовок `Accept-Language`.
4. **Расширения**: разрешено добавлять свои поля (например, `errors` — массив деталей валидации). Главное — не переопределять стандартные.

### Отличия от RFC 7807

RFC 9457 — эволюция RFC 7807. Ключевые изменения:

- уточнены правила для полей `type` и `instance` (когда использовать URI, когда относительные пути);
- добавлены примеры для сложных случаев (например, пакетных операций);
- улучшена совместимость с другими стандартами IETF;
- актуализированы ссылки на HTTP-спецификации ([[http-semantics|RFC 9110]] и др.).

| Параметр | RFC 7807 | RFC 9457 |
|---|---|---|
| Статус | Устаревший (Obsolete) | Актуальный |
| Год | 2016 | 2023 |
| Что нового | Оригинальная спецификация | Уточнения семантики, примеры, HTTP/3 |

**Совместимость форматов**

- Полная обратная совместимость: любой парсер RFC 7807 поймёт RFC 9457.
- Формат не изменился — те же поля (`type`, `title`, `status`, `detail`, `instance`).
- Для новых проектов используется RFC 9457, старые можно не менять.

### Как применять на практике

1. Для всех ошибок с кодами 4xx и 5xx возвращайте JSON с полями `title`, `status` и опционально `type`, `detail`, `instance`.
2. Настройте middleware (в Express, Spring, ASP.NET и т. д.), которое перехватывает исключения и формирует ответ по шаблону.
3. Создайте словарь `type`-URI для типовых ошибок (валидация, аутентификация, лимиты и т. д.).
4. Укажите в документации API, что вы следуете RFC 9457, и приведите примеры ответов.
5. В логах связывайте `instance` с ID запроса — это упростит отладку.

**Итог**

RFC 9457 делает ошибки HTTP-API предсказуемыми и машиночитаемыми:

- клиенты получают чёткую структуру для разбора ошибок;
- разработчики API — единый шаблон для всех сервисов;
- команды поддержки — ссылки на контекст (`instance`) для расследования проблем.

Стандарт особенно полезен для публичных API, [[microservice|микросервисов]] и систем с множеством интеграций.
