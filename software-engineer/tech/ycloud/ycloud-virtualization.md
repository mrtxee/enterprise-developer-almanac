## виртуализация в Yandex Cloud

### управление доступом

- **[[identity-access-management|IAM]] — Identity and Access Management**
  - Проверяет все операции в Yandex Cloud и управляет доступом на основе ролей.
  - Отвечает на вопрос «кому можно».
- **ACL — Access Control List**
  - Распространяется на [[amazon-s3|объектное хранилище]]. Есть списки: READ, WRITE, FULL_CONTROL.
  - Отвечает на вопрос «что можно».
- **Политика доступа — Bucket Policy**
  - Задаёт дополнительные условия действий с бакетами и объектами.
  - Элементы политики доступа:
    - **ресурс**
    - **действие**
    - **результат** — запрет (Deny) или разрешение (Allow) действия.
    - **пользователь**
    - **условие**
    - **принцип выбора** — включить или исключить пользователей.

### мониторинг состояния

#### метрики кластера БД

- **[[metrics-qps|Queries per second]]** — общее количество запросов в секунду, для каждого хоста.
- **Average query time** — среднее время исполнения запросов, для каждого хоста (в миллисекундах).
- **Slow queries per second** — количество SQL-запросов в секунду, выполняющихся дольше, чем параметр `long_query_time`, для каждого хоста.
- **Connections** — количество подключений, для каждого хоста.
- **Threads running** — количество запущенных потоков, для каждого хоста. При увеличении нагрузки на кластер это значение быстро растёт.
- **Disk usage** — занятое дисковое пространство (в байтах), для каждого хоста и для кластера в целом.
- **Is Primary** — показывает, какой хост является мастером и как долго.
- **Is Alive** — доступность кластера в виде суммы состояний его хостов. Каждый хост в состоянии `Alive` увеличивает общую доступность на 1. При выходе из строя одного из хостов общая доступность уменьшается на 1. Добавление хостов повышает доступность кластера.
- **[[metrics-highload|Replication lag]]** — отставание реплики от мастера (в секундах).

#### метрики состояния хостов

- **CPU usage** — загрузка процессорных ядер. При повышении нагрузки значение `Idle` уменьшается.
- **Memory usage** — использование оперативной памяти (RAM) в байтах. При высоких нагрузках значение параметра `Free` уменьшается, а `Used` и остальные растут.
- **Disk read/write bytes** — средний объём данных, записанных в хранилище и прочитанных из него (в байтах).
- **Disk IOPS** — среднее количество операций ввода-вывода в хранилище.
- **Network bytes** — средний объём данных, отправленных в сеть и полученных из неё (в байтах).
- **Network packets** — среднее количество пакетов, отправленных в сеть и полученных из неё.

Графики на дашборде позволяют оперативно выявлять просадку производительности хостов и следить за состоянием всего кластера.

За мониторинг ресурсов в Yandex Cloud отвечает сервис [[ycloud-monitoring|Yandex Monitoring]].

В блоке **MySQL overview** отображаются расширенные сведения о состоянии БД на хосте.

#### типы логирования

- `MYSQL_GENERAL` — общий журнал запросов к БД.
- `MYSQL_ERROR` — журнал ошибок MySQL.
- `MYSQL_SLOW_QUERY` — журнал медленных запросов MySQL.
- `MYSQL_AUDIT` — информация о подключениях к БД.

### репликация

**Репликация** — механизм синхронизации копий БД внутри кластера.

- Асинхронный механизм репликации допускает задержку между подтверждением транзакции (целостного выполнения связанных между собой операций) на одном хосте и её передачей на другие хосты. Это ускоряет работу, но при сбое данные могут быть потеряны.
- В кластерах ClickHouse используется асинхронная репликация.
- В кластерах [[PostgreSQL|PostgreSQL]] используется синхронная репликация.
- **Логическая репликация** отличается от физической тем, что вместо последовательностей байтов копируются таблицы и строки. В PostgreSQL также реализован метод логической репликации.
- **Каскадная репликация** — когда реплика-подписчик используется для синхронизации с другими репликами группы.

#### миграция данных в облако через репликацию

**План**
1. Настроить сервер с источником данных.
2. Экспортировать схему БД из источника.
3. Создать кластер Managed Service for PostgreSQL и восстановить схему БД.
4. Создать публикации и подписки.
5. Перенести PostgreSQL-sequences после репликации.
6. Отключить репликацию и перенести нагрузки.

### Yandex Data Transfer — сервис миграции баз данных

Сервис Yandex Data Transfer позволяет ускорить миграцию и минимизировать простой при переключении на новую БД.

**Эндпоинт** — конфигурация для подключения к БД. Эндпоинты доступны для разных [[software-architect/data/data-base/rdbms/rdbms|СУБД]] и делятся на два типа:
1. Источник — описывает настройки БД, откуда передаётся информация.
2. Приёмник — описывает настройки БД, куда переносится информация.

**Трансфер** — перенос данных из источника в приёмник. Трансфер должен находиться в одном каталоге с эндпоинтами, которые соединяет.

Трансферы бывают следующих типов:
- **Копирование** — перенос снапшота (моментального снимка) БД.
- **Репликация** — непрерывное получение изменений из БД источника и применение их к БД приёмника.
- **Копирование и репликация** — перенос состояния базы источника в базу приёмника и поддержание этого состояния.

### шардирование — горизонтальное масштабирование

**Шардирование** — это горизонтальное масштабирование данных, при котором данные разбиваются на **шарды** (то есть части) и размещаются на разных хостах кластера. Нагрузка на БД при этом распределяется по хостам, что позволяет добиться большей производительности системы, чем если бы она была расположена на одном мощном сервере.

В [[mongo-db|MongoDB]] шардирование коллекций поддерживается по умолчанию — части коллекций [[mongo-db|MongoDB]] размещаются на разных хостах кластера. На какой шард попадает фрагмент данных, определяет **ключ шардирования**.

**Особенности**
- ✅ Обойти технические ограничения. Если БД работает на пределе производительности — можно разбить её на части и распределить запросы на чтение между ними.
- ✅ Ускорить доступ к данным для пользователей из конкретного региона. Например, международные соцсети могут хранить контент на русском языке на серверах ближе к России.
- ✅ Выполнить юридические требования. Например, хранить конфиденциальные данные на шарде, публичный доступ к которому отключен.
- ✅ Повысить доступность. Если БД находится на одном нешардированном хосте, то его выход из строя приведёт к потере всех данных. Если же БД шардирована, то при отказе одного шарда все данные на других остаются доступными. Для шардов можно дополнительно настроить репликацию, а размещение реплик в разных зонах доступности даёт отказоустойчивую систему.
- ✅ Ускорить запросы. Они могут выполняться медленнее из-за того, что конкурируют за ресурсы сервера. Шардирование устраняет конкуренцию, исполняя запросы параллельно на разных серверах.
- ❌ Правильно шардировать данные, то есть разбить их на части, — непростая задача. Если сделать это неверно, мощности серверов будут использоваться нерационально. Например, потребуется много межсерверных запросов.
- ❌ Из-за несбалансированного распределения данных между шардами появляются горячие точки — разделы БД, к которым идет намного больше обращений по сравнению с остальными. Запросы к горячим точкам обрабатываются заметно медленнее.

### DataLens — анализ информации

[[ycloud-economics|DataLens]] — сервис Yandex Cloud для визуализации и анализа данных. Он позволяет создавать **чарты** — диаграммы и графики, а также **дашборды** — страницы с инфографикой. Для работы нужно взять источник данных, создать **датасет** и настроить его визуальное представление.

DataLens можно подключить из маркетплейса Yandex Cloud.

### виртуальные машины в Compute Cloud

#### Yandex Network Load Balancer

**Целевая группа** — набор серверов или других облачных ресурсов, по которым распределяются запросы пользователей. Целевая группа выглядит как список внутренних IP-адресов и подсетей, к которым эти IP-адреса относятся. Для каждого адреса указан идентификатор его подсети. Все адреса целевых ресурсов должны принадлежать одной облачной сети.

**Обработчик** — приложение, которое принимает соединения от пользователей, распределяет их между IP-адресами целевой группы, а затем передаёт обратный трафик клиентам. Список подсетей и их идентификаторов доступен в консоли управления в разделе **Virtual Private Cloud** на вкладке **Облачные сети**.

Адресация трафика строится по принципу **5-tuple**. Учитываются следующие параметры:
1. адрес отправителя.
2. порт отправителя.
3. адрес целевого (принимающего) облачного ресурса.
4. порт целевого (принимающего) облачного ресурса.
5. протокол передачи информации.

Для приёма трафика обработчик использует порты от 1 до 32767.

#### проверка состояния

Балансировщик запрашивает у каждой [[yandex-cloud-cli|ВМ]] страницу по HTTP раз в 10 секунд (это **интервал выполнения проверки**). Если ВМ за заданное **время ожидания**, которое должно быть меньше интервала выполнения проверки минимум на 1 секунду, отдаёт код `200`, то она находится в состоянии `Healthy` (здорова) и готова принимать трафик. Если ВМ не успеет ответить, её состояние изменяется на `Unhealthy` (нездорова) с учётом установленного **порога неработоспособности** — числа последовательных неудачных проверок, по достижении которого ресурс считается недоступным. Балансировщик перестаёт отправлять трафик на эту ВМ.

Если работа проблемной ВМ будет восстановлена и она снова начнёт отдавать код `200` за установленное время ожидания (с учётом **порога работоспособности** — числа последовательных удачных проверок, по достижении которого ресурс считается доступным), то ей опять будет присвоен статус `Healthy`.

#### группы безопасности

Главный принцип: **запрещено всё, что не разрешено явно**. Если назначить сетевому интерфейсу ВМ [[cloud-security|группу безопасности]] без правил, ВМ не сможет передавать и принимать трафик, и подключиться к ней по SSH не получится.

Группы безопасности выполняют функцию межсетевого экрана и контролируют входящий и исходящий трафик ВМ.

Группа безопасности назначается сетевому интерфейсу ВМ и содержит правила получения и отправки трафика.

Если нет правил для исходящего трафика, ответный трафик будет поступать на ВМ, но не инициироваться.

##### виды правил безопасности

- Для входящего трафика — определяют диапазоны адресов и портов или другие группы безопасности, откуда ВМ могут принимать трафик.
- Для исходящего трафика — определяют диапазоны адресов и портов или другие группы безопасности, куда ВМ могут отправлять трафик.

#### миграция локальной ВМ в Compute Cloud

Локальную ВМ можно перенести в Compute Cloud. Для этого подготовьте файл образа ВМ (поддерживаются форматы `Qcow2`, `VMDK` или `VHD`) и загрузите его в бакет Yandex Object Storage, после чего образ станет доступен при создании ВМ.

#### маркетплейс Yandex Cloud

Маркетплейс Yandex Cloud (ycloud marketplace) — каталог готовых решений и образов для облака, аналог [[containerization|Docker Hub]].

#### образ операционной системы

**Образ операционной системы** — дистрибутив ОС с предустановленными и настроенными приложениями. Создание ВМ из образа происходит быстрее, чем из снимка диска. Образы выбирают, когда важна скорость создания ВМ.

#### прерываемые ВМ

Для экономии стоимости аренды можно использовать ВМ с уровнем производительности меньше 100%. Это означает, что их аптайм будет не ниже указанного процента. Такие ВМ подходят для джобов, CI и подобных задач.

##### SLA — соглашение об уровне обслуживания

Соглашение об уровне обслуживания ([[ycloud-monitoring|Service Level Agreement]], или SLA) не распространяется на прерываемые ВМ.

#### загрузочные и дополнительные диски

Данные ВМ в Compute Cloud хранятся на загрузочном и дополнительных дисках: на загрузочном — операционная система и приложения (его нельзя отключить от ВМ), на дополнительных — любые данные (их можно отключить от одной ВМ и подключить к другой).

**Рекомендация**
Веб-сервер размещают на HDD, потому что при запуске ОС он загружается в оперативную память, а базу данных — на SSD, потому что к ней идёт постоянное обращение.

#### блоки размещения

Блоки размещения: 32 ГБ для SSD, 256 ГБ для HDD.

## yc cli

[[yandex-cloud-cli#Yandex Cloud CLI — аналог putty для ycloud|yandex-cloud-cli]]

### включение ВМ

Запуск ВМ:

```bash
yc compute instance start <INSTANCE-NAME>|<INSTANCE-ID> [Global Flags...]
```

### список ВМ

Список ВМ:

```bash
yc compute instance list
```

### создание ВМ через yc cli

Пример команды:

```bash
yc compute instance create \
--name demo-2 \
--hostname demo-2 \
--metadata-from-file user-data=startup.sh \
--create-boot-disk image-folder-id=standard-images,image-family=ubuntu-2004-lts \
--zone ru-central1-a \
--network-interface subnet-name=default-ru-central1-a,nat-ip-version=ipv4
```
