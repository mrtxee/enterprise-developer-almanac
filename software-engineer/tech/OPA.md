## Open Policy Agent

**Open Policy Agent (OPA)** — это универсальный движок политик с открытым исходным кодом, который позволяет вынести логику принятия решений («кто имеет доступ?», «соответствует ли конфигурация стандартам?») из кода приложений и инфраструктуры в централизованную декларативную систему.

Вместо того чтобы хардкодить проверки прав доступа или валидации в каждом микросервисе, OPA выступает как отдельный сервис или sidecar-контейнер, отвечающий исключительно на вопрос: **«Разрешено или запрещено?»**.

### Ключевые концепции

1. **Rego:** Специализированный декларативный язык запросов для описания политик. Он не является языком программирования общего назначения; его задача — сопоставлять входные данные (JSON) с правилами и возвращать булево значение или набор результатов.
2. **Отделение политики от кода:** Логика авторизации живет отдельно от бизнес-логики. Это позволяет изменять правила безопасности без пересборки и перезапуска приложений.
3. **Универсальность:** OPA работает везде, где есть JSON: Kubernetes, API-шлюзы, CI/CD пайплайны, Terraform, SSH, базы данных и кастомные приложения.
4. **High Performance:** Написан на Go, компилирует Rego-политики в байткод, обеспечивая субмиллисекундное время принятия решений даже при сложных правилах.

### Архитектура работы

Типичный паттерн интеграции выглядит так:

1. **Enforcer** (приложение, kube-apiserver, gateway) получает запрос.
2. Формирует **Input** (структурированный JSON с контекстом: кто, что, когда, откуда).
3. Отправляет запрос в OPA: `POST /v1/data/my_policy/allow`.
4. OPA оценивает Input против загруженных политик и возвращает `{ "result": true/false }`.
5. Enforcer применяет решение.

### Основные сценарии применения

| Сфера | Пример использования |
| :--- | :--- |
| **Kubernetes** | Admission Controller (OPA Gatekeeper/Kyverno): запрет деплоя контейнеров без лимитов ресурсов, проверка labels, блокировка privileged-режима |
| **API Authorization** | Fine-grained RBAC/ABAC: «пользователь может читать только свои заказы», «менеджер видит данные отдела» |
| **Infrastructure as Code** | Валидация Terraform/Pulumi до apply: проверка тегов, шифрования дисков, открытых портов |
| **CI/CD** | Проверка Dockerfile, Helm-charts, манифестов K8s перед сборкой |
| **Data Access** | Динамическая маскировка полей в ответах БД в зависимости от роли запрашивающего |

### Почему OPA, а не встроенные средства?

- **Единая точка истины:** Не нужно дублировать логику проверки в 20 микросервисах.
- **Аудируемость:** Политики — это код (Policy-as-Code). Их можно версионировать в Git, ревьюить через PR, тестировать unit-тестами.
- **Гибкость моделей:** Поддерживает RBAC, ABAC, ReBAC и кастомные модели без изменения схемы БД.
- **Независимость от вендора:** CNCF Graduated проект, стандарт де-факто для Policy-as-Code.

### Ограничения

- **Кривая обучения Rego:** Язык мощный, но непривычный для разработчиков императивных языков. Отладка сложных политик требует практики.
- **Операционные накладные расходы:** Требует мониторинга latency, управления жизненным циклом политик (bundle distribution), обработки ошибок связи с OPA.
- **Не заменяет IAM:** OPA отвечает за *authorization* (что можно делать), но не за *authentication* (кто ты). Интегрируется с OAuth2/OIDC/LDAP, но не подменяет их.

OPA стал отраслевым стандартом для реализации принципа **Policy-as-Code**, позволяя организациям управлять безопасностью и соответствием требованиям так же, как они управляют инфраструктурой: декларативно, версионируемо и автоматически.

**Rego‑правила** — это политики (правила принятия решений), написанные на языке Rego для движка **Open Policy Agent (OPA)**. С их помощью декларативно описывают, какие действия разрешены или запрещены в системе, исходя из входных данных (обычно JSON/YAML).

## Rego
### Как устроено правило в Rego

Типичное Rego‑правило состоит из **заголовка (head)** и **тела (body)** в фигурных скобках:

```rego
allow := true {
    input.user == "alice"
    input.action == "read"
}
```

Здесь:

- `allow := true` — заголовок: что будет результатом, если условия выполнены.
- `{ input.user == "alice", input.action == "read" }` — тело: условия, которые должны выполниться.

Если все условия в теле истинны, правило «срабатывает» и присваивает значение переменной. Если ни одно правило для `allow` не сработало, по умолчанию считается, что доступа нет.

Rego — **декларативный** язык (как Datalog/SQL): вы описываете *что* должно быть истинно, а движок сам ищет совпадения во входных данных.

### Где и зачем используют Rego‑правила

Учитывая ваши прошлые интересы к безопасности, комплаенсу и инфраструктуре, вот самые частые сценарии:

- **Авторизация и контроль доступа** в Kubernetes, CI/CD, облачных API. Например, запретить создание привилегированных контейнеров или разрешить деплой только в определённые неймспейсы.
- **Проверка конфигураций (IaC)**: Terraform, Kubernetes манифесты, Helm. Rego‑правила проверяют, соответствуют ли ресурсы политикам безопасности и комплаенса (например, «все поды должны иметь ограничения ресурсов», «не использовать образы без подписи»).
- **Compliance‑проверки**: формализация требований (ISO, NIST, внутренние стандарты) как Rego‑правил, чтобы автоматически выявлять отклонения.
- **Валидация запросов и ответов** в API‑шлюзах, service mesh, Docker/containerd (например, плагин OPA для авторизации Docker-команд).

Это хорошо ложится на тему комплаенса: политики становятся кодом, их можно версионировать в Git, тестировать и применять единообразно.

### Важные особенности Rego

- **Входные данные — это `input`.** Rego работает с JSON‑подобной структурой; правила «запрашивают» нужные поля через точечную нотацию (`input.resource.metadata.name`).
- **Правила могут возвращать не только `true/false`, но и наборы значений.** Например, список нарушающих ресурсов или отчёт о соответствии.
- **Есть встроенные функции** для работы со строками, массивами, агрегации, регулярных выражений и т. п.
- **Модульность и пакеты.** Правила группируют в пакеты (`package example.auth`), чтобы разделять политики по доменам и переиспользовать логику.

### Простой пример для комплаенс‑контекста

Допустим, нужно запретить поды без `resources.limits`:

```rego
deny[msg] {
    container := input.request.object.spec.containers[_]
    not container.resources.limits
    msg = sprintf("Container %v missing resource limits", [container.name])
}
```

Если такое правило сработает в Kubernetes Admission Controller, создание пода будет отклонено с понятным сообщением.

### Связь с инструментами

- **OPA** — движок, который исполняет Rego‑правила.
- **Conftest** — инструмент для проверки конфигурационных файлов (Kubernetes, Terraform и др.) с помощью Rego.
- В ряде продуктов (Snyk, Gatekeeper, некоторые CI‑системы) политики тоже пишут на Rego, потому что это стандарт де‑факто для policy‑as‑code.

Если скажете, под какой сценарий вам интереснее пример (Kubernetes, Terraform, проверка YAML, авторизация в микросервисах или что‑то связанное с комплаенсом), дам конкретный шаблон правила и как его протестировать.
