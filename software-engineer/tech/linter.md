**Линтер** (от англ. *linter*) — это инструмент статического анализа кода, который автоматически проверяет исходный код на ошибки, нарушения стиля, потенциальные баги и антипаттерны — ещё до запуска программы.

> [!info] Lint
> Название пошло от утилиты `lint` для языка C, созданной в 1978 году. Сейчас «линтер» — общее название для таких инструментов в любых языках.

---

## Что конкретно делает линтер

- **Находит очевидные ошибки**: неиспользуемые переменные, недостижимый код, сравнения разных типов и т. п.
- **Следит за стилем**: отступы, длина строк, именование переменных, пустые строки, форматирование.
- **Выявляет потенциальные проблемы**: возможные `NullPointerException`, утечки ресурсов, небезопасные конструкции.
- **Проверяет соответствие стандартам проекта**: можно настроить свои правила под команду.
- **Помогает соблюдать лучшие практики** (best practices) и архитектурные ограничения.

Результат — список предупреждений и ошибок с указанием файла и строки.

---

## Примеры линтеров по языкам (в том числе для твоих Java‑задач)

- **Java**: Checkstyle (стиль), PMD (антипаттерны), SpotBugs (потенциальные баги), Error Prone (жёсткие проверки).
- **JavaScript/TypeScript**: ESLint.
- **Python**: Pylint, Flake8, Ruff.
- **CSS**: Stylelint.
- **Go**: staticcheck, golangci‑lint.
- **Rust**: Clippy.

Для Java-проектов (как у тебя с Maven и JDK 17) часто используют связку: Checkstyle для стиля, PMD для подозрительных конструкций, SpotBugs для потенциальных ошибок. Их можно подключить как плагины Maven или запускать в CI.

---

## Линтер vs форматтер: в чём разница

- **Линтер** говорит: «тут потенциально опасно / не по правилам» и часто не исправляет сам.
- **Форматтер** (например, Prettier, Black, google-java-format) просто приводит код к единому виду: выравнивает, расставляет скобки, убирает лишние пробелы.

Их используют вместе: форматтер делает код красивым, линтер — безопасным и чистым.

## Как это связано с твоими задачами

Учитывая, что ты работаешь с Java, Maven, сложными структурами (Map, билдеры, varargs, обработка ресурсов), линтеры помогут:

- **Избежать ошибок с null**: линтер заметит места, где легко получить `NullPointerException` (актуально для твоих методов с `segments` и проверками на `null`).
- **Контролировать стиль**: единообразие именования статусов, констант, методов в больших конфигурациях переходов.
- **Заметить проблемы с дженериками и varargs**: например, подозрительные приведения типов или неочевидные случаи «загрязнения кучи» (heap pollution), о которых мы говорили в контексте `@SafeVarargs`.
- **Поддерживать чистоту кода** при работе с ресурсами (`src/main/resources`, потоки, ZIP‑архивы): линтеры могут подсказывать, где забыть закрыть поток или неправильно обработать исключения.

## Пример: как выглядит предупреждение линтера

Допустим, у тебя в коде:

```java
private static List<TaskTrackerCrpvIssueStatus> path(
        List<TaskTrackerCrpvIssueStatus>... segments) {
    var result = new ArrayList<>(); // raw type
    // ...
}
```

PMD или SpotBugs могут выдать предупреждение про использование raw‑типов, а Checkstyle — про стиль. Исправление:

```java
var result = new ArrayList<TaskTrackerCrpvIssueStatus>();
```
