## **Requests и Limits в Kubernetes (кратко)**

В Kubernetes **Requests** и **Limits** — это механизмы управления ресурсами (CPU и память) для контейнеров в Pod’ах.

---

## 1. **Requests (Запросы)**
* **Что это**: Минимальное количество ресурсов, которое **гарантированно** получает контейнер.
* **Как работает**: Scheduler (планировщик) использует эту цифру для **размещения** Pod’а на Node’е с достаточным количеством свободных ресурсов.
* **Аналогия**: "Бронирование" места — это как гарантированный минимум, который всегда будет доступен контейнеру.

## 2. **Limits (Лимиты)**
* **Что это**: Максимальное количество ресурсов, которое контейнер **может использовать**.
* **Как работает**: Если контейнер превышает лимит по CPU, его производительность ограничивается (throttling). Если превышает лимит по памяти — он будет **уничтожен** (OOMKilled) для защиты всей Node.
* **Аналогия**: "Потолок" — это барьер, выше которого контейнер не может прыгнуть.

---

## Сравнительная таблица

| Характеристика | **Requests (Запросы)** | **Limits (Лимиты)** |
| :--- | :--- | :--- |
| **Суть** | Гарантированный минимум. | Максимально допустимый потолок. |
| **Влияние на планирование** | ✅ **Критично** (Scheduler использует для выбора Node). | ❌ Не влияет (Scheduler игнорирует Limits). |
| **Последствия превышения** | Безопасно (ресурс гарантирован). | **Опасно**: Throttling (CPU) или **OOMKill** (память). |
| **Для чего нужен** | Обеспечить стабильную работу и справедливое распределение ресурсов. | Защитить Node от "прожорливых" контейнеров и предотвратить шумных соседей. |

---

## 📌 Важные правила и практики

1. **Обязательность**: Рекомендуется всегда указывать и `requests`, и `limits`. Если не указать `limits`, контейнер может потребить все ресурсы Node.
2. **Без указания `requests`**: Если указан только `limit`, Kubernetes автоматически устанавливает `request` равным `limit`.
3. **Качество обслуживания (QoS)**:
    * **Guaranteed**: `request == limit` (для всех контейнеров). Высший приоритет при вытеснении (eviction).
    * **Burstable**: `request < limit` (или только `request`). Средний приоритет.
    * **BestEffort**: Нет ни `request`, ни `limit`. Низший приоритет (вытесняется первым).
4. **Для чего это нужно**: Правильная настройка позволяет эффективно использовать ресурсы кластера, избегать конфликтов между приложениями и обеспечивать отказоустойчивость.
