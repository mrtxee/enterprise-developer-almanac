## Kubelet

**Kubelet** — это главный **агент (node agent)**, который работает на **каждой ноде** (узле) кластера Kubernetes.

Его можно назвать **«менеджером этажа»** или **«прорабом»** на строительной площадке. Он получает инструкции от «главного архитектора» (API Server / Control Plane) и следит за тем, чтобы на его ноде всё работало согласно плану.

### Главная задача Kubelet

> **Гарантировать, что контейнеры, описанные в Pod'ах, запущены и здоровы.**

Если API Server говорит: «На этой ноде должен работать Pod с Nginx», то Kubelet:

1. Скачивает образ.
2. Запускает контейнер через контейнерную среду (containerd, CRI-O).
3. Следит за его состоянием.
4. Если контейнер упал — перезапускает его.

### Как работает Kubelet? (Цикл жизни)

Kubelet работает в бесконечном цикле синхронизации:

1. **Слушает API Server:**
   - получает список Pod'ов, которые должны быть запущены на этой ноде (`PodSpec`);
   - это происходит через механизм **Watch** (подписка на изменения).
2. **Взаимодействует с Container Runtime:**
   - использует интерфейс **CRI** (Container Runtime Interface) для общения с `containerd`, `cri-o` или `Docker` (через shim);
   - отдаёт команды: `CreateContainer`, `StartContainer`, `StopContainer`.
3. **Мониторинг состояния (Probes):**
   - выполняет проверки **Liveness** (жив ли процесс?) и **Readiness** (готов ли принимать трафик?);
   - если Liveness провалилась → Kubelet **перезапускает** контейнер;
   - если Readiness провалилась → Kubelet сообщает об этом в API Server, и Service перестаёт слать туда трафик.
4. **Отчетность (Heartbeat):**
   - регулярно отправляет статус ноды и Pod'ов обратно в API Server;
   - если Kubelet молчит > 40 секунд (по умолчанию), нода помечается как `NotReady`.
5. **Управление ресурсами:**
   - следит за использованием CPU/Memory;
   - если ресурсов не хватает, может убить (evict) наименее важные Pod'ы.

### Где находится Kubelet?

- **НЕ входит** в состав Control Plane (Master Node).
- Устанавливается как **системный сервис** (`systemd`) на **каждую Worker Node** (и часто на Master Node тоже, если она запускает полезные нагрузки).
- Процесс обычно называется `kubelet`.

```bash
# Проверить статус на Linux-ноде
systemctl status kubelet
```

### Kubelet vs API Server

| Характеристика | **API Server** (Control Plane) | **Kubelet** (Worker Node) |
|---|---|---|
| **Роль** | «Мозг» кластера. Хранит состояние, принимает запросы. | «Руки» кластера. Выполняет работу на конкретной машине. |
| **Количество** | Обычно 1–3 экземпляра на весь кластер. | **Один экземпляр на каждую ноду**. |
| **Что делает** | Валидирует YAML, сохраняет в etcd, планирует Pod'ы. | Запускает контейнеры, проверяет их здоровье, монтирует диски. |
| **Инициатива** | Пассивен (ждёт запросов `kubectl` или Scheduler'а). | Активен (постоянно синхронизирует желаемое состояние с реальным). |

### Ключевые компоненты, с которыми общается Kubelet

1. **Container Runtime (CRI):**
   - запускает сами контейнеры. Сейчас стандарт — `containerd`.
2. **CNI (Container Network Interface):**
   - настраивает сеть для Pod'а (выделяет IP, настраивает iptables/rules). Kubelet вызывает плагины CNI (Calico, Flannel, Cilium).
3. **CSI (Container Storage Interface):**
   - монтирует тома (PV/PVC) к Pod'ам. Kubelet вызывает драйверы хранения (AWS EBS, NFS, Local Path).

### Почему Kubelet так важен?

Без Kubelet нода — это просто пустой сервер.

- Если **API Server упадёт**, уже запущенные Pod'ы **продолжат работать** (благодаря Kubelet), но нельзя будет создавать новые или менять конфигурацию.
- Если **Kubelet упадёт** на ноде, все Pod'ы на этой ноде станут недоступны, а сама нода перейдёт в статус `NotReady`, и Scheduler перестанет размещать там новые задачи.

### Резюме

> **Kubelet** — это агент на каждой ноде, который:
>
> 1. получает приказ «Запусти эти Pod'ы»;
> 2. запускает контейнеры через CRI;
> 3. настраивает сеть через CNI;
> 4. монтирует диски через CSI;
> 5. следит за здоровьем и перезапускает упавшие контейнеры;
> 6. докладывает обратно в центр: «Всё выполнено» или «Ошибка».

Это **самый важный компонент на уровне инфраструктуры**, обеспечивающий выполнение работы.

## Container Runtime Interface

**CRI (Container Runtime Interface)** — это стандартный интерфейс в Kubernetes, через который `kubelet` управляет контейнерами. Проще говоря, это «договор» между Kubernetes и движком контейнеров (containerd, CRI-O и др.): kubelet говорит «создай контейнер», а рантайм делает это.

**Local gRPC** — это как именно этот «договор» реализуется технически: по gRPC, но **локально на ноде** (через Unix-сокет, а не по сети). То есть трафик не уходит в сеть кластера — он только между процессами на одной машине.

### Что делает CRI

Когда в Argo Workflow запускается шаг:

1. `argo-workflow-controller` создаёт Pod (через Kubernetes API).
2. `kubelet` на ноде получает задачу.
3. `kubelet` через CRI (gRPC) отправляет рантайму команды:
   - `RunPodSandbox` — создать «песочницу» (сеть, volumes для пода);
   - `CreateContainer` — создать контейнер из образа;
   - `StartContainer` — запустить его.
4. Рантайм (containerd/CRI-O) исполняет команды.
5. По завершении kubelet через CRI удаляет контейнер и sandbox.

### Почему «local gRPC»

- **gRPC**: формат вызова методов (эффективный, бинарный, поверх HTTP/2).
- **Local**: соединение не сетевое, а локальный Unix-сокет (например, `/var/run/containerd/containerd.sock`). Поэтому это **не сетевой протокол для кластера**, а внутренний механизм ноды.

Пример пути сокета для разных рантаймов:

| Рантайм | Путь к сокету |
|---|---|
| containerd | `/var/run/containerd/containerd.sock` |
| CRI-O | `/var/run/crio/crio.sock` |
