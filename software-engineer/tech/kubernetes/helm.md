## Helm

Helm — это пакетный менеджер для [[kubernetes|Kubernetes]], который позволяет легко управлять развёртыванием, обновлением и удалением приложений. Helm предоставляет удобный способ определения, установки и обновления Kubernetes-ресурсов.

**Основные компоненты Helm**

- **Чарты (Charts)** — пакеты Helm, содержащие все необходимые описания Kubernetes-ресурсов для развёртывания приложения. Включают шаблоны YAML-файлов, которые определяют конфигурацию и ресурсы Kubernetes: Pods, Services, Deployments и другие.
- **Репозитории (Repositories)** — хранилища, где размещаются чарты. Упрощают доступ к чартам и управление ими, помогают находить и использовать готовые решения для распространённых задач, позволяют делиться чартами с другими пользователями и командами.
- **Релизы (Releases)** — развёрнутые инстансы чартов в кластере [[kubernetes|Kubernetes]]. Каждый раз, когда чарт устанавливается в кластер, создаётся новый релиз. Его можно обновлять, отменять и удалять, эффективно управляя жизненным циклом приложений.

Helm решает несколько важных задач при работе с Kubernetes:

1. **Управление приложениями** — позволяет легко развёртывать, обновлять и удалять приложения.
2. **Управление зависимостями** — обеспечивает управление зависимостями между компонентами приложения.
3. **Версионирование и откаты** — позволяет управлять версиями приложений и откатываться к предыдущим версиям при необходимости.
4. **Консистентность и воспроизводимость** — гарантирует идентичность развёртываний во всех средах.

**Цикл жизни Helm-чарта**

- Создание Helm-чарта
- Развёртывание Helm-чарта
- Обновление Helm-чарта

## Helm vs Terraform

**[[terraform|Terraform]]** и **Helm** — это два фундаментальных инструмента в современном [[dev-ops|DevOps]], но они решают разные задачи. Вкратце: **Terraform создаёт инфраструктуру, а Helm размещает на ней приложения.**

### Основная аналогия

Аналогия с запуском нового офиса:

- **Terraform** — строители. Арендуют землю, заливают фундамент, возводят стены, проводят электричество и интернет. Они готовят **здание** к работе.
- **Helm** — завхозы. Завозят внутрь здания мебель, компьютеры, настраивают телефоны, вешают вывески и расставляют сотрудников по кабинетам. Они наполняют **здание содержанием**.

### Terraform (Infrastructure as Code)

**Что это:** инструмент для безопасного и эффективного создания, изменения и управления инфраструктурой.

- **Что создаёт:** виртуальные машины, сети (VPC), балансировщики нагрузки, базы данных (как сервис), политики доступа (IAM) и даже сами кластеры [[kubernetes|Kubernetes]].
- **Язык:** HCL (HashiCorp Configuration Language) — декларативный язык конфигурации.
- **Как работает:** Terraform использует файл состояния (`tfstate`), хранящий «карту» всей инфраструктуры. При изменениях Terraform сравнивает желаемое состояние с реальным и показывает план изменений перед применением.
- **Когда использовать:**
  - нужно создать кластер Kubernetes с нуля (например, в AWS EKS или Google GKE);
  - нужно создать облачные ресурсы (S3, RDS, EC2);
  - нужно настроить сеть и безопасность между компонентами.

### Helm (Package Manager for Kubernetes)

**Что это:** менеджер пакетов для Kubernetes (аналог `apt` для Linux или `pip` для Python, но для K8s).

- **Что создаёт:** ресурсы внутри уже существующего кластера Kubernetes: Pod'ы, Сервисы, Deployment'ы, ConfigMap, Secrets, Ingress.
- **Язык:** YAML + Go Templates (упакованные в чарты).
- **Как работает:** Helm использует концепцию чартов (Charts) — набора файлов, описывающих приложение. При установке чарта Helm создаёт все необходимые ресурсы в кластере и хранит историю релизов прямо внутри кластера.
- **Когда использовать:**
  - нужно установить сложное приложение в Kubernetes (например, [[prometheus|Prometheus]], [[kafka|Kafka]], PostgreSQL внутри кластера);
  - нужно обновлять версии приложений (rollback, upgrade);
  - нужно управлять конфигурациями одного и того же приложения для разных окружений (Dev, Stage, Prod) через файлы значений (`values.yaml`).

### Сравнительная таблица

| Характеристика         | Terraform                              | Helm                                               |
| :--------------------- | :------------------------------------- | :------------------------------------------------- |
| **Основная цель**      | Provisioning (создание инфраструктуры) | Configuration Management (управление приложениями) |
| **Уровень**            | Облако / Дата-центр / Кластер          | Внутри кластера Kubernetes                         |
| **Объекты**            | VM, Сети, БД, [[identity-access-management|IAM]], K8s Cluster     | Deployments, Services, Pods, ConfigMaps            |
| **Хранение состояния** | Файл `tfstate` (локально или в S3)     | Secret/ConfigMap внутри самого K8s кластера        |
| **Жизненный цикл**     | Создание/Уничтожение ресурсов          | Установка/Обновление/Откат приложений              |
| **Шаблоны**            | Модули (Modules)                       | Чарты (Charts)                                     |

### Совместная работа

В современной архитектуре их почти всегда используют в связке, а не выбирают что-то одно.

**Типичный пайплайн:**

1. **Terraform** разворачивает облачную инфраструктуру и создаёт пустой кластер Kubernetes.
2. **Helm** подключается к этому кластеру и устанавливает туда необходимые приложения (мониторинг, логирование, бизнес-сервисы).

**Можно ли заменить одно другим?**

- Может ли Terraform ставить приложения в K8s? Да, у Terraform есть Kubernetes Provider. Но для сложных приложений это плохая практика: Terraform хуже управляет жизненным циклом обновлений (например, rolling updates) по сравнению с нативными механизмами K8s, которые использует Helm.
- Может ли Helm создавать инфраструктуру? Нет, Helm не умеет создавать виртуальные машины или сети в облаке. Ему нужен уже готовый кластер.

**Итог**

- Если нужно **построить площадку** (серверы, сеть, кластер) — используйте **Terraform**.
- Если нужно **запустить софт** на этой площадке (микросервисы, базы данных внутри K8s) — используйте **Helm**.

## Helm Chart vs Docker Compose

| Характеристика         | **Docker Compose**                                                    | **Helm Chart**                                                          |
| :--------------------- | :-------------------------------------------------------------------- | :---------------------------------------------------------------------- |
| **Где работает**       | Локально (один хост/Docker Engine)                                    | В кластере **[[kubernetes|Kubernetes]]**                                               |
| **Основная цель**      | Запуск мульти-контейнерных приложений для **разработки/тестирования** | Управление сложными приложениями в **продакшене** (масштабирование, HA) |
| **Шаблонизация**       | ❌ Нет (статический YAML)                                              | ✅ Да (использует Go templates + `values.yaml`)                          |
| **Масштабирование**    | Ручное (`docker-compose up --scale`)                                  | Автоматическое (через K8s Deployment/HPA)                               |
| **Сложность**          | Низкая (простой синтаксис)                                            | Высокая (кривая обучения)                                               |
| **Пакетный менеджер**  | ❌ Нет                                                                 | ✅ Да (версионирование чартов, зависимости)                              |
| **Отказоустойчивость** | Зависит от Docker restart policy                                      | Встроенная (Self-healing, Liveness/Readiness probes)                    |

### 🎯 Когда что использовать

- **[[docker-compose|Docker Compose]]** — для локальной разработки, быстрых прототипов, CI-тестов на одном сервере: «запусти и работай».
- **Helm** — для продакшена в Kubernetes, когда нужны масштабирование, обновления без простоя, управление конфигурациями разных окружений (dev/stage/prod): «управляй инфраструктурой как кодом».

**Связь:** Docker Compose используют для локальной отладки сервисов, а Helm — для их деплоя в реальный кластер.
