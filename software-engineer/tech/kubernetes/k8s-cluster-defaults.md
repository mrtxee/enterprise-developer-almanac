Перечисленные ниже поды относятся к **инфраструктурным компонентам кластера Kubernetes** (в частности, судя по названиям `cceaddon`, `everest` и `icagent`, это управляемый кластер **Huawei Cloud CCE**).

Они находятся в namespace `kube-system`, потому что обеспечивают жизненно важные функции самого кластера, а не бизнес-логику приложений.

**Эти поды управляются операторами кластера или аддонами CCE и не должны удаляться или модифицироваться вручную.** Удаление любого из них может привести к:

- потере DNS-резолвинга (поды перестанут общаться);
- невозможности монтировать PVC;
- потере мониторинга нод;
- автоматическому пересозданию (если есть контроллер), но с временным простоем.

Проблемы с этими подами — сигнал о проблемах инфраструктуры кластера, а не повод для ручного вмешательства.

## Сетевая инфраструктура

- **`coredns-...`**: встроенный DNS-сервер кластера. Преобразует имена сервисов (например, `my-service.default.svc.cluster.local`) в IP-адреса. Без него поды не смогут находить друг друга по именам.
- **`node-local-dns-...`**: локальный DNS-кэш на каждом узле. Кэширует ответы от CoreDNS, чтобы снизить нагрузку на центральный DNS и уменьшить задержки при разрешении имён.
- **`node-local-dns-admission-controller-...`**: контроллер, который автоматически внедряет настройки NodeLocal DNS в конфигурацию подов при их создании, обеспечивая прозрачное использование локального кэша.

## Хранение данных (Storage)

- **`everest-csi-controller-...`**: контроллер CSI-драйвера Everest (собственное решение Huawei Cloud для управления хранилищами). Отвечает за создание/удаление PersistentVolumeClaim, привязку томов к нодам и управление жизненным циклом дисков (EVS/OBS).
- **`everest-csi-driver-...`**: DaemonSet драйвера, работающий непосредственно на каждой ноде. Выполняет операции монтирования/размонтирования томов в файловую систему пода.

## Мониторинг узлов

- **`cceaddon-npd-...`** (Node Problem Detector): агент, который мониторит состояние нод на предмет проблем, невидимых для kubelet (ошибки ядра, сбои Docker/containerd, проблемы с файловой системой). При обнаружении проблем помечает ноду как `NotReady` или добавляет соответствующие условия.
- **`node-problem-controller-...`**: контроллер, который обрабатывает события от NPD и принимает решения (например, изоляция проблемной ноды, алертинг). Работает в паре с NPD.

## Наблюдаемость (Observability)

- **`icagent-...`** (ICAgent / Cloud Eye Agent): агент сбора метрик и логов для интеграции с мониторингом Huawei Cloud (Cloud Eye / LTS). Собирает метрики нод, контейнеров, сетевой статистики и отправляет их в облачную платформу для визуализации и алертинга.

## Сбор логов и телеметрии (namespace `monitoring`)

- **`log-agent-fluent-bit-xxxx`** — агент сбора логов на каждой ноде (почти всегда DaemonSet).
  Fluent Bit читает логи контейнеров из `/var/log/containers`, обогащает их метаданными (namespace, pod name, container name) и отправляет дальше (в Elasticsearch, Loki, Cloud Logging и т. п.). Fluent Bit лёгкий, должен стоять на каждой ноде, быстро читать файлы логов и минимально влиять на рабочие нагрузки.

- **`log-agent-log-operator-5474b88bf9-xxxx`** (несколько реплик) — оператор/контроллер для управления логированием.
  Он следит за CRD (Custom Resources) вроде `ClusterLogConfig`, применяет настройки, управляет жизненным циклом агентов, может создавать индексы, настраивать ротацию и политики хранения. Несколько реплик нужны для отказоустойчивости: если один под упадёт, второй продолжит управлять конфигурациями.

- **`log-agent-otel-collector-78844587c5-xxxx`** (несколько реплик) — OpenTelemetry Collector.
  Собирает метрики и трейсы (а иногда и логи) в едином формате, делает сэмплирование, агрегацию, фильтрацию и пересылает в бэкенд (Prometheus, Jaeger, Cloud Monitoring и т. д.). Несколько реплик позволяют балансировать нагрузку и не терять телеметрию при перезапуске.

Без этих подов не будет ни логов приложений, ни метрик, ни распределённых трейсов — то есть никакой наблюдаемости (observability). Именно эти поды дают данные для мониторинга стабильности деплоев и диагностики инцидентов.

## NGINX Ingress: входящий трафик и маршрутизация

- **`cceaddon-nginx-ingress-controller-d567748b7-xxxx`** — сам контроллер Ingress.
  Это процесс, который следит за объектами `Ingress`, преобразует их в конфигурацию NGINX, перезагружает NGINX при изменениях и управляет правилами маршрутизации (Host, Path, TLS, rewrite и т. д.). Обычно это Deployment с несколькими репликами для отказоустойчивости.

- **`cceaddon-nginx-ingress-default-backend-8677ddf4cd-xxxx`** — default backend (часто называют «404-сервис»).
  Он отвечает на запросы, для которых нет подходящего Ingress-правила: возвращает HTTP 404 (или кастомную страницу) и генерирует метрики «неизвестный путь». Без него NGINX может вести себя непредсказуемо на неизвестных маршрутах.

Ingress-поды — это «входные ворота» для внешнего трафика в кластер. Они дают URL-маршрутизацию, терминирование TLS, rate limiting и другие функции, без которых большинство приложений не смогут принимать запросы извне.

## Как понять назначение пода

```bash
# Посмотреть образ и команду
kubectl get pod <имя> -n monitoring -o jsonpath="{.spec.containers[0].image}{'\n'}{.spec.containers[0].command}"

# Посмотреть лейблы (часто сразу дают подсказку)
kubectl get pod <имя> -n monitoring -L app,component

# Описать под и увидеть volumes, env, initContainers
kubectl describe pod <имя> -n monitoring
```

Для Ingress-подов особенно полезно смотреть `ownerReferences` — они покажут, какой Deployment/DaemonSet их создал, и `annotations` — там часто хранится версия и настройки.
