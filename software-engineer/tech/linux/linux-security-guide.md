## desktop linux security guide1
## Как проверять PKGBUILD из AUR

Главное правило: **PKGBUILD — это shell-скрипт, который выполняется от root при сборке**. Любая строка там — потенциальный вредоносный код. Проверять надо каждый раз, особенно при обновлении пакета ( maintainer мог смениться, аккаунт угнать).

### Что смотреть в PKGBUILD

#### 1. Основные функции — где прячется код

```bash
prepare() { ... }   # вызывается первой — сюда часто прячут payload
build() { ... }
package() { ... }   # выполняется от «фейкового root» — тоже опасна
```

Подозрительно: вызовы `curl ... | sh`, `wget ... | bash`, `eval`, `base64 -d` с длинными строками, обфусцированные переменные, команды, не связанные со сборкой.

#### 2. Источники (source = ...)

- Проверьте, что URL ведут на **официальный сайт проекта / GitHub-организацию проекта**, а не на левый pastebin, Discord, личный хостинг.
- Должны быть `sha256sums`/`b2sums` — и они должны **совпадать с хешами релиза от апстрима** (сверьте с GitHub Releases). Пустые `sha256sums=('SKIP')` — повод насторожиться (легитимно только для VCS-пакетов, где версия «плавающая»).
- Для `-bin` пакетов (готовые бинарники): бинарь качается откуда-то — вы доверяете тому, кто его собрал. Сверяйте хеш с официальным релизом вендора. Безопаснее пакеты без `-bin` — они собираются из исходников у вас.

#### 3. Файлы .INSTALL

Рядом с PKGBUILD лежит `<pkg>.install` — скрипты `post_install()`, `pre_remove()` и т.д. Они выполняются **от настоящего root при установке**. Смотрите, что они делают: создание systemd-юнитов, записи в cron, `systemctl enable`, правка `/etc`, установка pacman-хуков в `/etc/pacman.d/hooks/` — всё это легитимные техники, но должно быть осмысленным для данного пакета.

#### 4. Репутация пакета на странице AUR

- **Maintainer**: давно ли поддерживает, есть ли другие пакеты.
- **Votes / Popularity**: у популярного софта (тысячи голосов) вредонос долго не проживёт — комьюнити ревьюит.
- **Last Updated** и ** orphaned** (без мейнтейнера — кто угодно может его угнать).
- **Комментарии** — там часто пишут «в новой версии появилась странная сетевая активность».
- **Git history PKGBUILD**: резкая смена стиля/содержания — красный флаг (возможен угнанный аккаунт).

### Практический процесс

```bash
# 1. Скачать PKGBUILD и только извлечь исходники, НЕ собирая
git clone https://aur.archlinux.org/пакет.git
cd пакет
less PKGBUILD *.install          # читаем всё вручную
makepkg --verifysource -o        # проверка хешей + распаковка в src/

# 2. Осмотреть распакованные исходники
ls src/ && grep -rn "curl\|wget\|base64\|eval" src/ | head

# 3. Собирать в изолированном чруте (devtools), а не в своей системе
extra-x86_64-build               # сборка в чистом chroot — скрипт не трогает вашу систему

# 4. Посмотреть, что пакет вообще кладёт в систему
makepkg --packagelist
# после установки: pacman -Ql имя-пакета
```

**AUR-хелперы:** `paru` по умолчанию показывает PKGBUILD и diff изменений перед сборкой — не игнорируйте этот шаг. У `yay` нужно проверять, что показ включён (`--answerdiff`).

### Как убедиться, что в системе нет вредоносного ПО

Честный ответ: **гарантировать 100% нельзя** — можно только снизить риск и увеличить вероятность обнаружения. Архитектура защиты:

#### 1. Снижение риска (профилактика)

- Минимум AUR, только проверенные пакеты; основной софт — из официальных реп (`[core]`, `[extra]`) — они проходят ревью мейнтейнеров.
- Сборка в chroot, чтение PKGBUILD (см. выше).
- Не запускать скрипты из интернета (`curl ... | sh`), которые не прочитали.
- Обновления ставить регулярно — патчи закрывают дыры.

#### 2. Обнаружение (мониторинг)

```bash
# Проверка целостности файлов пакетов — файлы, изменённые после установки
# 1. Перезапустить проверку с рутовыми правами
sudo pacman -Qkk | grep -v "backup file" > /tmp/verify.txt
# 2. Посмотреть, что реально изменилось среди БИНАРНИКОВ
#    (конфиги в /etc — меняются всегда и это ок)
grep "^warning" /tmp/verify.txt | grep -E "/usr/(bin|lib|sbin)" 

# Кто слушает сеть — неожиданные открытые порты
ss -tulpn

# Автозагрузка: всё ли тут знакомо
ls ~/.config/autostart/ /etc/xdg/autostart/
systemctl list-unit-files --state=enabled

# Скрытые точки входа: cron, sudoers, shell-инициализация
cat /etc/cron.d/* 2>/dev/null; sudo cat /etc/sudoers.d/*
grep -rn "curl\|wget" ~/.bashrc ~/.profile ~/.config/fish/ 2>/dev/null

# Логи: подозрительные failed/критические сообщения
journalctl -p 3 -xb
```

- **AIDE или tripwire** — базeline целостности файловой системы: при первом запуске запоминает хеши системных файлов, потом отчитывается об изменениях. Это самый близкий к «антивирусу» инструмент для Linux.
- **[[rkhunter]] / chkrootkit** — проверка на известные руткиты (сигнатурно, ограниченная польза, но лучше, чем ничего).
- **ClamAV** — сигнатурный антивирус; полезен в основном для сканирования файлов, которыми обмениваетесь с Windows, а не для поиска руткитов.
- **Аудит подключений**: `opensnitch` (фаервол уровня приложений — как на Android: «приложение X хочет подключиться к host:port, разрешить?»). Это лучший детектор «звонящего домой» софта.

#### 3. Усложнение для атакующего

- **Firewall** (nftables/[[ufw]]) — закрыть входящие.
- **AppArmor** — MAC-профили для браузера, торрент-клиента и пр.: даже взломанный процесс не выйдет за пределы профиля.
- Не работать под root, `sudo` только для нужного.
- Браузер — основной вектор заражения Linux-десктопа: uBlock Origin, не ставить расширения из левых источников.

### Итоговая модель доверия

```
Официальные репы    → доверяем мейнтейнерам Arch
AUR с ревью PKGBUILD → доверяем после своей проверки
Бинарники (-bin)     → доверяем upstream-вендору
Случайные скрипты    → не доверяем вообще, читаем или не запускаем
```

Практическое правило: **один подозрительный `curl | sh` в PKGBUILD — отказ от пакета**, независимо от репутации. Всё остальное — слои обнаружения (opensnitch, AIDE, audit логи), потому что 100% гарантии не даёт никто.
