Чтобы посмотреть текущие настройки Git, используй `git config` с разными флагами — в зависимости от того, что именно нужно: всё сразу, только конкретный параметр или источник значения.

## Основные команды

- **Все настройки (с учётом всех уровней: local, global, system):**
  ```bash
  git config --list
  # или короче
  git config -l
  ```

- **С указанием, откуда взято каждое значение (очень полезно при конфликтах):**
  ```bash
  git config --list --show-origin
  ```

  Покажет что‑то вроде: `file:/home/user/.gitconfig    user.name=Ivan` или `file:.git/config    branch.main.remote=origin`.

- **Только локальные настройки репозитория (`.git/config`):**
  ```bash
  git config --list --local
  ```

- **Только глобальные настройки пользователя (`~/.gitconfig`):**
  ```bash
  git config --list --global
  ```

- **Системные настройки (для всех пользователей на машине):**
  ```bash
  git config --list --system
  ```

---

## Посмотреть конкретное значение

- **Итоговое значение параметра:**
  ```bash
  git config user.email
  git config core.editor
  ```
- **То же, но с источником:**
  ```bash
  git config --show-origin user.email
  ```

---

## Где физически лежат настройки

Зная уровни, проще понять, где искать вручную:

- **Локально (для текущего репозитория):** `.git/config` в корне репозитория.
- **Глобально (для пользователя):** `~/.gitconfig` (Linux/macOS) или `%USERPROFILE%\.gitconfig` (Windows).
- **Системно (для всей машины):** `/etc/gitconfig` (Linux), `C:\ProgramData\Git\config` (Windows).

---

## Практично под твой стек (CI, комплаенс, Kubernetes, Argo)

- В CI/CD (в том числе в Argo Workflows) часто важно убедиться, что в рантайме нет неожиданных локальных настроек — для этого удобно делать `git config --list --show-origin` в логах джобы.
- При деплое в Kubernetes (например, sidecar‑контейнер с Git) полезно явно задавать нужные конфиги через переменные или монтируемые конфиг‑файлы и проверять их той же командой.
- Если в команде разные настройки у разработчиков, `--show-origin` быстро покажет, где переопределено значение (например, локально в репозитории вместо глобального).

В папке `/my-project/.git` нет файла с именем `.gitconfig` — локальные настройки проекта хранятся в файле **`config`** (без точки в начале) прямо внутри `.git`:

```text
/my-project/.git/config
```

---

## Почему путаница с именем

- **Глобальные настройки** (для пользователя) лежат в `~/.gitconfig` (отсюда и имя с точкой).
- **Локальные настройки** (для конкретного репозитория) лежат в `.git/config` — это отдельный файл, он не называется `.gitconfig`.

Git использует их по приоритету: локальный (` .git/config`) переопределяет глобальный (`~/.gitconfig`), а тот — системный (`/etc/gitconfig`).

---

## Как проверить, что это именно тот файл

Выполни в корне проекта:

```bash
git config --list --show-origin
```

Ты увидишь строки вида:

```text
file:.git/config    user.name=Ivan
file:.git/config    core.editor=vim
```

Это и есть локальные настройки, которые хранятся в `/my-project/.git/config`.

---

## Практический нюанс под твой стек (CI, комплаенс, Kubernetes, Argo)

Файл `.git/config` **не нужно коммитить** и не стоит включать в артефакты сборки (в том числе в Docker‑образы или в CI‑пайплайны типа Argo Workflows): он содержит локальные настройки конкретного репозитория и может включать чувствительные данные (например, переопределения remote‑адресов, credential‑помощников и т. п.).

Если тебе нужно зафиксировать какие‑то настройки для всей команды (например, `core.autocrlf`, `receive.denyCurrentBranch`), лучше вынести их в:

- шаблон `.gitattributes` (он коммитится и работает предсказуемо);
- скрипты инициализации в CI;
- документированные требования к окружению.

**Да, файл `.git/config` (локальный) может переопределить настройки из блока `[user]` в `~/.gitconfig` (глобальный).**

## Как это работает

Git использует иерархию уровней конфигурации, и локальный уровень имеет **наибольший приоритет**:

1. **Локальный** (`.git/config` в репозитории) — переопределяет всё.
2. **Глобальный** (`~/.gitconfig`) — значения по умолчанию для пользователя.
3. **Системный** (`/etc/gitconfig` или аналог) — настройки для всей машины.

Если в обоих файлах задан, например, `user.name`, Git возьмёт значение из `.git/config`.

---

## Пример

**В `~/.gitconfig`:**

```ini
[user]
    name = Ivan Petrov
    email = ivan.personal@example.com
```

**В `/my-project/.git/config`:**

```ini
[user]
    name = Ivan Petrov (Work)
    email = ivan@company.com
```

Для этого репозитория Git будет использовать `Ivan Petrov (Work)` и `ivan@company.com` — глобальные значения игнорируются.

---

## Как проверить, какое значение реально применяется

Выполни в корне проекта:

```bash
git config --list --show-origin | grep -E '^user\.(name|email)'
```

Ты увидишь что‑то вроде:

```text
file:.git/config    user.name=Ivan Petrov (Work)
file:.git/config    user.email=ivan@company.com
```

Это явно покажет, что используется локальная настройка.

---

## Практический совет под твой стек (CI, комплаенс, Kubernetes, Argo)

- **Для рабочих репозиториев** это нормальная практика: локально переопределять `user.email`, чтобы коммиты подписывались корпоративным email, а не личным.
- **В CI/CD (Argo, GitHub Actions и т. п.) не полагайся на `.git/config`** для задания `user.name/email`: в рантайме этого файла нет. В пайплайне всегда явно задавай через переменные или команды:
  ```bash
  git config --local user.name "CI Bot"
  git config --local user.email "ci-bot@company.com"
  ```
- **Не коммить `.git/config`**: он не должен попадать в репозиторий (и не попадает, потому что лежит внутри `.git/`). Это персональные настройки конкретного клона репозитория.

---

## Частые ошибки

- Пытаться положить свой «шаблон» `.git/config` в корень проекта и коммитить его — бесполезно: Git не читает его оттуда.
- Думать, что `git init` копирует глобальные `user.name/email` в локальный конфиг — он этого не делает. Если локально не задано, Git просто берёт глобальное значение «на лету».

Если скажешь, какую именно задачу решаешь (например, «хочу, чтобы в этом проекте все коммиты были от имени команды» или «нужно разное поведение в разных окружениях»), подскажу безопасный способ реализовать это. 😊

Чтобы обновить значения в блоке `[user]` файла `~/.gitconfig` (глобальные настройки), используй команды с флагом `--global`:

```bash
git config --global user.name "Твоё Имя"
git config --global user.email "tvoi.email@example.com"
```

---

## Как проверить, что обновилось

```bash
git config --global --list | grep -E '^user\.(name|email)'
# или сразу с источником:
git config --list --show-origin | grep -E '^user\.(name|email)'
```

Ты должен увидеть строки с `file:~/.gitconfig`.

---

## Важные нюансы под твой стек (CI, комплаенс, Kubernetes, Argo)

- **Это глобальные настройки**: они применяются ко всем репозиториям на машине, если в них не заданы локальные переопределения (в `.git/config`).
- **В CI/CD (Argo, GitHub Actions и т. п.) не полагайся на эти настройки**: там нет твоего `~/.gitconfig`. В пайплайне всегда задавай явно, например:
  ```bash
  git config --local user.name "CI Bot"
  git config --local user.email "ci-bot@company.com"
  ```
- **Старые коммиты не меняются**: новые значения влияют только на будущие коммиты. Если нужно исправить автора в уже сделанных коммитах — это отдельная задача (через `git commit --amend` или `git filter-repo`).
