# DNS
### Что такое DNS


**DNS (Domain Name System)** — это распределённая система, которая **преобразует доменные имена** (например, `example.com`) **в IP‑адреса** (например, `93.184.216.34`), необходимые для маршрутизации трафика в сети.


Проще говоря: DNS — это «телефонная книга» интернета, позволяющая пользователям вводить удобные для запоминания имена сайтов, а не числовые IP‑адреса.


### Зачем нужен DNS


Без DNS интернет был бы крайне неудобен:
* пользователям пришлось бы запоминать и вводить IP‑адреса вместо доменных имён;
* изменение IP‑адреса сервера потребовало бы оповещения всех пользователей;
* масштабирование сервисов стало бы затруднительным.


### Как работает DNS: пошаговый процесс


1. **Инициация запроса**  
   Пользователь вводит доменное имя в браузере (например, `example.com`).

2. **Проверка локального кэша**  
   Устройство сначала ищет запись в:
   * файле `hosts`;
   * кэше операционной системы;
   * кэше браузера.
   Если запись найдена — используется сразу.

3. **Запрос к локальному DNS‑серверу**  
   Если в локальном кэше нет данных, запрос отправляется на DNS‑сервер провайдера или корпоративной сети.
4. **Рекурсивный поиск**  
   Локальный сервер:
   * проверяет свой кэш;
   * если данных нет — отправляет запрос к **корневым DNS‑серверам**.
5. **Обращение к корневым серверам**  
   Корневые серверы (их 13 основных) указывают серверы для нужной доменной зоны (например, `.com`).
6. **Запрос к серверу доменной зоны**  
   Сервер зоны `.com` направляет запрос к **авторитетному DNS‑серверу** домена `example.com`.
7. **Получение ответа**  
   Авторитетный сервер возвращает IP‑адрес домена.
8. **Кэширование и возврат результата**  
   Локальный сервер сохраняет ответ в кэш и передаёт его пользователю. Браузер подключается к сайту по IP‑адресу.


### Типы DNS‑серверов


1. **Локальные**  
   * принадлежат провайдерам или корпоративным сетям;
   * обрабатывают запросы пользователей и кэшируют записи для ускорения.


2. **Корневые**  
   * 13 главных серверов, распределённых по миру;
   * хранят информацию о доменных зонах верхнего уровня (`.com`, `.org`, `.ru` и др.).


3. **Серверы доменных зон**  
   * содержат данные о конкретных зонах (например, все домены `.com`);
   * перенаправляют запросы к авторитетным серверам.


4. **Авторитетные**  
   * хранят точные записи для конкретных доменов;
   * отвечают финальным IP‑адресом.


5. **Публичные**  
   * предоставляются крупными компаниями (Google, Cloudflare);
   * предлагают ускоренный доступ и дополнительные функции (фильтрация, безопасность).


### Основные DNS‑записи (ресурсные записи)


- **A** — связывает домен с IPv4‑адресом (`example.com → 93.184.216.34`).  
- **AAAA** — аналогично для IPv6‑адресов.  
- **CNAME** — создаёт псевдоним для другого домена (`www.example.com → example.com`).  
- **MX** — указывает почтовые серверы домена (для приёма email).  
- **TXT** — хранит текстовую информацию (используется для SPF, DKIM, DMARC).  
- **NS** — определяет DNS‑серверы, управляющие доменом.  
- **SOA** — содержит метаданные зоны (контакт администратора, параметры обновления).  
- **PTR** — обеспечивает обратное преобразование IP → домен.  

- **SRV** — указывает сервер для конкретного сервиса (например, VoIP).


### Ключевые функции DNS


1. **Преобразование имён**  
   Перевод доменов в IP‑адреса и обратно.


2. **Кэширование**  
   Хранение временных копий записей для ускорения последующих запросов.


3. **Маршрутизация**  
   Направление запросов к ближайшему серверу (например, через CDN).


4. **Безопасность**  
   * фильтрация вредоносных сайтов;  
   * защита от атак (DNS Spoofing) через DNSSEC.


5. **Отказоустойчивость**  
   Резервирование серверов гарантирует работу даже при сбоях.


6. **Управление внутренними сетями**  
   Корпоративные DNS‑серверы организуют доступ к внутренним ресурсам.


### Важные особенности


- **Распределённость** — данные хранятся на множестве серверов по всему миру.  
- **Иерархическая структура** — серверы организованы в древовидную систему (корневые → зоны → авторитетные).  
- **TTL (Time to Live)** — время жизни записи в кэше (в секундах). После истечения TTL сервер запросит обновлённые данные.  
- **DNSSEC** — расширение для защиты от подделки записей (цифровые подписи).  
- **Рекурсивные запросы** — сервер самостоятельно ищет ответ, если его нет в кэше.  
- **Итеративные запросы** — сервер возвращает ссылку на другой сервер, продолжая поиск.


### Примеры использования DNS


- **Веб‑сайты** — преобразование `google.com` в IP.  
- **Почта** — MX‑записи направляют письма на нужные серверы.  
- **CDN** — DNS распределяет запросы между серверами в разных регионах.  
- **Блокировка контента** — DNS‑фильтры запрещают доступ к опасным сайтам.  
- **Мониторинг** — обратные PTR‑запросы помогают анализировать трафик.


### Типичные проблемы и их решения



- **Ошибка «DNS‑сервер не отвечает»** — смените DNS‑сервер (например, на Google DNS `8.8.8.8`).  
- **Задержка при открытии сайта** — очистите кэш DNS (`ipconfig /flushdns` в Windows).  
- **Подмена DNS (Spoofing)** — включите DNSSEC на сервере.  
- **Некорректная запись** — проверьте синтаксис и TTL в DNS‑настройках.


### Итог


DNS — фундаментальная технология интернета, обеспечивающая:
* удобство использования (доменные имена вместо IP);
* скорость (кэширование);
* надёжность (резервирование);
* безопасность (фильтрация, DNSSEC).

Без DNS современный интернет был бы невозможен.
## DNS‑record
### Что такое DNS‑запись


DNS‑запись (ресурсная запись) — элемент базы данных DNS, который связывает доменное имя с определённой информацией: IP‑адресами, настройками почты, служебными данными и др. Без записей DNS интернет‑адреса (например, `example.com`) не могли бы «превращаться» в IP‑адреса, нужные для маршрутизации трафика.


### Основные типы DNS‑записей

1. **A (Address Record)**  
   - **Назначение**: связывает доменное имя с IPv4‑адресом.  
   - **Пример**:  
     ```
     example.com.  IN  A  192.0.2.1
     ```
   - **Где используется**: для веб‑сайтов, API, любых сервисов, работающих по IPv4.

2. **AAAA (IPv6 Address Record)**  
   - **Назначение**: аналогично A, но для IPv6‑адресов.  
   - **Пример**:  
     ```
     example.com.  IN  AAAA  2001:db8::1
     ```
   - **Зачем нужно**: поддержка современных сетей с IPv6.

3. **CNAME (Canonical Name Record)**  
   - **Назначение**: создаёт алиас (псевдоним) для другого домена или поддомена.  
   - **Пример**:  
     ```
     www.example.com.  IN  CNAME  example.com.
     ```
   - **Ограничение**: нельзя использовать вместе с другими записями для того же имени (например, A или MX).  
   - **Где применяется**: CDN, балансировщики, сторонние сервисы (GitHub Pages, Vercel).

4. **NS (Name Server Record)**  
   - **Назначение**: указывает авторитетные DNS‑серверы для домена.  
   - **Пример**:  
     ```
     example.com.  IN  NS  ns1.example.com.
     example.com.  IN  NS  ns2.example.com.
     ```
   - **Зачем нужно**: делегирование управления зоной, настройка поддоменов с отдельными DNS.

5. **MX (Mail Exchange Record)**  
   - **Назначение**: определяет почтовые серверы для домена и их приоритет.  
   - **Пример**:  
     ```
     example.com.  IN  MX  10  mail1.example.com.
     example.com.  IN  MX  20  mail2.example.com.
     ```
   - **Приоритет**: меньшее число = выше приоритет.  
   - **Зачем нужно**: маршрутизация почты, резервирование серверов.

6. **TXT (Text Record)**  
   - **Назначение**: хранит произвольный текст (часто — служебные данные).  
   - **Примеры использования**:  
     - SPF‑записи для защиты от спама:  
       ```
       example.com.  IN  TXT  "v=spf1 include:_spf.google.com ~all"
       ```
     - DMARC‑настройки:  
       ```
       _dmarc.example.com.  IN  TXT  "v=DMARC1; p=quarantine; rua=mailto:dmarc@example.com"
       ```
     - Верификация домена (Google, Microsoft).  
   - **Зачем нужно**: аутентификация почты, интеграция сервисов.

7. **SRV (Service Record)**  
   - **Назначение**: указывает сервер для конкретного сервиса (протокол + порт).  
   - **Формат**: `_service._proto.name TTL class SRV priority weight port target`.  
   - **Пример**:  
     ```
     _sip._tcp.example.com.  IN  SRV  10 60 5060 sipserver.example.com.
     ```
   - **Где используется**: VoIP (SIP, XMPP), Active Directory.

8. **PTR (Pointer Record)**  
   - **Назначение**: обратное разрешение IP → домен (reverse DNS).  
   - **Пример**:  
     ```
     1.1.168.192.in-addr.arpa.  IN  PTR  example.com.
     ```
   - **Зачем нужно**: проверка легитимности отправителей почты, логирование.


9. **SOA (Start of Authority Record)**  
   - **Назначение**: содержит метаданные зоны (основной сервер, email администратора, параметры обновления).  
   - **Пример**:  
     ```
     example.com.  IN  SOA  ns1.example.com. admin.example.com. (
                               2024010101 ; Serial
                               7200       ; Refresh
                               3600       ; Retry
                               1209600    ; Expire
                               86400      ; Minimum TTL
                             )
     ```
   - **Зачем нужно**: контроль синхронизации между DNS‑серверами.

### Важные детали

- **TTL (Time to Live)**: указывается для всех записей; определяет, сколько времени кэш DNS‑серверов будет хранить запись (в секундах).  
- **Синтаксис**: в записях используются стандартные поля:  
  - имя домена;  
  - класс (обычно `IN` для Internet);  
  - тип записи (A, MX и т. д.);  
  - значение (IP, домен, текст и др.).  
- **Безопасность**: для защиты DNS используются расширения вроде DNSSEC (подписи записей).

### Где применяются записи

- **A/AAAA**: веб‑сайты, API.  
- **CNAME**: поддомены, интеграция с облачными сервисами.  
- **MX**: настройка почты.  
- **TXT**: SPF, DMARC, верификация.  
- **NS**: делегирование домена.  
- **SRV**: корпоративные сервисы (AD, VoIP).  
- **PTR**: обратная проверка IP.  
- **SOA**: управление зоной.

# SPF
### Что такое SPF


**SPF (Sender Policy Framework)** — это DNS‑запись типа `TXT`, которая позволяет владельцу домена **указать, с каких IP‑адресов разрешено отправлять письма от имени этого домена**. Это механизм защиты от подделки email‑адресов (спуфинга) и спама.

### Как это работает


1. **Владелец домена** добавляет SPF‑запись в DNS.  
2. **Почтовый сервер получателя** при получении письма:  
   - находит SPF‑запись домена отправителя;  
   - проверяет, входит ли IP‑адрес отправителя в разрешённый список;  
   - принимает решение: пропустить письмо, пометить как подозрительное или отклонить.  
3. **Результат проверки** передаётся через заголовки письма (например, `Received-SPF: pass`).

### Формат SPF‑записи

Запись всегда начинается с `v=spf1` (версия SPF 1). Далее идут **механизмы** (правила) и **модификаторы** (действия).

#### Основные механизмы

- `ip4:<адрес>` — разрешить конкретный IPv4‑адрес или подсеть.  
  Пример: `ip4:192.0.2.0/24`.  
- `ip6:<адрес>` — то же для IPv6.  
- `a` — разрешить IP‑адреса, указанные в A‑ и AAAA‑записях домена.  
- `mx` — разрешить IP‑адреса из MX‑записей домена.  
- `include:<домен>` — добавить правила из SPF‑записи другого домена.  
  Пример: `include:_spf.google.com`.  
- `all` — соответствует любому IP (обычно используется в конце как «остальные случаи»).  

#### Модификаторы (квалификаторы)

Определяют действие при совпадении с механизмом. По умолчанию — `+` (`pass`).  
- `+` (pass) — письмо разрешено.  
- `-` (fail) — письмо запрещено (рекомендуется).  
- `~` (softfail) — письмо не запрещено, но вызывает подозрения.  
- `?` (neutral) — нет чёткого разрешения/запрета.  

### Примеры SPF‑записей

1. **Разрешить письма только с одного IP**  
   ```
   v=spf1 ip4:198.51.100.1 -all
   ```  
   *Письмо пройдёт, только если отправлено с IP 198.51.100.1.*

2. **Разрешить IP из A‑записей и MX, запретить остальное**  
   ```
   v=spf1 a mx -all
   ```  
   *Письма с IP, указанных в A/AAAA и MX домена, будут приняты.*

3. **Интеграция с Google Workspace**  
   ```
   v=spf1 include:_spf.google.com ~all
   ```  
   *Разрешает отправку через серверы Google, остальные IP — с пометкой softfail.*

4. **Сложный пример (несколько сервисов)**  
   ```
   v=spf1 ip4:192.0.2.1 include:_spf.example.com include:sendgrid.net ~all
   ```  
   *Разрешает: конкретный IP, правила из example.com и SendGrid.*

### Важные правила

1. **Одна запись на домен**  
   В DNS может быть только одна SPF‑запись для домена (иначе — ошибка).  
2. **Ограничение на длину**  
   SPF‑запись не должна превышать **255 символов** (включая `v=spf1`).  
3. **Ограничение на DNS‑запросы**  
   При проверке SPF сервер не должен выполнять более **10 DNS‑запросов** (иначе — ошибка `permerror`).  
4. **Порядок механизмов**  
   Правила проверяются последовательно. Первый совпавший механизм определяет результат.  
5. **Использование `~all` vs `-all`**  
   - `~all` (softfail): письма с неизвестных IP попадут в спам, но не будут отброшены.  
   - `-all` (fail): письма с неизвестных IP могут быть отклонены.  

### Как проверить SPF

1. **Через командную строку**  
   ```bash
   nslookup -type=txt example.com
   ```  
   В выводе ищите строку, начинающуюся с `v=spf1`.  

2. **Онлайн‑сервисы**  
   Например:  
   - MXToolbox SPF Record Lookup;  
   - Google Admin Toolbox.  

3. **Тестовые письма**  
   Отправьте письмо на сервис вроде `check-auth@verifier.port25.com` — он пришлёт отчёт о проверке SPF, DKIM, DMARC.

### Типичные ошибки

- **Дублирование SPF‑записей** — приводит к сбоям.  
- **Слишком много `include`** — превышает лимит DNS‑запросов.  
- **Некорректные IP‑адреса** — блокируют легитимные письма.  
- **Отсутствие SPF** — повышает риск подделки домена.

### Зачем нужен SPF

- **Защита от спама**: злоумышленники не смогут отправлять письма от вашего домена.  
- **Улучшение доставляемости**: почтовые сервисы доверяют доменам с корректной SPF.  
- **Репутация домена**: отсутствие SPF может привести к помещению писем в спам.  

**Итог**: SPF — простой, но эффективный способ защитить домен от подделки и повысить доверие к вашей почте.

# DMARC

### Что такое DMARC

**DMARC (Domain-based Message Authentication, Reporting & Conformance)** — это стандарт защиты электронной почты, позволяющий:
* **подтверждать подлинность** писем, отправленных от имени домена;
* **получать отчёты** о попытках подделки домена;
* **задавать правила** обработки подозрительных писем.

DMARC работает **в связке с SPF и DKIM**, используя их результаты для принятия решений.


### Как работает DMARC

1. **Владелец домена** публикует DMARC‑запись в DNS.  
2. **Почтовый сервер получателя** при получении письма:  
   * проверяет SPF и DKIM для домена отправителя;  
   * сверяет результаты с политикой DMARC;  
   * выполняет заданные действия (принять, пометить, отклонить);  
   * отправляет отчёт владельцу домена.  
3. **Владелец домена** анализирует отчёты для выявления угроз и настройки политик.

### Структура DMARC‑записи (DNS TXT)

Запись начинается с `v=DMARC1` и содержит **теги** в формате `тег=значение`.

#### Основные теги

- **`v`** — версия протокола (всегда `DMARC1`).  
- **`p`** (*policy*) — основная политика обработки:  
  * `none` — только мониторинг (отчёты, но без действий);  
  * `quarantine` — помещать подозрительные письма в спам;  
  * `reject` — отклонять подозрительные письма.  
- **`rua`** — email для отчётов о агрегированных данных (формат: `mailto:адрес`).  
- **`ruf`** — email для отчётов о неудачных проверках (формат: `mailto:адрес`).  
- **`adkim`** — строгость проверки DKIM (`r` — relaxed, `s` — strict).  
- **`aspf`** — строгость проверки SPF (`r` — relaxed, `s` — strict).  
- **`pct`** — процент писем, к которым применяется политика (по умолчанию — 100).  
- **`fo`** — режим отладки (например, `0` — только при полном провале).

### Примеры DMARC‑записей

1. **Режим мониторинга** (только отчёты, без блокировки)  
   ```
   v=DMARC1; p=none; rua=mailto:reports@example.com
   ```

2. **Режим карантина** (подозрительные письма в спам)  
   ```
   v=DMARC1; p=quarantine; rua=mailto:reports@example.com; ruf=mailto:failures@example.com
   ```

3. **Строгая политика** (отклонять подделки)  
   ```
   v=DMARC1; p=reject; rua=mailto:reports@example.com; adkim=s; aspf=s
   ```

4. **С ограничением процента** (применять политику к 50 % писем)  
   ```
   v=DMARC1; p=quarantine; pct=50; rua=mailto:reports@example.com
   ```

### Как DMARC использует SPF и DKIM

DMARC проверяет, прошли ли письмо **хотя бы одну** из проверок:
* **SPF**: IP‑адрес отправителя соответствует разрешённым в DNS;  
* **DKIM**: цифровая подпись письма валидна и соответствует домену.


Если **хотя бы один механизм пройден**, DMARC считает письмо легитимным. Если оба провалены — применяет политику (`p`).

### Отчёты DMARC

1. **Агрегированные отчёты (RUA)**  
   * отправляются ежедневно;  
   * содержат статистику: сколько писем прошло/не прошло проверку, с каких IP;  
   * формат — XML.  

2. **Отчёты о неудачных проверках (RUF)**  
   * детализируют каждое подозрительное письмо;  
   * включают заголовки, IP, причины отказа.  

### Настройка DMARC: пошаговая инструкция

1. **Убедитесь, что настроены SPF и DKIM** для вашего домена.  
2. **Определите политику** (`none` → `quarantine` → `reject`). Начинайте с `none`.  
3. **Укажите email для отчётов** (`rua` и `ruf`).  
4. **Создайте TXT‑запись** в DNS:  
   ```
   _dmarc.example.com. IN TXT "v=DMARC1; p=none; rua=mailto:reports@example.com"
   ```  
5. **Проверьте запись** через онлайн‑сервисы (например, MXToolbox).  
6. **Анализируйте отчёты** и постепенно ужесточайте политику.  

### Типичные ошибки

- **Отсутствие SPF/DKIM** — DMARC не будет работать.  
- **Некорректный email в `rua`/ `ruf`** — отчёты не дойдут.  
- **Резкий переход на `p=reject`** — риск потери легитимных писем.  
- **Дублирование записей** — приводит к ошибкам.  
- **Слишком строгие настройки** (`adkim=s`, `aspf=s`) — могут блокировать легитимные рассылки.

### Зачем нужен DMARC

- **Защита бренда**: предотвращает подделку вашего домена.  
- **Улучшение доставляемости**: почтовые сервисы доверяют доменам с DMARC.  
- **Анализ угроз**: отчёты показывают, кто пытается использовать ваш домен.  
- **Соответствие стандартам**: требуется для некоторых корпоративных и государственных сервисов.  

### Важные нюансы

- **DMARC не защищает от фишинга** через похожие домены (например, `examp1e.com`).  
- **Требует регулярного мониторинга** отчётов для настройки.  
- **Работает только для писем с явным указанием домена отправителя** (From:).  

**Итог**: DMARC — ключевой инструмент защиты email‑репутации. Начинайте с мониторинга (`p=none`), постепенно переходите к более строгим политикам, опираясь на отчёты.

# DKIM
### Что такое DKIM

**DKIM (DomainKeys Identified Mail)** — это технология аутентификации электронной почты, которая **подтверждает подлинность отправителя** и **гарантирует целостность письма** с помощью цифровой подписи.

Суть: отправитель «подписывает» письмо закрытым ключом, а получатель проверяет подпись открытым ключом из DNS. Если подпись валидна, значит:
* письмо действительно отправлено с заявленного домена;
* содержимое не было изменено в пути.

### Как работает DKIM

1. **Генерация ключей**  
   * Владелец домена создаёт **пару ключей**: закрытый (хранится на почтовом сервере) и открытый (размещается в DNS).  
   * Обычно используются ключи длиной 1024–2048 бит (RSA).

2. **Подпись письма**  
   * Почтовый сервер отправителя:  
     * вычисляет хеш-сумму выбранных заголовков и тела письма;  
     * шифрует хеш закрытым ключом;  
     * добавляет в письмо заголовок `DKIM-Signature` с подписью и метаданными.

3. **Проверка подписи**  
   * Сервер получателя:  
     * извлекает открытый ключ из DNS (по селектору из заголовка);  
     * расшифровывает подпись открытым ключом;  
     * сравнивает полученный хеш с заново вычисленным для письма;  
     * если хеши совпадают — подпись валидна.

4. **Результат проверки**  
   * `pass` — подпись корректна;  
   * `fail` — подпись не прошла проверку;  
   * `neutral`/`temperror`/`permerror` — ошибки проверки.

### Структура DKIM‑подписи (заголовок `DKIM-Signature`)

Пример:
```
DKIM-Signature: v=1; a=rsa-sha256; d=example.com; s=mail;
  c=relaxed/relaxed; q=dns/txt; t=1678888800;
  h=From:To:Subject:Date; bh=abc123...;
  b=def456...
```

Ключевые параметры:
* **`v`** — версия протокола (`1`).  
* **`a`** — алгоритм подписи (`rsa-sha256`, `ed25519-sha256`).  
* **`d`** — домен отправителя (`example.com`).  
* **`s`** — селектор (имя записи в DNS, например `mail`).  
* **`c`** — режим канонизации (обработка пробелов и переносов):  
  * `relaxed` — нормализует пробелы;  
  * `simple` — строгое соответствие.  
* **`h`** — список подписываемых заголовков (`From`, `To`, `Subject` и др.).  
* **`bh`** — хеш тела письма.  
* **`b`** — сама цифровая подпись.  
* **`t`** — время создания подписи (Unix-время).

### Настройка DKIM: пошаговая инструкция

1. **Сгенерируйте ключи**  
   * Используйте утилиты вроде `openssl` или панели управления хостингом.  
   * Пример для RSA‑2048:  
     ```bash
     openssl genrsa -out private.key 2048
     openssl rsa -in private.key -pubout -out public.key
     ```

2. **Разместите открытый ключ в DNS**  
   * Создайте TXT‑запись с именем: `<селектор>._domainkey.<домен>`.  
   * Значение записи:  
     ```
     v=DKIM1; k=rsa; p=<ваш_открытый_ключ_в_base64>
     ```  
   * Пример:  
     ```
     mail._domainkey.example.com. IN TXT "v=DKIM1; k=rsa; p=MIGfMA0GCSqGSIb3DQEBAQUAA4GNADCBiQKBgQC..."
     ```

3. **Настройте почтовый сервер**  
   * Укажите путь к закрытому ключу и параметры подписи.  
   * Для Postfix: используйте `opendkim` или `dkim-filter`.  
   * Для Exchange/Office 365 — включите DKIM в настройках домена.

4. **Проверьте работу**  
   * Отправьте тестовое письмо на сервис вроде `check-auth@verifier.port25.com`.  
   * Проверьте заголовки письма на наличие `DKIM-Signature`.  
   * Используйте онлайн‑проверялки (MXToolbox, DKIM Validator).

### Важные нюансы

* **Селекторы** позволяют использовать несколько ключей для одного домена (например, для разных сервисов).  
* **Ротация ключей**: рекомендуется менять ключи каждые 6–12 месяцев.  
* **Совместимость**: DKIM поддерживает большинство почтовых сервисов (Gmail, Outlook, Yahoo).  
* **Ограничения**:  
  * Не защищает от подмены домена в поле `From:` (для этого нужен DMARC).  
  * Не гарантирует доставку письма (только аутентификацию).  

### Зачем нужен DKIM

* **Повышение доставляемости**: письма с валидной DKIM реже попадают в спам.  
* **Защита репутации домена**: предотвращает использование вашего домена злоумышленниками.  
* **Целостность данных**: гарантирует, что письмо не было изменено после отправки.  
* **Соответствие стандартам**: требуется для крупных рассылок и корпоративных сервисов.

### Типичные ошибки

* **Некорректный DNS‑запись**: проверьте синтаксис и TTL.  
* **Несовпадение ключей**: закрытый и открытый ключи должны быть парой.  
* **Отсутствие подписываемых заголовков**: убедитесь, что `h=` включает важные поля.  
* **Проблемы с канонизацией**: выбирайте `relaxed`, если серверы могут изменять форматирование.  


**Итог**: DKIM — критически важный инструмент для аутентификации email. Его настройка требует внимания к деталям, но значительно повышает доверие к вашей почте.
