**Use Case**, **Use Case Flow** и **User Story** — это три ключевых инструмента **анализа требований** в разработке ПО, но они **разные по форме, глубине и цели**. Их часто путают, хотя они **дополняют друг друга** и используются на разных этапах.

---

## ✅ 1. Что такое **Use Case**?

### 🔹 Определение:
> **Use Case** — это **описание взаимодействия между пользователем (актором) и системой**, направленное на достижение **конкретной цели**.

Это **структурный, формализованный способ** описания **функциональных требований** с точки зрения **пользовательского сценария**.

### 📌 Пример:
**Цель:** Пользователь хочет оформить заказ  
**Актор:** Клиент  
**Система:** Интернет-магазин

> **Use Case: Оформление заказа**  
> **Актор:** Клиент  
> **Предусловие:** Клиент авторизован, корзина не пуста  
> **Основной поток:**  
> 1. Клиент нажимает «Оформить заказ»  
> 2. Система показывает форму доставки  
> 3. Клиент выбирает способ доставки  
> 4. Система рассчитывает стоимость  
> 5. Клиент подтверждает заказ  
> 6. Система создает заказ и отправляет подтверждение  
> **Постусловие:** Заказ создан, на email отправлено подтверждение  

### ✅ Для чего нужен Use Case?
- Детальное описание **всех сценариев взаимодействия**
- Помогает **выявить исключения** (альтернативные/ошибочные потоки)
- Используется в **традиционной разработке** (Waterfall, Rational Unified Process)
- Часто применяется в **корпоративных системах**, **банках**, **медицинских системах**

### ✅ Формат Use Case (стандартный шаблон):
| Элемент | Описание |
|--------|----------|
| **Название** | Оформление заказа |
| **Актор** | Клиент |
| **Цель** | Заказать товар |
| **Предусловие** | Пользователь авторизован, есть товары в корзине |
| **Основной поток** | Последовательность шагов при успешном выполнении |
| **Альтернативные потоки** | Например: «клиент не выбрал доставку» → система предлагает выбрать |
| **Исключения** | «Нет в наличии товара» → уведомление, отмена заказа |
| **Постусловие** | Заказ создан, письмо отправлено |

> ✅ **Use Case — это "документ", а не "заметка".**

---

## ✅ 2. Что такое **Use Case Flow**?

### 🔹 Определение:
> **Use Case Flow** — это **конкретная последовательность шагов**, описывающая **как система и пользователь взаимодействуют** в рамках Use Case.  
> Часто **синоним** основного потока (Main Flow) в Use Case.

### 📌 Пример:
**Use Case Flow для «Оформления заказа»**:

1. Клиент кликает «Оформить заказ»  
2. Система отображает форму с адресами доставки  
3. Клиент выбирает «Домашний адрес»  
4. Система показывает способы оплаты: картой, PayPal  
5. Клиент выбирает «Картой»  
6. Система открывает форму оплаты  
7. Клиент вводит данные карты  
8. Система отправляет запрос на платёж  
9. Платёж успешен → система создает заказ  
10. Система показывает «Заказ успешно оформлен!»

### ✅ Для чего нужен Use Case Flow?
- **Детализация** основного потока Use Case
- Используется для **проектирования UI/UX**
- Основа для **написания тест-кейсов**
- Часто визуализируется как **диаграмма последовательности** ([[Sequence Diagram]]) или **потоковая схема**

> ✅ **Use Case Flow = «как это работает в реальности»**  
> **Use Case = «что делает система и зачем»**

---

## ✅ 3. Что такое **User Story**?

### 🔹 Определение:
> **User Story** — это **краткое, неформальное описание функциональности** с точки зрения **конечного пользователя**, написанное в простом языке.

Формат:  
> **«Как [роль], я хочу [цель], чтобы [причина]»**

### 📌 Пример:
```text
Как клиент,  
я хочу оформить заказ с доставкой на дом,  
чтобы получить товар без посещения магазина.
```

### ✅ Для чего нужна User Story?
- Используется в **Agile/Scrum** методологиях
- Служит **основой для обсуждения** в спринте
- Не детализирована — **нужно дополнять** (разговором, acceptance criteria)
- Помогает **фокусироваться на ценности для пользователя**, а не на технических деталях

### ✅ Дополнение: **Acceptance Criteria (Критерии приемки)**
User Story без критериев — бесполезна. Критерии — это **условия, при которых история считается завершённой**:

```text
Как клиент,  
я хочу оформить заказ с доставкой на дом,  
чтобы получить товар без посещения магазина.

Критерии приемки:
- Можно выбрать адрес из сохранённых
- Можно добавить новый адрес
- Можно выбрать способ оплаты: карта, PayPal
- После оплаты появляется сообщение «Заказ оформлен»
- На email приходит подтверждение
```

> ✅ **User Story = «напоминание о разговоре»** — не документ, а повод для обсуждения.

---

## 🆚 Сравнение: Use Case vs Use Case Flow vs User Story

| Критерий             | **Use Case**                                | **Use Case Flow**                           | **User Story**                    |
| -------------------- | ------------------------------------------- | ------------------------------------------- | --------------------------------- |
| **Формат**           | Формальный, структурированный документ      | Последовательность шагов (часть Use Case)   | Неформальная фраза (1–3 строки)   |
| **Детализация**      | Высокая (включает исключения, альтернативы) | Средняя (только основной поток)             | Очень низкая                      |
| **Цель**             | Полное описание взаимодействия              | Как работает сценарий                       | Быстрая передача идеи             |
| **Кто использует**   | Бизнес-аналитики, архитекторы, тестировщики | UI/UX-дизайнеры, разработчики, тестировщики | Product Owner, команда разработки |
| **Где используется** | Waterfall, RUP, корпоративные системы       | Всегда как часть Use Case                   | Agile, Scrum, Kanban              |
| **Создаётся до**     | Перед проектированием                       | Во время проектирования                     | Перед спринтом                    |
| **Измеримость**      | Да (можно тестировать)                      | Да                                          | Только с Acceptance Criteria      |
| **Пример**           | 5–10 страниц документа                      | 5–10 шагов в списке                         | «Как клиент, хочу оформить заказ» |

## 🎯 Для какого анализа нужны эти инструменты?

| Цель анализа                                          | Рекомендуемый инструмент                    | Почему                                                                    |
| ----------------------------------------------------- | ------------------------------------------- | ------------------------------------------------------------------------- |
| ✅ **Понять, что система должна делать**               | **User Story**                              | Быстро собрать идеи от пользователей, фокус на ценности                   |
| ✅ **Детализировать, как это работает**                | **Use Case Flow**                           | Показать последовательность действий — для UI, тестов, разработки         |
| ✅ **Задокументировать все сценарии (включая ошибки)** | **Use Case**                                | Для сложных систем: банки, медицина, госуслуги — где нельзя ошибаться     |
| ✅ **Написать тест-кейсы**                             | **Use Case Flow** + **Acceptance Criteria** | Каждый шаг — это тест                                                     |
| ✅ **Планировать спринт (Agile)**                      | **User Story + Acceptance Criteria**        | Легко оценить, спланировать, разбить на задачи                            |
| ✅ **Создать архитектурную документацию**              | **Use Case**                                | Показывает взаимодействие между акторами и системой — основа для диаграмм |
| ✅ **Провести аудит требований**                       | **Use Case**                                | Полный, проверяемый, версионируемый документ                              |

## ✅ Когда что использовать? (Рекомендации)

| Сценарий | Рекомендация |
|----------|--------------|
| **Вы делаете стартап, MVP, продукт для рынка** | ✅ Используйте **User Stories** + Acceptance Criteria — быстро, гибко, фокус на пользователе |
| **Вы пишете систему для банка, госуслуг, медицины** | ✅ Используйте **Use Case** — требует полной документации, аудита, соответствия стандартам |
| **Вы проектируете UI или пишете тесты** | ✅ Используйте **Use Case Flow** — чтобы точно понять, как пользователь проходит сценарий |
| **Вы работаете в команде Agile** | ✅ Комбинируйте: **User Story → Use Case Flow → Acceptance Criteria** |
| **Вы пишете техническое задание** | ✅ Используйте **Use Case** как основу, а User Stories — как «пакет» требований |

## 💡 Как они связаны? (Пример)

| Этап | Инструмент |
|------|------------|
| **1. Сбор требований** | `Как клиент, я хочу оформить заказ` — **User Story** |
| **2. Детализация** | Команда обсуждает: «А что, если нет товара?», «А если платёж не прошёл?» → **Use Case Flow** |
| **3. Документирование** | Записывают всё в **Use Case** (основной, альтернативный, исключительный потоки) |
| **4. Тестирование** | Из Use Case Flow генерируют **Acceptance Criteria** → пишут тест-кейсы |
| **5. Разработка** | Разработчик смотрит на Use Case Flow и Acceptance Criteria — пишет код |

> ✅ **User Story — это начало. Use Case — это конец. Use Case Flow — это мост между ними.**

---

## ✅ Финальный вывод: Как не запутаться?

| Вопрос                                        | Ответ                                                                                                        |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| **Что такое Use Case?**                       | **Документ**, описывающий **все возможные сценарии** взаимодействия системы с пользователем.                 |
| **Что такое Use Case Flow?**                  | **Последовательность шагов** — как система работает в **основном сценарии**. Часть Use Case.                 |
| **Что такое User Story?**                     | **Краткая фраза** от пользователя — **повод для разговора**, а не документ.                                  |
| **Когда использовать User Story?**            | В **Agile**, когда нужно быстро собрать идеи и начать разработку.                                            |
| **Когда использовать Use Case?**              | В **корпоративной разработке**, где нужны **документы, аудит, соответствие стандартам**.                     |
| **Можно ли заменить Use Case на User Story?** | **Только если система простая.** Для сложных систем — **нет**. Use Case даёт полноту, User Story — скорость. |

## ✅ **Таблица функциональных требований на основе Use Case**

> **Проект:** Онлайн-банк — мобильное приложение  
> **Use Case:** *Оформление перевода между счетами*  
> **Автор:** Бизнес-аналитик  
> **Дата:** 2025-04-05  
> **Версия:** 1.2

| № | ID Требования | Use Case | Функциональное требование | Тип | Приоритет | Источник | Примечания |
|----|----------------|----------|---------------------------|-----|-----------|----------|------------|
| 1 | **FR-001** | Оформление перевода | Система должна позволять пользователю выбрать счет-отправитель из списка своих активных счетов | Функциональное | **Высокий** | ТЗ клиента | Счета должны быть активными (не заблокированы) |
| 2 | **FR-002** | Оформление перевода | Система должна позволять пользователю выбрать счет-получатель из списка контактов или ввести номер счета вручную | Функциональное | **Высокий** | Интервью с пользователями | Поддержка ввода номера счета в формате `12345678901234567890` |
| 3 | **FR-003** | Оформление перевода | Система должна позволять ввести сумму перевода с точностью до 2 знаков после запятой | Функциональное | **Высокий** | ТЗ клиента | Минимальная сумма: 1 рубль, максимальная: 500 000 руб. |
| 4 | **FR-004** | Оформление перевода | Система должна проверять, что сумма перевода не превышает остаток на счете-отправителе | Функциональное | **Высокий** | Бизнес-правила | Если недостаточно средств — показать ошибку: «Недостаточно средств» |
| 5 | **FR-005** | Оформление перевода | Система должна позволять добавить комментарий к переводу (до 200 символов) | Функциональное | **Средний** | Пользовательские опросы | Комментарий отображается в истории операций |
| 6 | **FR-006** | Оформление перевода | Система должна запрашивать подтверждение через двухфакторную аутентификацию (SMS-код или биометрия) | Функциональное | **Высокий** | Регуляторные требования (ФЗ-115) | Двухфакторная аутентификация обязательна для сумм > 10 000 руб. |
| 7 | **FR-007** | Оформление перевода | Система должна отображать предварительный итог: «Вы переведете 5 000 руб. со счета XXXX на счет YYYY. Комиссия: 0 руб.» | Функциональное | **Высокий** | UX-исследование | Подтверждение должно быть подписано кнопкой «Перевести» |
| 8 | **FR-008** | Оформление перевода | После подтверждения система должна создать операцию перевода и сохранить её в истории | Функциональное | **Высокий** | Бизнес-логика | Операция должна быть помечена как «Выполнена» |
| 9 | **FR-009** | Оформление перевода | Система должна отправить пользователю уведомление (push + SMS) об успешном переводе | Функциональное | **Средний** | ТЗ клиента | Уведомление должно содержать: сумму, дату, номера счетов |
| 10 | **FR-010** | Оформление перевода | Система должна разрешить отменить перевод в течение 5 минут после подтверждения | Функциональное | **Средний** | Бизнес-аналитика | Только для переводов между своими счетами, не для внешних |
| 11 | **FR-011** | Оформление перевода | Система должна блокировать перевод, если счет-отправитель заблокирован (по решению банка) | Функциональное | **Высокий** | Регуляторные требования | Проверка статуса счета перед началом операции |
| 12 | **FR-012** | Оформление перевода | Система должна отображать ошибку «Неверный номер счета», если введённый счет не существует | Функциональное | **Средний** | Тест-кейсы | Проверка через API реестра счетов банка |
| 13 | **FR-013** | Оформление перевода | Система должна автоматически запоминать последние 5 получателей для быстрого выбора | Функциональное | **Средний** | UX-рекомендации | Данные хранятся локально на устройстве (не на сервере) |

## ✅ Пояснения к таблице

| Колонка | Описание |
|--------|----------|
| **№** | Нумерация для удобства ссылок |
| **ID Требования** | Уникальный идентификатор (например, `FR-XXX`) — используется в тестах, бэклоге, отчётах |
| **Use Case** | К какому Use Case относится требование — для трассировки |
| **Функциональное требование** | Чёткое, измеримое, однозначное описание того, **что система должна делать** — в повелительном наклонении |
| **Тип** | `Функциональное` — это то, что система **делает**. Отличается от нефункциональных (производительность, безопасность) |
| **Приоритет** | **Высокий** — без этого требование система не может работать<br>**Средний** — важно, но не критично<br>**Низкий** — желательно, но не обязательно |
| **Источник** | Откуда требование взято: интервью, регламент, TЗ, UX-исследование |
| **Примечания** | Дополнительные условия, ограничения, форматы, исключения |

## ✅ Почему такая таблица работает?

| Преимущество | Объяснение |
|--------------|------------|
| ✅ **Трассируемость** | Каждое требование связано с Use Case → можно отследить: «Зачем это нужно?» |
| ✅ **Чёткость** | Нет размытых фраз вроде «система должна быть удобной» — только конкретные действия |
| ✅ **Тестируемость** | Каждое требование можно превратить в тест-кейс: `FR-004` → «Попытка перевода 10 000 руб. при балансе 5 000 → ошибка» |
| ✅ **Разработка и QA** | Разработчики знают, что делать. Тестировщики знают, что проверять. |
| ✅ **Управление изменениями** | Можно отслеживать: «Какие требования изменились?» |
| ✅ **Согласование с заказчиком** | Заказчик может легко понять, что именно он просит — и подтвердить |

## ✅ Пример: Как из этого сделать тест-кейс?

**Требование:** `FR-004` — *Система должна проверять, что сумма перевода не превышает остаток на счете-отправителе*

### ✅ Тест-кейс:
```gherkin
Scenario: Попытка перевода больше остатка на счете
  Given пользователь авторизован
  And на счете-отправителе остаток 5 000 руб.
  And пользователь выбирает счет-получатель
  And пользователь вводит сумму перевода: 10 000 руб.
  When пользователь нажимает "Перевести"
  Then система отображает ошибку: "Недостаточно средств"
  And перевод не выполняется
```
