Разберу подробно паттерн **Unit of Work (UoW)** из книги Мартина Фаулера *Patterns of Enterprise Application Architecture*.

## Суть паттерна

**Unit of Work** отслеживает все объекты, которые были загружены из базы данных или изменены в ходе выполнения бизнес‑транзакции, и координирует их сохранение в БД. Он выступает «единицей» работы с данными — от начала до фиксации изменений.

**Основная задача:** гарантировать, что все изменения будут сохранены согласованно (либо все, либо ни одного) в рамках одной транзакции.

## Проблема, которую решает UoW

Без UoW при работе с множеством объектов возникает ряд проблем:

* **Множество отдельных запросов.** Каждое изменение объекта требует отдельного SQL‑запроса, что снижает производительность.
* **Нарушение целостности данных.** Если часть операций завершится успешно, а часть — нет, данные окажутся в несогласованном состоянии.
* **Дублирование объектов.** Один и тот же объект может быть загружен несколько раз, что приводит к конфликтам при сохранении.
* **Сложность управления транзакциями.** Программисту приходится вручную координировать вызовы `INSERT`, `UPDATE`, `DELETE`.

## Как работает Unit of Work

UoW действует как **регистратор изменений** и **координатор сохранения**. Его работа состоит из нескольких этапов:

1. **Регистрация объектов:**
    * при загрузке объекта из БД UoW запоминает его в состоянии «чистый» (`Clean`);
    * если объект изменён, он помечается как «грязный» (`Dirty`);
    * новые объекты помечаются как «новые» (`New`);
    * удалённые — как «удалённые» (`Deleted`).

2. **Отслеживание изменений:** UoW следит за всеми операциями над объектами в рамках сессии (например, веб‑запроса).

3. **Координация сохранения:** при вызове метода `commit()` UoW:
    * группирует операции по типам;
    * выполняет их в оптимальном порядке (обычно: `INSERT` → `UPDATE` → `DELETE`);
    * оборачивает всё в транзакцию.

4. **Управление транзакциями:** гарантирует, что либо все изменения применятся, либо ни одно (при ошибке выполняется `rollback`).

## Ключевые методы и состояния объектов

**Основные методы UoW:**

* `registerNew(object)` — регистрирует новый объект для вставки;
* `registerDirty(object)` — отмечает объект как изменённый;
* `registerDeleted(object)` — помечает объект для удаления;
* `commit()` — применяет все накопленные изменения в БД;
* `rollback()` — отменяет все изменения.

**Состояния объектов:**

| Состояние | Описание |
|---------|----------|
| **New** | Объект создан в памяти, но ещё не сохранён в БД |
| **Clean** | Объект загружен из БД и не изменён |
| **Dirty** | Объект изменён после загрузки из БД |
| **Deleted** | Объект помечен для удаления из БД |

## Пример работы (на псевдокоде)

Представим бизнес‑операцию «Перевод денег между счетами»:

```python
# Создаём Unit of Work
uow = UnitOfWork()

# Загружаем объекты (регистрируются как Clean)
account_from = repository.get_account(1)
account_to = repository.get_account(2)

# Изменяем объекты (помечаются как Dirty)
account_from.withdraw(100)
account_to.deposit(100)

# Регистрируем изменения в UoW
uow.registerDirty(account_from)
uow.registerDirty(account_to)

# Создаём запись о транзакции (новый объект)
transaction = Transaction(from_id=1, to_id=2, amount=100)
uow.registerNew(transaction)

# Применяем все изменения одной транзакцией
uow.commit()
# Генерирует SQL:
# UPDATE accounts SET balance = ... WHERE id = 1
# UPDATE accounts SET balance = ... WHERE id = 2
# INSERT INTO transactions (...) VALUES (...)
```

Если на любом этапе возникнет ошибка, `commit()` выполнит `rollback`, и ни одно изменение не попадёт в БД.

## Взаимодействие с другими паттернами

UoW часто используется совместно с:

* **Identity Map** — гарантирует, что для одной записи БД существует только один объект в памяти. Предотвращает дублирование и конфликты.
* **Repository** — предоставляет интерфейс для загрузки и сохранения объектов. UoW координирует работу нескольких репозиториев.
* **Domain Model** — UoW сохраняет состояние объектов предметной области.
* **Lazy Load** — UoW может отслеживать лениво загружаемые связи между объектами.

## Преимущества

* **Согласованность данных.** Все изменения применяются атомарно.
* **Оптимизация производительности.** Группировка запросов снижает нагрузку на БД.
* **Упрощение кода.** Программист работает с объектами, а не с SQL.
* **Централизованное управление транзакциями.** Не нужно вручную оборачивать операции в `BEGIN TRANSACTION` / `COMMIT`.
* **Гибкость.** Легко добавить логирование, аудит или кэширование изменений.

---

## Недостатки и сложности

* **Сложность реализации.** Требуется корректно отслеживать состояния объектов и зависимости между ними.
* **Потребление памяти.** UoW хранит все изменённые объекты в памяти до `commit()`.
* **Конфликты при параллельном доступе.** Если два UoW пытаются изменить один объект, возможны ошибки.
* **Отложенное выполнение.** Изменения не применяются сразу, что может запутать разработчика.
* **Проблемы с долгоживущими UoW.** Если UoW существует слишком долго (например, в веб‑сессии), он накапливает много объектов и может «утечь» память.

## Реализация в ORM

Большинство современных ORM включают UoW «из коробки»:

* **Hibernate (Java):** `Session` — это UoW. Методы `save()`, `update()`, `delete()` регистрируют изменения, `flush()` применяет их.
* **Entity Framework (C#):** `DbContext` реализует UoW и Identity Map. Метод `SaveChanges()` выполняет `commit()`.
* **Doctrine (PHP):** `EntityManager` — UoW. `persist()`, `remove()` регистрируют объекты, `flush()` сохраняет их.
* **SQLAlchemy (Python):** `Session` — UoW. Изменения отслеживаются автоматически, `commit()` применяет их.

## Когда использовать Unit of Work

**Подходит:**
* сложные бизнес‑транзакции с множеством объектов;
* приложения с многоуровневой архитектурой;
* системы, где важна целостность данных;
* работа с ORM.

**Не нужен:**
* простые CRUD‑операции с одним объектом;
* read‑only приложения;
* сценарии с очень короткими транзакциями.

---

## Краткий итог

**Unit of Work:**
* отслеживает изменения объектов в памяти;
* группирует SQL‑запросы для оптимизации;
* гарантирует атомарность транзакций;
* упрощает работу с данными, скрывая детали взаимодействия с БД;
* является ключевым компонентом большинства ORM.

Его главная ценность — в **централизованном управлении изменениями** и обеспечении **целостности данных** при сложных операциях.
