### Кратко о паттерне Data Mapper

**Data Mapper** — паттерн из книги Мартина Фаулера *Patterns of Enterprise Application Architecture*, который обеспечивает **двунаправленное отображение** между объектами предметной области (domain objects) и записями в базе данных.

Ключевая идея: **полное разделение** бизнес‑логики и слоя доступа к данным. Объекты не знают о БД, а БД не знает об объектах.

## Как работает

Data Mapper действует как **прослойка‑посредник**:

1. **Из БД в объекты:** берёт данные из таблиц и создаёт/обновляет объекты предметной области.
2. **Из объектов в БД:** берёт изменённые объекты и сохраняет их состояние в таблицах.

**Схема взаимодействия:**

```
Бизнес‑логика (Domain Objects) ↔ Data Mapper ↔ База данных
```


## Ключевые особенности

* **Разделение ответственности:** бизнес‑объекты содержат только логику предметной области.
* **Независимость схем:** структура объектов может отличаться от структуры таблиц.
* **Двунаправленность:** умеет и читать из БД, и записывать в неё.
* **Отсутствие «заражения»:** объекты не наследуют от БД‑классов и не содержат методов типа `save()`.

## Преимущества

* **Гибкость:** можно менять схему БД без изменения бизнес‑объектов (и наоборот).
* **Тестируемость:** легко мокировать mapper для unit‑тестов бизнес‑логики.
* **Чистота архитектуры:** строгое разделение уровней приложения.
* **Поддержка сложных маппингов:** один объект может собираться из нескольких таблиц; одна таблица может маппиться на несколько объектов.

## Недостатки

* **Сложность:** требует больше кода и классов по сравнению с Active Record.
* **Производительность:** дополнительный слой может давать небольшие накладные расходы.
* **Кривая обучения:** сложнее для понимания новичками.

## Когда использовать

* сложные бизнес‑правила и модели;
* необходимость чёткого разделения уровней (например, в DDD);
* частые изменения схемы БД или бизнес‑логики;
* работа с legacy‑БД, структура которой не соответствует объектам;
* крупные проекты с командой разработчиков.

## Отличие от Active Record

| Критерий | Data Mapper | Active Record |
|--------|------------|--------------|
| **Связь с БД** | Через отдельный слой‑посредник | Объект сам знает, как сохраняться (`save()`, `delete()`) |
| **Гибкость** | Высокая (полная независимость) | Низкая (тесная связь с таблицей) |
| **Сложность** | Выше | Ниже |
| **Типичные примеры** | Hibernate, Entity Framework, Doctrine | Rails ActiveRecord, Laravel Eloquent |

# Data Mapper vs Mapper

Разберу разницу между **Mapper** и **Data Mapper** согласно книге Мартина Фаулера *Patterns of Enterprise Application Architecture*.

## Mapper (общий паттерн)

**Mapper** — обобщённый паттерн, описывающий любой объект, который **преобразует данные из одного представления в другое**. Это широкая категория, включающая разные виды мапперов.

**Суть:** преобразование структуры данных между двумя разными слоями или форматами.


**Примеры задач:**
* преобразование объектов домена в DTO (Data Transfer Object);
* конвертация JSON/XML в объекты приложения;
* маппинг между разными моделями данных (например, между API‑ответами разных версий);
* преобразование данных между слоями приложения (бизнес‑логика ↔ представление).

**Ключевые черты:**
* может работать с любыми форматами данных (объекты, JSON, XML, таблицы);
* не обязательно связан с БД;
* фокусируется на **преобразовании структуры** данных.

**Пример на псевдокоде:**
```python
class UserToUserDTOConverter:
    def convert(self, user: User) -> UserDTO:
        return UserDTO(
            id=user.id,
            name=user.full_name,
            email=user.contact.email
        )
```

## Data Mapper (конкретный паттерн)

**Data Mapper** — специализированный вид маппера, который **обеспечивает двунаправленное отображение между объектами предметной области (domain objects) и записями в базе данных**.

**Суть:** полное разделение бизнес‑логики и слоя доступа к данным. Объекты не знают о БД, БД не знает об объектах.

**Задачи:**
* загрузка объектов из БД (`findById`, `findAll`);
* сохранение изменений объектов в БД (`insert`, `update`, `delete`);
* синхронизация состояния объектов с записями в таблицах;
* работа с транзакциями и единицами работы (Unit of Work).

**Ключевые черты:**
* всегда связан с **БД**;
* обеспечивает **двунаправленность** (чтение и запись);
* поддерживает **независимость** моделей от схемы БД (разные структуры);
* часто работает с **Unit of Work** и **Identity Map**;
* гарантирует **целостность данных** при сохранении.

**Пример на псевдокоде:**
```python
class UserMapper:
    def find_by_id(self, user_id: int) -> User:
        row = db.execute("SELECT * FROM users WHERE id = ?", user_id)
        return User(id=row['id'], name=row['name'], email=row['email'])

    def save(self, user: User):
        if user.is_new():
            db.execute("INSERT INTO users (name, email) VALUES (?, ?)",
                      user.name, user.email)
        else:
            db.execute("UPDATE users SET name = ?, email = ? WHERE id = ?",
              user.name, user.email, user.id)
```

## Сравнительная таблица

| Критерий | Mapper | Data Mapper |
|--------|--------|------------|
| **Назначение** | Общее преобразование данных между любыми форматами | Двунаправленное отображение между объектами и БД |
| **Связь с БД** | Не обязательна (может работать с JSON, XML, DTO и т. д.) | Обязательна (всегда взаимодействует с БД) |
| **Направление** | Однонаправленное или двунаправленное | Двунаправленное (чтение и запись) |
| **Зависимость слоёв** | Может связывать любые слои приложения | Разделяет слой бизнес‑логики и слой данных |
| **Типичные задачи** | Конвертация DTO, адаптация API, трансформация форматов | Сохранение объектов в БД, загрузка из БД, транзакции |
| **Паттерны‑партнёры** | — | Unit of Work, Identity Map, Repository |
| **Пример реализации** | `UserToUserDTOConverter`, `JSONToObjectMapper` | `UserMapper`, `OrderMapper` с SQL‑запросами |

## Взаимосвязь

* **Data Mapper — это частный случай Mapper.** Любой Data Mapper является маппером, но не каждый маппер — Data Mapper.
* **Data Mapper решает более узкую задачу** (работа с БД), тогда как Mapper — общий инструмент для любых преобразований данных.
* В сложных системах оба паттерна могут использоваться **вместе**: Data Mapper загружает объекты из БД, а другие мапперы преобразуют их в DTO для передачи по API.

---

## Краткий итог

* **Mapper** — общий паттерн для преобразования данных между разными форматами и слоями. Пример: конвертация объекта в JSON или DTO.
* **Data Mapper** — специализированный паттерн для двунаправленного маппинга между объектами предметной области и записями в БД. Гарантирует независимость бизнес‑логики от схемы хранения.

**Аналогия:**
* Mapper — переводчик между любыми языками (английский ↔ французский, русский ↔ китайский).
* Data Mapper — специализированный переводчик с «языка объектов» на «язык SQL» и обратно.
