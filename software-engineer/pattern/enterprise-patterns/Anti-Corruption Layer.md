## Паттерн Anti-Corruption Layer (ACL)

Anti-Corruption Layer – это шаблон проектирования программного обеспечения, который действует как буфер между вашим внутренним, «чистым» приложением и внешними системами или устаревшими приложениями с несовместимыми или «испорченными» данными и моделями. Его основная задача — изолировать вашу основную систему, переводя и трансформируя данные, чтобы предотвратить попадание внешних концепций и структур данных в вашу внутреннюю доменную модель.

> *антикоррупционный слой* ≡ **слой, который предотвращает повреждение данных**

ACL помогает создать границу между новой системой и унаследованной. Через этот уровень проходят все данные, которые системы передают друг другу. ACL знает их форматы и модели данных и адаптирует информацию под требования получателя.

Чтобы создать Anti-Corruption Layer, применяют несколько популярных паттернов проектирования. Обычно это Facade и Adapter. Их используют, чтобы сопоставить API монолитных систем с типами и интерфейсами, которые являются частью [[microservice|микросервисов]].

### Как работает ACL

- **Перевод данных и концепций:** ACL выступает в роли переводчика, преобразуя данные из формата внешних систем в формат, понятный вашей внутренней системе, и наоборот.
- **Изоляция:** создаёт границу, которая защищает вашу основную архитектуру от негативного влияния внешних систем.
- **Разделение:** ACL обеспечивает слабую связанность (декуплинг) между вашим основным доменом и внешними системами.
- **Использование дизайн-шаблонов:** ACL часто включает в себя другие шаблоны проектирования, такие как «Фасад» (Facade) и «Адаптер» (Adapter).

### Когда используется ACL

- **Интеграция с устаревшими системами:** при миграции данных из старых систем в новые, более современные приложения.
- **Взаимодействие с сторонними сервисами:** когда нужно интегрировать ваше приложение с внешними сервисами или API, которые имеют другие модели данных.
- **В архитектуре микросервисов:** для изоляции микросервисов друг от друга и защиты их доменных моделей от «коррупции» со стороны других сервисов.

### Преимущества использования ACL

- **Сохранение целостности доменной модели:** защищает вашу внутреннюю бизнес-логику и структуру данных.
- **Гибкость:** позволяет легко интегрировать новые или изменять существующие внешние системы без ущерба для основного приложения.
- **Поддержание чистоты архитектуры:** предотвращает «заражение» вашей архитектуры сторонними решениями.

### Технологии и инструменты для создания ACL

- **[[api-gateway|API-шлюзы]].** Kong, NGINX и AWS API Gateway можно использовать для управления и маршрутизации запросов между старой системой и микросервисами.
- **Инструменты для преобразования данных.** Такие технологии, как Apache Camel и MuleSoft, упростят трансформацию данных и преобразование протоколов.
- **Брокеры сообщений.** Обеспечивают связь и обмен данными между старой системой и новыми сервисами. Например, можно использовать RabbitMQ, [[kafka|Apache Kafka]] или AWS SQS.
- **[[service-mesh|Service Mesh]].** Решения Service Mesh, такие как Istio и Linkerd, могут предоставить дополнительные возможности для управления взаимодействиями микросервисов: управление трафиком, безопасность и наблюдаемость.
- **Настраиваемое промежуточное ПО.** Можно самостоятельно разработать пользовательское промежуточное ПО с использованием языков программирования и фреймворков. Например, Java с [[spring|Spring Boot]] и Node.js. Такой вариант поможет обеспечить индивидуальные решения для конкретных требований ACL.

### Типы реализации ACL

- **[[reverse-proxy|Обратный прокси-сервер]]** — примеры решений: NGINX.
- **API-шлюз** — примеры решений: Kong, Apigee, AWS API Gateway, Zuul.
- **Service Mesh** — специфичное решение в Kubernetes, основанное на сайдкарах внутри подов.
