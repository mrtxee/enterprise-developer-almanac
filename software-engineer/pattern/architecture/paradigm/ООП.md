ООП — **объектно-ориентированное программирование**.

## Парадигма ООП

**Парадигма** — «взгляд на мир».

Парадигма ООП — парадигма программирования, которая предлагает воспринимать бизнес-логику приложений как объекты. `Объекты` — это сущности, у которых есть `поля (состояние) и методы`. Каждый объект — это сущность некоторого `класса`. Все классы Java наследуют базовый класс [[object]].

Есть постулаты ООП, направленные на повышение эффективности кода в рамках данной парадигмы:

- **Структурирование методов и полей.** При функциональной парадигме с ростом программы растёт «простыня» методов, в которой разработчик начинает теряться. ООП позволяет строить упорядоченную иерархическую структуру программных сущностей, в которой ориентироваться намного проще.
- ООП позволяет упростить групповую разработку и повысить переиспользование кода.

## Принципы ООП

Все принципы используются для повышения степени **переиспользуемости кода**.

### Наследование

- Предполагается расширять имеющиеся классы объектов через наследование. Класс-наследник получает от родителя весь набор полей и методов, но при этом его возможности расширяются. Это позволяет не писать похожие методы дважды и повышает возможность переиспользования кода.
- В Java можно унаследовать интерфейс или класс через директивы `implements` или `extends`. Разница между интерфейсом и классом в том, что интерфейс прежде всего следует использовать как форму контракта между разработчиком и клиентами класса. Класс может унаследовать несколько интерфейсов, но только один класс.

### Инкапсуляция

Сокрытие реализации:

- Сущности закрываются модификаторами доступа `private`, `protected`. Это снижает вероятность нежелательного поведения и возникновения сайд-эффектов.

### Полиморфизм

Одна форма может иметь несколько реализаций.

```java
Animal cat = new Cat();
Animal dog = new Dog();
```

Бывают следующие типы полиморфизма.

#### Полиморфизм подтипов (истинный полиморфизм)

Через разную реализацию методов внутри интерфейса.

#### Параметрический полиморфизм (генерики)

Через применение генериков позволяет одному методу работать независимо от типов данных.

#### Ad hoc полиморфизм

Делается через перегрузку входных параметров метода.

### Инверсия контроля — Inversion of Control

Инверсия управления (англ. Inversion of Control, IoC) — важный принцип объектно-ориентированного программирования, используемый для уменьшения зацепления (связанности) в компьютерных программах. Также архитектурное решение интеграции, упрощающее расширение возможностей системы, при котором поток управления программы контролируется фреймворком.

> **Don't call us — we call you!**

#### Методы реализации IoC

- Шаблон [[gof]] `Factory pattern`.
- Шаблон [[gof]] `Locator`.
- Внедрение зависимости (англ. `Dependency injection`):
  - через конструктор (англ. Constructor injection);
  - через метод класса (англ. Setter injection);
  - через интерфейс внедрения (англ. Interface injection).
- Контекстный поиск (англ. contextualized `Lookup`).

### Композиция «has a»

Принцип, который является альтернативой постулату Наследования:

- Наследование предлагает концепцию Предметы → Мебель → Стул.
- Композиция предлагает концепцию Стул «has a» Спинка, «has a» Ножки, «has a» Сиденье.
  - Композиция предлагает включение более мелких простых сущностей.
    - Пример `инъекция зависимости` — когда вместо того, чтобы описывать зависимость внутри объекта, указывается внешний интерфейс зависимости и передаётся сущность данного интерфейса в конструктор.

**Композиция** (`агрегирование` по значению) — более строгий вариант агрегирования. Когда включаемый объект может существовать только как часть контейнера. Если контейнер будет уничтожен, то и включённый объект тоже будет уничтожен.

**Агрегирование** (англ. `object aggregation, object composition`), или, как его называли ранее, делегирование — методика создания нового класса из уже существующих классов путём их включения. Об агрегировании также часто говорят как об «отношении принадлежности» по принципу «у машины есть корпус, колёса и двигатель».

### Абстракция

Если это считать принципом, то речь идёт о том, что нужно выстраивать контракты связывания кода между разными источниками через применение абстрактных классов и интерфейсов.

### Отправка сообщений

Объекты могут обмениваться состояниями и реагировать на события (изменения состояний).

### Пакетирование

Классы можно пакетировать, а пакеты можно импортировать.
