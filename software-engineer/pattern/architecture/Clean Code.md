# Robert C. Martin — Clean Code: A Handbook of Agile Software Craftsmanship

Главный принцип книги[^1] [^2]

> **Правило бойскаута: «Оставь место стоянки чище, чем оно было до тебя».**
Каждый раз, работая с кодом, делайте его чуть чище, чем он был до вашего изменения. Чистый код — это не результат одного рефакторинга, а непрерывная дисциплина всей команды.

## Краткое изложение Robert C. Martin — Clean Code

### Что такое чистый код

Чистый код — это код, который:

- Легко читается и понимается другими разработчиками
- Легко изменяется, расширяется и тестируется
- Содержит минимальное количество зависимостей
- Не дублирует логику (принцип DRY)

> «Чистый код читается как хорошо написанная проза» — Грэди Буч #👨 (Grady Booch)

### Имена (Meaningful Names)

- **Используйте говорящие имена:** `elapsedTimeInMs` вместо `d`
- **Избегайте дезинформации:** не называйте `List` объектом, который не является списком (`accountList` → `accounts`)
- **Осмысленные различия:** если имена должны отличаться — делайте их по смыслу, а не через цифры (`a1`, `a2`)
- **Произносимые имена:** `genymdhms` плохо, `generationTimestamp` хорошо
- **Имя класса** — существительное (`Customer`, `OrderProcessor`), **имя метода** — глагол (`fetchRecord`, `calculateTotal`)
- **Избегайте кодировок:** `Hungarian notation` устарел, IDE справляется без неё

### Функции

- **Короткие:** функция должна быть 2-20 строк, максимум — не более одной страницы экрана
- **Одна задача:** функция должна делать ОДНУ вещь, делать её хорошо и только это (`doOneThing`)
- **Один уровень абстракции на функцию:** не смешивайте высокоуровневую логику с деталями реализации
- **Чтение сверху вниз:** код должен читаться как газетная статья — от общего к частному
- **Параметры:**
  - Идеал — 0 аргументов
  - 1-2 допустимо
  - 3 и более — избегайте
  - Флаг-аргументы (`boolean`) — зло, разделяйте на два метода
- **Отсутствие побочных эффектов:** функция не должна делать то, о чём не говорит её имя
- **Query/Command Separation:** метод либо что-то делает, либо возвращает данные, но не оба сразу

### Комментарии

- **Комментарии — это зло, которое иногда необходимо.** Они компенсируют неспособность выразиться кодом
- **Правильное использование:**
  - Юридическая информация, лицензия
  - Объяснение намерения (почему так, а не иначе)
  - Предупреждения о последствиях
  - TODO-комментарии (но с тикетом в трекере!)
  - Усиление важности нетривиального кода
- **Неправильное использование:**
  - Закомментированный код — удаляйте (есть Git)
  - Комментарии-бормотания, объясняющие очевидное
  - Комментарии, которые устарели и вводят в заблуждение
  - «Шумные» комментарии типа `return 0; // return 0`

### Форматирование

- **Вертикальное форматирование:** файл должен умещаться в один экран
- **Плотность vs открытость:** связанные строки — без пустых строк; несвязанные концепции — разделены
- **Порядок:** вызывающие функции — сверху, вызываемые — снизу
- **Горизонтальное форматирование:** строка не длиннее 120 символов
- **Отступы:** строгая иерархия через отступы
- **Командный стандарт:** весь проект должен выглядеть так, будто его писал один человек

### Объекты и структуры данных

- **Объекты** скрывают данные и предоставляют поведение (методы)
- **Структуры данных** раскрывают данные и не имеют поведения
- **Закон Деметры:** модуль не должен знать о внутренностях объектов, которыми он манипулирует. Избегайте `a.getB().getC().doSomething()`
- **Data Transfer Object (DTO):** структуры данных без поведения, полезные для передачи между слоями
- **Active Record:** особая форма DTO с методами сохранения, но не бизнес-логикой

### Обработка ошибок

- **Используйте исключения** вместо кодов возврата
- **Сначала пишите `try/catch/finally`** — это определяет контракт функции
- **Неисключительные (unchecked) исключения** предпочтительнее в большинстве случаев
- **Предоставляйте контекст** в исключениях: операция, источник, причина
- **Определяйте классы исключений** по способу их обработки, а не по источнику
- **Не передавайте `null`** и не возвращайте `null` из методов — используйте `Optional` или пустые коллекции
- **Оберните сторонние API** в собственные исключения

### Границы (Boundaries)

- Изолируйте зависимости от сторонних библиотек через интерфейсы и адаптеры
- Пишите **learning tests** для изучения чужих API
- Ожидаемые изменения в чужом коде — инкапсулируйте

### Модульные тесты

Три закона TDD (Test-Driven Development):

1. Нельзя писать рабочий код, пока нет падающего теста
2. Нельзя писать теста больше, чем нужно для падения
3. Нельзя писать рабочего кода больше, чем нужно для прохождения теста

**Принципы чистых тестов (FIRST):**

- **F**ast — быстрые
- **I**ndependent — независимые друг от друга
- **R**epeatable — воспроизводимые в любой среде
- **S**elf-Validating — с булевым результатом (прошёл/не прошёл)
- **T**imely — написанные вовремя (до кода или параллельно)

**Тестовый код так же важен, как продукционный.** Никаких «и так сойдёт».

### Классы

- **Маленькие:** класс должен быть 50-500 строк, желательно меньше 100
- **Single Responsibility Principle (SRP):** у класса должна быть только одна причина для изменения
- **Open/Closed Principle:** классы открыты для расширения, но закрыты для модификации
- **Liskov Substitution Principle:** подклассы должны заменять базовые классы
- **Interface Segregation:** не заставляйте клиентов зависеть от методов, которые они не используют
- **Dependency Inversion:** зависимость от абстракций, а не от конкретики
- **Инстанс-переменные** в начале класса, **приватные методы** — сразу после методов, которые их используют

### Системы

- **Разделяйте настройку и использование:** конструктор должен только конструировать, а не запускать работу
- **Lazy Initialization:** откладывайте создание тяжёлых объектов
- **Dependency Injection:** внедряйте зависимости, а не создавайте их внутри
- **Правильная архитектура** позволяет откладывать решения до последнего момента (когда есть больше информации)
- **Стандарты** должны облегчать жизнь, а не быть самоцелью

### Появление (Emergence)

Четыре правила простого дизайна по Кенту Беку #👨:

1. **Все тесты проходят**
2. **Нет дублирования кода**
3. **Код выражает намерение программиста**
4. **Минимум классов и методов**

### Конкурентность

- **Конкурентность ≠ параллелизм**
- Защищайте общие данные (`synchronized`, `atomic`, `Lock`)
- Используйте высокоуровневые конструкции из `java.util.concurrent`
- Разделяйте данные, если это возможно, вместо синхронизации
- **Producer-Consumer, Readers-Writers, Dining Philosophers** — типичные паттерны
- Тестируйте многопоточность отдельно и под нагрузкой

### Запахи кода и эвристики (Smells and Heuristics)

Ключевые антипаттерны, которые надо устранять:

| Запах | Описание                                                   |
| ----- | ---------------------------------------------------------- |
| `C1`  | Комментарии, которые могут быть удалены (заменяются кодом) |
| `C2`  | Устаревшие комментарии                                     |
| `F1`  | Слишком много аргументов у функции                         |
| `F2`  | Флаги как параметры                                        |
| `F3`  | Мёртвые функции (не вызываются)                            |
| `G1`  | Несколько языков в одном файле                             |
| `G3`  | Неочевидное поведение                                      |
| `G5`  | Дублирование                                               |
| `G9`  | Мёртвый код                                                |
| `G12` | Замусоривание                                              |
| `G14` | Feature Envy (метод работает с данными другого объекта)    |
| `G28` | Инкапсуляция нарушена                                      |
| `J1`  | Избегайте длинных импортов через `*`                       |
