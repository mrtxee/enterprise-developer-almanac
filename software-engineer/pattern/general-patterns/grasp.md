# GRASP
> General Responsibility Assignment Software Patterns
> Паттерны распределения ответственности
> GRASP

**GRASP** — это набор принципов распределения ответственностей между классами и объектами в объектно‑ориентированном проектировании. Не является строгой методологией, а служит руководством для принятия проектных решений.
* Помогают принимать обоснованные решения на этапе проектирования классов: «Кто должен делать X?»
 * Служат основой для понимания и применения классических паттернов проектирования.

Перечень принципов
1. Information Expert
2. Creator
3. Low Coupling
4. High Cohesion
5. Controller
6. Pure Fabrication
7. Indirection
8. Polymorphism
9. Protected Variation

# Паттерны распределения ответственности

## Information Expert
> Информационный эксперт
   * **Принцип:** ответственность присваивается классу, который владеет наибольшей частью необходимой информации для её выполнения.
   * **Цель:** максимизировать инкапсуляцию и минимизировать зависимости.
   * **Пример:** класс `Order` отвечает за расчёт общей суммы, потому что содержит список позиций `OrderItems`.

## Creator
> Создатель
   * **Принцип:** определяет, какой класс должен создавать экземпляры других классов.
   * **Критерии:** создающий класс:
     * содержит или агрегирует создаваемые объекты;
     * записывает создаваемые объекты;
     * активно использует создаваемые объекты;
     * имеет данные для инициализации создаваемых объектов.
   * **Пример:** `Order` создаёт экземпляры `OrderItem`.

## Low Coupling
> Слабая сцепленность
   * **Принцип:** минимизировать зависимости между классами.
   * **Цель:** повысить переиспользуемость и упростить поддержку кода.
   * **Следствие:** изменения в одном классе меньше влияют на другие.

## High Cohesion
> Сильная связность
   * **Принцип:** элементы класса должны быть тесно связаны по функциональности и иметь одну чётко определённую цель.
   * **Цель:** сделать классы понятными, управляемыми и переиспользуемыми.
   * **Противоположность:** «божественный объект» (God Object) с множеством разнородных обязанностей.

## Controller
> Контроллер
   * **Принцип:** внешний запрос (от пользователя или системы) обрабатывается специальным классом‑контроллером, а не UI‑классом.
   * **Цель:** отделить логику обработки запросов от интерфейса.
   * **Пример:** `OrderController` обрабатывает команду «оформить заказ», вызывая методы `Order` и `PaymentService`.

## Pure Fabrication
> Чистая выдумка
   * **Принцип:** создать класс, не имеющий прямого аналога в предметной области, чтобы:
     * снизить сцепленность;
     * повысить связность;
     * упростить переиспользование.
   * **Аналог:** сервис или утилита.
   * **Пример:** класс `EmailSender` для отправки уведомлений, не отражающий сущность из бизнес‑домена.

## Indirection
> Косвенное обращение
   * **Принцип:** добавить промежуточный класс для снижения прямой связи между двумя другими.
   * **Цель:** реализовать слабую связность.
   * **Реализация:** посредник ([[gof|Mediator]]), фасад ([[gof|Facade]]), адаптер ([[gof|Adapter]]).
   * **Пример:** интерфейс `PaymentGateway` между `Order` и конкретными платёжными системами.

## Polymorphism
> Полиморфизм
   * **Принцип:** поведение, различающееся в зависимости от типа, реализуется через переопределение методов в подклассах.
   * **Цель:** заменить условные операторы (`if/else`, `switch`) на полиморфные вызовы.
   * **Пример:** метод `calculateDiscount()` переопределён в классах `RegularCustomer` и `VIPCustomer`.

## Protected Variations
> Защищённые изменения
   * **Принцип:** спроектировать систему так, чтобы изменения в одной части не затрагивали другие.
   * **Реализация:** использовать интерфейсы и абстракции для изоляции точек изменчивости.
   * **Пример:** абстракция `NotificationService` позволяет менять реализации (`SMSNotifier`, `EmailNotifier`) без правки клиентского кода.
