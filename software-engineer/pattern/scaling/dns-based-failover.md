**DNS-based failover** — это метод обеспечения высокой доступности, который автоматически перенаправляет пользовательский трафик с отказавшего сервера или дата-центра на резервный, используя механизмы системы доменных имён ([[dns|DNS]]) и мониторинга состояния серверов. По сути, это «план Б» для вашего домена.

## Как это работает

Процесс состоит из нескольких автоматизированных этапов:

- **[[monitoring|Мониторинг]] (Health Checks):** система DNS-провайдера постоянно проверяет состояние вашего основного сервера, отправляя ему различные запросы (например, HTTP/HTTPS, TCP, ICMP/ping).
- **Обнаружение сбоя (Detection):** если в течение определённого периода несколько проверок подряд заканчиваются неудачей, сервер помечается как «недоступный» или «нездоровый».
- **Перенаправление (Redirection):** система автоматически обновляет DNS-записи (обычно типа **A** или **CNAME**), заменяя IP-адрес отказавшего сервера на адрес заранее настроенного резервного сервера.
- **Восстановление (Recovery):** после того как основной сервер вновь становится доступным и успешно проходит проверки, система может автоматически вернуть DNS-записи в исходное состояние.

> **Важно:** скорость применения этих изменений для конечных пользователей напрямую зависит от значения **TTL (Time to Live)** в ваших DNS-записях. Чем ниже TTL (например, 30–60 секунд), тем быстрее произойдёт переключение на резервный сервер.

## Активный-активный vs. Активный-пассивный

Этот паттерн может быть реализован в двух основных конфигурациях.

- **Активный-пассивный (Active-Passive)**
  - **Описание:** в обычном режиме весь трафик идёт на основной сервер (Primary). Резервный (Secondary) находится в режиме ожидания и не принимает запросы.
  - **Поведение при сбое:** при отказе основного сервера DNS-сервис начинает возвращать IP-адрес резервного сервера, который «становится активным».
- **Активный-активный (Active-Active)**
  - **Описание:** трафик распределяется между несколькими серверами, которые все являются активными (например, с помощью балансировщика нагрузки).
  - **Поведение при сбое:** если один из серверов выходит из строя, DNS-сервис просто перестаёт включать его IP-адрес в ответы на запросы, и трафик перераспределяется между оставшимися здоровыми серверами.

## Настройка и ключевые параметры

Настройка DNS failover обычно включает в себя:

- **Определение конечных точек:** указание IP-адресов или доменных имён основного и резервного серверов.
- **Настройка проверок здоровья:** определение типа проверки (HTTP, TCP и т. д.), частоты, таймаутов и критериев, по которым сервер считается «здоровым».
- **Настройка DNS-записей:** создание DNS-записи (например, A-записи для `www.example.com`) с политикой маршрутизации **Failover**.
- **Установка TTL:** выбор значения TTL, которое балансирует между скоростью переключения и нагрузкой на DNS-серверы.

## Преимущества и недостатки

**Преимущества:**

- **Простота и экономичность:** реализуется на уровне DNS без необходимости в специальном дорогостоящем оборудовании.
- **Глобальный охват:** эффективно для перенаправления трафика между серверами, расположенными в разных географических регионах.
- **Независимость от инфраструктуры:** может работать с серверами, размещёнными у разных провайдеров или в разных облаках (гибридные и мультиоблачные решения).

**Недостатки и ограничения:**

- **Задержка переключения (Lag):** основной недостаток. Из-за кэширования DNS время переключения может составлять от нескольких минут до часов.
- **Отсутствие «умной» балансировки:** DNS не учитывает загрузку сервера, и распределение трафика может быть неравномерным.
- **Задержки при отказе DNS-сервера:** клиент может ждать таймаута, если один из DNS-серверов не отвечает.

## Где используется

Этот подход широко применяется в различных сценариях для повышения отказоустойчивости:

- **Веб-сайты и приложения:** для обеспечения доступности при отказе сервера или дата-центра.
- **[[disaster-recovery-plan|Аварийное восстановление]] (Disaster Recovery):** как часть плана DR для переключения трафика между облачными регионами или между on-premise и облаком.
- **Глобальное распределение трафика ([[data-scaling|GSLB]]):** для направления пользователей к ближайшему или наиболее подходящему серверу, с функцией автоматического исключения неработающих узлов.

## Лучшие практики

- **Используйте несколько проверок здоровья (Health Checks):** комбинируйте различные типы проверок для более точной оценки состояния сервера.
- **Установите разумный TTL:** найдите баланс между скоростью переключения и нагрузкой. Для критичных сервисов можно установить TTL в 30–60 секунд.
- **Автоматизируйте процессы:** используйте инструменты провайдеров для автоматического переключения и, при необходимости, автоматического возврата на основной сервер.
- **Регулярно тестируйте:** периодически проводите учебные аварийные переключения, чтобы убедиться в работоспособности всей системы.
