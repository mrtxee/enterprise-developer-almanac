## Масштабирование приложения

Сервисы мультиконтейнерного приложения делятся на категории, влияющие на сложность масштабирования:

- Stateless service
- Stateful service

Для масштабирования нужен балансировщик нагрузки.

### Stateful vs Stateless service

**Stateful vs Stateless Application Scaling** — это фундаментальное различие, определяющее, как масштабировать приложение, насколько легко оно восстанавливается и насколько надёжно работает в распределённой среде.

| Характеристика | Stateless | Stateful |
| --- | --- | --- |
| Состояние (state) | Нет — всё хранится вне приложения (например, в БД) | Есть — приложение само управляет состоянием |
| Масштабирование | Очень просто: `replicas: 10` → Kubernetes делает всё | Сложное: нужно управлять данными, идентичностью, репликацией |
| Безопасность и отказоустойчивость | Высокая: любой экземпляр может заменить другой | Требует сложных механизмов (raft, zookeeper) |
| Примеры | REST API, веб-серверы, микросервисы | Базы данных, Kafka, etcd, Redis, ZooKeeper |

> Stateless масштабируется как клоны. Stateful — каждый экземпляр уникален.

#### Stateless Application

**Определение**
Stateless-приложение — это приложение, которое не хранит состояние между запросами.

Каждый запрос содержит все необходимые данные (например, токен, сессия в JWT) и не зависит от предыдущих.

**Пример: REST API**

```http
POST /api/orders
Authorization: Bearer <JWT>
Content-Type: application/json

{
  "productId": "123",
  "quantity": 2
}
```

Сервер ничего не запоминает: проверяет JWT → обрабатывает заказ → отвечает → забывает.

**Преимущества масштабирования stateless-приложений**

| Плюс | Объяснение |
| --- | --- |
| ✅ Легко масштабируется | Добавьте 100 реплик — все одинаковые |
| ✅ Нет привязки к инстансу | Любой сервер может обработать запрос |
| ✅ Балансировка проста | Round-robin, least connections — без разницы |
| ✅ Высокая доступность | Если один под падает — другие работают |
| ✅ Идеально для Kubernetes | `Deployment`, `ReplicaSet` — созданы для этого |
| ✅ Подходит для CI/CD | Можно делать rolling update, canary, blue-green |

**Масштабирование (Kubernetes)**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api-service
spec:
  replicas: 10   # 10 одинаковых подов
  selector:
    matchLabels:
      app: api
  template:
    metadata:
      labels:
        app: api
    spec:
      containers:
      - name: app
        image: myapp:v1.2.3
```

Все 10 подов полностью независимы: могут быть перезапущены, удалены, перемещены.

#### Stateful Application

**Определение**
Stateful-приложение — это приложение, которое хранит состояние на себе (в памяти или локальном хранилище) и не может быть просто заменено другим экземпляром.

**Примеры**
- Базы данных: PostgreSQL, MySQL
- Распределённые ключ-значения: etcd, Consul
- Message brokers: Kafka, RabbitMQ
- Кэши с persist: Redis (если использует RDB/AOF)
- Файловые серверы: NFS, Samba

**Особенности stateful-масштабирования**
Такие приложения масштабируют не напрямую, а через масштабирование базы данных, распределённое кеширование и разбиение на более независимые микросервисы, каждый из которых работает только над отдельными частями процесса.

| Проблема | Решение |
| --- | --- |
| ❌ Экземпляры не взаимозаменяемы | У каждого свой ID (`kafka-0`, `kafka-1`) |
| ❌ Нужна постоянная файловая система | `PersistentVolume` + `StorageClass` |
| ❌ Порядок запуска важен | `pod-0` должен стартовать первым |
| ❌ Сложный failover | Нужны механизмы согласования (Raft, Paxos) |
| ❌ Масштабирование медленнее | Нельзя просто добавить `replicas=5` |

> **Failover** (аварийное переключение) — передача функциональной нагрузки на резервный компонент компьютерной системы или сети (сервер, сетевое устройство, функциональный модуль и т. п.) в случае сбоя или нарушения функционирования основного компонента.

**Масштабирование Stateful-приложения (Kubernetes)**
Используется **StatefulSet**, а не `Deployment`.

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: kafka
spec:
  serviceName: kafka-headless
  replicas: 3
  selector:
    matchLabels:
      app: kafka
  template:
    metadata:
      labels:
        app: kafka
    spec:
      containers:
      - name: kafka
        image: confluentinc/cp-kafka:7.6.0
        volumeMounts:
        - name: data
          mountPath: /var/lib/kafka
  volumeClaimTemplates:
  - metadata:
      name: data
    spec:
      accessModes: ["ReadWriteOnce"]
      storageClassName: fast-ssd
      resources:
        requests:
          storage: 100Gi
```

**Что даёт StatefulSet**
- ✅ Стабильные сетевые идентификаторы: `kafka-0`, `kafka-1`, `kafka-2`
- ✅ Постоянные тома: `data-kafka-0`, `data-kafka-1`
- ✅ Упорядоченный деплой и обновление: `kafka-0` → `kafka-1` → `kafka-2`
- ✅ Оркестрация с помощью headless-сервиса: `kafka.default.svc.cluster.local`

> **Headless Service** — тип сервиса в Kubernetes, который не использует кластерный IP-адрес для маршрутизации трафика. Вместо этого он напрямую возвращает IP-адреса подов, связанных с этим сервисом.

#### Сравнение Stateless и Stateful масштабирования

| Критерий | Stateless | Stateful |
| --- | --- | --- |
| Где хранится состояние | В БД, Redis, JWT, внешнем сервисе | На самом приложении |
| Масштабируемость | ✅ Отличная: `replicas: 100` | ⚠️ Сложная: нужно управлять данными |
| Failover | ✅ Легко — балансировщик перенаправит | ❌ Сложно — нужно выбрать новый лидер |
| Обновления | ✅ Rolling Update, Canary | ❌ Осторожно — порядок важен |
| Типичные технологии | Nginx, Spring Boot, Express.js | Kafka, etcd, [[mongo-db]], Redis |
| Восстановление после сбоя | ✅ Автоматическое | ❌ Может потребовать ручного вмешательства |
| Зависимость от диска | ❌ Нет | ✅ Да — `PersistentVolume` |
| Kubernetes-объект | `Deployment` | `StatefulSet` |
| Балансировка нагрузки | ✅ Round-robin | ❌ Только клиент знает, кто лидер |
| Idempotency | Не обязательно | Часто требуется |
| Пример использования | API Gateway, фронтенд | Kafka, базы данных |

**Когда использовать каждый тип**

| Приложение | Тип | Почему |
| --- | --- | --- |
| Web API | Stateless | Легко масштабируется, не зависит от сессии |
| Фронтенд (React, Vue) | Stateless | UI — только отображение |
| Аутентификация | Stateless | JWT — нет состояния на сервере |
| Kafka | Stateful | Хранит сообщения, есть лидер, реплики |
| etcd / Consul | Stateful | Хранит конфиги, координация через Raft |
| PostgreSQL | Stateful | Master-slave, WAL, репликация |
| Redis (если с AOF/RDB) | Stateful | Но можно использовать как stateless (кеширование) |
| Elasticsearch | Stateful | Индексы, шарды, мастер-узел |
| Session-based web app | Stateful | Сессия хранится на сервере → нельзя менять поды |

**Современная практика: сделать stateful-сервис stateless**
Часто используют гибридный подход — например, Kafka + внешнее состояние:

- **Kafka** — stateful (сообщения, offset'ы)
- **Потребитель** — stateless:
  - offset хранится в `__consumer_offsets` (внутри Kafka)
  - или в `Redis` (внешний state)

Это позволяет масштабировать потребителей, даже если сам Kafka — stateful.

**Советы по проектированию**

| Рекомендация | Объяснение |
| --- | --- |
| ✅ Делайте бизнес-логику stateless | Так её проще масштабировать |
| ✅ Храните состояние во внешних системах | Redis, PostgreSQL, S3 |
| ✅ Используйте JWT вместо сессий | Чтобы не зависеть от сервера |
| ✅ Не храните данные в памяти пода | Они потеряются при перезапуске |
| ✅ Stateful — только когда необходимо | Базы данных, message brokers, consensus-системы |
| ✅ Stateless — для всего остального | API, UI, ETL, event processing |

**Ключевое отличие**

|  | Stateless | Stateful |
| --- | --- | --- |
| Состояние | ❌ Нет | ✅ Да |
| Масштабирование | ✅ Простое (`+N pods`) | ⚠️ Сложное (нужны PV, порядок, identity) |
| Замена пода | ✅ Без последствий | ❌ Может сломать кластер |
| Идеальный кандидат | HTTP API, микросервисы | Kafka, etcd, базы данных |

> Stateless — выбор, когда возможность есть. Stateful — вынужденный компромисс, когда состояние — часть системы.

> **Persistent Volume (PV)** в контексте stateful-масштабирования в Kubernetes — ресурс хранения, который обеспечивает постоянное хранение данных для stateful-приложений. PV принадлежит кластеру и существует независимо от подов.

> «The fastest and cheapest resource is the one that doesn't exist.» — Google Site Reliability Engineering.

> Stateless-поды: их можно убить, создать — и ничего не изменится.

Stateless-поды делают систему гибкой; там, где нужно состояние, выбираются специальные инструменты: Kafka, etcd, CockroachDB, YugabyteDB.

> Stateless — это свобода. Stateful — это ответственность.

### Балансировщик нагрузки

Сервис балансировки нагрузки — это инструмент для распределения запросов между серверами внутри кластера.

Балансировщики нагрузки по устройству:

1. Программные
2. Аппаратные
3. Виртуальные

По функциям различают балансировщики уровня 4 и 7 модели [[open-systems-interconnection]].

**Уровень 4 (транспортный)**
Балансировщик быстрее обрабатывает запросы, поскольку не анализирует содержимое пакетов и работает с адресами серверов. Применяется, например, для балансировки трафика между ЦОДами по нагрузке сети.

**Уровень 7 (приложений)**
Балансировщик маршрутизирует контент с учётом содержимого и позволяет принимать сложные решения о маршрутизации, используя данные, специфические для конкретного приложения. Работает медленнее. Так работают кластеры (Redis, Mongo, микросервисы) — они применяют алгоритмы, чтобы выбрать экземпляр сервиса, который обработает запрос.

**Алгоритмы распределения нагрузки**

| Алгоритм | Механизм отправки запросов к серверам | Когда использовать |
| --- | --- | --- |
| Round Robin | В порядке очереди | В базовом варианте, если нет специальных требований |
| IP Hash, или Sticky sessions | На тот же сервер, откуда пришёл запрос, по хэшу IP-адреса пользователя | Чаще всего в stateful-приложениях |
| Least Connection | На наименее загруженный сервер | Микросервисная архитектура |
| Least Response Time | На сервер с наименьшим средним временем обработки ответа | Микросервисная архитектура |
| Least Bandwidth | На сервер с наименьшим трафиком | Микросервисная архитектура |

### [[Leaderless]]

В распределённых системах master-slave и multi-master наличие мастера и его выбор при сбое становится тонким местом. Leaderless-системы — антитеза этой проблеме.

Главное преимущество архитектуры без ведущего узла — высокая доступность и устойчивость к сбоям.

**Архитектура без ведущего узла на примере Apache Cassandra**

В треугольнике CAP для Apache Cassandra выбираются свойства Availability + Partition Tolerance вместо строгой Consistency.

Разные реплики принимают операции независимо, из-за чего возникает риск, что часть узлов успеет обновить данные, а часть — нет. Поэтому консистентность данных становится настраиваемым параметром. Разработчик сам выбирает, сколько узлов должны подтвердить операцию, чтобы она считалась успешной. Именно так достигается баланс между консистентностью и доступностью.

Apache Cassandra — яркий пример базы данных с репликацией без лидера. В кластере Cassandra все узлы равноправны и могут выступать координаторами запросов.

Например, если из трёх реплик запись была успешно применена на двух, пока третья оставалась недоступной, узел-координатор сохранит для неё подсказку (hint) и передаст обновление, когда узел вернётся в строй. Такой подход позволяет не отвергать запросы при кратковременных проблемах с узлами.

Даже кворум не даёт абсолютных гарантий консистентности, а параметры W и R лишь предоставляют возможность влиять на вероятность чтения устаревших значений и опираются на eventual consistency.

Apache Cassandra позволяет выбрать оптимальный способ восстановления консистентности:

1. Hinted Handoff
2. Read Repair
3. Anti-Entropy Repair
