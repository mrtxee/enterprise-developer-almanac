## Consistent Hashing

**Consistent Hashing (согласованное хеширование)** — это алгоритм распределения данных по узлам (серверам, кэшам, шардам), который **минимизирует количество перемещаемых ключей** при добавлении или удалении узлов.

Классическое хеширование по формуле `node = hash(key) % N` ломается при изменении числа узлов: почти все ключи пересчитываются. Consistent Hashing решает эту проблему за счёт **специальной структуры — хеш-кольца**.

## Основная идея

> **Consistent Hashing** распределяет ключи по **кольцу** (от 0 до $2^{32}-1$). Каждый узел тоже хешируется в кольцо, и каждый ключ сопоставляется первому узлу **по часовой стрелке** от его позиции.

- Кольцо — воображаемый круг с диапазоном значений хеш-функции.
- Узлы (серверы) размещаются на кольце по значению их хеша.
- Ключ попадает на первый узел, встреченный при движении по часовой стрелке.

**Основное преимущество**

- При изменении состава узлов перераспределяются **только соседние** ключи.
- Не нужно пересчитывать хеш для всех данных — только для части.

## Как это работает

Кольцо представляется как диапазон значений хеша от $0$ до $2^{32}-1$:

- Берется хеш-функция, например `SHA-256` или `MurmurHash`.
- Каждый узел хешируется: `hash("server-1")`, `hash("server-2")`, ...
- Каждый ключ хешируется: `hash("my-key")`.
- Ключ попадает на первый узел, идя по кругу по часовой стрелке.
- Если дошли до конца кольца — возвращаемся к началу (кольцо замкнутое).

Схематично:

- Кольцо: позиции узлов `Node A`, `Node B`, `Node C`
- Ключ `K1` между `Node A` и `Node B` → принадлежит `Node B`
- Ключ `K2` между `Node B` и `Node C` → принадлежит `Node C`
- Ключ `K3` между `Node C` и `Node A` (замыкание) → принадлежит `Node A`

## Пример на пальцах

Допустим, в системе 3 сервера:

1. `hash("server-1") = 10`, `hash("server-2") = 50`, `hash("server-3") = 90`
2. Кольцо: `0 → 10 → 50 → 90 → 0`
3. Ключи: `hash("a") = 20`, `hash("b") = 60`, `hash("c") = 95`
4. Распределение:
   - `"a"` ($20$) идёт по часовой стрелке → `server-2` ($50$)
   - `"b"` ($60$) идёт по часовой стрелке → `server-3` ($90$)
   - `"c"` ($95$) идёт по часовой стрелке → до конца кольца, замыкание → `server-1` ($10$)

## Зачем нужен

| Проблема без Consistent Hashing | Решение с Consistent Hashing |
|--------------------------------|------------------------------|
| Добавление узла → все ключи пересчитываются (`N` меняется) | Пересчитываются только соседние ключи |
| Удаление узла → вся система «мигрирует» | Перераспределяется только часть ключей |
| Маcштабирование кэша дорого | Пересчёт минимален |
| Нет балансировки нагрузки | Ключи распределяются равномерно по кольцу |

**Классическое хеширование** `node = hash(key) % N`:

| Случай | Кол-во перемещаемых ключей |
|--------|---------------------------|
| Добавление 1 узла (из $N$ в $N+1$) | Почти все ключи ($N/(N+1)$) |
| Удаление 1 узла (из $N$ в $N-1$) | Почти все ключи ($(N-1)/N$) |

**Consistent Hashing**:

| Случай | Кол-во перемещаемых ключей |
|--------|---------------------------|
| Добавление 1 узла | В среднем $K / (N+1)$ ключей |
| Удаление 1 узла | В среднем $K / N$ ключей |

## Проблема неравномерности

Ключи могут ложиться неравномерно, потому что позиции узлов на кольце случайны.

Допустим, узлы оказались близко друг к другу:

- `Node A` на позиции $10$
- `Node B` на позиции $12$

Тогда почти все ключи попадут на `Node A`. Это происходит, потому что сектор от `Node B` до `Node A` (через замыкание) мал, а реальные ключи распределяются примерно равномерно.

## Решение: виртуальные узлы

**Виртуальные узлы (Virtual Nodes)** — фиксируют проблему неравномерности. Каждый физический сервер представляется **несколькими виртуальными точками** на кольце.

- `server-1` → `server-1#1`, `server-1#2`, `server-1#3`, ...
- `server-2` → `server-2#1`, `server-2#2`, `server-2#3`, ...

**Результат**

- Кольцо покрыто виртуальными узлами более плотно.
- Ключи распределяются почти равномерно.
- При удалении узла снимаются все его виртуальные точки.

Именно так реализовано в библиотеках `Ketama` (memcached), `consistent` (Python), `ring` (Go) и в хранилищах Cassanadra, Riak, DynamoDB.

> **Примечание:** некоторые алгоритмы используют не «виртуальные узлы», а смещение от бaзового хеша узла (например, `hash(server-i)` для кратности). Суть та же — больше реплик узла на кольце.

## Сравнение подходов

| Параметр | Обычное хеширование (`% N`) | Consistent Hashing |
|---------|-----------------------------|---------------------|
| Пересчёт при изменении $N$ | Почти все ключи | Небольшая часть |
| Требует знать число узлов заранее | Да | Нет |
| Балансировка | Плохая, зависит от порядка | Хорошая (с Virtual Nodes) |
| Удаление узла | Большинство ключей перераспределяется | Часть ключей |
| Сложность | O(1) | O(log N) (списание по бинарному поиску по кольцу) |

## Пример

```python
import hashlib
import bisect

class ConsistentHash:
    def __init__(self, nodes):
        self.ring = []
        self.nodes_map = {}
        for node in nodes:
            key = int(hashlib.sha256(node.encode()).hexdigest()[:8], 16)
            self.ring.append(key)
            self.nodes_map[key] = node
        self.ring.sort()

    def get_node(self, key):
        h = int(hashlib.sha256(key.encode()).hexdigest()[:8], 16)
        idx = bisect.bisect_right(self.ring, h)
        if idx == len(self.ring):
            idx = 0
        return self.nodes_map[self.ring[idx]]

ch = ConsistentHash(["server-1", "server-2", "server-3"])
print(ch.get_node("some-key"))
```

## Когда использовать

| Ситуация | Использовать? |
|----------|---------------|
| Распределённый кэш (Memcached, Redis Cluster) | ✅ Да — уже встроено |
| [[sharding|Шардирование]] базы данных | ✅ Да |
| Распределённое хранилище (Cassandra, DynamoDB, Riak) | ✅ Да — основа |
| [[CDN|CDN]] и балансировка | ✅ Да |
| Единичный сервер, число узлов фиксировано | Не обязательно |
| Микросервисы без распределённых данных | Не обязательно |

## Особенности

- ✅ Минимальное перемещение ключей при добавлении/удалении узлов.
- ✅ Равномерное распределение при использовании виртуальных узлов.
- ✅ Подходит для динамических кластеров (автоскейлинг).
- ✅ Позволяет эластично менять состав узлов.
- ❌ Сложность реализации выше, чем у `hash % N`.
- ❌ При удалении узла его ключи переходят соседям — может создаваться «горячий» узел.
- ❌ Требует настройки количества виртуальных узлов.

## Итог

Consistent Hashing — стандартное решение для **динамических распределённых систем**: кэши, шардирование, хранилища. Основной выигрыш — **малое число перемещаемых ключей** при изменении состава узлов, а проблема неравномерности решается виртуальными узлами.
