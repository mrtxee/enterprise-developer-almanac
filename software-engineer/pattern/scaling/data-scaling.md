## Масштабирование (scaling)

**Масштабирование решения** — это адаптация программного обеспечения к увеличению нагрузки или требований с сохранением высокой производительности и доступности.

Масштабирование нужно, когда приложение сталкивается с резким увеличением пользовательской базы или трафика, что приводит к перегрузке текущей инфраструктуры.

Горизонтальное масштабирование предпочтительнее для обработки больших объёмов данных и высоких нагрузок. Вертикальное масштабирование эффективнее для улучшения производительности отдельных операций (например, по выборке данных из нескольких десятков таблиц).

**Облачное (гибридное) масштабирование** — использование облачных сервисов для масштабирования IT-решений: быстрое масштабирование в зависимости от потребностей, снижение затрат на инфраструктуру и обслуживание. По факту это комбинация вертикального и горизонтального масштабирования за счёт ресурсов облака.

**Автоматическое масштабирование (Auto-Scaling)** — динамическое добавление или удаление ресурсов в зависимости от текущей нагрузки.

### Профили нагрузки

Чтобы эффективно продумать и реализовать стратегию масштабирования, необходимо понимать профиль нагрузки — насколько, когда и как долго происходит недостаток ресурсов. Профили выделяются по критериям: статическая / динамическая нагрузка, а у динамической — регулярность и предсказуемость.

Примеры профилей нагрузки:

- **Статический** — каждую ночь в 00:00 количество активных пользователей менее 100, а загрузка ЦП на серверах приложений снижается на 90% на всех узлах.
- **Динамический, регулярный и предсказуемый** — каждый понедельник утром в систему 1С входит 1000 сотрудников из нескольких регионов.
- **Динамический, нерегулярный и предсказуемый** — запуск продукта в первый день месяца, есть исторические данные о том, как увеличивается трафик в таких ситуациях.
- **Динамический, нерегулярный и непредсказуемый** — крупномасштабное событие вызывает всплеск спроса на продукт, например распродажа остатков.

### Вертикальное масштабирование

С вертикальным масштабированием всё просто: оно требует просто добавления ресурсов.

### Горизонтальное масштабирование

Методы горизонтального масштабирования:

1. Репликация.
2. Шардирование (+ репликация).
3. Кеширование.
4. Географически распределённые ресурсы.
5. Разделение данных по специализированным базам.
6. Auto-scaling.

#### Репликация

**Репликация** ([[replication|replication]]) — создание и поддержание копий базы данных на нескольких серверах для обеспечения их согласованности и доступности.

Существует два основных типа репликации:

- master-slave
- multi-master

#### Шардирование (партиционирование)

**Шардирование** ([[sharding|sharding]]) — метод разделения данных на отдельные фрагменты (шарды) для повышения производительности и надёжности баз данных. Иногда шардирование называют партиционированием в целом, но на самом деле шардирование — частный случай партиционирования.

**Вертикальное партиционирование** — разделение одной широкой таблицы на несколько более узких, связанных через внешние ключи. Делается в первую очередь при проблемах с производительностью: поможет оптимизировать запросы, но не решит проблему большого количества данных.

**Горизонтальное партиционирование (шардирование, сегментирование)** — распределение данных по нескольким базам, чаще всего на отдельных физических серверах. Каждый сегмент (шард) включает одни и те же столбцы, но разные строки информации.

Пример:

- шард-1 в таблице users содержит пользователей с id ∈ \[1..50\]
- шард-2 в таблице users содержит пользователей с id ∈ \[51..99\]

Методы горизонтального шардирования:

1. **Хэшированное шардирование** (key based sharding) — разделение данных на шарды на основе хэш-функции: она принимает входные данные и возвращает хэш-значение, которое определяет шард для каждой записи.
2. **Диапазонное шардирование** (range based sharding) — разделение на шарды на основе диапазона значений (chunk). Значения разделяются не с помощью функции, а по ключу или другим атрибутам.
3. **Динамическое шардирование** (dynamic sharding) — автоматическое масштабирование хранилища в зависимости от текущей производительности и объёма данных. Очень гибкое, но требует сложной балансировки нагрузки, надёжного мониторинга и тщательно продуманной архитектуры базы данных. Обычно использует внешний поисковый сервис для определения местоположения записей.
4. **Геошардинг** (geo sharding) — хранение в разных сегментах информации, относящейся к определённой географической зоне.

Способы реализации шардирования:

- **Средствами базы данных** — MongoDB, [[elastic-search|Elasticsearch]], ClickHouse и другие автоматически распределяют данные между своими экземплярами. Для этого достаточно настроить конфигурацию. Самый простой способ.
- **С использованием надстроек к базе данных** — сторонние утилиты, например Citus для [[PostgreSQL|PostgreSQL]]. Есть риск потери данных и снижения производительности.
- **С применением клиентских средств** — экземпляры базы данных не знают о существовании друг друга, а шардированием управляет приложение.

**Особенности шардирования**

- ✅ Преодоление технических ограничений.
- ✅ Повышение надёжности.
- ✅ Ускорение доступа к данным с простыми запросами.
- ❌ Сложность реализации.
- ❌ Риск снижения эффективности разработки.
- ❌ Неравномерность загрузки серверов.
- ❌ Снижение скорости обработки сложных запросов.

#### Кеширование

**Кеширование** ([[software-engineer/pattern/scaling/caching|caching]]) — временное хранение данных в памяти, чтобы сократить время доступа. Снижает нагрузку при большом количестве операций чтения одинаковых данных.

Принцип работы кеширования, или паттерна Cache Aside:

1. Приложение проверяет наличие нужных данных в кеше.
2. Если данных там нет, запрос направляется в хранилище.
3. На обратном пути данные передаются в кеш, а запрос возвращается пользователю.

Сложность: данными в кеше нужно управлять, чтобы поддерживать их согласованность.

**Распределённый кеш** — система, в которой данные хранятся на нескольких узлах кластера и в нескольких кластерах в разных центрах обработки данных по всему миру. Система распределённого кеша объединяет оперативную память нескольких сетевых компьютеров в единое хранилище данных, которое используется как кеш для быстрого доступа к данным.

**Redis Cluster**

Redis — популярный и стабильный сервис для кеширования. Клиенты выполняют операции чтения и записи с узлами M1, M2, M3 и только чтения с S1, S2, S3. Между ведущими и подчинёнными узлами выполняется репликация данных. Для определения общего состояния кластера используется протокол gossip.

#### Географически распределённые ресурсы

В системах с глобальной аудиторией данные могут храниться в географически распределённых центрах обработки данных, чтобы обеспечить минимальные задержки доступа для пользователей из разных регионов.

#### Использование специализированных баз данных

В некоторых случаях целесообразно использовать разные базы данных для разных типов данных: реляционные — для транзакционных данных, NoSQL — для больших объёмов неструктурированных данных.
