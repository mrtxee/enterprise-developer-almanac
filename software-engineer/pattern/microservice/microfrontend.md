# микрофронтенд

Микрофронтенды распространяют концепцию [[microservice|микросервисов]] на фронтенд

> [!definition] **Микрофронтенд** — это концепция, которая распространяет принципы архитектуры микросервисов на мир фронтенда.

**Пример.** Во время акции «Чёрная пятница» выросла нагрузка на каталог товаров и системы оформления заказа. Чтобы справиться с потоком заказов пришлось масштабировать весь фронтенд. При этом нагрузка на другие разделы — например, на управление профилем пользователя — не изменилась.    

Все эти проблемы говорят об одном: монолит больше не отвечает запросам проекта. Чтобы устранить источник проблем, нужно разбить монолитный фронтенд на небольшие автономные части — микрофронтенды.

Логика такая:
- Каждый микрофронтенд отвечает за отдельную функцию или область приложения. Например, за функцию поиска или процесс оформления заказа.
- Микрофронтенды объединяют в целостный пользовательский опыт. Интеграцию можно проводить с помощью разных технологий. Например, через веб-компоненты, JavaScript-фреймворки или даже [[SSI]] (SSI)

Микрофронтенды не зависят друг от друга и могут использовать разные технологии. Например, команда каталога выбирает React из-за его богатой экосистемы, а команда личного кабинета использует Vue из-за его простоты и лёгкой интеграции.

**Основные преимущества микрофронтендов**
1. Повышение организационной гибкости
2. Можно выбрать несколько технологических стеков
3. Упрощение управления кодом
	* В архитектуре микрофронтенда каждая команда управляет только тем кодом, который относится к её функциональности.
4. Более управляемое масштабирование
	* Каждый микрофронтенд можно развернуть независимо от остальных. Это делает масштабируемость более управляемой. Команды могут масштабировать свои сервисы в зависимости от спроса на конкретные функции. Масштабировать всё приложение теперь не обязательно.
	* Например, во время «Чёрной пятницы» онлайн-магазин замечает повышение трафика на страницах товаров. Команда увеличит здесь ресурсы, а другие части приложения масштабировать не будет.
5. Повышение отказоустойчивости
6. Ускорение времени выхода на рынок

Архитектура микрофронтенда состоит из четырёх компонентов: 
* модули микрофронтенда, 
* слой композиции, 
* маршрутизация 
* коммуникационный слой

Чтобы микрофронтенды работали как единый пользовательский интерфейс, нужно настроить коммуникацию между ними. Для управления коммуникацию есть три стратегии: 
- взаимодействие на основе API
- библиотеки глобального состояния
- паттерн [[Publish-Subscribe|Pub/Sub]].

В архитектуре микрофронтенда четыре ключевых компонента. К ним относятся:

1. **Модули микрофронтенда.** Это основные элементы архитектуры. Каждый модуль — это определённая бизнес-область или функциональность. Модули разрабатывают, тестируют и развёртывают независимо друг от друга.
2. **Слой композиции.** Он отвечает за сборку различных модулей микрофронтенда в целостное приложение, а также управляет потоком данных и взаимодействием между клиентом и сервером. Компоновка модулей может происходить на стороне сервера, на стороне клиента или с помощью гибридного подхода. Выбор подхода зависит от потребностей и ограничений приложения.
3. **Маршрутизация.** При работе с микрофронтендами важно выбрать эффективные механизмы маршрутизации. Надо гарантировать, что запросы будут направляться к нужному микрофронтенду. Это поможет сохранить модульность приложения и при этом обеспечить плавную навигацию для пользователей. Если маршрутизация продумана плохо, микрофронтенды будут зависеть друг от друга. Как итог — все преимущества архитектурного стиля сойдут на нет.
4. **Коммуникационный слой.** Этот слой управляет взаимодействием между микрофронтендами и остальной инфраструктурой приложения. Реализовать коммуникацию можно через API, шины сообщений или собственные системы событий.

Главная сложность перехода на архитектуру микрофронтэндов – метод композиции микрофронтентов. Их всего два — `build time` и `run time`.

# композиция микрофронтендов

> [!info] композиция микрофронтендов
> Композиция микрофронтендов — это процесс сборки нескольких микрофронтендов в единое целое.

Есть три метода композиции:
- серверная,
	- все микрофронтенды собирают на сервере. Вся функциональность находится в бэкенде. Он решает, какой микрофронтенд собрать и загрузить. Сервер будет определять, к какому URL направить запрос.
- клиентская,
	- браузер отвечает за динамическую загрузку каждого микрофронтенда во время выполнения.
	- **Инструменты и техники.** В основном используют JavaScript-фреймворки, которые упрощают интеграцию на стороне клиента. Например, Single SPA или Module Federation. Ещё такой подход можно реализовать с помощью специальных библиотек для фреймворков. Например, `lazy` и `Suspense` в React или динамического импорта в Vue и Angular. Третий путь — это Iframes или веб-компоненты (Web Components).
- гибридная
	- При гибридной композиции вы получаете преимущества двух предыдущих вариантов композиции. Это возможно благодаря паттерну Backend for Frontend (BFF). При таком подходе каждый микрофронтенд имеет свой выделенный бэкенд (BFF).
	- BFF обрабатывает все данные, взаимодействует с API и при необходимости предоставляет клиенту предварительно отрендеренный HTML. Это полезно для начальной загрузки страниц и SEO. Сервер передаёт клиенту полностью сформированную страницу.
	- После первоначальной загрузки за дело берётся клиентская часть. Она берёт на себя динамические взаимодействия, которые необязательно требуют обращения к серверу. В этом случае фреймворки и JavaScript-библиотеки управляют обновлениями DOM, состоянием клиента и рендерингом на основе взаимодействия с пользователем.

build time компоновка бывает:
* серверная компоновка
* клиентская
* гибридная
run time компоновка
* серверная компоновка
## композиция vs компоновка микрофронтендов

Композиция отличается от компоновки микрофронтендов уровнем проектирования. Два взаимосвязанных, но разных уровня сборки микрофронтенд-приложения. Композиция относится к архитектурному уровню, а компоновка к техническому
* **Композиция** `Composition` — это **архитектурное проектирование** того, как микрофронтенды взаимодействуют и сочетаются друг с другом.
* **Компоновка** `Assembly` — это **технический процесс сборки** компонентов на стороне клиента или сервера.  

## [[build-time-compositon|build-time компоновка]]

Вы помещаете все компоненты в контейнер так же, как библиотеки, которые вы устанавливаете из npm.

Этот подход мало отличается от монолитного фреймворка. А ещё у него есть ряд недостатков:
- Нужно синхронизировать разные версии библиотек, иначе возникнут проблемы со сборкой.
- Сложно использовать разные технологии.
- Конечный бандл получится большим, ведь он содержит все зависимости.
- Если появятся изменения в зависимостях, вам придётся развёртывать пакет заново.
- Между контейнером и микрофронтендами будет тесная связь.

## run-time компоновка

Вы объединяете микрофронтенды в единый интерфейс во время исполнения кода на стороне пользователя.

При этом подходе нужно продумать управление маршрутизацией, разделением состояний и интеграцией компонентов.

# коммуникация микрофронтэндов

Для того, чтобы управлять состоянием и коммуникациями между микрофронтендами можно использовать три стратегии управления состоянием:
- взаимодействие на основе API
	- Rest
- паттерн Pub/Sub,
	- [[Publish-Subscribe]], EDA
- библиотека глобального состояния
	- global state, shared state
	- eg Redux, MobX и Context API в React

# проектирование микрофронтендов

Чтобы получить максимум преимуществ от архитектуры микрофронтендов, можно использовать три **стратегии проектирования**:
- **вертикальная нарезка** — выстраивайте микрофронтенды вокруг бизнес-функций или пользовательских путей. Можно использовать [[Domain-Driven Development]] модель декомпозиции 
- **автономность команд** — разрешите командам выбрать технологический стек под свои задачи.
- **изоляция микрофронтендов** — включайте в пакет развёртывания каждого микрофронтенда все его зависимости.
