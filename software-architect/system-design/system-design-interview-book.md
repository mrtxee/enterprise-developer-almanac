## 🔑 Четырёхшаговый фреймворк для решения задач

1. **Уточнение требований** — задавайте вопросы, чтобы сузить область задачи, понять функциональные и нефункциональные требования (масштаб, задержки, доступность) [[1]].
2. **Высокоуровневый дизайн** — предложите архитектуру из основных компонентов (клиент, API, БД, кэш, балансировщик) и согласуйте её с интервьюером [[3]].
3. **Детализация** — углубитесь в ключевые компоненты: шардирование, кэширование, репликация, обработка сбоев.
4. **Итог и улучшения** — резюмируйте решение, обсудите компромиссы и возможные оптимизации.

> 💡 Книга подчёркивает: не прыгайте сразу в детали — сначала договоритесь о границах задачи [[6]].

## ⚙️ Ключевые технические концепции

### 1. **Consistent Hashing**
Решает проблему перераспределения данных при добавлении/удалении серверов. Использует «кольцо хешей» и виртуальные узлы для равномерного распределения [[6]].

### 2. **Rate Limiting**
Защита от перегрузки и DoS-атак. Алгоритмы:
- Token Bucket
- Fixed/Sliding Window
- Хранение состояния в Redis для скорости [[4]]

### 3. **Генерация уникальных ID**
Проблема: автоинкремент не работает в распределённой системе. Решение: **Snowflake**-подобные алгоритмы (таймстемп + машина + последовательность) [[7]].

### 4. **CAP-теорема и согласованность**
При сетевом разделении выбор между:
- **CP**: согласованность ценой доступности
- **AP**: доступность ценой согласованности (eventual consistency)
Механизмы: векторные часы, кворумы, меркловы деревья [[6]]

### 5. **Оценки «на салфетке» (Back-of-envelope)**
Умение быстро прикинуть:
- Пиковый RPS: `DAU × запросы-пользователя / 86400`
- Хранилище: `размер_объекта × кол-во × срок_хранения`
- Пропускную способность сети [[2]]

> 📊 Важно ориентироваться на **пиковые**, а не средние значения [[3]].

## 🎯 Принципы, которые повторяются во всех решениях

1. **Избегайте единой точки отказа** — репликация, балансировка, health checks.
2. **Stateless-сервисы** — упрощают горизонтальное масштабирование.
3. **Асинхронность** — очереди развязывают компоненты и сглаживают пики.
4. **Кэшируйте всё, что можно** — но продумывайте стратегию инвалидации.
5. **Мониторинг и метрики** — без observability нельзя управлять сложной системой.
6. **Компромиссы важнее «идеального» решения** — обсуждайте trade-offs: сложность vs производительность, consistency vs latency.

> 🔄 Архитектура эволюционирует: начинайте с простого (один сервер), затем добавляйте компоненты по мере роста требований [[6]].

## 💡 Практические советы для собеседований

- **Не изобретайте велосипеды**: говорите «используем CDN/Redis/Kafka», а не проектируйте их с нуля [[3]].
- **Рисуйте диаграммы**: визуализация потока данных — основной язык коммуникации.
- **Обсуждайте edge cases**: что при сбое БД? при всплеске трафика? при конфликте данных?
- **Говорите вслух**: интервью оценивает не только решение, но и ход мысли, коммуникацию.
