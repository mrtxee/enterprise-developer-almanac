## Cassandra

**Cassandra** (NoSQL, wide-column) vs **PostgreSQL** (реляционная SQL) — принципиально разные архитектуры.

| Критерий | Cassandra | PostgreSQL |
|----------|-----------|------------|
| **Модель данных** | Широкие столбцы (колоночная семья) | Таблицы со строгой схемой (реляционная) |
| **Язык запросов** | CQL (Cassandra Query Language) | SQL (полноценный) |
| **ACID** | Нет (BASE, eventual consistency) | ✅ Полная ACID |
| **Транзакции** | Нет (только lightweight transactions, Paxos) | ✅ Полноценные транзакции, изоляция |
| **JOIN** | ❌ (не поддерживаются) | ✅ Сложные JOIN, подзапросы, CTE |
| **Индексы** | Ограниченные (secondary indexes — медленные) | Полноценные (B-tree, GIN, GiST, hash) |
| **Масштабирование** | Горизонтальное (masterless, легко добавить узлы) | Вертикальное (или шардирование вручную, сложно) |
| **Согласованность** | Настраиваемая (ONE, QUORUM, ALL) | Строгая (по умолчанию) |
| **Восстановление при сбоях** | Автоматическое (hinted handoff, repair) | Требует ручного вмешательства (репликация, failover) |
| **Нагрузка** | Высокая запись (write-heavy), большие объёмы | Смешанная, сложные чтения (read-heavy, аналитика) |
| **Схема** | Гибкая (динамические столбцы) | Строгая (миграции) |
| **Использование в Spring** | Spring Data Cassandra | Spring Data JPA / JDBC |
| **Типичный сценарий** | Логи, сенсорные данные, IoT, временные ряды, рекомендации | Бизнес-приложения, CRM, ERP, аналитика, OLTP |

**Когда выбрать Cassandra:**
- Огромные объёмы данных (> ТБ)
- Высокая нагрузка на запись (тысячи/миллионы записей/сек)
- Горизонтальное масштабирование в нескольких дата-центрах
- Отказоустойчивость выше консистентности
- Не нужны сложные запросы, JOIN, транзакции

**Когда выбрать PostgreSQL:**
- Нужны ACID и транзакции
- Сложные запросы, JOIN, аналитика
- Небольшой/средний объём данных (< 10-20 ТБ)
- Строгая схема и целостность данных
- Команда знает SQL

**Итог:** **Cassandra — AP** (доступность + устойчивость к разделению), **PostgreSQL — CA** (консистентность + доступность) по CAP-теореме. Выбор — компромисс между гибкостью схемы/масштабированием и строгой консистентностью/сложными запросами.



## Wide-column

**Wide-column** — модель хранения данных, где каждая строка может содержать **произвольное количество столбцов**, объединённых в **колоночные семьи** (column families). Это не реляционная таблица, а **мульти-измеряемый ассоциативный массив**.

---

### Структура

**Реляционная модель (строгая):**
```
| id | name | age | email |
|----|------|-----|-------|
| 1  | John | 30  | j@e.m |
| 2  | Jane | 25  | NULL  |  ← пустая ячейка (NULL)
```

**Wide-column модель (гибкая):**
```
Row Key: user_1
  → "profile": { name: "John", age: 30, email: "j@e.m" }
  → "preferences": { lang: "en", theme: "dark" }

Row Key: user_2
  → "profile": { name: "Jane", age: 25 }          ← нет email, добавила свои
  → "preferences": { lang: "ru" }                 ← нет theme, только lang
```

**Ключевые понятия:**

| Термин | Описание | Пример |
|--------|----------|--------|
| **Row Key** | Уникальный идентификатор строки (первичный ключ) | `user_1` |
| **Column Family** | Группа логически связанных столбцов (аналог таблицы) | `profile`, `preferences` |
| **Column** | Пара (имя → значение) внутри семьи | `name: "John"` |
| **Cell** | Пересечение строки, семьи и столбца | `user_1:profile:name = "John"` |

---

### Сравнение моделей

| Характеристика | Реляционная (SQL) | Wide-column (NoSQL) |
|----------------|-------------------|---------------------|
| **Схема** | Фиксированная (каждая строка одинаковые столбцы) | Гибкая (каждая строка свои столбцы) |
| **NULL** | Есть (тратит место) | Нет (просто отсутствует) |
| **Динамичность** | Требует ALTER TABLE | Можно добавить новый столбец в любой строке |
| **Запросы** | SQL, JOIN, агрегации | CQL (ограниченные запросы) |
| **Индексы** | Полноценные | Ограниченные |
| **Пример БД** | PostgreSQL, MySQL | Cassandra, HBase, ScyllaDB |

---

### Визуализация wide-column (Cassandra)

```
Row Key       → Column Family: "users"
──────────────────────────────────────────────────
user_1        → name: "John"  | age: 30  | city: "NY"
user_2        → name: "Jane"  | age: 25  | (нет city)
user_3        → name: "Bob"   | age: 40  | city: "LA"  | phone: "+123"
```

**Особенности:**
- Столбцы **не обязаны** присутствовать во всех строках
- Столбцы можно **добавлять** на лету в конкретную строку
- Хранение по колоночным семьям оптимизирует чтение конкретных групп

---

### Где применяется

| Сценарий | Почему |
|----------|--------|
| **IoT / сенсоры** | Каждое устройство передаёт свой набор полей |
| **Временные ряды** | Строка = устройство, столбцы = метки времени |
| **Пользовательские профили** | Разные пользователи имеют разные поля (настройки) |
| **Каталоги товаров** | У разных категорий разные атрибуты (одежда vs электроника) |

---

### Важное ограничение (Cassandra)

- **Запросы** только по **Row Key** + **Clustering Key**
- **Нельзя** делать `SELECT * FROM users WHERE email = ...` без индекса (secondary index — медленный)
- Динамические столбцы удобны для **записи**, но сложны для **произвольных чтений**

**Итог:** Wide-column — это **не таблица**, а **гибкое хранилище строк с переменным набором столбцов**, оптимизированное для быстрой записи и чтения по первичному ключу.


## wide-column vs документоориентированная db
**Wide-column** и **документоориентированные** БД — оба NoSQL, гибкая схема, но разная структура хранения и использования.

---

### Сравнение

| Характеристика | Wide-column (Cassandra, HBase) | Документоориентированная (MongoDB, DocumentDB) |
|----------------|--------------------------------|------------------------------------------------|
| **Единица хранения** | Строка + колоночные семьи | Документ (JSON/BSON) |
| **Вложенность** | Ограниченная (колоночные семьи) | Глубокая (массивы, вложенные объекты) |
| **Схема** | Гибкая, но фиксированные семьи | Полностью динамическая |
| **Запросы** | По первичному ключу (ограниченные) | Гибкие, индексы по любым полям |
| **JOIN** | Нет (денормализация) | Нет (документ содержит всё) |
| **Согласованность** | Настраиваемая (eventual) | Строгая (по умолчанию) |
| **Транзакции** | Нет (только LWT) | Да (ACID для документа) |
| **Масштабирование** | Горизонтальное (masterless) | Горизонтальное (шардирование) |
| **Использование** | Огромные объёмы, высокая запись | Универсальное, сложные данные |

---

### Структура данных

**Документоориентированная (MongoDB):**
```json
{
  "user_id": "u1",
  "name": "John",
  "profile": {
    "age": 30,
    "city": "NY",
    "preferences": { "lang": "en", "theme": "dark" }
  },
  "orders": [
    { "id": "o1", "total": 100 },
    { "id": "o2", "total": 200 }
  ]
}
```
✅ **Глубокая вложенность** — массивы, вложенные объекты

**Wide-column (Cassandra):**
```
Row Key: u1
  → "profile": { name: "John", age: 30, city: "NY" }
  → "preferences": { lang: "en", theme: "dark" }
```
❌ **Нет массивов** — только плоские пары "имя → значение" внутри семьи

---

### Ключевые отличия

| Аспект | Wide-column | Документоориентированная |
|--------|-------------|--------------------------|
| **Вложенность** | Ограничена (2 уровня: row → family → колонки) | Глубокая (массивы, объекты внутри объектов) |
| **Индексы** | Только по ключам (secondary — медленный) | По любым полям (быстро) |
| **Запросы** | CQL (ограниченный SQL-подобный) | MongoDB Query Language (гибкий) |
| **Агрегации** | Ограниченные (count, sum через асинхронные) | Полноценные агрегации (Aggregation Pipeline) |
| **Согласованность** | Eventual по умолчанию (AP) | Строгая (CP) |
| **Нагрузка** | Огромная запись (логи, временные ряды) | Смешанная (CRUD) |
| **Пример** | Cassandra, HBase | MongoDB, Couchbase, DocumentDB |

---

### Когда выбирать

| Сценарий | Wide-column | Документоориентированная |
|----------|-------------|--------------------------|
| **Огромная запись (> 1M записей/сек)** | ✅ | ❌ (слабее) |
| **Временные ряды, IoT** | ✅ | ⚠️ (можно, но хуже) |
| **Сложные структуры (массивы, вложенность)** | ❌ | ✅ |
| **Гибкие запросы, произвольные фильтры** | ❌ | ✅ |
| **ACID транзакции** | ❌ | ✅ |
| **Горизонтальное масштабирование** | ✅ (легко) | ✅ (сложнее) |
| **Сложная аналитика (агрегации)** | ❌ | ✅ |

---

### Итог

- **Wide-column** — **аппарат для записи** (огромные объёмы, простые ключи, AP-система)
- **Документоориентированная** — **универсальный инструмент** (гибкая схема, сложные данные, CP-система)

**Простые аналогии:**
- **Wide-column** = огромная таблица Excel с динамическими колонками (но нет формул)
- **Документоориентированная** = папка с файлами JSON (можно искать по содержимому)
