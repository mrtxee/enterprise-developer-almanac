# Single‑Page Application
**SPA** в данном контексте — это **Single‑Page Application** (одностраничное приложение).

### Что такое SPA

SPA — веб‑приложение, которое:
- загружается в браузер **один раз** (как одна HTML‑страница);
- динамически обновляет содержимое **без полной перезагрузки страницы** (через JavaScript);
- взаимодействует с бэкендом через API (обычно REST/JSON или GraphQL);
- реализует навигацию и логику на клиенте (React, Angular, Vue.js и т. п.).

Примеры: Gmail, Google Maps, Facebook (веб‑версия).

### Почему в SPA нельзя надёжно хранить `client_secret`

В OAuth 2.0/OpenID Connect параметр `client_secret` — это секрет клиента, который должен храниться **только на доверенной стороне** (бэкенде). В SPA это невозможно по следующим причинам:

1. **Код исполняется на стороне клиента**  
   Весь JavaScript кода SPA доступен пользователю в браузере. Любой секрет, «зашитый» в код, можно извлечь через DevTools, статический анализ или перехват запросов.

2. **Нет изолированной среды выполнения**  
   В отличие от серверного приложения, SPA не имеет защищённого окружения, где можно безопасно держать секреты.

3. **Угроза перехвата**  
   Злоумышленник может:
   - подменить скрипт SPA (XSS‑атака);
   - перехватить `client_secret` из сетевого трафика (если нет HTTPS);
   - извлечь секрет из исходников страницы.

4. **Нарушение принципов безопасности OAuth**  
   Спецификации OAuth 2.0 (RFC 6749, RFC 7591) прямо запрещают использование `client_secret` в публичных клиентах (к которым относятся SPA).

### Как решают проблему в SPA

Вместо `client_secret` используют механизмы, подходящие для публичных клиентов:

- **PKCE (Proof Key for Code Exchange)**  
  Добавляет динамический «код проверки» (`code_verifier`) и его хеш (`code_challenge`), чтобы предотвратить перехват кода авторизации. Это **обязательный** элемент для SPA в современных реализациях OAuth.

- **Неявный поток (Implicit Flow) — устарел**  
  Раньше использовался, но сейчас не рекомендован (удалён из OAuth 2.1).

- **Authorization Code Flow + PKCE**  
  Современный стандарт для SPA:  
  1. Клиент генерирует `code_verifier` и `code_challenge`.  
  2. Отправляет `code_challenge` в авторизационный запрос.  
  3. После получения `code` обменивает его на токен, предъявив `code_verifier`.  
  4. `client_secret` не используется.

- **Использование бэкенд‑прокси**  
  SPA отправляет запросы на свой бэкенд, который уже с `client_secret` общается с OAuth‑сервером. Так секрет остаётся на сервере.

### Итог

**SPA = публичный клиент**, для которого:
- хранение `client_secret` **невозможно** и **небезопасно**;
- вместо этого применяют **[[PKCE]]** в рамках Authorization Code Flow;
- цель — защитить токены и коды авторизации от перехвата, несмотря на исполнение кода на стороне пользователя.
