### Data Vault vs Data Warehouse: ключевые различия


#### 1. Определение и суть

- **Data Warehouse ([[DWH модели]])** — централизованное хранилище структурированных данных, оптимизированное для отчётности и анализа. Строится по схеме «звезда» или «снежинка» (Kimball), либо по 3NF (Inmon).
- **Data Vault** — методология моделирования данных, ориентированная на **историчность, гибкость и масштабируемость**. Сочетает черты 3NF и dimensional modeling, но с акцентом на отслеживание изменений.

#### 2. Архитектура и структура

**Data Warehouse:**
- **Схемы «звезда»/«снежинка»**:
  - *Fact-таблицы* (измерения) + *Dimension-таблицы* (атрибуты).
  - Пример: продажи (факт) + время, продукт, регион (измерения).
- **Нормализация**: обычно 2NF–3NF для транзакционных DWH.
- **ETL-процесс**: жёстко заданные потоки загрузки с трансформацией данных.


**Data Vault:**
- **Три типа сущностей**:
  1. **Hub** — ключевые бизнес-сущности (клиент, заказ, продукт). Хранят только ключи и метаданные (дата загрузки).
  2. **Link** — связи между Hub-ами (например, «заказ → клиент»).
  3. **Satellite** — атрибуты сущностей и связей (с историчностью).
- **Слабая [[database normalization|Нормализация]]**: Hub/Link — 1NF, Satellite — денормализованные.
- **Гибкость**: легко добавлять новые атрибуты и связи без изменения структуры.


#### 3. Историчность и отслеживание изменений

- **DWH**:
  - Историчность реализуется через *Slowly Changing Dimensions (SCD)* (типы 1–3).
  - Ограниченная поддержка сложных сценариев (например, множественных изменений в один момент).
- **Data Vault**:
  - **Встроенное отслеживание изменений**: каждый Satellite хранит полную историю атрибутов с датами загрузки.
  - Поддержка *point-in-time* запросов (данные на конкретный момент времени).
  - Возможность аудита всех изменений.

#### 4. Масштабируемость и гибкость
- **DWH**:
  - Жёсткая схема требует изменений при добавлении новых данных.
  - Сложности с интеграцией разнородных источников.
- **Data Vault**:
  - **Горизонтальное масштабирование**: новые Hub/Link/Satellite добавляются без перестройки.
  - Подходит для **разнородных и растущих источников данных**.

#### 5. Производительность
- **DWH**:
  - Оптимизирован для **быстрых запросов** (агрегация, отчёты).
  - Индексы, партиции, материализованные представления.
- **Data Vault**:
  - Запросы сложнее (много JOIN между Hub/Link/Satellite).
  - Требует **дополнительных слоёв** (Business Vault, Information Mart) для аналитики.

#### 6. ETL/ELT-процессы
- **DWH**: ETL с жёсткой трансформацией перед загрузкой.
- **Data Vault**: ELT с минимальной трансформацией на входе. Данные «очищаются» позже (в Business Vault).

#### 7. Сценарии использования
- **Data Warehouse**:
  - Корпоративная отчётность.
  - BI-аналитика с фиксированными требованиями.
  - Системы с предсказуемой структурой данных.
- **Data Vault**:
  - Большие объёмы разнородных данных (IoT, лог-файлы).
  - Частые изменения требований к данным.
  - Необходимость аудита и историчности.
  - Интеграция данных из множества источников (M&A, глобальные компании).


#### 8. Преимущества и недостатки

**Data Warehouse:**  
*Плюсы:*  
- Простота запросов для аналитиков.  
- Высокая производительность отчётов.  
- Готовые инструменты (Power BI, Tableau).  

*Минусы:*  
- Низкая гибкость при изменениях.  
- Сложность поддержки историчности.  

**Data Vault:**  
*Плюсы:*  
- Гибкость и масштабируемость.  
- Полная историчность данных.  
- Лёгкая интеграция новых источников.  

*Минусы:*  
- Сложные запросы (много JOIN).  
- Требуется дополнительный слой для аналитики.  
- Меньше готовых инструментов.  

#### 9. Вывод

- **Выбирайте Data Warehouse**, если:  
  - Нужны быстрые отчёты и аналитика.  
  - Структура данных стабильна.  
  - Приоритет — удобство пользователей BI.  

- **Выбирайте Data Vault**, если:  
  - Данные поступают из множества разнородных источников.  
  - Требуется полная историчность и аудит.  
  - Ожидается рост и изменения в структуре данных.  

  - Важна гибкость и масштабируемость.  


> **Важно**: Data Vault часто используется как **промежуточный слой** перед DWH (Data Vault → Business Vault → Information Mart). Это позволяет сочетать гибкость Data Vault с удобством DWH для конечных пользователей.

### Business Vault и Information Mart: роль в архитектуре данных


Эти компоненты обычно выступают «надстройкой» над **Data Vault** и обеспечивают удобство работы конечных пользователей (аналитиков, BI‑систем).

---

### 1. Business Vault

**Что это**  
Промежуточный слой между сырым Data Vault и конечными витринами (Information Mart). Здесь данные:
* очищаются от ошибок и дублей;
* приводятся к единым бизнес‑правилам и словарям;
* обогащаются расчётными метриками;
* агрегируются до уровня, удобного для аналитики.

**Ключевые задачи**  
* **Стандартизация**: унификация наименований, единиц измерения, кодов.
* **Валидация**: проверка на соответствие бизнес‑логике (например, «сумма заказа > 0»).
* **Обогащение**: добавление производных полей (маржа, LTV, конверсия).
* **Упрощение структуры**: сокращение числа JOIN за счёт предварительных агрегаций.


**Особенности**  
* Сохраняет историчность (как Data Vault), но с очищенными данными.
* Использует те же сущности (Hub, Link, Satellite), но с бизнес‑смысловыми атрибутами.
* Может включать **конформные измерения** (shared dimensions) для согласованности между разными темами.


**Пример**  
В Data Vault есть сырые данные о заказах с кодами продуктов. В Business Vault:
* коды заменяются на понятные названия;
* добавляется категория продукта;
* рассчитывается сумма со скидкой;
* фильтруются отменённые заказы.

### 2. Information Mart (Витрина данных)

**Что это**  
Специализированное подмножество данных, оптимизированное для конкретной аналитической задачи или департамента (продажи, маркетинг, логистика).


**Ключевые задачи**  
* **Упрощение доступа**: предоставление данных в формате, понятном пользователям без глубоких знаний SQL.
* **Высокая производительность**: за счёт денормализации, индексов, партиций.
* **Фокус на бизнес‑потребности**: только релевантные поля и агрегаты для конкретной задачи.
* **Готовые метрики**: предосчитанные KPI (например, «средний чек», «отток клиентов»).

**Типы витрин**  
1. **Зависимые** (Dependent) — строятся на основе Business Vault/DWH.  
2. **Независимые** (Independent) — загружаются напрямую из источников (редко).  
3. **Гибридные** — комбинация обоих подходов.

**Форматы реализации**  
* **Схема «звезда»** (Star Schema): центральная fact‑таблица + dimension‑таблицы.  
* **Схема «снежинка»** (Snowflake Schema): нормализованные dimension‑таблицы.  
* **Columnar storage** (например, на базе Redshift, BigQuery) для быстрой агрегации.

**Пример**  
Витрина для отдела продаж:
* Fact‑таблица: продажи по дням (сумма, количество).  
* Dimensions: продукт (категория, бренд), регион (город, страна), время (квартал, год).  
* Метрики: «рост продаж к прошлому году», «доля рынка по регионам».  

---

### Как это работает вместе (цепочка преобразований)

1. **Data Vault**
   → Сырые данные с полной историчностью.  
   → Много таблиц, сложные JOIN.  

2. **Business Vault**  
   → Очищенные и стандартизированные данные.  
   → Бизнес‑правила применены.  
   → Меньше таблиц, чем в Data Vault.  

3. **Information Mart**  
   → Денормализованные данные для аналитики.  
   → Готовые метрики и агрегаты.  
   → Простые запросы для BI‑инструментов.  

---

### Ключевые отличия

| Критерий               | Business Vault                           | Information Mart                                    |
| ---------------------- | ---------------------------------------- | --------------------------------------------------- |
| **Цель**               | Стандартизация и очистка данных          | Упрощение аналитики для конечных пользователей      |
| **Структура**          | Близко к Data Vault (Hub/Link/Satellite) | Денормализованная (звезда/снежинка)                 |
| **Историчность**       | Полная (все изменения сохранены)         | Частичная (только актуальные/агрегированные данные) |
| **Сложность запросов** | Высокая (много JOIN)                     | Низкая (1–2 таблицы)                                |
| **Аудитория**          | Инженеры данных, архитекторы             | Аналитики, бизнес‑пользователи, BI‑системы          |
| **Производительность** | Средняя (требуется обработка)            | Высокая (оптимизировано для чтения)                 |


---

### Когда что использовать

- **Business Vault**:  
  * Когда нужно обеспечить единый источник «чистых» данных для разных витрин.  
  * При интеграции данных из разнородных источников.  
  * Для соблюдения регуляторных требований (аудит изменений).  

- **Information Mart**:  
  * Когда аналитики требуют быстрых отчётов без сложных SQL‑запросов.  
  * Для специализированных дашбордов (например, для маркетинга или финансов).  
  * Если нужна высокая производительность на агрегатных запросах.  


> **Важно**: Information Mart часто строится на основе Business Vault, а не напрямую из Data Vault. Это позволяет избежать дублирования логики очистки и стандартизации.
