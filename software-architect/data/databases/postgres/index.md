# Индекс
индекс представляет собой коллекцию пар. Ключом выступает значение индекса, а значением – битовый сдвиг от начала в системе хранения до объекта.
* объекты с одинаковым индексом допускаются
	* в таком случае в структуре хранения такого индекса под одним ключом индекса будет лежать группа ссылок (HEAP) на строки ([[PostgreSQL#TID – Tuple ID|TID-ов]])
# Кластеризация индексов
Кластеризация – это разбиение множества объектов на подмножества (кластеры) по заданному критерию. Каждый кластер включает в себя максимально схожие объекты.

**кластерный индекс**
* кластерный индекс **определяет физический прядок размещения объектов** в системе хранения
	* изменение кластерного индекса приводит к изменению порядка упорядочивания объектов хранения
* **первичный ключ**, `PK` – частный случай кластерного индекса

**некластерный индекс**
* не влияет на физическую упорядоченность объектов в системе хранения
* представляет собой таблицу с где ключом выступает индекс, а значением – адрес объекта в памяти
* изменение индекса приводит к изменению структуры файла индекса, но не влияет на физическое размещение объектов в памяти

>[!tip] CLUSTER
>`CLUSTER` — отдельная команда, которая физически переупорядочивает таблицу по индексу (но не меняет структуру хранения индекса) 
>```sql
>CLUSTER ваша_таблица USING ваш_pk_индекс;`  -- eg
```
# Частичные индексы – partial index

**Частичный индекс** — это индекс, построенный не для всей таблицы, а только для строк, удовлетворяющих заданному условию (`WHERE`). Это позволяет:
- **Уменьшить размер индекса** (хранятся только нужные данные).
- **Ускорить запросы** к определенному подмножеству строк.
- **Снизить накладные расходы** на поддержку индекса (вставка/обновление только при изменении релевантных строк).

```sql
CREATE INDEX idx_partial ON table_name(column_name)
WHERE condition;
-- Индекс только для активных пользователей
CREATE INDEX idx_active_users ON users(email)
WHERE is_active = true;
-- Индекс для дорогих товаров
CREATE INDEX idx_expensive_products ON products(price)
WHERE price > 1000;
-- Ускоряет запросы типа:
SELECT * FROM products WHERE price > 1000 ORDER BY price DESC;
```


# Покрывающий индекс – covering index

Покрывающий индекс - это особый тип индекса, который содержит все данные, необходимые для выполнения запроса, без необходимости обращаться к самой таблице. Это позволяет PostgreSQL выполнять запрос, используя только индекс, что значительно ускоряет выполнение.

Покрывающий индекс включает не только столбцы для поиска, но и все остальные столбцы, требуемые запросом, что позволяет избежать дополнительного чтения данных из таблицы.

Создание покрывающего индекса
```sql
CREATE INDEX idx_covering ON orders (customer_id) INCLUDE (order_date, total_amount);
```
# Параметры индекса
## Поддержка сортировки

Поддержка сортировки нужна для
1. ускорения диапазонных запросы `>`, `<=`, `BETWEEN`
2. ускорения выполнение сортировки `ORDER BY`

Отсутствие поддержи сортировки ведет к дорогостоящим операциями
* `Sort` в памяти **`ORDER BY` без индекса**
* `Seq Scan` для диапазонных запросов

**Какие индексы не поддерживают сортировку**

| **Тип индекса**       | **Поддерживает сортировку?** | **Примечания**                                                                                        |
| --------------------- | ---------------------------- | ----------------------------------------------------------------------------------------------------- |
| **B-Tree**            | ✅ **Да** (полная поддержка)  | Оптимален для `ORDER BY` по одному или нескольким столбцам.                                           |
| **GiST**              | ⚠️ **Частично**              | Поддерживает сортировку только для специализированных типов (например, геоданных с оператором `<->`). |
| **SP-GiST**           | ⚠️ **Частично**              | Может поддерживать сортировку для некоторых типов (например, точек в k-d деревьях).                   |
| **Hash**              | ❌ **Нет**                    | Не хранит данные в упорядоченном виде.                                                                |
| **GIN**               | ❌ **Нет**                    | Предназначен для поиска в составных данных (массивы, JSON), а не для сортировки.                      |
| **BRIN**              | ❌ **Нет**                    | Не хранит точный порядок данных, только диапазоны блоков.                                             |
| <br><br><br>**Bloom** | ❌ **Нет**                    | Не предназначен для сортировки.                                                                       |
## Поддержка типов данных

В PostgresSQL есть следующие операторы поиска
`=`, `>`, `<`, `>=`, `<=`, `BETWEEN`, `LIKE`, `IS NULL`, `IN`, `@>`, `<@`, `&&`, `~`, `~*`, `!~`, `!~*`

Не все типы индексов влияют на скорость поиска по каждому оператору поиска.
## Поддержка репликация индексов

Репликация индексов — это процесс автоматического копирования структуры и данных индексов с **основного сервера (мастера)** на **реплики** в режиме реального времени. В PostgreSQL это часть механизма **Streaming Replication** (потоковой репликации), который обеспечивает синхронизацию не только таблиц, но и связанных с ними индексов.

**Реплики применяют изменения индекса** на slave-ах при стриминге WAL-записей журнал транзакций (Write-Ahead Log)

Репликация индексов не работает для Hash на postgresSQL < 10 по причине отсутствия логирования в WAL

1. При **физической репликация** (Streaming Replication)
    - Копирует **байт-в-байт** изменения с WAL, включая индексы.
2. При **логическая репликация** (Logical Replication)
    - Передаёт только изменения данных (DML), но **не структуру индексов**.
    - Индексы на реплике нужно создавать вручную или через скрипты.

## Поддержка UNIQUE index

Поддержка уникальности индексом означает, что индекс **гарантирует отсутствие дубликатов** значений в проиндексированном столбце (или комбинации столбцов). Это ключевой механизм для обеспечения целостности данных.

- **Уникальные индексы** — это механизм защиты от дубликатов.
- **Только B-Tree** поддерживает `UNIQUE` в PostgreSQL.
- **Частичные уникальные индексы** позволяют гибко настраивать условия.

**Частичные уникальные индексы**
Можно гарантировать уникальность **только для части данных**.
```sql
-- уникальный email только для активных пользователей
CREATE UNIQUE INDEX idx_unique_active_email ON users(email)
WHERE is_active = true;
```
# Типы индексов в postgres

Postgres предлагает 7 типов индексов, которые отличаются поддерживаемыми операциями, соответственно типами данных, скоростью и типовыми сценариями использования

| **Тип индекса**                                                                                                  | **Скорость поиска (Big O)**                  | **Операции, которые ускоряет**                                                         | **Подходящие типы данных**                                                                            |
| ---------------------------------------------------------------------------------------------------------------- | -------------------------------------------- | -------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| **B-Tree** Сбалансированное дерево                                                                               | `O(log n)`                                   | `=`, `>`, `<`, `>=`, `<=`, `BETWEEN`, `IN`, `IS NULL`, `LIKE 'prefix%'`, `ORDER BY`    | Числа (`int`, `float`), даты (`timestamp`), строки (`text`), UUID, IP-адреса (`inet`)                 |
| **Hash** <br>Хеш-таблица                                                                                         | `O(1)` (в среднем)                           | Только `=`                                                                             | Числа, строки (но не поддерживает `UNIQUE` и сортировку)                                              |
| **GIN**<br>Generalized Inverted Index<br>Обратный индекс                                                         | `O(log n)`<br>(зависит от данных)            | `@>` (содержит), `<@` (содержится в), `&&` (пересекается), `@@` (полнотекстовый поиск) | Массивы (`int[]`, `text[]`), <br>JSONB,<br>`tsvector` (полнотекстовый поиск)                          |
| **GiST**<br>Generalized Search Tree<br>Обобщённое дерево поиска                                                  | `O(log n)` – `O(n)`<br>(зависит от операции) | `&&` (пересечение), `@>` (содержит), `<->` (расстояние), `@@` (полнотекстовый поиск)   | Геоданные (`point`, `polygon`), <br>`tsvector`, <br>диапазоны (`int4range`, `tsrange`), <br>IP-адреса |
| **SP-GiST**<br>Space-Partitioned Generalized Search Tree<br>Пространственно-разделённое Обобщённое дерево поиска | `O(log n)` – `O(n)`<br>(зависит от операции) | `<->` (расстояние), `<<` (входит в подсеть), `LIKE 'prefix%'` (префиксный поиск)       | Точки (`point`), <br>IP-адреса (`inet`), <br>строки (префиксный поиск), <br>квадродеревья             |
| **BRIN**<br>Block Range Index<br>Блочный диапазонный индекс                                                      | `O(n)` с блочной оптимизацией                | `=`, `>`, `<`, `BETWEEN` (если данные упорядочены)                                     | Упорядоченные данные: `timestamp`, `int`, `bigint` (логи, временные ряды)                             |
| **Bloom index**<br>Фильтр Блума<br>                                                                              | `O(1)`<br>(ложные срабатывания)              | Множественные `AND` по разным столбцам (`col1 = A AND col2 = B AND col3 = C`)          | Любые типы, но эффективен только для комбинаций `AND`                                                 |
**Какой индекс выбирать в зависимости от задачи**
- **`B-Tree`** – дефолтный индекс для `PRIMARY KEY`, `UNIQUE`, сортировки (`ORDER BY`)
- **`Hash`** – если нужен **только точный поиск** (`=`), но не поддерживает `UNIQUE`, сортировку и диапазоны
- **`GIN`** – для составных типов (массивы, JSON, полнотекстовый поиск `@@`).
- **`GiST`** – геоданные (`POINT`, `POLYGON`), поиск сложным структурам (пересечение, расстояние)
- **`SP-GiST`** – нерегулярные структуры (IP-адреса, `k-d tree`).
- **`BRIN`** – большие таблицы с **естественной сортировкой** (логи, временные ряды)
	- Для аналитики по временным рядам
- **`Bloom`** – множественных  `AND` условий по разным столбцам.

## B-Tree – Сбалансированное дерево

Сбалансированное дерево

Универсальный индекс
* индекс по умолчанию для **первичных (PK)** и **внешних ключей (FK)**
* При объявлении `PRIMARY KEY` автоматически создаётся **уникальный B-Tree индекс**
	```sql
	CREATE TABLE users (
	    id SERIAL PRIMARY KEY,  -- Создаётся B-Tree индекс на id
	    email TEXT UNIQUE       -- Ещё один B-Tree индекс для email
	);
	```
	
	Эквивалентно явному:
	```sql
	CREATE UNIQUE INDEX users_pkey ON users(id);  -- B-Tree
	```

* Для FK индекс **не создаётся автоматически**, но его рекомендуется добавлять вручную (B-Tree):

	```sql
	CREATE TABLE orders (
	    id SERIAL PRIMARY KEY,
	    user_id INTEGER REFERENCES users(id)  -- FK на users.id
	);
	-- Ручное создание индекса для ускорения JOIN и проверок FK:
	CREATE INDEX idx_orders_user_id ON orders(user_id);
	```
	Если индекс для FK отсутствует, операции `DELETE`/`UPDATE` на главной таблице будут медленными.


**Преимущества**
* Поддержка `UNIQUE`
* Диапазонные запросы
	* `>`, `<`, `BETWEEN`, `ORDER BY`
* Поддержка сортировки
	* Данные хранятся в отсортированном виде
* Устойчив к сбоям (поддерживает WAL).
* Поддержка частичных индексов

Недостатки
* Неэффективен для полнотекстового поиска
	* LIKE '%suffix'

## Hash – [[Хеш-таблица]]

Структура хранения
* Хеш-таблица

Назначение
* Точный поиск (WHERE x = value)

Преимущества
* Быстрее B-Tree для =
* Поиск за O(1)

Недостатки
* Не поддерживает UNIQUE index, 
* Не работает после сбоя
	* В PostgreSQL **Hash-индексы** считаются **неустойчивыми к сбоям** (non-crash-safe) из-за особенностей их реализации
	* Hash-индексы **до версии PostgreSQL 10** не поддерживали запись изменений в **Write-Ahead Log (WAL)** — журнал транзакций, который используется для восстановления после сбоев.
		- Если сервер аварийно завершает работу (например, из-за отключения электричества), изменения в Hash-индексе **могут быть потеряны**.
		- Индекс становится **битым** и требует перестроения.
	- Для **Для PostgreSQL ≤ 9.6:** 
		- Hash индекс не рекомендован для production
		- Требует вызов в случае сбоя REINDEX INDEX <имя_hash_индекса>;

## GIN – Generalized Inverted Index

Обобщенный обратный индекс

**Структура хранения**
- B-дерево над ключами (лексемами, элементами)
	- Каждому ключу сопоставлен **список TID** (tuple identifiers) - местоположений строк в таблице

В отличие от B-Tree, который хранит данные в упорядоченном виде, обратный индекс отображает **каждый элемент на список строк**, где он встречается.*

**Принцип работы**
1. **Разбиение данных**:  
    Значение (например, массив `[1, 2, 3]` или JSON `{"a": 1}`) разбивается на отдельные элементы (`1`, `2`, `3` или ключ `"a"`).
2. **Создание пар "элемент → строки"**:  
    Для каждого элемента хранится список идентификаторов строк (TIDs), где он встречается.

Назначение
* Составные данные (JSONB, массивы, полнотекстовый поиск)

Преимущества
* Оптимизирован для сложных типов

Недостатки
* Медленная вставка
* больше места
## GiST – Generalized Search Tree

**GiST (Generalized Search Tree)** — это индексная структура, которая обобщает идею классических деревьев поиска (как B-Tree) для поддержки **сложных типов данных** и **нестандартных операций**. 

В отличие от B-Tree, GiST позволяет определять собственные правила разбиения данных, что делает его универсальным для геоданных, полнотекстового поиска, диапазонов и других специализированных сценариев.
* GiST ускоряет выполнение сложные операций, таких как 
	* `&&` (пересечение) / `&&` (перекрытие) для диапазонов
	* `@>` (содержит) / `<@` (содержится), 
	* `<->` (расстояние), 
	* `@@` (соответствие tsquery)

GiST – позволяет оптимизировать поиск по **сложным типам данных** там где B-Tree и GIN не подходят.
* GiST позволяет реализовать собственные функции для CRUD операций

**Принцип работы**
GiST организует данные в дерево, где каждый узел содержит **предикаты** (условия), описывающие поддеревья.
- Например, для геоданных узел может хранить bounding box (ограничивающий прямоугольник), покрывающий все дочерние объекты.

Структура хранения
* 1. **Для геоданных (геометрия, точки)**:
    - R-деревья (R-trees) - наиболее распространённый вариант
    - RD-деревья (для высокоразмерных данных)
    - Квадродеревья (quadtrees) для 2D данных
2. **Для полнотекстового поиска**:
    - Деревья подписи (signature trees)
3. **Для диапазонных типов**:
    - Деревья отрезков (segment trees)
4. **Для IP-адресов и сетевых данных**:
    - Trie-подобные структуры

Назначение
1. **Геоданные** (PostGIS): `ST_Distance`, `ST_Contains`.
2. **Диапазоны**: Проверка перекрытия (`&&`).
3. **Полнотекстовый поиск**: Если не нужна высокая точность GIN.
4. **Специальные типы**: IP-адреса, графы, нестандартные структуры

Преимущества
* Гибкость (поддерживает R-деревья, KD-деревья)
* **Универсальность**: Подходит для типов, которые нельзя индексировать B-Tree.
- **Расширяемость**: Можно добавлять новые методы для своих типов данных.

Недостатки
* Медленнее GIN для JSONB
* **Медленнее B-Tree** для простых операций (`=`).
- **Больший размер индекса** из-за хранения предикатов.
- **Сложность настройки** для пользовательских типов.


## SP-GiST – Space-Partitioned Generalized Search Tree
**SP-GiST** — это индексная структура, предназначенная для эффективного поиска в **пространственных** и **нерегулярных данных**. Она обобщает идею деревьев, которые рекурсивно разбивают пространство на непересекающиеся области, и оптимизирована для специализированных типов данных, таких как:
- Геометрические объекты (точки, линии).
- IP-адреса.
- Квадродеревья ([[quadtree]]) и k-d деревья.
- Префиксные деревья ([[trie]]) для строк.

**Ключевые особенности**
1. **Рекурсивное разбиение пространства**:
    - Пространство делится на **непересекающиеся** области.
    - Каждая область соответствует узлу дерева.
2. **Поддержка пользовательских стратегий разбиения**:
    - Можно реализовать свои правила разделения (например, для IP-адресов или строк).
3. **Типы узлов**:
    - **Внутренние узлы**: Хранят условия разбиения (например, "все точки с x<10x<10").
    - **Листья**: Содержат ссылки на данные (TID — Tuple ID).
4. **Методы доступа** (аналогично GiST, но с акцентом на пространственное разбиение):
    - `choose` — определяет, в какое поддерево направить поиск.
    - `picksplit` — решает, как разделить узел при переполнении.

**Структура хранения**
* Пространственно-разделённое Обобщённое дерево поиска
* Реализация структуры хранения индекса зависит от типа данных
	* Для `point` (геометрия) → **[[KD-Tree]]**
	- Для `inet` (IP-адреса) → **[[trie]]**
	- Для `text` (строки) → **[[radix tree]]**

Назначение – Основные сценарии использования

1. **Поиск ближайших соседей (KNN)** для точек:
	1. `SELECT * FROM points ORDER BY coord <-> point '(10,20)' LIMIT 5;`
2. **Работа с IP-адресами** (поиск подсетей):
	1. `SELECT * FROM ips WHERE ip << '192.168.1.0/24'::inet;`
3. **Префиксный поиск строк** (автодополнение):
	1. `SELECT * FROM words WHERE word LIKE 'abc%';`
4. **Квадродеревья** для 2D-данных (например, картографические приложения).

Преимущества
* Эффективен для нерегулярных данных

Недостатки
* Ограниченная поддержка типов


SP-GiST (Space-Partitioned Generalized Search Tree) использует **разделяемые пространственные структуры данных**, которые адаптируются под конкретные типы данных. В отличие от GiST, SP-GiST поддерживает **нерегулярные разбиения пространства**.
### Основные структуры данных в SP-GiST
1. **Префиксные деревья (Trie-структуры)**
    - Используются для строковых данных и IP-адресов
    - Пример: индекс для типа `inet` (IP-адреса)
    - Оптимален для поиска по префиксам (например, подсетям)
        
2. **К-мерные деревья (k-D trees)**
    - Применяются для многомерных данных
    - Каждый уровень дерева разбивает пространство по одной из координат
        
3. **Четверичные деревья (Quadtrees)**
    - Используются для 2D-данных (геометрия, точки)
    - Пространство рекурсивно делится на 4 квадранта
        
4. **Осьмерные деревья (Octrees)**
    - Аналог quadtree для 3D-данных
    - Пространство делится на 8 октантов
        
5. **Деревья радиального разбиения (Radial trees)**
    - Альтернатива quadtree с круговыми разбиениями
    - Реже используются на практике
        

### Реализация для конкретных типов данных

|Тип данных|Структура SP-GiST|Класс операторов|Применение|
|---|---|---|---|
|IP-адреса (inet)|Префиксное дерево (Trie)|`inet_ops`|Поиск по подсетям|
|Точки (point)|Quadtree|`point_ops`|Пространственные запросы|
|Диапазоны (range)|Дерево отрезков|`range_ops`|Поиск пересечений|
|Текст (text)|Префиксное дерево|`text_ops`|Поиск по шаблонам|

### Особенности SP-GiST

1. **Рекурсивное разбиение пространства**:
    
    - Пространство делится на непересекающиеся области
        
    - Каждая область может делиться дальше
        
2. **Не требует балансировки**:
    
    - В отличие от B-деревьев
        
    - Может быть эффективнее для неравномерных данных
        
3. **Поддержка пользовательских типов**:
    
    - Можно реализовать свои методы разбиения
        
    - Через API расширений PostgreSQL

### GiST vs SP-GiST на прирмере геоданных

| **Критерий**                   | **R-дерево**                         | **KD-дерево**                      |
| ------------------------------ | ------------------------------------ | ---------------------------------- |
| **Структура**                  | Вложенные прямоугольники             | Рекурсивное разбиение пространства |
| **Оптимальные запросы**        | Пересечение (`&&`), вхождение (`@>`) | Точечные запросы, KNN (`<->`)      |
| **Балансировка**               | Автоматическая                       | Зависит от данных                  |
| **Гибкость**                   | Лучше для сложных форм               | Лучше для точечных данных          |
| **Использование в PostgreSQL** | GiST (геоданные)                     | SP-GiST (специализированные типы)  |

- **[[R-Tree|R-дерево]] (GiST)**:
    - Геоданные (полигоны, линии).
    - Запросы на пересечение (`&&`), вхождение (`@>`).
    
- **[[KD-Tree|KD-дерево]] (SP-GiST)**:
    - Точечные данные (координаты, IP-адреса).
    - Поиск ближайших соседей ([[KNN]]).


**Примеры**
```sql
--R-дерево (GiST)
-- Найти все магазины в радиусе 1 км от точки
SELECT * FROM shops 
WHERE ST_Distance(geom, ST_Point(10, 20)) < 1000;

-- KD-дерево (SP-GiST)
-- Найти 3 ближайших города к координатам (10, 20)
SELECT * FROM cities 
ORDER BY geom <-> ST_Point(10, 20) 
LIMIT 3;
```


## BRIN – Block Range Index

**BRIN** (Block Range INdex) — это специализированный тип индекса, разработанный для работы с **очень большими таблицами**, где данные физически упорядочены (или слабо меняются). Он не хранит информацию о каждой строке, а вместо этого запоминает только **минимальные и максимальные значения для блоков данных**, что делает его компактным и быстрым для определённых сценариев.

**Работа с блоками (страницами)**:
- Таблица в PostgreSQL делится на **блоки** (по умолчанию 8 КБ).
- BRIN хранит **минимум и максимум** значений для каждого блока (или группы блоков).
- При поиске, если искомое значение вне диапазона, блок (страница) пропускается

**Пример**
```sql
-- Создание BRIN-индекса для временного столбца
CREATE INDEX idx_logs_brin ON logs USING BRIN(created_at);
-- Поиск данных за январь 2023 (если created_at упорядочен)
SELECT * FROM logs
WHERE created_at BETWEEN '2023-01-01' AND '2023-01-31';
```

Структура хранения
- Данные Блочный диапазонный индекс организованы в **последовательный список диапазонов**.
- Каждый диапазон ссылается на группу блоков таблицы (HEAP).
- **BRIN-индекс** – это отдельный файл в каталоге PostgreSQL (аналогично другим индексам).
	- `[HEADER] → [Метаданные] → [Диапазон 1: min, max] → [Диапазон 2: min, max] → ...`

**Назначение – основные сценарии использования**
1. **Таблицы с естественной сортировкой**:
    - Данные, которые уже упорядочены (например, временные ряды `timestamp`).
    - Логи, транзакции, IoT-данные.
2. **Очень большие таблицы (ТБ+)**:
    - Где обычные индексы (B-Tree) занимают слишком много места.
3. **Слабо изменяемые данные**:
    - Данные, которые редко обновляются (архивы, исторические записи).

Преимущества
* **Компактность**: Занимает **в 100–1000 раз меньше места**, чем B-Tree.
- **Быстрая вставка**: Не требует частого обслуживания (`VACUUM`).
- **Эффективен для диапазонных запросов** (`BETWEEN`, `>`).

Недостатки
* **Требует упорядоченности данных**: Если данные в таблице перемешаны — BRIN бесполезен.
- **Неточность**: Может возвращать «лишние» блоки (ложные срабатывания).
- **Не поддерживает уникальность**: Нельзя использовать для `PRIMARY KEY` или `UNIQUE`.
## Bloom index

**Bloom-индекс** — это специализированный тип индекса, основанный на **[[Фильтр Блума|фильтре Блума]]** (probabilistic data structure). Он предназначен для ускорения запросов с **множественными условиями `AND` по разным столбцам**, особенно когда:
- Нужно проверить несколько столбцов одновременно.
- Точный порядок столбцов в запросе неизвестен заранее.
- Данные часто читаются, но редко обновляются.

Структура хранения
* [[Фильтр Блума]]

Назначение
* Множественные AND-условия по разным столбцам

Преимущества
* **Эффективен для множественных `AND`-условий**.
- **Компактнее GIN/GiST** для многоколоночных индексов.
- **Быстрая проверка** (отсеивает >90% неподходящих строк).

Недостатки
* **Ложные срабатывания** (требуется дополнительная проверка строк).
- **Не поддерживает `OR`** и `ORDER BY`.
- **Неэффективен для обновлений** (перестраивает битовую карту).
