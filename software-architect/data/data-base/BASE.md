## BASE vs ACID: философии консистентности БД

**BASE vs ACID** — это **две противоположные философии**, определяющие, как работает база данных:

- **ACID** — строгая согласованность (как в банке).
- **BASE** — доступность и гибкость (как в соцсетях).

> [!NOTE] ACID vs BASE
> ACID приоритет отдаётся согласованности в ущерб доступности.
> BASE — приоритизируется доступность в ущерб согласованности.

---

## ACID

Аббревиатура из 4 свойств:

### A: Atomicity (Атомарность)

> Транзакция — единое целое: либо всё выполнится, либо ничто.

**Пример транзакции:**

```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;
```

→ Если вторая строка не сработала → первая тоже откатится (`ROLLBACK`).

### C: Consistency (Согласованность)

> После транзакции данные остаются в **валидном состоянии** (по триггерам, FK, CHECK).

**Ограничение `balance >= 0`:**

```sql
ALTER TABLE accounts ADD CONSTRAINT chk_balance CHECK (balance >= 0);
```

→ Никакой транзакции не удастся сделать `balance = -50`.

### I: Isolation (Изолированность)

> Параллельные транзакции не мешают друг другу.

Уровни:

- `READ UNCOMMITTED`
- `READ COMMITTED`
- `REPEATABLE READ`
- `SERIALIZABLE` — самый строгий

### D: Durability (Надёжность)

> После `COMMIT` данные сохранены навсегда (даже при падении сервера).

Через WAL (Write-Ahead Log), репликацию, RAID.

### Где применяется ACID

| Отрасль | Пример |
|--------|--------|
| 🏦 Банки | Перевод денег — нельзя потерять копейку |
| 💰 Финтех | Платежи, биржи |
| 📊 Бухгалтерия | Налоги, проводки |
| 🛒 E-commerce | Заказы, инвентарь (если важна точность) |

> Если каждая запись критична — используется ACID.

## BASE

> **BASE** — это **альтернатива ACID**, подходящая для **масштабируемых, отказоустойчивых систем**.

Аббревиатура:

### BA: Basically Available

> Система **всегда доступна**, даже если часть узлов упала.

### S: Soft State

> Состояние может меняться со временем, даже без внешних воздействий (например, через репликацию).

### E: Eventual Consistency

> Данные станут согласованными **со временем**, но **не сразу**.

---

## Как это работает на практике

### Пример: социальная сеть (Instagram)

**Последовательность событий:**

```text
Alice делает пост → публикуется только в EU-регионе
Bob в США видит: «ещё нет»
Через 2 секунды — появляется
```

→ Это **eventual consistency**:

- Сначала доступно в одном регионе;
- Потом реплицируется;
- Через несколько секунд — повсюду.

**Не ACID:**

- Нет гарантии atomicity между регионами;
- Состояние не consistent сразу;
- Но система **доступна** и **масштабируется**.

### Пример: DynamoDB (AWS)

DynamoDB — **классический пример BASE**.

**Запись в us-west-2 и чтение в eu-central-1:**

```bash
# Пишем в us-west-2
PUT /items/123 { "status": "active" }

# Читаем в eu-central-1 → может быть старое значение
GET /items/123 → { "status": "inactive" } # пока не реплицировалось
```

→ Через 1–2 секунды станет `"active"`.

→ Это **eventual consistency** — основа **BASE**.

> Можно включить **strong consistency**, но это замедлит систему.

### Пример: PostgreSQL

**Перевод между счетами:**

```sql
BEGIN;
UPDATE users SET balance = balance - 100 WHERE id = 1;
UPDATE users SET balance = balance + 100 WHERE id = 2;
COMMIT;
```

→ Обе строки изменятся **или ни одна**.

→ Баланс всегда **valid**.

→ Консистентность — **немедленная**.

> **ACID** — каждый шаг контролируется.

## Сравнение ACID и BASE

### Сводное сравнение

| Критерий | **ACID** | **BASE** |
|----------|----------|---------|
| **Философия** | Согласованность над всем | Доступность и масштабируемость |
| **Цель** | Целостность данных | Доступность и масштабирование |
| **Согласованность** | Strong / Immediate | Eventual / Delayed |
| **Транзакции** | Полные ACID-транзакции | Частичные или отсутствуют |
| **Производительность** | Ниже (блокировки, логика) | Выше (асинхронно) |
| **Масштабирование** | Горизонтально сложно | Легко (sharding, leaderless) |
| **Геораспределение** | Проблемы с задержками | Идеально |
| **Failover** | Может быть медленным | Почти мгновенный |
| **Примеры БД** | PostgreSQL, Oracle, SQL Server | Cassandra, DynamoDB, Riak |
| **Подходит для** | Финансовых систем | Мобильных приложений, SaaS, IoT |
| **Конфликты** | Решаются до записи | Решаются после (на клиенте) |
| **CAP-теорема** | Жертвует **A** (Availability) ради **C** (Consistency) | Жертвует **C** ради **P** и **A** |

> 💡 **CAP-теорема:**
> - **ACID** → CP (Consistency + Partition Tolerance);
> - **BASE** → AP (Availability + Partition Tolerance).

### Преимущества и недостатки

| Критерий | **ACID** | **BASE** |
|--|---------|---------|
| **Строгая согласованность** | ✅ Да | ❌ Нет |
| **Надёжность** | Высокая | Умеренная |
| **Безопасность** | ✅ Для финансовых систем | ⚠️ Только если допустимы временные расхождения |
| **Простота понимания** | ✅ Любой разработчик знает транзакции | ❌ Нужно объяснять eventual consistency |
| **Масштабируемость** | ❌ Ограниченная | ✅ Отличная |
| **Доступность** | Может падать при сетевых проблемах | ✅ Работает почти всегда |

### Рекомендации по выбору

| Сценарий | Рекомендация |
|----------|--------------|
| Банковский перевод | ➤ **ACID** |
| Финтех, платёжные системы | ➤ **ACID** |
| Деньги, безопасность, аудит | ➤ **ACID** |
| Реестр пациентов | ➤ **ACID** |
| Требуется полная согласованность | ➤ **ACID** |
| Чат в реальном времени | ➤ **BASE** |
| Лента новостей | ➤ **BASE** |
| IoT-устройства | ➤ **BASE** |
| Геораспределённая система | ➤ **BASE** |
| Миллионы пользователей, low latency | ➤ **BASE** |
| Быстрый выпуск продукта | ➤ **BASE** |
| CRM с тысячами пользователей | ➤ **BASE** |

**Финальный вывод**

| ACID — это... | BASE — это... |
| -------------------------------- | -------------------------------- |
| 🔹 **«Я сделаю правильно»** | 🔹 **«Я буду работать»** |
| 🔹 Согласованность > Доступность | 🔹 Доступность > Согласованность |
| 🔹 Подходит для банков | 🔹 Подходит для стартапов, SaaS |
| 🔹 Транзакции, блокировки | 🔹 Асинхронность, gossip |
| 🔹 PostgreSQL, Oracle | 🔹 DynamoDB, Cassandra |

> 💬 _"ACID is about correctness. BASE is about availability."_
> — Martin Kleppmann #👨
