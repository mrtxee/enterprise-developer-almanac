## Модели согласованности данных (Data Consistency Models)

### 🔴 Строгие (Strong)

| Модель                     | Суть                                                                                                                        |
| -------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| **Strict Consistency**     | Любое чтение возвращает результат последней записи. Идеал, недостижим в распределённых системах.                            |
| **Linearizability**        | Все операции выглядят так, будто выполняются мгновенно и в реальном времени. Самая сильная реализуемая модель.              |
| **Sequential Consistency** | Все операции всех узлов можно упорядочить в одну глобальную последовательность, сохраняющую локальный порядок каждого узла. |

### 🟡 Средние

| Модель                      | Суть                                                                                                               |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| **Causal Consistency**      | Гарантирует порядок только для причинно-связанных операций; независимые могут переупорядочиваться.                 |
| **PRAM (FIFO) Consistency** | Операции одного писателя видны всем читателям в том же порядке, но операции разных писателей могут перемешиваться. |
| **Bounded Staleness**       | Чтение отстаёт от записи не более чем на заданный лимит (время или кол-во версий).                                 |

### 🟢 Слабые (Weak / Eventual)

| Модель                   | Суть                                                                                                                              |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------------- |
| **Eventual Consistency** | При отсутствии новых записей все реплики сойдутся к одному значению. Самая слабая.                                                |
| **Read-Your-Writes**     | Клиент всегда видит свои собственные записи.                                                                                      |
| **Monotonic Reads**      | Если клиент прочитал значение X, он никогда не увидит более старое значение.                                                      |
| **Monotonic Writes**     | Записи одного клиента применяются в порядке их отправки.                                                                          |
| **Write-Follows-Reads**  | Запись, следующая за чтением, применяется после данных, которые были прочитаны.                                                   |
| **Session Consistency**  | Комбинация всех четырёх выше (read-your-writes + monotonic reads + monotonic writes + write-follows-reads) в рамках одной сессии. |

---

**Иерархия по строгости** (от сильной к слабой):
> Strict → Linearizability → Sequential → Causal → Session → Eventual

Выбор модели — это компромисс между **согласованностью**, **доступностью** и **задержкой** (теорема [[cap-theorem|CAP]] / [[pacelc|PACELC]]).


## Альтернативы моделей устойчивости данных

Помимо уже упомянутых, существуют подходы, которые ломают бинарный выбор «строгий ACID или слабый BASE»:

### HAT (Highly Available Transactions)
   Гарантирует атомарность и изоляцию (как в ACID), но **без жертвования доступностью** (Availability) при сетевых сбоях. Достигается за счет отказа от самой строгой глобальной упорядоченности (Serializable), но с сохранением читаемости своих записей и монотонности.

### RedBlue Consistency
   Гибридная модель, разделяющая операции на два типа:
   - *Красные*: требуют строгой согласованности и координации (например, списание уникального промокода).
   - *Синие*: коммутативные операции, которые можно выполнять с Eventual Consistency без координации (например, добавление лайков или товаров в корзину).

### TCC (Try-Confirm-Cancel)
   Паттерн распределенных транзакций для микросервисов (альтернатива Sagas и 2PC).
   - `Try`: резервирование ресурсов (заморозка суммы).
   - `Confirm`: финальное применение, если все шаги успешны.
   - `Cancel`: освобождение ресурсов при сбое. Более синхронный и строгий, чем классическая Saga.

### Event Sourcing + CQRS
   Архитектурная альтернатива традиционным CRUD-транзакциям. Состояние не перезаписывается, а хранится как неизменяемый поток событий (Event Log). Запись событий строго атомарна, но проекция этих событий в модели для чтения (CQRS) происходит асинхронно (Eventual Consistency).

### OCC (Optimistic Concurrency Control)
   Альтернатива пессимистичным блокировкам (Pessimistic Locking), типичным для строгого ACID. Транзакции выполняются без блокировок, а проверка конфликтов происходит только в момент коммита (через версии или timestamp). При конфликте транзакция откатывается и повторяется. Эффективно при низкой конкуренции за данные.

**Резюме:** Современный тренд — не выбирать одну модель для всей системы, а комбинировать их (например, строгий ACID для биллинга и RedBlue/HAT для пользовательских интерфейсов).
