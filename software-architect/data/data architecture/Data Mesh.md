# Data Mesh
**Data Mesh** — это **современная архитектурная и организационная парадигма управления данными**, призванная решить ключевые проблемы централизованных [[Data Warehouse]] и [[Data Lake]].

---

## 🔍 Что такое Data Mesh?

> **Data Mesh** — это подход, при котором **данные рассматриваются как продукт**, а их **владельцы — команды, которые их создают** (а не централизованная команда данных).

### 💬 Простыми словами:
> «Вместо того чтобы всё тянуть в одно хранилище, каждая бизнес-команда сама управляет своими данными — как продуктом».

---

## 🎯 Почему он появился? (Проблемы старых подходов)

| Подход | Проблемы |
|--------|----------|
| **Централизованный Data Warehouse** | Узкое горлышко: все зависят от одной команды данных. Медленно, дорого, не масштабируется. |
| **Data Lake** | «Болото данных»: данные есть, но никто не знает, что делать с ними. Нет качества, нет владения. |
| **Monolithic Data Platform** | Сложность, высокая стоимость, слабая гибкость под бизнес-нужды. |

→ При росте компании эти системы **ломаются под нагрузкой**.

---

## ✅ Четыре основных принципа Data Mesh
> Zhamak Dehghani #👨 

### 1. Данные как продукт (Data as a Product)
- Каждый домен (например, «Запись на приём», «Биллинг») **владеет своими данными**.
- Команда этого домена **отвечает за качество, доступность, документацию** — как за продукт.
- Данные должны быть **обнаруживаемыми, адресуемыми, надёжными**.

> 💡 Пример:  
> Команда «Лаборатория» публикует поток событий `LabResultCreated` — как API для других.

---

### 2. Децентрализованное владение данными (Domain-Oriented Decentralized Data Ownership)
- Нет единой команды данных.  
- **Бизнес-команды сами управляют своими данными** — от сбора до публикации.
- Централизованная команда данных становится **платформенной** — предоставляет инструменты, а не делает всё сама.

> 💡 Это как переход от монолита к микросервисам — но для данных.

---

### 3. Самообслуживаемая платформа данных (Self-Serve Data Infrastructure as a Platform)
- Централизованная команда создаёт **платформу**, которая позволяет доменным командам:
  - Публиковать данные
  - Запрашивать данные
  - Управлять доступом
  - Мониторить качество
- Без необходимости глубоких знаний в Big Data.

> 💡 Пример платформы:  
> Единый каталог данных + шаблоны Kafka + автоматическая документация + RBAC.

---

### 4. Федеративное вычисление и глобальное управление (Federated Computational Governance)
- Нет жёстких централизованных правил.  
- Но есть **общие стандарты**: форматы, безопасность, метаданные, соответствие GDPR/HIPAA.
- Глобальная политика + локальная свобода.

> 💡 Пример:  
> Все команды обязаны шифровать ПДн, но могут выбирать, как именно (AES, Vault и т.д.).

---

## 🏥 Пример: Data Mesh в «Медикаменте»

| Домен            | Данные как продукт                                    |
| ---------------- | ----------------------------------------------------- |
| **Регистратура** | Поток `PatientRegistered` → в каталоге данных         |
| **Лаборатория**  | Таблица `lab_results` + события `AnalysisCompleted`   |
| **Биллинг**      | Поток `PaymentProcessed` + агрегаты по дням           |
| **Аналитика**    | Не создаёт данные, а **потребляет** из других доменов |

→ Аналитики больше не ждут, пока центральная команда выгрузит Excel. Они **сами находят и используют данные** через платформу.

## ✅ Преимущества Data Mesh

| Преимущество | Объяснение |
|-------------|------------|
| **Масштабируемость** | Новые домены — новые данные, без перегрузки центра |
| **Скорость** | Команды публикуют данные сразу, без очереди |
| **Качество** | Владелец лучше знает свои данные |
| **Инновации** | Легко экспериментировать с новыми источниками |
| **Соответствие** | Глобальные правила безопасности соблюдаются автоматически |

---

## ⚠️ Когда НЕ стоит внедрять Data Mesh?

- У вас **менее 5–10 доменов** → избыточно сложно.
- Нет **зрелой культуры DevOps и ownership**.
- Нет ресурсов на создание **самообслуживаемой платформы**.
- Данные **очень однородны** (например, только IoT-сенсоры).

> 💡 Data Mesh — это **не технология**, а **организационная трансформация**.

## 🛠️ Технологический стек (пример)

| Компонент | Инструменты |
|----------|-------------|

| **Хранилища** | Delta Lake, Iceberg, S3 |
| **Платформа** | Kubernetes, Airflow, dbt, Great Expectations |
| **Governance** | OpenPolicyAgent, HashiCorp Vault |

## ✅ Итог

> **Data Mesh — это микросервисная архитектура для данных.**  
> Он переносит ответственность за данные **туда, где они рождаются** — в бизнес-домены.

> 💬 _«Instead of moving data to the experts, bring the expertise to the data.»_  
> — Zhamak Dehghani

---

📌 **Когда использовать?**  
→ Когда ваша компания растёт, данные становятся критичными, а централизованная модель тормозит бизнес.

> 🔐 **Главное**: Data Mesh — это не про технологии, а про **культуру, ответственность и платформенное мышление**.


# Преимущества и ограничения внедрения подхода Data Mesh

| Параметр | Пояснение |
| --- | --- |
| Безопасность | Повышает порядок данных, что упрощает работу с ними |
| Скорость и качество аналитики | Уменьшает время на аналитику данных и повышает качество отчётов |
| Штат сотрудников | Позволяет не раздувать штат аналитиков и упростить онбординг новых сотрудников |
| Автоматизация | Позволяет встроить в CI/CD-пайплайны проверку на соответствие стандартам API, схемам и интерфейсу системы |
| Внедрение | Как и любое значительное изменение в компании, требует преодоления возможных сопротивлений сотрудников новому и работы с персоналом |
| Технические изменения | Требует хранения данных в единой инфраструктуре и построения соответствующей платформы данных |
| Инфраструктура | Повышает сложность инфраструктуры и требует увеличения средств на её обслуживание |
