**Файловое**, **блочное** и **объектное** хранение — это три фундаментальных подхода к организации данных в системах хранения. Они отличаются **структурой**, **уровнем абстракции**, **производительностью** и **сценариями использования**. Это типы систем хранения данных ([[Storage-System]]).

## Краткое сравнение

| Характеристика       | Блочное                 | Файловое                  | Объектное                              |
| -------------------- | --------------------------- | ----------------------------- | ------------------------------------------ |
| **Уровень**          | Низкий (сырые блоки)        | Средний (файлы и папки)       | Высокий (объекты с метаданными)            |
| **Доступ**           | По адресу блока (LUN)       | По пути (`/dir/file.txt`)     | По уникальному ID (URL)                    |
| **Метаданные**       | Минимальные                 | Стандартные (владелец, права) | Расширяемые (произвольные ключ-значение)   |
| **Масштабируемость** | Ограниченная                | Средняя                       | Очень высокая (миллиарды объектов)         |
| **Примеры**          | SAN, iSCSI, локальные диски | NAS, NFS, SMB/CIFS | Amazon [[S3]], Google Cloud Storage, MinIO |

## 1. Блочное хранение (Block Storage)

**Что это:**

- диск делится на **фиксированные блоки** (обычно 512 Б – 4 КБ);
- каждый блок имеет **уникальный адрес**;
- файловая система (NTFS, ext4, XFS) накладывается **поверх** блочного устройства.

**Как работает:**

```text
[Приложение] → [Файловая система] → [Блок 100, Блок 101, ...]
```

**Особенности:**

- ✅ **Высокая производительность** (низкая задержка).
- ✅ Полный контроль над данными.
- ✅ Подходит для **баз данных**, **виртуальных машин**.
- ❌ Нет встроенной структуры (файлы/папки).
- ❌ Сложно масштабировать (ограничено размером тома).
- ❌ Требует управления файловой системой.

**Где используется:**

- локальные диски серверов;
- SAN (Storage Area Network);
- облачные тома: AWS EBS, Azure Disk, Google Persistent Disk.

**Аналогия:** чистый лист бумаги — вы сами решаете, как писать.

## 2. Файловое хранение (File Storage)

**Что это:**

- данные организованы в **иерархию файлов и папок**;
- доступ по **пути** (`/home/user/document.pdf`);
- протоколы: **NFS** (Linux), **SMB/CIFS** (Windows).

**Как работает:**

```text
[Приложение] → [Сетевой запрос] → [NAS: /shared/docs/report.docx]
```

**Особенности:**

- ✅ Простота использования (привычная файловая система).
- ✅ Совместный доступ от нескольких клиентов.
- ✅ Встроенные права доступа.
- ❌ Производительность ниже, чем у блочного (сетевая задержка).
- ❌ Иерархия усложняет поиск при большом количестве файлов.
- ❌ Ограничения на длину пути и имена файлов.

**Где используется:**

- общие сетевые папки (NAS);
- home-директории пользователей;
- облачные файловые системы: AWS EFS, Azure Files.

**Аналогия:** папки в шкафу — всё разложено по полочкам.

## 3. Объектное хранение (Object Storage)

**Что это:**

- данные хранятся как **объекты** в **плоском пространстве** (без иерархии);
- каждый объект содержит:
  - **данные** (бинарный blob);
  - **уникальный ID** (ключ, например, `photos/2025/vacation.jpg`);
  - **метаданные** (произвольные: `author=Alice`, `resolution=1920x1080`);
- доступ через **HTTP/HTTPS API** (RESTful).

**Как работает:**

```text
[Приложение] → HTTP PUT https://storage.example.com/bucket/photo.jpg
[Приложение] → HTTP GET https://storage.example.com/bucket/photo.jpg
```

**Особенности:**

- ✅ **Массовая масштабируемость** (миллиарды объектов).
- ✅ **Высокая долговечность** (репликация, erasure coding).
- ✅ **Богатые метаданные**.
- ✅ **Низкая стоимость** хранения.
- ❌ **Высокая задержка** (не подходит для БД).
- ❌ Нет поддержки **частичной записи** (только полная перезапись).
- ❌ Не поддерживает **блокировку файлов**.

**Где используется:**

- хранение медиа (фото, видео);
- резервное копирование;
- Big Data / аналитика;
- статический контент веб-сайтов;
- облачные сервисы: **Amazon [[S3]]**, **Google Cloud Storage**, **Azure Blob Storage**, **MinIO**.

**Аналогия:** склад с ящиками — каждый ящик имеет уникальный штрихкод и наклейку с описанием.

## Сравнение по сценариям

| Сценарий | Лучший тип хранения |
|----------|---------------------|
| **База данных (PostgreSQL, MySQL)** | Блочное |
| **Виртуальная машина (VM disk)** | Блочное |
| **Общая папка для офиса** | Файловое |
| **Хранение логов приложений** | Объектное |
| **Статические файлы сайта (CSS, JS, изображения)** | Объектное |
| **Резервное копирование** | Объектное |
| **Разработка ПО (общий репозиторий)** | Файловое |

## Гибридные решения

Современные системы часто комбинируют подходы:

- **MinIO** поверх блочных томов → предоставляет объектное хранилище.
- **AWS EFS** (файловое) поверх **S3** (объектное) — в некоторых архитектурах.
- **Ceph** поддерживает все три типа: RBD (блочное), CephFS (файловое), RGW (объектное).

## Важные нюансы

1. **Производительность ≠ только скорость**:
   - блочное: низкая latency, высокая IOPS;
   - объектное: высокая пропускная способность (throughput), но высокая latency.
2. **Стоимость**:
   - блочное: дорого (высокая производительность);
   - объектное: дёшево (холодное хранение).
3. **Согласованность**:
   - блочное/файловое: строгая согласованность;
   - объектное: **eventual consistency** (в большинстве реализаций).

**Итог:**

- **Блочное** — для **высокой производительности** и **полного контроля** (БД, VM).
- **Файловое** — для **удобства** и **совместной работы** (офис, разработка).
- **Объектное** — для **масштаба**, **долговечности** и **низкой стоимости** (медиа, бэкапы, аналитика).

Выбор зависит от **характера данных**, **требований к производительности** и **бюджета**.
