## MVCC – Multi-Version Concurrency Control

**MVCC (Multi-Version Concurrency Control)** — это механизм **параллельного доступа к данным**, при котором **несколько версий одной записи** существуют одновременно, чтобы избежать блокировок при чтении и записи.

> 💡 Цель MVCC: **позволить читателям не блокировать писателей, а писателям — не блокировать читателей** — без потери согласованности.

Каждая [[ACID|транзакция]] получает **снимок (snapshot)** базы данных на момент её начала.  
Все изменения (обновления/удаления) **не перезаписывают** старые данные — они создают **новую версию строки** с меткой времени или ID транзакции.

**Пример**
```sql
-- Исходное состояние:
id | name   | version
1  | Alice  | 1

-- Транзакция T1 (начата в момент t=100): UPDATE name = 'Alice2' WHERE id = 1;
-- Создаёт новую версию:
id | name   | version | txn_id_start | txn_id_end
1  | Alice  | 1       | 50           | 100        ← видна только до T1
1  | Alice2 | 2       | 100          | ∞          ← видна после T1

-- Транзакция T2 (начата в t=90): SELECT name FROM users WHERE id = 1;
-- Видит версию с txn_id_start ≤ 90 → "Alice"
-- Даже если T1 уже commited, T2 не видит изменений — потому что она "увидела" базу на t=90.
```

🔹 Ключевые компоненты:

| Элемент                         | Описание                                                                                                              |
| ------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| **[[Transaction]] ID (TXN ID)** | Уникальный номер транзакции (возрастает монотонно)                                                                    |
| **Visible To**                  | Для каждой версии строки определяется, каким транзакциям она видна (на основе TXN ID и состояния — active/completed)  |
| **Heap + Visibility Map**       | Данные хранятся как “цепочка версий”; СУБД использует карты видимости для быстрого определения, какие версии подходят |
| **Garbage Collection**          | Старые версии удаляются асинхронно (в PostgreSQL — `VACUUM`)                                                          |

🔹 Преимущества MVCC:

| Плюс                             | Объяснение                                                             |
| -------------------------------- | ---------------------------------------------------------------------- |
| ✅ **Чтение не блокирует запись** | Читатели работают со своей версией — нет shared locks                  |
| ✅ **Запись не блокирует чтение** | Писатели пишут новые версии — не мешают читателям                      |
| ✅ **Высокая параллельность**     | Подходит для OLTP-систем с множеством пользователей                    |
| ✅ **Изолированные снимки**       | Реализует уровень изоляции **Repeatable Read** (и выше) без блокировок |

🔹 Недостатки:

| Минус                                | Объяснение                                                              |
| ------------------------------------ | ----------------------------------------------------------------------- |
| ❌ **Рост размера данных**            | Хранятся старые версии → растёт размер таблицы                          |
| ❌ **Необходимость очистки (VACUUM)** | В PostgreSQL нужно запускать `VACUUM`, иначе таблицы раздуваются        |
| ❌ **Оверхед на управление версиями** | Требуется дополнительная логика для отслеживания видимости              |
| ❌ **Проблема “bloated tables”**      | Если долго не делать VACUUM — таблица может занимать в 10x больше места |
> bloated tables ~ *раздутые таблицы*

🔹 Где используется?
- **PostgreSQL** — основной механизм
- **Oracle** — под названием *Multiversion Read Consistency*
- **MySQL (InnoDB)** — реализует MVCC через Undo Log
- **SQL Server** — с опцией `READ_COMMITTED_SNAPSHOT`
- **CockroachDB, TiDB, YugabyteDB** — распределённые системы с MVCC

> 📌 **MVCC — ключевой элемент для реализации [[ACID]]-изоляции без блокировок.**
