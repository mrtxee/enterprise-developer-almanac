## Уровни изоляции транзакций
Уровень изоляции транзакций обеспечивается внутренними механизмами СУБД и определяет степень защиты от ошибок возникающих при параллельном выполнении транзакций. Чем выше степень изоляции, тем выше аномалий параллельного выполнения транзакций может возникнуть, но выше время работы.

| **Уровень изоляции** | **Фантомное чтение** | **Неповторяющееся чтение** | **«Грязное» чтение** | **Потерянное обновление** |
| -------------------- | -------------------- | -------------------------- | -------------------- | ------------------------- |
| **SERIALIZABLE**     | ✅                    | ✅                          | ✅                    | ✅                         |
| **REPEATABLE READ**  | ❌                    | ✅                          | ✅                    | ✅                         |
| **READ COMMITTED**   | ❌                    | ❌                          | ✅                    | ✅                         |
| **READ UNCOMMITTED** | ❌                    | ❌                          | ❌                    | ✅                         |
>- ✅ — уровень изоляции **предотвращает** указанную аномалию.
>- ❌— уровень изоляции **не предотвращает** указанную аномалию.
### Read uncommitted — чтение незафиксированных данных
Гарантирует защиту только от `Lost Update`, так как гарантирует последовательное выполнение всех операций обновления. Но не защищает от чтения данных между серией обновлений.
### Read committed — чтение зафиксированных данных
Гарантирует защиту от `Dirty Read`, `Lost Update`. В большинстве СУБД (PostgreSql, MS SQL) эта степень изоляции ==используется по-умолчанию==. Суть данного типа изоляции в том, что SELECT-запросы не будут обработаны до коммита активной транзакции. Бывают 2 способа реализации Read committed изоляции:
- блокировка
- версирование
### Repeatable read — повторяющееся чтение
Гарантирует защиту от `Non-Repeatable Read`, `Dirty Read`, `Lost Update` так как
1. Транзакция, которая изменила данные, не видит своих же обновленных данных
2. Другие транзакции не могут менять данные, пока не будет завершена первая транзакция
### Serializable — упорядоченность
Гарантирует защиту от `Phantom Reads`, `Non-Repeatable Read`, `Dirty Read`, `Lost Update`. Самый высокий уровень изолированности. Результат выполнения параллельных транзакций такой, будто они выполнялись последовательно.

# Проблемы параллельного доступа с использованием транзакций
При параллельном выполнении транзакций возможны следующие аномалии (проблемы):
### lost update — потерянное обновление
- **lost update — потерянное обновление** — при одновременном изменении одного блока данных разными транзакциями теряются все изменения, кроме последнего;

| ***Транзакция 1***                           | ***Транзакция 2***                           |
| -------------------------------------- | -------------------------------------- |
| `UPDATE tbl1 SET f2=f2+20 WHERE f1=1;` | `UPDATE tbl1 SET f2=f2+25 WHERE f1=1;` |
> Ожидаемое поведение f2=f2+45, но может случится, что будет 20 либо 25, если одна из транзакции прочитала до того, как оно обновилось другой транзакцией
### dirty read — грязное чтение
- **грязное чтение — dirty read** — чтение данных, добавленных или изменённых транзакцией, которая впоследствии не подтвердится (откатится);

| ***Транзакция 1***                          | ***Транзакция 2***                      |
| ------------------------------------- | --------------------------------- |
| `UPDATE tbl1 SET f2=f2+1 WHERE f1=1;` |                                   |
|                                       | `SELECT f2 FROM tbl1 WHERE f1=1;` |
| `ROLLBACK;`                           |                                   |
### non-repeatable read — неповторяющееся чтение
 **неповторяющееся чтение — non-repeatable read** — при повторном чтении в рамках одной транзакции ранее прочитанные данные оказываются изменёнными;

| *Транзакция 1*                      | *Транзакция 2*                  |
| ------------------------------------- | --------------------------------- |
|                                       | `SELECT f2 FROM tbl1 WHERE f1=1;` |
| `UPDATE tbl1 SET f2=f2+3 WHERE f1=1;` |                                   |
| `COMMIT;`                             |                                   |
|                                       | `SELECT f2 FROM tbl1 WHERE f1=1;` |
>Два раза будет получено разное значение. Это бывает назойливой проблемой в ситуации, когда я обновляю данные опираясь на текущее значения поля, которые было изменено.
### phantom reads — фантомное чтение
**фантомное чтение — phantom reads** — одна транзакция в ходе своего выполнения несколько раз выбирает множество строк по одним и тем же критериям. Другая транзакция в интервалах между этими выборками добавляет строки или изменяет столбцы некоторых строк, используемых в критериях выборки первой транзакции, и успешно заканчивается. В результате получится, что одни и те же выборки в первой транзакции дают разные множества строк.

| *Транзакция 1*                             | *Транзакция 2*              |
| ------------------------------------------ | --------------------------- |
|                                            | `SELECT SUM(f2) FROM tbl1;` |
| `INSERT INTO tbl1 (f1,f2) VALUES (15,20);` |                             |
| `COMMIT;`                                  |                             |
|                                            | `SELECT SUM(f2) FROM tbl1;` |

Фантомное чтение отличается от неповторяющегося чтения тем, что результат повторного обращения к данным изменился не из-за изменения/удаления самих этих данных, а из-за появления новых (фантомных) данных.
