## Блокировка строк при чтении (SELECT) в SQL

Чтобы **заблокировать строку при выборке** так, чтобы другие транзакции **пропускали её при чтении**, используется сочетание:

- `SELECT ... FOR UPDATE` (или `FOR SHARE`) – блокирует строку для изменений.
- `SKIP LOCKED` – заставляет другие транзакции игнорировать (пропускать) уже заблокированные строки.

### 📌 Как установить lock на строку

```sql
-- Блокировка строки от изменений (монопольная)
SELECT * FROM my_table WHERE id = 123 FOR UPDATE;

-- Блокировка строки только от изменений, но позволит другим читать (shared lock)
SELECT * FROM my_table WHERE id = 123 FOR SHARE;

-- При выборке нескольких строк – пропустить уже заблокированные другими транзакциями
SELECT * FROM my_table WHERE status = 'pending' FOR UPDATE SKIP LOCKED;
```

🔹 **`FOR UPDATE`** – блокирует строку для записи. Другие транзакции не смогут **обновить, удалить или заблокировать** эту строку (но могут читать, если уровень изоляции позволяет).  
🔹 **`SKIP LOCKED`** – при сканировании набора строк, строки, уже заблокированные другой транзакцией, просто не включаются в результат. Это и есть механизм «пропускания» строки при чтении.  
🔹 **`FOR SHARE`** – блокирует строку от изменений, но позволяет другим транзакциям также взять `FOR SHARE` (совместимая блокировка).

### ⏱️ Как долго установлен lock

**Lock действует до конца текущей транзакции.**  
То есть он автоматически снимается при выполнении:

- `COMMIT` – фиксация транзакции
- `ROLLBACK` – откат транзакции

Пока транзакция активна, блокировка сохраняется (даже если вы выполнили только `SELECT ... FOR UPDATE` и больше ничего не делаете).

### 🧹 Как снять lock

Только **завершить транзакцию**:

```sql
COMMIT;   -- или ROLLBACK;
```

Никакой специальной команды «разблокировать строку» внутри активной транзакции нет (кроме завершения самой транзакции).

> Некоторые СУБД позволяют снять блокировку по таймауту (`LOCK_TIMEOUT`), но это не прямое «снятие».

### ⚠️ Важные нюансы

- **`SKIP LOCKED` поддерживается не всеми СУБД**.  
  ✅ PostgreSQL (с 9.5), Oracle (19c+), MySQL 8.0+ (InnoDB), SQL Server (через `READPAST` подсказку).  
  ❌ H2 (до последних версий) не поддерживает `SKIP LOCKED`.

- **Уровни изоляции** влияют на видимость строк. Например, в `READ COMMITTED` другие транзакции увидят старую версию строки (если она заблокирована, но не изменена) – не пропустят. Именно `SKIP LOCKED` заставляет **исключать** строку из результата, а не просто ждать или читать старую версию.

- **Если не использовать `SKIP LOCKED`**, то `SELECT ... FOR UPDATE` будет ждать освобождения строки (по умолчанию) или выдаст таймаут.

### 📊 Пример для PostgreSQL (рабочий сценарий)

```sql
-- Транзакция A
BEGIN;
SELECT * FROM tasks WHERE status = 'new' FOR UPDATE SKIP LOCKED LIMIT 1;
-- получит одну незаблокированную строку и заблокирует её
-- ... долгая обработка ...
COMMIT;

-- Транзакция B (запущена параллельно)
BEGIN;
SELECT * FROM tasks WHERE status = 'new' FOR UPDATE SKIP LOCKED;
-- не увидит строку, заблокированную транзакцией A
-- вернёт другую (если есть) или пустой результат
COMMIT;
```

### 💡 Альтернативы для СУБД без `SKIP LOCKED`

- **MySQL / H2** – можно использовать `SELECT ... FOR UPDATE` без пропуска. Строка будет ждать или выдаст таймаут.  
  Чтобы «пропустить», приходится эмулировать через `GET_LOCK()` или другие механизмы очередей.

- **SQL Server** – используйте подсказку `READPAST`:
  ```sql
  SELECT * FROM my_table WITH (READPAST) WHERE ...;
  ```
  Это аналог `SKIP LOCKED`.

### 🧠 Итог

| Вопрос | Ответ |
|--------|-------|
| Как установить lock, чтобы другие пропускали строку при чтении? | `SELECT ... FOR UPDATE SKIP LOCKED` (в поддерживаемых СУБД) |
| Как долго действует lock? | До конца транзакции (COMMIT / ROLLBACK) |
| Как снять lock? | Завершить транзакцию |

Для H2 (из контекста предыдущих вопросов): `SKIP LOCKED` **не поддерживается**, поэтому «пропустить строку» напрямую не получится. Придётся использовать другие подходы (например, уровень изоляции `READ UNCOMMITTED` или внешнюю координацию).
