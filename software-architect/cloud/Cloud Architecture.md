### 1. Облачная архитектура

**Облачная архитектура** — это способ создания и запуска цифровых продуктов без необходимости управления физической серверной инфраструктурой. Все вычисления, хранение данных и работа приложений происходят на серверах облачного провайдера, к которым пользователи получают доступ через интернет [```2```](https://practicum.yandex.ru/blog/pro-oblachnaya-arhitektura-chto-eto/).

**Ключевые компоненты облачной архитектуры:**
* **Виртуальные серверы** — удалённые компьютеры в облаке для запуска сайтов, мобильных бэкендов и сервисов.
* **Базы данных** — сервисы для хранения и обработки информации (данные пользователей, заказы, сообщения) с автоматическим резервным копированием.
* **Облачные хранилища** — место для хранения файлов (изображений, видео, документов, резервных копий).
* **Сетевые сервисы** — компоненты для маршрутизации трафика (балансировщики распределяют запросы между серверами, DNS направляет пользователей по нужному адресу).
* **Инструменты мониторинга и логирования** — системы наблюдения за работой проекта (сбор логов, отслеживание ошибок и нагрузки) [```2```](https://practicum.yandex.ru/blog/pro-oblachnaya-arhitektura-chto-eto/).

**Виды облачной архитектуры:**
* **Публичное облако** — используется многими компаниями одновременно.
* **Частное облако** — создаётся для одной организации (важно для контроля и безопасности данных).
* **Гибридное облако** — сочетает публичное и частное облака (чувствительные данные остаются в частной инфраструктуре, публичное облако используется для расширения).
* **Мульти-облако** — использование сервисов от разных провайдеров в одной архитектуре [```1```](https://RedLab.dev/blog/how-to-organize-migration-to-the-cloud/).

**Принципы облачной архитектуры:**
* масштабируемость;
* отказоустойчивость;
* автоматизация;
* модульность;
* безопасность по умолчанию [```2```](https://practicum.yandex.ru/blog/pro-oblachnaya-arhitektura-chto-eto/).

### 2. Миграция из on-premise в облако

**Миграция в облако (cloud migration)** — это процесс переноса данных, ИТ-инфраструктуры и приложений из локальной (on-premise) структуры в среду провайдера [```1```](https://RedLab.dev/blog/how-to-organize-migration-to-the-cloud/).

**Бизнес-цели миграции:**
* снижение затрат на ИТ (отсутствие необходимости в собственном оборудовании и штате ИТ-специалистов);
* гибкость ИТ-инфраструктуры (быстрое масштабирование ресурсов);
* повышение надёжности и производительности систем;
* ускорение модернизации ИТ-продуктов;
* обеспечение совместимости приложений на разных устройствах;
* повышение уровня безопасности данных [```1```](https://RedLab.dev/blog/how-to-organize-migration-to-the-cloud/).

**Этапы миграции в облако:**
1. **Анализ инфраструктуры** (ИТ-аудит технологических активов, исследование ПО).
2. **Определение целей миграции** (фиксация задач, бюджета, оценка рисков).
3. **Составление плана миграции** (дорожная карта с информацией о переносимых объектах, последовательности переезда, необходимых ресурсах и сроках).
4. **Выбор облачного провайдера** (оценка технических возможностей, безопасности, соответствия требованиям бизнеса).
5. **Тестирование** (перенос нескольких компонентов в cloud-платформу, проведение тестов для минимизации времени простоя).
6. **Миграция данных и мониторинг** (перенос всех данных, настройка и оптимизация ресурсов, решение вопросов бесперебойной работы) [```1```](https://RedLab.dev/blog/how-to-organize-migration-to-the-cloud/).

### 3. Стратегии миграции в облако (модель 7Rs)

Модель 7Rs — это набор стратегий для планирования, реализации и оптимизации проектов миграции. Разработана с участием компании Amazon Web Services (AWS) как расширение первоначальной модели 5Rs от Gartner [```3```](https://www.computerra.ru/288572/7-rs-strategii-migratsii-v-oblako/).

**Стратегии миграции:**

**1. Retire (устранение)**
* **Суть:** завершение работы или сокращение приложений, которые больше не нужны в производстве.
* **Цель:** вывод из эксплуатации неэффективных устаревших платформ.
* **Плюсы:** минимальные затраты средств, времени и усилий; снижение ИТ-затрат на неиспользуемые ресурсы.
* **Минусы:** риск несовместимости с взаимосвязанными стеками при незапланированном завершении [```3```](https://www.computerra.ru/288572/7-rs-strategii-migratsii-v-oblako/).

**2. Rehost («Lift and Shift», перенос «как есть»)**
* **Суть:** использование облачной инфраструктуры как услуги (IaaS) для перераспределения рабочих нагрузок без изменений в архитектуре.
* **Цель:** быстрый перенос приложений в облако без модернизации.
* **Плюсы:** простота исполнения, подходит для предприятий без опыта миграции.
* **Минусы:** возможны эксплуатационные и технические несовместимости, ограниченные возможности Cloud Native систем [```3```](https://www.computerra.ru/288572/7-rs-strategii-migratsii-v-oblako/).

**3. Repurchase («Drop and Shop», замена)**
* **Суть:** замена внутренних систем на управляемые сервисы сторонних компаний (SaaS).
* **Цель:** отказ от устаревших систем, переход на модель подписки.
* **Плюсы:** сокращение операционных усилий по управлению инфраструктурой.
* **Минусы:** высокая стоимость для малоиспользуемых приложений из-за базовых затрат [```3```](https://www.computerra.ru/288572/7-rs-strategii-migratsii-v-oblako/).

**4. Replatform («Lift and Reshape», перенос с оптимизацией)**
* **Суть:** перенос приложения в облако с оптимизацией платформы без изменения исходного кода и архитектуры.
* **Цель:** сохранение работоспособности старых приложений с обеспечением соответствия требованиям облачных технологий.
* **Плюсы:** повышение гибкости, возможность автоматизации, максимизация ROI.
* **Минусы:** большие затраты и время на изменения, возможное снижение доступности приложений на этапе миграции [```3```](https://www.computerra.ru/288572/7-rs-strategii-migratsii-v-oblako/).

**5. Refactor («Re-architect», рефакторинг)**
* **Суть:** переархитектура рабочих нагрузок для поддержки Cloud Native возможностей с нуля.
* **Цель:** оптимизация производительности сложных приложений.
* **Плюсы:** высокая доступность, повышенный уровень автоматизации, непрерывность бизнеса.
* **Минусы:** требует тщательного планирования, больших затрат, экспертизы, постоянного мониторинга для оптимизации затрат [```3```](https://www.computerra.ru/288572/7-rs-strategii-migratsii-v-oblako/).

**6. Retain («Revisit», сохранение)**
* **Суть:** сохранение части инфраструктуры локально с постепенным переносом остальных компонентов.
* **Цель:** контроль над ресурсами, возможность миграции в гибридное облако.
* **Плюсы:** сокращение потерь при использовании облачных вычислений, оценка обновлённых сервисов.
* **Минусы:** сдерживание перехода на современные, экономичные и безопасные сервисы [```3```](https://www.computerra.ru/288572/7-rs-strategii-migratsii-v-oblako/).

**7. Relocate («Hypervisor-Level Lift and Shift», перемещение на том же уровне гипервизора)**
* **Суть:** миграция рабочих нагрузок без влияния на текущую деятельность, переписывания исходного кода или приобретения нового оборудования.
* **Пример:** перенос с локальной платформы (Kubernetes, VMware) на облачную версию той же платформы.
* **Плюсы:** минимальная downtime (время простоя), сокращение операционных расходов, минимальное обучение персонала.
* **Минусы:** ограничение возможностей Cloud Native среды, возможные высокие затраты на PaaS-сервисы [```3```](https://www.computerra.ru/288572/7-rs-strategii-migratsii-v-oblako/).

**Комбинирование стратегий:** компании часто используют комбинацию стратегий (например, Replatform + Refactor + Retire для разложения монолита на микросервисы) в зависимости от специфики работы и потребностей [```4```](https://www.it-world.ru/cionews/byxzysifh7sok0cks0o04k4sko4k4co.html).
