## Промпт ≠ контекст

| Свойство          | Промпт                    | Контекст                                  |
| ----------------- | ------------------------- | ----------------------------------------- |
| Когда формируется | В момент задачи           | До задачи и поддерживается между задачами |
| Кто отвечает      | Автор запроса             | Автор + команда + агент                   |
| Где живёт         | В чате                    | В репозитории, IDE, истории, tools        |
| Масштаб улучшения | Локальный, на один запрос | Командный, на все задачи команды          |

* Качество ответа агента определяется качеством контекста
## Зачем управлять контекстом

|                                           | Junior-подход (нет работы с контекстом) | Middle-подход к работе с контекстом |
| ----------------------------------------- | --------------------------------------- | ----------------------------------- |
| Токенов на типовую задачу                 | 15–30k                                  | 5–10k                               |
| Итераций до merge                         | 4–8                                     | 1–2                                 |
| Доля кода от агента, ушедшая в production | 30–50%                                  | 80–95%                              |

## Мини-глоссарий
* **Постоянный (always-on) контекст** — слой, который агент видит в каждой задаче по умолчанию.
* **ADR (Architectural Decision Record)** — короткий документ с архитектурным решением: что выбрано, почему, какие альтернативы рассматривались.
* **Инвариант** — то, что не должно ломаться: контракт API, схема события, формат ключей кеша, политика логирования.
* **Точка расширения** — место в проекте, куда добавляют новое (новый эндпоинт, новый feature-флаг, новая команда CLI).
* **Мёртвый rules (мёртвый контекст)** — правило или документ, который формально лежит в репозитории, но не отражает реальность проекта и не влияет на поведение агента; такой пункт можно заменить на противоположный без последствий.
* **Контекстный стандарт команды** — согласованное описание того, что должно быть в окне агента у каждой роли на типовых задачах: какие артефакты и какие их части читает конкретная роль.
* **Слой документа под роль** — раздел в общем артефакте (spec.md, README, ADR), явно адресованный одной из ролей; читается этой ролью, остальными пропускается.
* **Карта читателей артефакта** — явный список ролей, которые читают данный документ, и того, что каждая из них там ищет.
* **Командный контекстный слой под три роли** — состояние контекстного стандарта, в котором у каждой из трёх ролей есть свой кусок работы по поддержанию артефактов.
* **Бюджет-модель окна** — взгляд на окно как на бюджет: лимит размера и лимит качества, а не контейнер фиксированного размера.
* **Context rot / lost in the middle** — деградация качества ответа из-за того, что информация из середины длинного контекста используется моделью хуже, чем из начала или конца, даже если она там есть.
* **Проектный слой** — контекст подсистемы (README, архитектурные заметки, ADR решений), который подаётся не автоматически, а по запросу или когда его подтянул инструмент. Живёт месяцами, владелец — владелец подсистемы.
* **Сессионный слой** — накопившаяся история сообщений и рассуждений в текущей сессии; самый частый источник тихой деградации при долгих сессиях.
* **Инструментальный слой** — результаты вызовов tools (Read, Grep, MCP-вызовов); часть контекста, у которой нет верхней границы по умолчанию.
* **Командный контекст** — общая часть постоянного контекста, видимая всем разработчикам команды через репозиторий.
* **Этап зрелости** (0–4) — шкала, по которой можно оценить, где сейчас контекстный слой команды.
* **Контекст как продукт** — отношение к контекстному слою как к фиче: с версиями, ревью, метриками, ретроспективами.
* **Стандарт артефакта** — согласованные ответы на четыре вопроса: где лежит, как называется, что обязательно содержит, как меняется.
* **CODEOWNERS** — файл репозитория, сопоставляющий пути и обязательных ревьюеров; технический способ закрепить владение артефактом.
* **Горячий ритм** — обновление артефактов в том же PR, который меняет поведение системы.
* **Тёплый ритм** — регулярная проверка постепенного дрейфа артефактов относительно реальности (на ретро / еженедельно).
* **Холодный ритм** — квартальный аудит контекстного слоя с правом удалять то, что больше не соответствует реальности.
* **Tools (инструменты)** — набор функций, которые дают агенту возможность взаимодействовать с внешним миром: выполнять реальные действия, получать данные и работать с разными системами. Проще говоря, это «руки» агента: без них модель только генерирует текст, а с ними — способна автоматизировать задачи.
* **Налог системного промпта** — постоянный объём токенов на описания подключённых tools и MCP-серверов, который платится в каждой сессии независимо от вызовов.
* **Grep** — утилита для поиска в текстовых файлах строк, соответствующих заданному регулярному выражению (шаблону).
* **MCP (Model Context Protocol)** — стандартизированный способ подключать к агенту внешние tools; каждый сервер добавляет свой налог в системный промпт.
* **Базовый / контекстный / точечный набор MCP** — три уровня подключения: нужно почти всегда / только под класс задач / только под конкретную сессию.
* **Субагент** — отдельный экземпляр модели с изолированным контекстным окном для чётко очерченной подзадачи; в основной поток возвращает одно финальное сообщение.
* **Контракт сводки** — заранее заданный формат и ограничение размера ответа субагента, благодаря которому достигается экономия контекста.
* **Lead time** — реальное время от постановки задачи до момента, когда PR влит.
* **Доля переделок (rework rate)** — доля строк из сгенерированного агентом кода, переписанная до merge или сразу после ревью.
* **Доля ИИ-кода** — доля строк в финальном merge, написанная агентом, а не инженером.
* **Vanity metric** — метрика, которая выглядит как данные, но не помогает принимать решения (длина системного промпта, число подключённых tools).
* **A/B-прогон задачи** — пара прогонов одной задачи в двух подходах (junior против middle) с замером одинаковых метрик.
* **Симптом деградации** — наблюдаемое изменение поведения агента (повторный вопрос, игнор правила, цикл, ползучая область, галлюцинация), по которому можно поставить диагноз о состоянии контекста.
* **Триаж сессии** — решение, что делать с текущей сессией: продолжать с локальной коррекцией, ремонтировать через сводку или открыть новую.
* **Ранний сигнал** — индикатор приближающейся деградации (длинная сессия, повторный Read, рост времени ответа), позволяющий вмешаться до того, как появится выраженный симптом.
* **Скилл (Skill)** — именованный набор инструкций для агента под класс задач: что подгрузить в контекст, что сделать, в каком виде вернуть; вызывается командой или подбирается агентом по полю description.
* **Встроенный скилл** — скилл, поставляемый агентной средой из коробки (например, review, init, simplify); markdown-инструкция, читаемая глазами.
* **Контракт результата** — заранее заданный формат вывода (разделы, размер, обязательные элементы); фиксируется в самом скилле, не в каждом вызове.
* **Правило сужения параметра** — если значение всегда одно, это константа в скилле, а не параметр.
* **Обкатка скилла** — прогон на 3–5 реальных случаях со сравнением с ручным результатом перед тем, как класть скилл в общий репозиторий.
* **Библиотека скиллов** — папка skill-файлов + индекс + владельцы + квартальная ревизия; общий артефакт команды, часть контекстного стандарта.
* **Plan mode** — режим работы агента, в котором ему запрещены любые изменения состояния (запись в файлы, миграции, push, установка зависимостей), а на выход требуется структурированный план.
* **Системный промпт** — слой, который видит модель до вашего запроса: общая инструкция, описания tools, активный режим, rules. Не редактируется в момент запроса.
* **План** — структурированный артефакт намерения: цель, область, шаги, что НЕ делаем, открытые вопросы, точки сверки.
* **Точка сверки** — место в плане, где исполнение должно остановиться и показать промежуточный результат до продолжения.
* **Формальный план** — план, который формально присутствует, но не содержит границ, открытых вопросов и точек сверки; по сути это лишь договорённость, что всё будет хорошо.
* **Plan mode как диагностика постоянного контекста** — практика по виду готового плана выявлять пробелы в rules/README: то, чего агент не знает из постоянного слоя, видно в плане раньше, чем в коде.
* **SDD** (**spec-driven development**) — подход, при котором первый артефакт задачи — короткая markdown-спецификация, и работа агента идёт по ней, а не по чату.
* **spec.md** — компактный документ задачи: цель, контекст, что делаем, что НЕ делаем, критерии приёмки, открытые вопросы. Лежит рядом с кодом задачи (в docs/specs/, шапке PR, ветке).
* **Сворачивание контекста** — приём, при котором по завершении подзадачи агента просят сформулировать сводку в несколько строк, и дальше работа идёт по сводке, а не по сырой истории.
* **Актуализация контекста** — приведение постоянного слоя (rules, README, ADR) в соответствие с текущим состоянием кода и команды; идёт постоянно, маленькими шагами.
* **Триггер актуализации** — событие, после которого имеет смысл обновить постоянный контекст: повторное объяснение, новое ограничение, которое нигде не записано, принятое решение, инцидент, устаревший раздел README.
* **Паттерн инцидент → инвариант** — фиксация причины инцидента как правила в rules в течение 24 часов после разбора, с пометкой Причина: ….
* **Паттерн решение → ADR** — оформление принятого выбора подхода как ADR-NNNN в том же PR, который реализует решение, с короткой ссылкой из rules.
* **Паттерн повторяющаяся боль → rules** — перенос правила в постоянный слой при втором повторении, не дожидаясь третьего.
* **Гипер-актуализация** — антипаттерн, при котором в rules тащится всё подряд, включая пожелания и спорные позиции; убивает качество постоянного слоя.
* **Ревью контекстного пакета** — критический разбор пакета до запуска агента по четырём осям: стоимость, ясность, границы, безопасность.
* **Ignore-файл** — файл репозитория с путями, исключаемыми из контекста агента; синтаксис как у .gitignore, но .gitignore его не заменяет.
* **Prompt injection (прямой)** — атака, при которой во внешнем тексте, попадающем в контекст (комментарий тикета, веб-страница), встроена инструкция, которую модель может выполнить как команду.
* **Prompt injection (косвенный)** — атака через ответ скомпрометированного или вредоносного MCP-сервера, которому агент авторизован и доверяет.
* **Защита слоями** — стратегия, при которой каждый из шести слоёв (ignore, правила, отбор MCP, режим без записи, ревью пакета, ревью diff) закрывает свой класс рисков, и общая надёжность выше любого одного слоя.
* **Принцип одной переменной** — дисциплина диагностики: менять только одно за раз, в порядке контекст → tools → rules → модель.
* **Поведенческий слой spec.md** — раздел спецификации, описывающий наблюдаемое поведение системы: входы, лимиты, ожидаемые состояния, сообщения, коды ответа, побочные эффекты. Главный артефакт для тест-дизайна с агентом.
* **Контекстный пакет под тест-дизайн** — поведенческая спецификация + граничные условия + история похожих багов + точки наблюдения.
* **Контекстный пакет под баг-репорт** — воспроизведение + ожидаемое и фактическое + отфильтрованный контекст ошибки + связь с похожими дефектами.
* **Субагент-анализатор логов** — субагент, которому передают сырой лог, а в основное окно возвращают только релевантные строки; предотвращает загрязнение основного контекста.
* **Discovery-сборка** — приём, когда агент структурирует сырые источники (заметки интервью, тикеты, чаты) в карту фактов без достраивания выводов.
* **Structuring vs inferring** — граница, на которой работа с агентом в исследовании остаётся честной: агент группирует то, что есть, и не придумывает того, чего нет.
* **Слоистый spec.md** — спецификация с явными слоями под три роли: бизнес-контекст / поведенческие требования / технические детали.
* **Смысловой diff spec** — разница между двумя версиями spec.md, отфильтрованная агентом до смысловых изменений (расширили скоуп, сузили, изменили поведение); сильнее обычного git diff.
* **Подсветка устаревшего** — практика: при изменении spec.md агент находит в проекте все связанные артефакты (тест-планы, README, ADR, rules), которые могли устареть, и возвращает список ссылок; обновляет человек.

## Always-on context
* `GACODE.md` в корне репозитория и `rules`-файлы агента (командные и персональные);
* ключевые `README` уровня репозитория и подсистем;
* архитектурные заметки и ADR

**Что находится в постоянном контексте**

* Технологический скелет
	* стек: язык, версии, ключевые фреймворки;
	* система сборки и команды для запуска тестов;
	* структура репозитория: где модули, где тесты, где миграции;
	* внешние сервисы и их роли (БД, очередь, кеш, observability).
* Конвенции команды
	* стиль кода и линтеры (что включено, что отключено);
	* именование (формат ключей кеша, имена эндпоинтов, ID-ы событий);
	* формат логирования, телеметрии, обработки ошибок;
	* что считается командным паттерном в типовых ситуациях.
* Инварианты
	* что нельзя ломать без отдельного PR-обсуждения: миграции, контракты API, схемы событий;
	* ограничения безопасности: что не уходит в логи, что не пускается в контекст агента;
	* архитектурные решения и причины их принятия (ADR).
* Точки расширения
	* куда добавлять новое: эндпоинты, feature-флаги, команды CLI;
	* что нужно обновлять одновременно (например, OpenAPI + клиент + тесты).

### Агенту нужен README под потребителя-агента:
* Явные цели и границы подсистемы
* Инварианты с причинами (нельзя X, потому что Y случилось в марте 2025)
* Команды для сборки, тестов, запуска
* Точки расширения

### Минимальный пример rules-файла
```markdown
# Project rules

## Стек
- Node.js 20, TypeScript strict, Fastify.
- Кеш — Redis (Upstash). Формат ключа: `<сервис>:v<схема>:<id>`.
- Логи — Pino, structured, поля `request_id`, `span_id` обязательны.

## Команды
- Тесты: `pnpm test` (минимально — `pnpm test:unit`).
- Линтер: `pnpm lint`. Без зелёного линтера в merge не идёт.

## Инварианты (не ломать без отдельного PR с обсуждением)
- Контракты в `packages/api-contract/` — public API, любое изменение версии
  + обновление потребителей.
- Миграции в `db/migrations/` — append-only, никогда не редактировать существующие.
- В логи никогда не уходят: токены, e-mail в полном виде, тело платёжных payload-ов.

## Точки расширения
```

### Структура `rules`

Мождно удалить раздел структуры, если не нужен в проекте.

```markdown
# Project rules

## 1. Стек и команды
- Node.js 20.x, TypeScript strict, Fastify 4.x.
- Менеджер пакетов: pnpm (lockfile только pnpm-lock.yaml).
- Тесты: `pnpm test:unit` (быстрые), `pnpm test:integration` (с БД).
- Линтер: `pnpm lint`. Без зелёного линта merge не идёт.

## 2. Конвенции
- Логи: Pino, поля `request_id` и `span_id` обязательны во всех логах.
- Кеш: Redis, формат ключа `<сервис>:v<схема>:<id>`. Пример: `orders:v2:42`.
- Ошибки наружу: всегда обёрнуты в `AppError` с полем `code`.

## 3. Инварианты (не ломать без отдельного PR с обсуждением)
- Контракты в `packages/api-contract/` — public API. Любое изменение
  версии + обновление всех потребителей в одном PR.
- Миграции в `db/migrations/` — append-only. Никогда не редактировать
  существующие, всегда новый файл.
- В логи **никогда** не уходят: токены, e-mail в полном виде,
  тело платёжных payload-ов. Маскировать через `lib/redact.ts`.

## 4. Точки расширения
- Новый эндпоинт: `apps/api/routes/<domain>/` + контракт в
  `packages/api-contract/<domain>/` + тест рядом с обработчиком.
- Feature-флаг: `packages/flags/`. Изменение дефолта = ADR.
- Фоновая задача: `apps/worker/jobs/`. Зарегистрировать в `jobs/index.ts`.

## 5. Что НЕ автоматизировать без согласования
- Установку новых зависимостей в `package.json` корневого workspace.
- Создание новых сервисов в `apps/`.
- Изменение CI-пайплайна в `.github/workflows/`.
```

Что важно в этой структуре:

1. Раздел про стек и команды отвечает на вопросы первого уровня: какой язык, какие версии, как запустить. Без этого агент в каждой сессии угадывает.
2. Раздел про конвенции — это правила, которые не очевидны из кода. Что используется Redis, агент увидит сам из package.json. А формат ключа кеша — нет, поэтому это в rules.
3. Раздел про инварианты — самый ценный. Это запреты с причиной. Каждый пункт здесь экономит ревью.
4. Раздел про точки расширения — куда добавлять новое. Без него агент разместит эндпоинт по типовому шаблону, а не так, как принято в вашем проекте.
5. Раздел про то, что не автоматизировать — явные стопы. Это про доверие, а не про технику: некоторые вещи команда хочет принимать руками.

### Структура `ADR`

`ADR` хранится append-only: новое решение — новый файл со следующим номером.

```markdown
# ADR-014: Логирование через Pino с обязательными request_id и span_id

## Контекст
К началу 2025 года в проде было ~15 сервисов с разными форматами логов
(JSON, plaintext, разные имена полей для trace id). При инциденте
сшивание логов между сервисами занимало 30–40 минут ручной работы.

## Решение
- Всем сервисам перейти на Pino, JSON-output.
- Обязательные поля: `request_id` (uuid из входящего HTTP-запроса
  или сгенерированный) и `span_id` (для распределённого трейсинга).
- В фоновых задачах: `request_id` = id задачи, `span_id` = id попытки.

## Альтернативы, которые рассматривали
- **Winston** — отброшено: медленнее на типовых нагрузках,
  меньше встроенных средств для structured logging.
- **OpenTelemetry полностью** — отброшено на момент решения: слишком
  большой шаг для команды, оставили на следующий квартал.

## Последствия
- Все новые сервисы — Pino из коробки.
- Существующие сервисы переведены до конца Q2 2025.
- Появилось правило в CI: лог без `request_id` и `span_id` — фейл линтера.
```

## Стандарт ведения артефактов постоянного контекста

Стандарт — это не один шаблон, а набор согласованных решений на четыре вопроса:

1. Где лежит. Конкретный путь в репозитории: не где-то в docs/, а docs/adr/.
2. Как называется. Конвенция имени: ADR-NNNN-короткое-название.md.
3. Что обязательно содержит. Минимальный набор разделов. Документ без обязательного раздела не валиден.
4. Как меняется. Через PR, с ревью владельца, с обновлением соседних артефактов, если задеты.

| Артефакт              | Где                                                     | Имя                           | Обязательные разделы                                                          |
| --------------------- | ------------------------------------------------------- | ----------------------------- | ----------------------------------------------------------------------------- |
| rules                 | Корень / подкаталог                                     | `GIGACODE.md`<br>/ `rules.md` | Стек, <br>конвенции, <br>инварианты, <br>точки расширения                     |
| README подсистемы     | `apps/<name>/README.md` или `services/<name>/README.md` | `README.md`                   | Цель, <br>что НЕ входит, <br>интеграции, <br>инварианты, <br>точки расширения |
| ADR                   | `docs/adr/`                                             | `ADR-NNNN-<slug>.md`          | Контекст, <br>решение, <br>альтернативы, <br>последствия                      |

```markdown
4. Подождать 30 дней (deprecation window для старых клиентов).

- Шаг 1: удалить v2-роут, изменения локализованы.

- Шаг 4: вернуть v1 из `410 Gone` обратно в `200`.

## Совместимость
- Период с шага 1 по шаг 4: v1 и v2 живут параллельно, отдают одно и то же,
  только в разной форме.
- v1 после шага 4 возвращает `410 Gone` с заголовком `Sunset` (RFC 8594).

## Чек-лист
- [ ] Старые клиенты продолжают работать в течение всех шагов 1–3.
- [ ] Новые клиенты не отправляют запросы в v1.
- [ ] Метрики `/v1/orders` падают до нуля до шага 5.
```

## скилл

**Скилл vs rules**.

В rules — то, что относится ко всем задачам подряд. В скилле — то, что нужно только при разборе бага (или только при ревью). Если rules разбухает от инструкций вида на баге делай X, на миграции — Y, это засоряет каждое окно: специфику надо вытащить в скилл. Если скилл повторяет базовые правила (напомнить про стек, про формат логов) — этим правилам место в rules.

* скилл вызывается конскольной командой.
	* примрер вызова: `/triage-bug SUPP-1244`

**примеры силлов по ролям:**

* разработчик — технические сборки: `triage-bug`, `migrate-module`, `add-feature-skeleton`;
* тестировщик — тестовые: `test-cases-from-spec`, `regression-scan`;
* аналитик — discovery-сборки: `spec-from-notes`, `spec-diff`.

**пример `~/.gigacode/skills/<name>/`**

```markdown
---
name: triage-bug
description: Первичный разбор бага из тикета — гипотезы причины и план воспроизведения. 
	Не пишет в код; только чтение и анализ.

- содержимое тикета через MCP-трекер;
- GIGACODE.md (стек и формат логирования);

- последние 200 строк логов упомянутого сервиса (если доступ есть).

3. Для каждой — минимальный план воспроизведения (шаги, ожидаемое,

## Чего не делать
```

### встроенные скиллы gigacode
1. `review` — ревью изменений, PR или файла: `/review`, `/review <pr>`,` /review <file>`. CLI-версия запускает четыре параллельных агента (корректность и безопасность, качество кода, производительность, свободный аудит); IDE-версия — только явные баги и нарушения правил проекта, без придирок к стилю. Подтягивает diff, GIGACODE.md и rules, релевантные ADR; сверяет изменения с ними. Если постоянный слой слабый, /review тоже работает слабо — ему не с чем сверяться.
2. `init` — генерирует GIGACODE.md (гайд по репозиторию, 200–400 слов), изучив структуру проекта. 3. `simplify` — упрощает недавно изменённый код без изменения поведения; запускается после написания кода.
4. `skill-creator` — помогает создавать и обновлять скиллы.

## plan mode

Plan mode не улучшает мышление модели — он создаёт протокол согласования намерения до того, как агент имеет право что-либо трогать.

На входе у модели в plan mode лежит не голый запрос, а следующий набор контекста:

```
┌─────────────────────────────────────────────────────────────┐
│ Системный промпт IDE/агента                                 │
│  ─ общая инструкция «как ведём себя»                        │
│  ─ описания всех подключённых tools                         │
│  ─ описания подключённых MCP-серверов                       │
│  ─ активный режим (plan mode → нет прав на write)           │
├─────────────────────────────────────────────────────────────┤
│ Постоянный контекст проекта                                 │
│  ─ Rules.md / .cursorrules / аналог                         │
│  ─ ключевые README                                          │
├─────────────────────────────────────────────────────────────┤
│ Сессия и tool-результаты                                    │
│  ─ предыдущие сообщения                                     │
│  ─ открытые в IDE файлы, выделение                          │
├─────────────────────────────────────────────────────────────┤
│ Ваш запрос                                                  │
│  ─ ~1–2% от общего объёма                                   │
└─────────────────────────────────────────────────────────────┘
```

Пример блока в rules.md:

```
## Plan mode

В plan mode план должен содержать:
- Цель — 1–2 предложения, что именно делаем и для чего.
- Область — конкретные файлы и модули, которые будут затронуты.
- Шаги — упорядоченные, привязанные к файлам, не `изучить / сделать / проверить`.
- Что НЕ делаем — явные границы, что вне области этой задачи.
- Открытые вопросы — чего не знаешь, что нужно подтвердить до старта.
- Точки сверки — где остановиться и показать промежуточный результат.

Не разворачивай шаблон формально, если задача укладывается в один-два
файла. Коротко перечисли изменения и пропусти разделы, которые не нужны.
```

## Spec-driven development

Spec-driven development лучше чем promt-drive development

Как работает SDD:

1. Сначала пишется spec.md — короткий документ с целью, границами и критериями приёмки.
2. Документ помещается в репозиторий (или передаётся в сессию как файл).
3. Агент работает по spec.md, а не по чату.
4. Изменения требований идут через правку spec.md, а не через новое сообщение в чате.
5. На ревью сравнивается diff со spec.md, а не с устным запросом.

### Сворачинвание контекста SDD

Сценарий, в котором это нужно: задача большая — несколько подзадач, каждая со своим прочитанным набором файлов. К третьей подзадаче в окне накопится:

* весь контекст первой подзадачи (прочитанные файлы, обсуждения, отброшенные гипотезы),
* весь контекст второй подзадачи (то же самое),
* начальный контекст третьей подзадачи.

В этот момент агент начинает терять детали из первого этапа: они уже глубоко в середине окна (lost in the middle).

Что делать без перезапуска сессии — активное сворачивание:

Шаг 1. В момент перехода между подзадачами попросить агента сформулировать сводку сделанного:

```
Подзадача 1 завершена. Сделай сводку в 5–8 строк:
- что именно реализовано
- какие файлы тронуты
- какие решения приняты (с обоснованием)
- что осталось открытым для следующих шагов
```

Шаг 2. Проверить сводку (несколько секунд) и зафиксировать:

```
Сводка верная. Дальше работаем только по этой сводке и по spec.md;
содержимое прочитанных файлов из подзадачи 1 больше не нужно.
```

Шаг 3. При необходимости вернуться к деталям — точечный Read с offset/limit.

Что произошло на уровне окна: прочитанные файлы и обсуждения остались в истории — их нельзя удалить, но зона внимания сместилась: свежая сводка лежит в конце окна и попадает в фокус, а старые детали остаются далеко позади. Качество ответов восстанавливается.

Риски

	* угроза утечки данных 

		* Через Prompt injection (на MCP или прямой запрос) могут утечь данные

	* утечка секретов в контекст

### Защита слоями
```
Слой 1: ignore-файлы
   ↓ закрывают: секреты в файлах, локальные данные
Слой 2: rules — явные правила про данные
   ↓ закрывают: что считать инструкцией, что данными
Слой 3: отбор MCP по типу задач
   ↓ закрывают: чрезмерные права, утечки в сторонние сервисы
Слой 4: режим без записи при чтении внешнего ресурса
   ↓ закрывают: prompt injection с действиями
Слой 5: ревью контекстного пакета до запуска
   ↓ закрывают: проблемы контекста, пойманные до исполнения
Слой 6: ревью diff кода после исполнения
   ↓ закрывают: проблемы результата и кода, пойманные после исполнения
```

## Поведенческий слой spec.md

Поведенческий слой spec.md нужен для генерации тесткейсов.

Пример поведенческого spec.md

```
> Сгенерируй тест-план под фичу «Экспорт заказов в CSV для роли
> store_manager».
>
> Контекст:
> - spec.md (поведенческий слой) — см. ниже
> - связанные баги за последние 90 дней — см. ниже
> - точки наблюдения: API-ответ, файл на диске у клиента, лог
>   аудита в audit-log
> - тестовые данные: tests/fixtures/orders/manager-scope.ts
>
> [вставлен spec.md]
> [вставлены 5–8 связанных тикетов с резюме]
>
> Требования к тест-плану:
> - сгруппировать по: позитивные, негативные, граничные, безопасность,
>   производительность
> - для каждого пункта указать конкретную ссылку на пункт spec или на
>   связанный баг (а не общую формулировку «по практике»)
> - граничные — указать конкретные значения (пустой список, 50000+1,
>   50001-я строка с unicode)
> - формат: таблица «название | предусловие | шаги | ожидаемый
>   результат | источник»
> - максимум 25 пунктов; если получается больше — сгруппируй
>   эквивалентные классы
>
> Не выдумывай требования, которых нет в spec. Если чего-то не
> хватает — отдельным разделом «открытые вопросы», без выдуманных
> ответов.
```

Результат такого запроса — не финальный тест-план, а черновик, который

тестировщик дорабатывает вручную: агент закрывает около 70%

механической работы, тестировщик добавляет доменные нюансы и убирает

лишнее.

## Контекст для исследований

Главный принцип: Финал спецификации всегда ручной. Агент полезен на этапе черновиков, структурировании, поиске пробелов и противоречий, но не как автор того, что уйдёт в работу команде.

### Аналитика агентом

**Жизненный цикл требования** — шесть стадий: discovery → гипотезы → черновик → согласование → реализация → эволюция. На каждой стадии контекст агента другой.

**Discovery** — главная стадия, где работа с агентом окупается лучше всего: структурирование, а не выводы. Агент группирует то, что есть, не придумывает новое.

**spec.md** — слоистый артефакт под три роли (бизнес-контекст / поведенческие требования / технические детали). Аналитик — владелец слоя «бизнес-контекст» и главный ревьюер связности.

**Подсветка устаревшего при изменении spec** — обязательная практика команды уровня «контекст как продукт». Без неё устаревание копится тихо и через квартал-два даёт расхождения.

**Аналитик** — владелец смысла. У него есть обязательства перед разработчиком и тестировщиком, и он использует агента как инструмент их выполнения.

### Версионирование смыслов

Полезный скилл /spec-diff (или ручной запрос) на конкретный коммит:

```
> Сравни spec.md в HEAD с spec.md в коммите abc123. Опиши
> смысловые изменения — не текстовые. Сгруппируй по типам:
> - расширили скоуп (что добавилось)
> - сузили скоуп (что убрали)
> - изменили поведение (что должно происходить иначе)
> - изменили формулировку без изменения смысла (опустить)
>
> Для каждого пункта — короткая цитата было / стало.
```
