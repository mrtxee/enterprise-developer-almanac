## Release Policy

**Release Policy (Политика релизов)** — это формализованный набор правил и стандартов, который определяет **как, когда и при каких условиях** программное обеспечение выпускается в продакшен.

Это не просто график выпусков, а **стратегический документ**, связывающий инженерные процессы с бизнес-целями и ожиданиями пользователей.

### Назначение Release Policy

| Проблема без политики | Решение с политикой |
|-----------------------|---------------------|
| Хаотичные релизы «когда готово» | Предсказуемый cadence (ритм) |
| Споры о том, что включать в релиз | Чёткие критерии включения/исключения |
| Клиенты не знают, до когда поддерживается версия | Прозрачные сроки EOL/EOS |
| Разные команды работают по разным правилам | Единый стандарт для всей организации |
| Непонятно, когда выпускать хотфикс | Определённые триггеры для экстренных релизов |

### Ключевые компоненты Release Policy

#### Типы релизов

- **Major (X.0.0):** новые фичи, breaking changes. Редко (раз в 6–12 мес).
- **Minor (X.Y.0):** новые фичи без breaking changes. Регулярно (ежемесячно/ежеквартально).
- **Patch (X.Y.Z):** только багфиксы и security. По необходимости или по расписанию.
- **Hotfix:** экстренный фикс критической уязвимости или инцидента. Вне расписания.
- **Pre-release (alpha/beta/RC):** для тестирования, не для продакшена.

#### Каденция

- **Time-based:** фиксированное расписание (например, «каждый первый вторник месяца»). Предсказуемо для клиентов.
- **Feature-based:** релиз, когда фича готова. Гибко, но непредсказуемо.
- **Hybrid:** регулярные минорные + мажорные по готовности.

**Тренд**

Индустрия движется к time-based cadence (Ubuntu, Firefox, Chrome, Kubernetes), потому что предсказуемость важнее полноты фич.

#### Критерии качества (Definition of Done)

Релиз допускается **только если**:

- все P0/P1 баги закрыты;
- test coverage ≥ порога (например, 80%);
- security scan пройден без critical/high уязвимостей;
- performance regression tests пройдены;
- документация обновлена;
- stakeholder sign-off получен.

#### Поддержка и жизненный цикл

- **LTS (Long-Term Support):** поддержка N лет (обычно 3–5). Только патчи безопасности.
- **Standard/STS:** поддержка до следующего мажорного релиза + grace period.
- **EOL (End of Life):** дата прекращения поддержки.
- **EOS (End of Support):** дата прекращения даже security-патчей.

**Пример lifecycle**

| Версия | Тип | EOL |
|--------|-----|-----|
| v3.0 | LTS | 2029 |
| v4.0 | STS | 2027 |
| v5.0 | STS | 2028 |

Между соседними версиями действует grace period — поддержка до следующего мажорного релиза.

#### Версионирование

- Обычно **Semantic Versioning (SemVer):** `MAJOR.MINOR.PATCH`
- Или **CalVer:** `YYYY.MM.PATCH` (Ubuntu, JetBrains)
- Политика должна чётко определять, что считается breaking change

#### Коммуникация

- **Changelog / Release Notes:** обязательны для каждого релиза
- **Deprecation notices:** предупреждение за N релизов до удаления
- **Security advisories:** CVE + инструкция по обновлению
- **Каналы:** блог, GitHub Releases, email-рассылка, RSS

### Примеры политик известных проектов

| Проект | Каденция | LTS | Примечание |
|--------|----------|-----|------------|
| **Ubuntu** | Каждые 6 мес | 5 лет (LTS каждые 2 года) | CalVer (24.04, 24.10) |
| **Kubernetes** | Каждые ~4 мес | ~14 мес (3 последние версии) | Строгий deprecation policy |
| **Node.js** | Каждые 6 мес | 30 мес (чётные версии = LTS) | Odd = Current, Even = LTS |
| **Java (OpenJDK)** | Каждые 6 мес | 5+ лет (LTS каждые 2 года) | JDK 17, 21, 25 = LTS |
| **Firefox** | Каждые 4 недели | ESR (~1 год) | Rapid release model |
| **Spring Framework** | По готовности | 3+ года (OSS), 5+ (Commercial) | Minor = новые фичи |

### Как создать Release Policy

1. **Определите потребности бизнеса:** что важнее — скорость доставки или стабильность?
2. **Выберите каденсию:** time-based vs feature-based
3. **Определите критерии качества:** что является блокатором релиза?
4. **Установите lifecycle:** сколько версий поддерживаете одновременно?
5. **Задокументируйте и опубликуйте:** политика должна быть публичной (для open-source) или внутренней (для enterprise)
6. **Автоматизируйте enforcement:** CI/CD pipeline должен проверять критерии автоматически
7. **Пересматривайте регулярно:** рынок и технологии меняются

### Частые ошибки

- **Политика есть, но её никто не читает** → интегрируйте в onboarding и CI/CD
- **Слишком жёсткие критерии** → релизы задерживаются, команда обходит правила
- **Нет обратной связи** → не собираете данные о качестве релизов post-release
- **LTS без ресурсов** → обещаете поддержку, но не выделяете команду на бекпортирование
- **Неясная коммуникация** → клиенты узнают о breaking changes постфактум

**Итог**

**Release Policy — это контракт между разработчиками и пользователями.** Она превращает хаос выпусков в **предсказуемый, надёжный процесс**, которому доверяют клиенты и на который может опираться бизнес-планирование.

Без неё процесс превращается в «релизы по настроению». С ней — **продуктовая дисциплина**.

## Пример Release Policy

Ниже представлен шаблон **Release Policy**, адаптированный для **внутреннего enterprise-продукта**.

В отличие от публичных продуктов, здесь акцент смещён с маркетинга и продаж на **стабильность бизнес-процессов, интеграцию с внутренними системами и минимизацию простоев сотрудников**.

**Release Policy: [Название Внутреннего Продукта]**

**Версия документа:** 1.0 | **Владелец:** Head of Internal Platform | **Дата:** 2026-07-16

### Цель и область применения

Настоящая политика регламентирует процесс выпуска обновлений продукта `[Название]`, используемого сотрудниками компании для `[описание бизнес-функции, например: обработки заявок / управления закупками]`.

**Главный приоритет:** непрерывность бизнес-процессов и отсутствие регрессий в интегрированных внутренних системах (ERP, CRM, HRM).

### Типы релизов и каденция

| Тип | Частота | Содержание | Окно деплоя |
|-----|---------|------------|-------------|
| **Scheduled Minor** | 1-й и 3-й четверг месяца, 22:00–02:00 | Новые фичи, улучшения UX, некритические фиксы | Ночное окно (вне рабочих часов) |
| **Patch** | По необходимости (не чаще 1 раза/неделю) | Только багфиксы P0/P1, блокирующие работу | Любое время после approval |
| **Hotfix** | Экстренно | Критический инцидент, остановка бизнес-процесса | Немедленно, 24/7 |
| **Major** | 2 раза в год (март, сентябрь) | Breaking changes, миграции БД, новые интеграции | Выделенное окно выходного дня |

**Правило**

Scheduled-релизы **запрещены** в периоды закрытия финансового года, праздников и пиковых бизнес-нагрузок (Black Friday, отчётные периоды). Blackout-dates публикуются в корпоративном календаре.

**Определение**

**Каденция в разработке и релизах ПО** — это регулярный ритм (цикл) событий (планирования, демо, релизов и др.), который делает процесс предсказуемым и синхронизирует команду. Пример: двухнедельные спринты или ежемесячные релизы.

### Критерии допуска к релизу (Definition of Done)

Релиз **НЕ** может быть развёрнут в прод, если не выполнены **все** условия:

- все тесты E2E по критическим бизнес-сценариям пройдены;
- интеграционные тесты со смежными системами (SAP, 1C, AD) пройдены;
- нет открытых дефектов с приоритетом P0 и P1;
- security scan (SAST/DAST) не выявил Critical/High уязвимостей;
- performance test: p95 latency ≤ базовой линии ±10%;
- UAT подписан представителем бизнес-заказчика;
- runbook / rollback plan подготовлен и протестирован;
- change request одобрен CAB (Change Advisory Board) для Major/Patch.

### Версионирование и совместимость

- Формат: **SemVer** (`MAJOR.MINOR.PATCH`)
- **Backward Compatibility:** Minor-релизы обязаны поддерживать обратную совместимость API минимум с **2 предыдущими версиями** (для постепенной миграции внутренних клиентов).
- **Deprecation:** устаревшие эндпоинты помечаются за **3 minor-релиза** до удаления. Уведомления рассылаются владельцам интегрированных систем через Service Catalog.

### Поддержка и жизненный цикл

| Статус | Длительность | Что включено |
|--------|--------------|--------------|
| **Active** | Текущая + 1 предыдущая minor-версия | Багфиксы, security-патчи, поддержка |
| **Maintenance** | Ещё 2 месяца после выхода новой minor | Только security-патчи P0/Critical |
| **EOL** | После Maintenance | Поддержка прекращена, миграция обязательна |

Для внутреннего продукта **одновременно поддерживается максимум 2 minor-версии**. Это снижает нагрузку на команду поддержки и стимулирует своевременное обновление.

### Коммуникация

| Событие | Канал | Срок | Ответственный |
|---------|-------|------|---------------|
| Плановый релиз | Slack #product-releases + Email | За 3 рабочих дня | Release Manager |
| Changelog | Confluence / Wiki | В день релиза | Product Owner |
| Hotfix / Инцидент | Slack #incidents + PagerDuty | Немедленно | On-call Engineer |
| Deprecation Notice | Email владельцам систем + Jira ticket | За 3 месяца | Tech Lead |
| Post-release Report | Confluence | На следующий рабочий день | QA Lead |

### Откат (Rollback Policy)

- **Триггеры отката:** ошибка > 1%, P0-баг в проде, падение ключевой интеграции.
- **Максимальное время принятия решения:** 15 минут с момента обнаружения.
- **Механизм:** Blue-Green deployment → переключение трафика на предыдущую версию.
- **Post-mortem:** обязателен для каждого отката. Публикуется в течение 48 часов.

### Исключения и escalation

Отклонения от политики (например, релиз без полного UAT) требуют письменного одобрения:

- **Minor:** Head of Engineering + Business Stakeholder
- **Hotfix вне окна:** CTO + VP Operations
- **Пропуск критерия качества:** Risk Acceptance Form с указанием компенсирующих мер

### Особенности для внутреннего Enterprise-продукта

| Аспект | Публичный продукт | Внутренний Enterprise |
|--------|-------------------|-----------------------|
| **Пользователи** | Неизвестная масса | Конкретные сотрудники/отделы |
| **Обновление** | Принудительное или opt-in | Координируется с IT-департаментами |
| **Feedback** | Отзывы, рейтинги | Прямая связь, Jira, SLA |
| **Критерий успеха** | Adoption, Revenue | Бизнес-KPI, uptime, satisfaction |
| **Риски** | Потеря клиентов | Остановка производства/продаж |
| **Интеграции** | Обычно внешние API | Глубокая связь с legacy-системами |
| **Compliance** | GDPR, SOC2 | Внутренние регламенты, ИБ-политики |

### Рекомендации по внедрению

1. **Начните с малого:** сначала утвердите только разделы «Типы релизов» и «Критерии допуска». Остальное добавляйте итеративно.
2. **Автоматизируйте enforcement:** встройте проверки Definition of Done в CI/CD pipeline. Политика, существующая только в Confluence, быстро забывается.
3. **Создайте CAB:** для внутренних продуктов Change Advisory Board (представители инфраструктуры, безопасности, бизнеса) — критически важный фильтр.
4. **Измеряйте соблюдение:** ведите метрики: % релизов по расписанию, % откатов, среднее время hotfix. Пересматривайте политику ежеквартально на основе данных.
5. **Учитывайте специфику:** если продукт используется на производстве или в call-центре, окно деплоя может быть только ночью в выходные. Для офисных инструментов — допустимы вечерние будни.

Шаблон адаптируется под реалии конкретной организации. Главное — чтобы политика была **живым документом**, а не бюрократической формальностью.
