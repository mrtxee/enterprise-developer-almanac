**Отказоустойчивость** — это способность системы **продолжать работать** даже при сбое одного или нескольких компонентов.  

Цель: **минимизировать время простоя** (downtime) и **избежать потери данных**.

## Resilience Patterns

**Паттерны устойчивости (Resilience Patterns)** — это проверенные архитектурные и программные решения, которые **помогают распределённым системам корректно реагировать на сбои**, сохраняя работоспособность даже при частичных отказах компонентов.

### [[Circuit Breaker]] – предохранитель

**Суть**: предотвращает каскадные сбои, временно блокируя запросы к ненадёжному сервису.
**Состояния**:
- *Закрытое* — запросы идут нормально.
- *Открытое* — сервис признан неисправным, запросы отклоняются.
- *Полуоткрытое* — проверка восстановления (ограниченное число пробных запросов).
**Когда применять**: при вызовах внешних API, микросервисов.

### [[Bulkhead]] – отсек
**Суть**: изоляция компонентов системы, чтобы сбой в одной части не затронул остальные.
**Примеры**:
- отдельные пулы потоков для разных сервисов;
- раздельные базы данных для критических и некритических данных.
**Когда применять**: в распределённых системах с множеством зависимостей.

### [[Rate Limiting|Rate limiter]] – ограничитель скорости
**Суть**: контроль числа запросов к сервису за единицу времени.
**Алгоритмы**:
- *Token Bucket* («ведро токенов») — запросы потребляют токены;
- *Leaky Bucket* («негерметичное ведро») — запросы обрабатываются с фиксированной скоростью.
**Когда применять**: защита от DDoS, предотвращение перегрузки сервисов.

### [[Load Shedding]] – сброс нагрузки
 Отклонение "низкоприоритетных" запросов при высокой нагрузке, чтобы сохранить работоспособность критических функций.
 
### Fallback – отступление
**Суть**: возврат альтернативного ответа при ошибке.
**Примеры**:
- показ статической страницы при падении БД;
- использование устаревших данных из кэша;
- упрощённый функционал («режим чтения»).
**Когда применять**: критичные сервисы, где недопустим полный отказ.

### [[Failover Strategy|Failover]] – переключение на резерв
**Суть**: автоматический переход на резервный ресурс при сбое основного.
**Примеры**:
- переключение на реплику БД;
- маршрутизация трафика на другой дата‑центр.
**Когда применять**: критически важные системы (финансы, телеком).

### [[Failover Strategy|Redundancy]] – Резервирование
**Суть**: дублирование компонентов для отказоустойчивости.
**Виды**:
- *активно‑активное* (все узлы работают);
- *активно‑пассивное* (резервные узлы ждут сбоя).
**Когда применять**: базы данных, сетевые узлы, серверы.

### Health Check – Проверка работоспособности
**Суть**: регулярные проверки состояния сервиса (эндопоинты `/health`, `/ready`).
**Что проверяется**:
- доступность БД;
- состояние очередей;
- внешние зависимости.
**Когда применять**: оркестрация контейнеров (Kubernetes), балансировщики нагрузки.

### Dead Letter Queue – Очередь мёртвых писем
**Суть**: хранение сообщений, которые не удалось обработать.
**Действия**:
- анализ причин ошибок;
- ручная повторная обработка;
- архивация.
**Когда применять**: системы с очередями сообщений (Kafka, RabbitMQ).

### Self-Healing – Самовосстановление
**Суть**: автоматическое исправление неполадок.
**Примеры**:
- перезапуск упавших контейнеров;
- пересоздание проблемных подключений;
- очистка временных файлов.
**Когда применять**: облачные сервисы, микросервисы.

### Graceful Degradation – Плавное снижение функциональности
**Суть**: отключение некритичных функций при перегрузке, чтобы сохранить основные.
**Примеры**:
- отключение рекомендаций в интернет‑магазине;
- запрет загрузки медиафайлов при высокой нагрузке.
**Когда применять**: высоконагруженные системы с разной приоритезацией функций.

### [[Load Shedding]] – Сброс нагрузки
**Суть**: отказ от части запросов при перегрузке, чтобы не упасть полностью.
**Стратегии**:
- отбрасывание наименее приоритетных запросов;
- ограничение новых подключений.
**Когда применять**: пиковые нагрузки, защита от лавины запросов.

### Chaos Engineering
**Суть**: намеренное введение сбоев для проверки устойчивости.
**Примеры**:
- отключение узлов;
- имитация задержек сети;
- заполнение диска.
**Когда применять**: зрелые системы с высокой доступностью.

### Idempotency – Идемпотентность
**Суть**: операция даёт одинаковый результат при многократном вызове.
**Реализация**:
- уникальные идентификаторы запросов;
- проверка статуса операции перед выполнением.
**Когда применять**: платежи, обновления данных, API.

### Как выбирать паттерны

1. **Анализ рисков**: какие сбои наиболее вероятны?
2. **Приоритеты**: доступность vs. консистентность данных.
3. **Сложность**: простые системы — базовые паттерны (*Timeout*, *Fallback*); сложные — комбинированные (*Circuit Breaker* + *Rate Limiter*).
4. **Мониторинг**: всегда добавляйте логирование и алерты для обнаруженных сбоев.

**Важно**: паттерны часто комбинируют. Например:
- *Circuit Breaker* + *Fallback* + *Health Check* — стандартный набор для микросервисов;
- *Rate Limiter* + *Load Shedding* — защита от перегрузок.
