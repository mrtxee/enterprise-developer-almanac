### Что такое логирование (logging)

**Логирование** — это процесс записи информации о работе программы, системы или сервиса в специальные файлы (логи) или внешние хранилища. Это «дневник» приложения, где фиксируются события, ошибки, действия пользователей и другие значимые факты.

### Зачем нужно логирование

- **Диагностика ошибок**. Позволяет понять, что пошло не так, когда и почему возникла проблема.
- **Мониторинг состояния**. Даёт представление о текущем состоянии системы (загрузка CPU, память, число запросов).
- **Анализ производительности**. Помогает выявить узкие места (долгие запросы, частые операции).
- **Аудит безопасности**. Фиксирует подозрительные действия (попытки входа, изменения данных).
- **Соответствие требованиям**. В ряде отраслей (финансы, медицина) ведение логов — обязательное требование регуляторов.
- **Отладка**. Упрощает поиск багов на этапе разработки и тестирования.

### Что обычно записывается в логи

- **Дата и время** события (с точностью до миллисекунд).
- **Уровень важности** (debug, info, warning, error, fatal).
- **Идентификатор запроса** (trace ID, correlation ID) для отслеживания цепочки действий.
- **Сообщение** — описание события (текст, код ошибки, параметры).
- **Источник** — имя модуля, класса, функции, где произошло событие.
- **Контекст** — дополнительные данные (IP‑адрес, пользователь, HTTP‑метод, время выполнения).

### logging levels – уровни логирования

| Уровень | Сокращение | Когда использовать | Пример |
|--------|------------|---------------------|--------|
| **TRACE** | `TRACE` | Подробные технические детали. Самый низкий уровень. | Вход в метод, переменные, шаги алгоритма |
| **DEBUG** | `DEBUG` | Для отладки во время разработки и тестирования | SQL-запросы, параметры вызовов |
| **INFO** | `INFO` | Информация о нормальной работе системы | "Сервис запущен", "Задача начата" |
| **WARN** | `WARN` | Предупреждение: что-то не так, но работает | Пустой результат, устаревший API |
| **ERROR** | `ERROR` | Ошибка, которая нарушает часть функциональности | Исключение, сбой подключения к БД |
| **FATAL** | `FATAL` | Критическая ошибка → сервис не может работать | Не удалось загрузить конфигурацию |

> ⚠️ Некоторые системы (Java, Log4j) используют `FATAL`, другие (Python, .NET) — только до `ERROR`.

Пример
```bash
2025-11-17 10:30:45 [ERROR] UserService: Failed to update profile (user_id=123, reason=DB connection timeout)
```

### Где хранятся логи
- **Файлы на диске** (`.log`, `.txt`) — простой и распространённый вариант.
- **Системный журнал** (syslog, journald) — для серверных ОС.
- **Базы данных** ([[Elasticsearch]], [[PostgreSQL]]) — для централизованного анализа.
- **Облачные сервисы** (AWS CloudWatch, Google Cloud Logging) — для масштабируемых систем.
- **[[SIEM]]‑системы** (Splunk, Graylog) — для безопасности и аудита.

### Как организовать логирование

1. **Выберите формат**:
 - **Простой текст** — легко читать, но сложно анализировать.
 - **JSON** — структурирован, удобен для машин (пример ниже).
 - **Syslog** — стандарт для серверных систем.


2. **Настройте ротацию**:
 - Разделяйте логи по дням/часам.
 - Ограничьте размер файлов.
 - Удаляйте старые записи по TTL.

3. **Используйте централизованный сбор**:
 - Собирайте логи с разных серверов в одно хранилище (ELK Stack, Fluentd).
4. **Добавьте контекст**:
 - Включайте trace ID для сквозной трассировки.
 - Фиксируйте IP, user agent, session ID.
5. **Защитите данные**:
 - Не записывайте пароли, токены, персональные данные.
 - Шифруйте логи при передаче.

### Пример структурированного лога (JSON)
```json
{
"timestamp": "2025-11-17T10:30:45.123Z",
"level": "ERROR",
"service": "UserService",
"message": "Failed to update profile",
"context": {
"user_id": 123,
"ip": "192.168.1.100",
"trace_id": "abc123-def456"
}
}
```

### Инструменты для работы с логами
- **[[ELK]] Stack** ([[Elasticsearch]] + [[Logstash]] + [[Kibana]]) — анализ и визуализация.
- **Graylog** — централизованное логирование с оповещениями.
- **[[Prometheus]] + Loki** — мониторинг и логи для Kubernetes.
- **Fluentd/[[Logstash]]** — сбор и агрегация логов.
- **journalctl** (Linux) — просмотр системных логов.


### Типичные ошибки
- **Слишком много DEBUG‑логов** — перегружает хранилище.
- **Отсутствие контекста** — сложно понять причину ошибки.
- **Неструктурированные сообщения** — трудно автоматизировать анализ.
- **Хранение чувствительных данных** — риск утечки.
- **Нет ротации** — диски переполняются.


### Итог

Логирование — ключевой инструмент для:
- диагностики проблем;
- мониторинга здоровья системы;
- анализа производительности;
- соблюдения требований безопасности.


**Лучшие практики**:
- Используйте уровни логирования (ERROR, INFO и др.).
- Структурируйте логи (JSON/[[syslog]]).
- Централизуйте сбор.
- Защищайте конфиденциальные данные.
- Настройте ротацию и очистку.
