## ✅ Что такое **Client Pull**?

> **Client Pull** — это модель, при которой **клиент сам запрашивает данные у сервера** по расписанию или по событию.  
> Сервер **не отправляет данные сам** — он ждёт, пока клиент спросит.

### 🔁 Противоположность: **[[Server push]]**
- Server Push: сервер отправляет данные клиенту без запроса ([[webRTC webSocket|webSocket]], [[Server push|SSE]], Webhooks)
- Client Pull: клиент должен **спросить** — как в обычном HTTP-запросе

---

## ✅ 1. Паттерн **Polling**

> Клиент **регулярно опрашивает** сервер:  
> _«Есть ли новые данные?»_  
> → Сервер отвечает: _«Нет»_ или _«Вот данные»_.

### 🔹 Подвиды Polling

---

### 🟠 **Short Polling (Короткий опрос)**

> Клиент отправляет запросы **часто**, например, каждые 1–5 секунд — даже если данных нет.

#### 💬 Пример:
```http
GET /api/notifications HTTP/1.1
Host: example.com
```
→ Клиент делает это **каждые 2 секунды**.

#### ✅ Плюсы:
- Простая реализация
- Работает через любой HTTP-сервер
- Совместим со всеми браузерами и клиентами

#### ❌ Минусы:
- **Высокая нагрузка на сервер** — много пустых запросов
- **Задержка до 2 секунд** (если опрос раз в 2с)
- **Потребление трафика и батареи** (на мобильных устройствах)

#### 📌 Где используется:
- Старые веб-приложения
- Простые чаты до появления WebSocket
- API без поддержки push

---

### 🟢 **Long Polling (Длинный опрос)**

> Клиент отправляет запрос — сервер **не отвечает сразу**, а **держит соединение открытым**, пока:
- Появятся новые данные → сервер отвечает
- Или истечёт таймаут (например, 30–60 сек)

После ответа клиент **сразу отправляет новый запрос**.

#### 💬 Пример:
```http
GET /api/notifications?timeout=60 HTTP/1.1
```
→ Сервер ждёт 60 секунд, пока не появится новое уведомление.

Если пришло уведомление через 10 сек — сервер сразу отвечает.  
Если нет — через 60 сек возвращает пустой ответ → клиент снова запрашивает.

#### ✅ Плюсы:
- **Низкая задержка** — данные приходят почти сразу
- **Меньше запросов** — не 30 в минуту, а ~1–2
- Поддерживается везде (HTTP/1.1)

#### ❌ Минусы:
- **Держит соединения открытыми** → нагрузка на сервер (много одновременных соединений)
- **Не масштабируется** как WebSocket
- Не подходит для миллионов клиентов

#### 📌 Где используется:
- Старые чаты, уведомления
- Системы без WebSocket (например, в старых браузерах)
- Как "запасной вариант" перед переходом на SSE/WebSocket

> 💡 **Long Polling — это "хак" для имитации push-уведомлений через HTTP**

## ✅ 2. **Композиция API (API Composition)**

> Это **не метод получения данных**, а **архитектурный паттерн**, при котором **клиент запрашивает данные у нескольких микросервисов**, чтобы собрать полный ответ.

### 🔧 Как работает:
1. Клиент делает один запрос:  
   `GET /api/user-profile/123`
2. Сервис-агрегатор (API Gateway / Backend-for-Frontend) делает **несколько внутренних запросов**:
   - `GET /api/user/info/123` → имя, email
   - `GET /api/user/orders/123` → последние заказы
   - `GET /api/user/notifications/123` → уведомления
3. Агрегатор объединяет ответы → отправляет клиенту единый JSON

#### 💬 Пример ответа:
```json
{
  "user": { "id": 123, "name": "Alice" },
  "orders": [ { "id": 55, "amount": 1200 } ],
  "notifications": [ { "type": "new_order", "time": "2025-04-05T10:00:00Z" } ]
}
```

#### ✅ Плюсы:
- Клиенту **не нужно знать про микросервисы**
- Упрощает фронтенд — один вызов вместо 5
- Можно кэшировать агрегированный ответ
- Удобно для **Frontend-специфичных моделей**

#### ❌ Минусы:
- **Сервис-агрегатор становится узким местом**
- **Сложнее отлаживать** — один запрос → 5 сервисов
- **Задержка растёт** — ждём самого медленного сервиса
- **Не подходит для реального времени** — это **pull**, а не push

#### 📌 Где используется:
- Микросервисные архитектуры
- BFF (Backend for Frontend)
- Системы с разрозненными данными (CRM, заказы, уведомления)

> 💡 Композиция API — это **Client Pull + агрегация**.  
> Клиент делает **один pull-запрос**, но за кулисами — **много внутренних pull-запросов**.

## ✅ Сравнение: Polling vs API Composition

| Критерий | **Short Polling** | **Long Polling** | **API Composition** |
|----------|-------------------|------------------|---------------------|
| **Цель** | Получить обновления | Получить обновления с меньшей задержкой | Получить агрегированный ответ |
| **Частота запросов** | Высокая (каждые 1–5с) | Низкая (1 раз за 30–60с) | Раз в запрос пользователя |
| **Задержка** | До 5 сек | До 1 сек | Зависит от сервисов |
| **Нагрузка на сервер** | Очень высокая | Средняя | Средняя/высокая (внутренние запросы) |
| **Используется для** | Уведомления, чаты | Уведомления, чаты | Фронтенд-данные (профиль, дашборд) |
| **Подходит для реального времени?** | ❌ Нет | ✅ Частично | ❌ Нет — это pull |
| **Требует WebSocket?** | ❌ Нет | ❌ Нет | ❌ Нет |

## ✅ Когда что использовать?

| Сценарий | Рекомендация |
|----------|--------------|
| ✅ Простой веб-интерфейс, без сложной инфраструктуры | ➤ **Short Polling** |
| ✅ Нужны уведомления, но нет WebSocket | ➤ **Long Polling** |
| ✅ Нужно собрать данные из 5 микросервисов для одного экрана | ➤ **API Composition** |
| ✅ Реальный чат, мониторинг, транзакции в реальном времени | ➤ **WebSocket / SSE** (не Client Pull!) |
| ✅ Высокая нагрузка, 100K+ клиентов | ➤ **Отказаться от Polling — перейти на Server Push** |

---

## ✅ Финальный вывод

| Тип | Что делает | Когда использовать |
|-----|------------|---------------------|
| **Short Polling** | Клиент спрашивает каждые 1–5 сек | Простые системы, MVP |
| **Long Polling** | Клиент спрашивает — сервер ждёт | Быстрые уведомления без WebSocket |
| **API Composition** | Клиент спрашивает — сервер собирает данные из 5 источников | Микросервисы + фронтенд |

> 💬 _“Client Pull is simple, but expensive.  
> Server Push is efficient, but complex.”_
