### Syslog: что это

**Syslog** — стандартный протокол и механизм для сбора, передачи и хранения системных сообщений (логов) в UNIX‑подобных ОС и сетевом оборудовании. Позволяет централизовать логи с множества устройств в едином хранилище.

### Назначение

- Сбор логов от приложений, сервисов, ОС, сетевого оборудования (маршрутизаторов, коммутаторов).
- Централизованное хранение для анализа и аудита.
- Мониторинг состояния инфраструктуры.
- Диагностика сбоев и инцидентов безопасности.

### Как работает

1. **Источник сообщений** (приложение, сервис, устройство) формирует лог‑сообщение.
2. **Syslog‑клиент** (демон `syslogd` / `rsyslog` / `journald`) упаковывает сообщение по правилам протокола.
3. **Передача** по сети ([[IP TCP UDP|UDP]]/[[IP TCP UDP|TCP]]/[[TLS]]) на сервер сбора.
4. **Сервер syslog** (например, `rsyslog`, `syslog‑ng`) принимает, фильтрует и сохраняет сообщения в файлы/БД.
5. **Хранение и анализ** — логи пишутся в файлы (обычно `/var/log/`), индексируются в [[Elasticsearch]] и т. п.

### Формат сообщения (RFC 5424)

Типовое сообщение syslog имеет структуру:
```
<PRI>VERSION TIMESTAMP HOSTNAME APP‑NAME PROCID MSGID [STRUCTURED‑DATA] MSG
```

**Пример**:
```
<165>1 2025-11-17T10:30:45.123Z myhost app 1234 ID47 [example@123 user="alice"] Login successful
```

**Поля**:
- `<PRI>` — приоритет (комбинация *Facility* и *Severity*).
- `VERSION` — версия протокола (обычно `1`).
- `TIMESTAMP` — время события в формате ISO 8601.
- `HOSTNAME` — имя хоста‑источника.
- `APP‑NAME` — название приложения/сервиса.
- `PROCID` — ID процесса.
- `MSGID` — идентификатор типа сообщения.
- `[STRUCTURED‑DATA]` — опциональные пары ключ‑значение.
- `MSG` — текстовое сообщение.

### Уровни серьёзности (Severity)

| Код | Уровень | Описание |
|-----|--------|---------|
| 0 | Emergency | Система не работоспособна |
| 1 | Alert | Требуется немедленное вмешательство |
| 2 | Critical | Критические условия |
| 3 | Error | Ошибки |
| 4 | Warning | Предупреждения |
| 5 | Notice | Нормальные, но значимые события |
| 6 | Informational | Информативные сообщения |
| 7 | Debug | Отладочная информация |

> *Примечание*: приоритет `<PRI>` вычисляется как `8 × Facility + Severity`.

### Транспортные протоколы

- **UDP (порт 514)** — простой, но ненадёжный (пакеты могут теряться).
- **TCP** — гарантированная доставка, поддержка больших сообщений.
- **TLS/SSL** — шифрование трафика (порты 6514 и др.).
- **RELPS** (Reliable Event Logging Protocol) — расширение с подтверждением доставки.

### Компоненты в Linux

1. **`rsyslog`** — современная реализация с поддержкой:
	 - фильтров;
	 - шаблонов форматирования;
	 - модулей для отправки в [[Elasticsearch]], [[software-engineer/технологии/kafka/Kafka]] и т. п.
2. **`syslog‑ng`** — гибкая альтернатива с расширенными возможностями маршрутизации.
3. **`journald`** (systemd) — внутренний логгер, может пересылать в rsyslog.

### Пример конфигурации rsyslog (`/etc/rsyslog.conf`)

```bash
# Отправка всех логов с приоритетом >= error на сервер
*.error @192.168.1.100:514

# Локализованное хранение аутентификационных событий
authpriv.* /var/log/secure

# Приём логов по UDP
module(load="imudp")
input(type="imudp" port="514")
```

### Где хранятся логи (типичные пути)

- `/var/log/syslog` — основные системные логи.
- `/var/log/auth.log` — события аутентификации.
- `/var/log/kern.log` — сообщения ядра.
- `/var/log/messages` — общие сообщения (в некоторых дистрибутивах).
- `/var/log/<приложение>/` — логи конкретных сервисов.

### Преимущества syslog

- **Стандартизация** — единый формат для разнородного оборудования.
- **Централизация** — сбор логов с сотен устройств в одном месте.
- **Масштабируемость** — поддержка TCP/TLS для надёжной передачи.
- **Гибкость** — фильтрация, маршрутизация, преобразование сообщений.
- **Интеграция** — совместимость с SIEM (Splunk, Graylog), ELK.

### Ограничения

- **UDP без гарантий доставки** — риск потери логов.
- **Отсутствие аутентификации в базовой версии** — возможны подделки сообщений.
- **Ограниченная структура** — сложнее анализировать, чем JSON.
- **Нагрузка на сеть** — при большом объёме логов.

### Лучшие практики

1. Используйте **TCP/TLS** для критичных логов.
2. Настройте **фильтрацию** на клиенте — не отправляйте избыточные DEBUG‑сообщения.
3. Применяйте **ротацию логов** (logrotate) для управления размером файлов.
4. Шифруйте **конфиденциальные данные** перед записью.
5. Мониторьте **заполненность диска** в `/var/log/`.
6. Интегрируйте с **[[SIEM]]/[[ELK]]** для анализа и оповещений.

### Итог

**Syslog** — фундамент мониторинга и аудита в UNIX‑системах:
- стандартизирует формат логов;
- обеспечивает централизованный сбор;
- поддерживает разные транспортные протоколы;
- интегрируется с современными инструментами анализа.

Используйте его для:
- сбора логов с серверов и сетевого оборудования;
- построения системы мониторинга;
- соблюдения требований безопасности и соответствия ([[PCI-DSS]] DSS, GDPR и др.).
