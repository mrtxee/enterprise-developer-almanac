### Паттерн Adaptive Concurrency («адаптивная параллельность»)

**Суть:** динамическое регулирование числа одновременно обрабатываемых запросов на основе *текущей производительности системы*, чтобы максимизировать пропускную способность **без перегрузки**.

### Зачем нужен

Традиционные подходы (фиксированные лимиты, очереди) часто:
- либо **недоиспользуют** ресурсы (лимит слишком низкий);
- либо **перегружают** систему (лимит слишком высокий).

Adaptive Concurrency решает эту проблему, автоматически подстраиваясь под реальную производительность.

### Как работает

1. **Мониторинг ключевых метрик**  
   Система непрерывно измеряет:
   - время отклика (latency);
   - процент ошибок (error rate);
   - утилизацию CPU/памяти/IO;
   - длину очереди запросов.

2. **Динамическая корректировка лимита параллельности**  
   На основе метрик алгоритм:
   - **увеличивает** число одновременных запросов, если система справляется (низкие latency и ошибки);
   - **уменьшает**, если появляются признаки перегрузки (рост latency, ошибок, утилизация близка к 100 %).

3. **Обратная связь**  
   Изменения лимита влияют на нагрузку → новые метрики → следующая корректировка. Цикл повторяется.

### Ключевые алгоритмы (примеры)

1. **Concurrency Limits (Netflix)**  
   - Измеряет *95‑й перцентиль latency* для текущих запросов.  
   - Если latency растёт → снижает лимит параллельности.  
   - Если latency стабильна → постепенно увеличивает лимит.

2. **Gradient‑based (Google)**  
   - Использует градиентный спуск для поиска оптимального лимита.  
   - Реагирует на изменения за секунды.

3. **Queue‑based**  
   - Регулирует лимит так, чтобы длина очереди не превышала порог.  
   - Учитывает время ожидания в очереди.

### Преимущества

- **Максимизация пропускной способности**: система работает на пределе, но без перегрузки.  
- **Устойчивость к всплескам**: автоматически снижает нагрузку при перегрузке.  
- **Адаптивность**: подстраивается под изменения (апгрейд железа, новые версии ПО).  
- **Снижение ошибок**: предотвращает каскадные сбои из‑за перегрузки.  
- **Автоматизация**: не требует ручной настройки лимитов.

### Недостатки и ограничения


- **Сложность реализации**: нужны мониторинг и алгоритмы обратной связи.  
- **Задержка реакции**: даже быстрые алгоритмы реагируют за секунды/минуты.  
- **Локальные оптимумы**: может не учитывать глобальные зависимости (например, нагрузку на БД).  
- **Конфигурация**: требует подбора параметров (порогов, шагов изменения).

### Где применяют

- **Высокотрафиковые API** (соцсети, маркетплейсы).  
- **Микросервисные архитектуры** (защита от каскадных сбоев).  
- **Облачные сервисы** (автомасштабирование).  
- **Базы данных** (контроль числа подключений).  
- **CDN/Edge‑серверы** (оптимизация обработки запросов).
### Пример работы

**Сценарий:** сервис обрабатывает 100 запросов параллельно.  
1. Метрики показывают:  
   - latency = 100 мс (норма);  
   - ошибки = 0 %;  
   - CPU = 70 %.  
2. Adaptive Concurrency **увеличивает лимит** до 120.  
3. Через минуту:  
   - latency вырос до 300 мс;  
   - ошибки = 5 %.  
4. Система **снижает лимит** до 110.  
5. Через 30 сек:  
   - latency = 150 мс;  
   - ошибки = 0 %.  
1. Лимит остаётся на 110 до следующего изменения метрик.
### Важные нюансы

- **Границы лимитов**: всегда задают min/max, чтобы избежать крайностей.  
- **Гистерезис**: добавляют задержку между корректировками, чтобы избежать «дёрганий».  
- **Мультисервисность**: в микросервисах учитывают зависимости (например, лимит для сервиса не должен перегружать его БД).  
- **Тестирование**: проверяют на нагрузочных тестах, имитируя всплески и сбои.


### Вывод

Adaptive Concurrency — это **динамический регулятор нагрузки**, который:  
- заменяет жёсткие лимиты гибким управлением;  
- максимизирует производительность без риска перегрузки;  
- особенно полезен в распределённых системах с переменной нагрузкой.


Его цель — найти *золотую середину* между «работать быстрее» и «не упасть».
