**RPS (Requests Per Second)** и **QPS (Queries Per Second)** — это очень близкие, но не всегда взаимозаменяемые метрики.

Если говорить максимально просто:
*   **RPS** считает **запросы** (HTTP-запросы, RPC-вызовы).
*   **QPS** считает **операции поиска/чтения** в базах данных (SQL SELECT) или поисковых системах (Elasticsearch).

Вот главные отличия в деталях.

### 1. Разница в определении

| Характеристика | **RPS** (Requests Per Second) | **QPS** (Queries Per Second) |
| :--- | :--- | :--- |
| **Основной смысл** | Количество **запросов** к серверу (API, веб-страницы) | Количество **операций чтения/поиска** внутри БД |
| **Где используют** | Веб-сервера, балансировщики, API-шлюзы | Базы данных, поисковые движки (Elasticsearch, Solr) |
| **Что измеряет** | Входящие HTTP/RPC/ gRPC запросы от клиентов | Выполненные `SELECT` (или аналогичные) запросы внутри СУБД |

### 2. Взаимосвязь (один RPS порождает много QPS)

Самый важный нюанс: **один пользовательский запрос (RPS) может вызвать множество внутренних запросов к базе данных (QPS).**

**Пример:**
Пользователь открывает страницу «Друзья» в социальной сети.
1.  **RPS:** +1 (браузер отправил 1 HTTP-запрос к API `/friends`).
2.  Серверное приложение, обрабатывая этот запрос, может выполнить несколько операций в БД (QPS):
    *   Запрос 1: Получить список `user_id` друзей.
    *   Запрос 2: Для каждого друга (или одним сложным запросом) получить профиль.
    *   Запрос 3: Получить статус «онлайн».
    *   **Итоговый QPS:** ~10-20.

> **Формула (приблизительная):**
> `QPS сервера = RPS приложения × Среднее количество запросов к БД на один обработчик`

### 3. Когда какая метрика важнее?

| Сценарий | Какая метрика важнее | Почему |
| :--- | :--- | :--- |
| **Планирование мощностей API** | **RPS** | Показывает реальную нагрузку на входе. |
| **Настройка пула соединений БД** | **QPS** | БД не важно, сколько пришло HTTP-запросов, важно, сколько реальных SQL-запросов выполняется. |
| **Оценка производительности бэкенда** | **Обе** | Нужно знать, сколько RPS может обработать приложение, и сколько QPS это создаст на БД. |
| **Поиск узких мест** | Сравнение **RPS → QPS** | Внезапное падение RPS при росте QPS — верный признак проблем с БД. |

### 4. Важный технический нюанс

В некоторых системах (например, в **Elasticsearch** или **Kafka**) разница стирается:

*   **Elasticsearch:** часто измеряют QPS, потому что «поисковый запрос» по смыслу ближе к Query.
*   **Балансировщики (Nginx, ALB):** почти всегда говорят об **RPS**.
*   **Базы данных:** внутри себя могут считать и RPS (для хранимых процедур, команд), и QPS (для обычных `SELECT`).

### Краткий итог

*   **RPS** — это про **внешние запросы** (сколько раз постучали в дверь).
*   **QPS** — это про **внутренние операции поиска** (сколько раз заглянули в базу данных за информацией).
*   **На практике для простых API (один запрос = один SQL) RPS ≈ QPS.** Но как только появляются сложные выборки или N+1 проблема, QPS может быть в 10-100 раз выше.
