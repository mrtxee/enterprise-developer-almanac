## Клиентское кэширование

**Клиентское кэширование** — это механизм сохранения данных **на стороне клиента** (браузера, мобильного приложения, десктоп‑программы) для уменьшения количества запросов к серверу и ускорения работы интерфейса.

**Где хранится кэш**
1. **Браузер**:
	- `localStorage` / `sessionStorage` (до 5–10 МБ);
	- IndexedDB (до сотен МБ);
	- Cache API (для HTTP‑ресурсов);
	- HTTP‑кэш (автоматическое сохранение по заголовкам).
2.  **Мобильные приложения**:
	- файловая система;
	- SQLite / Realm / другие локальные БД;
	- SharedPreferences (Android) / UserDefaults (iOS).
3. **Десктоп‑приложения**:
	- локальная файловая система;
	- встраиваемые БД (SQLite, LevelDB).

**Преимущества**
1. **Скорость**: данные загружаются мгновенно из локального хранилища.
2. **Снижение нагрузки на сервер**: меньше запросов = меньше трафика и CPU на сервере.
3. **Работа офлайн**: частичный функционал доступен без интернета.
4. **Плавность интерфейса**: нет «мигания» при повторных загрузках.
5. **Экономия трафика** для мобильных пользователей.

**Какие данные кэшируют**
- Статические ресурсы: CSS, JS, изображения, шрифты.
- API‑ответы: списки товаров, профили пользователей, настройки.
- Результаты вычислений: отформатированные даты, отсортированные массивы.
- Временные состояния: корзина, черновики форм.
### Механизмы управления кэшем
1. HTTP‑заголовки (для браузера)

#### 1. HTTP‑заголовки (для браузера)
Сервер указывает правила кэширования через заголовки:
- `Cache-Control: max-age=3600` — хранить 1 час.
	- `Expires: Wed, 25 Aug 2022 12:00:00 GMT`
		- Устаревший заголовок, аналог `Cache-Control: max-age`, с меньшим приоритетом чем max-age
- `ETag` / `Last-Modified` — проверка актуальности при `max-age=0`.
- `Vary` — учёт параметров (например, `Accept-Encoding`).

**Директивы заголовка Cache-Control**

| Директива         | Описание                                                                                                                                                                                                                        | Пример использования             |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------- |
| `max-age`         | Устанавливает максимальное время жизни кеша                                                                                                                                                                                     | `Cache-Control: max-age=600`     |
| `no-cache`        | Требует проверки данных на сервере перед использованиемя. Работает так, что клиент отправляет Etag версии данных в кэше. А сервер проверяет не является ли ETag актуальным                                                      | `Cache-Control: no-cache`        |
| `no-store`        | Сообщает не кешировать ресурс, например чувствительную информацию                                                                                                                                                               | `Cache-Control: no-store`        |
| `must-revalidate` | Сообщает, что каждый запрос нужно делать заново и ни при каких условиях не предоставлять пользователю закешированный контент. Вместе с использованием `no-cache` и устареванием кеша сообщает, что нужно брать данные с сервера | `Cache-Control: must-revalidate` |
| `public`          | Ресурс кешируется для всех пользователей                                                                                                                                                                                        | `Cache-Control: public`          |
| `private`         | Ресурс кешируется только для одного пользователя                                                                                                                                                                                | `Cache-Control: private`         |


#### 2. Сервис‑воркеры (Service Workers)
Позволяют:
- перехватывать сетевые запросы;
- возвращать данные из Cache API;
- обновлять кэш в фоне (`stale-while-revalidate`).

#### 3. Локальные хранилища (JS‑код)
- `localStorage.setItem('key', JSON.stringify(data))` — простые данные.
- IndexedDB — большие структурированные данные.
- Cache API — HTTP‑ресурсы.

#### 4. Библиотеки и фреймворки
- **React/Vue**: библиотеки вроде `react-query` / `vue-query` управляют кэшем API‑ответов.
- **Apollo Client** (для GraphQL): локальный кэш с нормализацией.
- **SWR** / **TanStack Query**: автоматическое обновление, инвалидация.

### Стратегии обновления кэша

1. **Time‑to‑Live (TTL)**
	- Данные хранятся N секунд/минут.
	- По истечении срока — запрос на сервер.
	- *Плюс*: простота. *Минус*: риск устаревания.

2. **Инвалидация по событию**
	- При изменении данных на сервере — отправка сигнала клиенту (WebSockets, SSE).
	- Клиент удаляет/обновляет кэш.
	- *Плюс*: актуальность. *Минус*: сложность.

3. **Stale‑while‑revalidate**
 - Возвращать старые данные + параллельно обновлять их в фоне.
 - *Плюс*: скорость + актуальность.

4. **Оптимистичное обновление**
 - Сразу менять кэш при действии пользователя (например, «лайк»), не дожидаясь ответа сервера.
 - *Плюс*: мгновенная реакция. *Минус*: риск конфликта.

5. **Версионирование ключей**
 - Ключ кэша включает версию: `user:123:v2`.
 - При обновлении версии — старый кэш игнорируется.

### Проблемы и ограничения

1. **Устаревание данных**
 - Решение: комбинации TTL + инвалидация.

2. **Ограниченный объём**
 - Решение: стратегии вытеснения (LRU, FIFO) для больших данных.

3. **Безопасность**
 - Не кэшировать чувствительные данные (пароли, токены).
 - Использовать `httpOnly` и `secure` для куки.

4. **Синхронизация между вкладками/устройствами**
 - Решение: BroadcastChannel, IndexedDB + события.

5. **Очистка при обновлении приложения**
 - Решение: версионирование кэша, автоматическая инвалидация при деплое.

### Итог

Клиентское кэширование — ключевой инструмент для:
- ускорения интерфейсов;
- снижения нагрузки на сервер;
- поддержки офлайн‑работы.

**Важно**:
- выбирать стратегию под сценарий (TTL, инвалидация, stale‑while‑revalidate);
- контролировать объём и актуальность;
- тестировать на разных устройствах и сетях.

`ETag` и `Last‑Modified` — это **HTTP‑заголовки**, позволяющие клиенту и серверу эффективно согласовывать актуальность кэшированных данных. Их цель — избежать повторной загрузки целого ресурса, если он не изменился.

### Как это работает в целом Last-Modified, ETag

1. Клиент впервые запрашивает ресурс (например, изображение или HTML‑страницу).
2. Сервер отправляет ресурс и добавляет к ответу один или оба заголовка: `ETag` или `Last‑Modified`.
3. Клиент сохраняет ресурс в кэш вместе с этими заголовками.
4. При повторном запросе клиент отправляет серверу **проверяющие заголовки**:
 - `If-None-Match` (со значением `ETag`);
 - `If-Modified-Since` (со значением `Last‑Modified`).
5. Сервер сравнивает значения:
 - Если ресурс **не изменился**, он отвечает статусом `304 Not Modified` **без тела ответа** — клиент использует кэш.
 - Если ресурс **изменился**, сервер отправляет новый ресурс со статусом `200 OK` и обновлёнными заголовками.

---

### `Last-Modified`

**Суть**: указывает дату и время последнего изменения ресурса на сервере (в формате GMT).

**Пример заголовка ответа**:
```
Last-Modified: Fri, 1 Dec 2014 01:01:01 GMT
```

**Как используется**:
- Клиент при повторном запросе добавляет заголовок:
```
If-Modified-Since: Fri, 1 Dec 2014 01:01:01 GMT
```
- Сервер проверяет, изменялся ли ресурс после указанной даты.
- Если не изменялся — ответ `304 Not Modified`.
- Если изменялся — ответ `20 Newton OK` с новым содержимым и обновлённым `Last-Modified`.

**Плюсы**:
- Простота реализации.
- Человекочитаемый формат (легко отлаживать).

**Минусы**:
- Точность до секунды — может не хватать для очень частых обновлений.
- Не учитывает изменения, которые не влияют на содержимое (например, переиндексация).

---

### `ETag` (Entity Tag)

**Суть**: уникальный идентификатор версии ресурса. Обычно это хеш (например, MD5) содержимого или комбинации метаданных (время изменения + размер).

**Пример заголовка ответа**:
```
ETag: "686897696a7c876b7e"
```

**Как используется**:
- Клиент при повторном запросе добавляет заголовок:
```
If-None-Match: "686897696a7c876b7e"
```
- Сервер сравнивает переданный `ETag` со своим текущим.
- Если совпадают — ответ `304 Not Modified`.
- Если не совпадают — ответ `200 OK` с новым содержимым и новым `ETag`.

**Виды `ETag`**:
- **Сильный (`"6868..."`)** — гарантирует байтовую идентичность ресурсов.
- **Слабый (`W/"6868..."`)** — указывает на семантическую эквивалентность (содержание может немного отличаться, например, разными рекламными блоками).

**Плюсы**:
- Высокая точность (даже для мельчайших изменений).
- Гибкость (сервер сам определяет алгоритм генерации).

**Минусы**:
- Нечитаемость для человека.
- Требует вычислений на сервере (генерация хеша).

---

### Сравнение `Last-Modified` и `ETag`

| Критерий | `Last-Modified` | `ETag` |
|--------|-----------------|--------|
| **Точность** | До секунды | До байта (сильный) / семантики (слабый) |
| **Формат** | Дата в GMT | Строка‑идентификатор (хеш) |
| **Нагрузка на сервер** | Низкая (чтение mtime файла) | Средняя (вычисление хеша) |
| **Человекочитаемость** | Да | Нет |
| **Устойчивость к «ложным» изменениям** | Ниже (переиндексация может обновить дату) | Выше (зависит от алгоритма хеширования) |

### Практические рекомендации

1. **Используйте оба заголовка**
 - `Last-Modified` как «быструю» проверку.
 - `ETag` для точной валидации.

 - Клиент может отправлять оба проверяющих заголовка: `If-Modified-Since` и `If-None-Match`.

2. **Для статических файлов** (CSS, JS, изображения):
 - `ETag` на основе хеша содержимого.
 - `Last-Modified` на основе mtime файла.

3. **Для динамических ресурсов** (API, HTML‑страницы):
 - `ETag` на основе хеша ответа или версии данных.
 - `Last-Modified` на основе даты последнего обновления сущности.

4. **Синхронизация серверов**
 - Если у вас несколько серверов, убедитесь, что `ETag` и `Last-Modified` генерируются одинаково (иначе клиент может получить `200 OK` вместо `304`).

5. **Отладка**
 - Проверьте заголовки в DevTools (вкладка *Network* → *Headers*).
 - Убедитесь, что сервер возвращает `304 Not Modified` при повторных запросах.

---

### Пример диалога клиент‑сервер

1. **Первый запрос клиента**:
 ```
 GET /style.css HTTP/1.1
 Host: example.com
 ```

2. **Ответ сервера**:
 ```
 HTTP/1.1 200 OK
 Content-Type: text/css
 Last-Modified: Fri, 1 Dec 2014 01:01:01 GMT
 ETag: "686897696a7c876b7e"
 ...тело файла...
 ```

3. **Повторный запрос клиента**:
 ```
 GET /style.css HTTP/1.1
 Host: example.com
 If-Modified-Since: Fri, 1 Dec 2014 01:01:01 GMT
 If-None-Match: "686897696a7c876b7e"
 ```

4. **Ответ сервера (если не изменилось)**:
 ```
 HTTP/1.1 304 Not Modified
 ```

---

**Итог**:
- `Last-Modified` и `ETag` — ключевые механизмы **валидации кэша**.
- Они экономят трафик и нагрузку на сервер, позволяя клиенту использовать локальную копию, если ресурс не изменился.
- Для максимальной эффективности используйте оба заголовка и убедитесь в их корректной генерации на сервере.

### Что такое заголовок `Vary`

`Vary` — HTTP‑заголовок ответа, который **указывает, по каким запросам‑заголовкам сервер может возвращать разные варианты ресурса**. Он помогает кэшу (браузеру, прокси, CDN) понять: *можно ли использовать сохранённую копию для нового запроса* или нужно обратиться к серверу за обновлённой версией.

### Зачем нужен `Vary`

Без `Vary` кэш может вернуть неподходящий вариант ресурса, если:
- сервер отдаёт разный контент в зависимости от заголовка запроса (например, `Accept-Encoding`, `User-Agent`);
- клиент меняет параметры, влияющие на ответ, но кэш этого «не замечает».

**Пример проблемы**:
- Клиент запрашивает сжатый (`gzip`) CSS‑файл — сервер возвращает его и кладёт в кэш.
- Другой клиент без поддержки `gzip` запрашивает тот же URL — кэш отдаёт сжатую версию, которая не работает.

### Как работает `Vary`

1. **Сервер** в ответе указывает, от каких заголовков зависит контент:
 ```http
 Vary: Accept-Encoding, User-Agent
 ```
2. **Кэш** при сохранении ответа запоминает не только URL, но и значения указанных заголовков из запроса.
3. **При новом запросе** кэш:
 - сравнивает текущие значения заголовков (`Accept-Encoding`, `User-Agent`) с сохранёнными;
 - если они совпадают — отдаёт кэшированную копию;
 - если отличаются — делает запрос к серверу.

### Ключевые сценарии использования

1. **Сжатие контента** (`Accept-Encoding`)
 ```http
 Vary: Accept-Encoding
 ```
 - Сервер может отдавать `gzip` или `br` (Brotli) в зависимости от поддержки клиента.
 - Кэш хранит отдельные версии для разных значений `Accept-Encoding`.

2. **Адаптивный контент** (`User-Agent`, `Device-Type`)
 ```http
 Vary: User-Agent
 ```
 - Разные версии страницы для мобильных и десктопов.
 - Кэш не перепутает мобильную и десктопную версии.

3. **Локализация** (`Accept-Language`, `Accept-Charset`)
 ```http
 Vary: Accept-Language
 ```
 - Отдельные кэшированные копии для `ru`, `en`, `es` и т. д.

4. **Контент с учётом региона** (`X-Geo-Region`)
 ```http
 Vary: X-Geo-Region
 ```
 - Разные цены/товары для разных стран.

5. **Авторизация** (`Authorization`, `Cookie`)
 ```http
 Vary: Authorization
 ```
 - Персональные данные пользователя не попадут в общий кэш.

### Важные нюансы

1. **Чувствительность к регистру**
 - Значения в `Vary` не чувствительны к регистру (например, `accept-encoding` = `Accept-Encoding`).
 - Но лучше использовать канонический регистр (как в спецификации).

2. **Множественные заголовки**
 - Можно указывать несколько заголовков через запятую:
 ```http
 Vary: Accept-Encoding, Accept-Language, User-Agent
 ```

3. **Значение `*` (звёздочка)**
 - ```http
 Vary: *
 ```
 - Означает: *«ответ зависит от любых заголовков запроса»*.
 - Кэш **не будет сохранять** копию — каждый запрос пойдёт на сервер.
 - Используйте осторожно: убивает эффективность кэширования.

4. **Взаимодействие с `Cache-Control`**
 - `Vary` работает вместе с `Cache-Control`/`Expires`.
 - Пример:
 ```http
 Cache-Control: max-age=3600
 Vary: Accept-Encoding
 ```
 - Кэш хранится 1 час, но только для совпадающих значений `Accept-Encoding`.

5. **Прокси и CDN**
 - Промежуточные кэши (Cloudflare, Nginx) тоже учитывают `Vary`.
 - Некорректный `Vary` может привести к избыточным запросам к бэкенду.

### Примеры

#### Пример 1: Сжатие CSS
**Ответ сервера**:
```http
HTTP/1.1 200 OK
Content-Type: text/css
Content-Encoding: gzip
Vary: Accept-Encoding
Cache-Control: max-age=86400
...тело сжатого CSS...
```

**Что происходит**:
- Клиент с `Accept-Encoding: gzip` получит сжатый CSS и сохранит его в кэш.
- Клиент без `gzip` сделает запрос к серверу — сервер вернёт несжатую версию.

#### Пример 2: Мобильная и десктопная версии
**Ответ сервера**:
```http
HTTP/1.1 200 OK
Content-Type: text/html
Vary: User-Agent
Cache-Control: max-age=1800
...HTML для мобильного...
```

**Что происходит**:
- Мобильный браузер (`User-Agent: Mobile`) получит мобильную версию и сохранит её.
- Десктопный браузер получит десктопную версию — кэш не перепутает их.

### Рекомендации

1. **Используйте `Vary` только для значимых заголовков**
 - Избегайте избыточных значений — это усложняет логику кэша.

2. **Тестируйте с DevTools**
 - Проверьте, что кэш возвращает правильные версии для разных комбинаций заголовков.

3. **Учитывайте CDN и прокси**
 - Некоторые кэши могут игнорировать `Vary` или обрабатывать его неоптимально.

4. **Не используйте `Vary: *` без крайней необходимости**
 - Это отключает кэширование.

5. **Комбинируйте с `ETag`/ `Last-Modified`**
 - Для дополнительной валидации актуальности данных.

### Итог

- `Vary` — ключевой заголовок для **умного кэширования** контента, который зависит от параметров запроса.
- Он позволяет кэшу различать версии ресурса по значениям заголовков (например, сжатие, локализация, устройство).
- Правильное использование `Vary` повышает эффективность кэша и предотвращает ошибки выдачи неподходящего контента.
