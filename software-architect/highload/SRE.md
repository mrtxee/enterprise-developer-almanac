## Site Reliability Engineering (SRE)

**SRE** — подход к обеспечению надёжности и устойчивости ИТ‑систем, разработанный в Google. Это синтез *инфраструктурной инженерии* и *разработки ПО*, нацеленный на баланс между **новыми функциями** и **стабильностью работы**.

### Суть подхода

В отличие от классического администрирования, SRE:
- использует **инженерные методы** (код, автоматизацию) вместо ручных операций;
- измеряет надёжность через **объективные метрики** ([[SLI|SLI, SLO, SLAs]]);
- рассматривает операции как **часть разработки**, а не отдельный процесс;
- допускает **контролируемые сбои** для обучения системы.

### Ключевые принципы

1. **Автоматизация везде, где возможно**
 - Ручные операции — источник ошибок. Автоматизируйте:
 - развёртывание;
 - мониторинг;
 - восстановление после сбоев;
 - масштабирование.

2. **Измеряемая надёжность**
 - **SLI** (Service Level Indicator) — метрика (например, latency, error rate).
 - **SLO** (Service Level Objective) — целевое значение SLI (например, «99,9 % запросов за <200 мс»).
 - **SLA** (Service Level Agreement) — договор с пользователем о допустимых простоях.

3. **Error budgets** (бюджет ошибок)
 - Разрешённый % времени простоя/ошибок (например, 0,1 % в месяц).
 - Пока бюджет не исчерпан — можно выпускать новые функции.
 - При исчерпании — приоритет на стабилизацию.

4. **Инцидент‑менеджмент как инженерная задача**
 - Чёткие процедуры реагирования.
 - Постмортемы (postmortems) без поиска виноватых — только анализ причин.
 - Автоматическое восстановление (self‑healing).

5. **Проектирование для сбоев**
 - Системы должны работать при частичных отказах (частичная деградация).
 - Регулярные «стресс‑тесты» (например, Chaos Engineering).

6. **Минимальные ручные вмешательства**
 - Операции — через код (Infrastructure as Code).
 - «Ручные действия» документируются и автоматизируются.

7. **Баланс «новые функции vs стабильность»**
 - 50 % времени SRE‑инженеров — на разработку, 50 % — на операции.
 - Новые фичи не должны ломать SLO.

### Основные практики

1. **[[Monitoring|Мониторинг]] и алертинг**
 - Сбор SLI (latency, throughput, error rate, saturation).
 - Умные алерты (не «шум», а сигналы о реальных проблемах).
 - Дашборды для анализа трендов.

2. **Управление изменениями**
 - Канареечные релизы ([[Canary release]]).
 - Фиче‑флаги (feature flags).
 - Откаты (rollbacks) за минуты.

3. **Capacity planning**
 - Прогнозирование нагрузки.
 - Горизонтальное масштабирование.
 - Резервирование ресурсов.

4. **Disaster recovery**
 - Регулярное тестирование восстановления.
 - Гео‑распределённые реплики.
 - Планы на случай катастроф.

5. **Chaos Engineering**
 - Искусственное создание сбоев (например, отключение серверов).
 - Проверка устойчивости системы.

 - Инструменты: Chaos Monkey, Gremlin.

6. **Документация и знания**
 - Runbooks (инструкции для типовых инцидентов).
 - База знаний (KB) по архитектуре и решениям.
 - Обучение команды.

### Отличия от DevOps

- **[[DevOps]]** — культура сотрудничества dev и ops, фокус на скорость доставки.
- **SRE** — конкретная инженерная методология с жёсткими метриками и процессами.
- SRE можно считать *реализацией DevOps* для высоконагруженных систем.

### Типичные метрики SRE (SLIs)

- **Latency**: p99 < 200 мс.
- **Error rate**: < 0,1 %.
- **Availability**: 99,95 % (5 минут простоя в месяц).
- **Throughput**: 1 000 RPS.
- **Saturation**: CPU < 70 %, memory < 80 %.

### Инструменты SRE
- **Мониторинг**: Prometheus, Grafana, ELK, Datadog.
- **Алерты**: Alertmanager, PagerDuty.
- **CI/CD**: GitLab CI, Jenkins, ArgoCD.
- **Инфраструктура**: Terraform, Ansible, Kubernetes.
- **Трассировка**: Jaeger, Zipkin.
- **Chaos**: Chaos Monkey, Litmus.

### Когда внедрять SRE

- Система растёт, и ручной контроль становится невозможным.
- Частые инциденты из‑за изменений.
- Нет чётких критериев надёжности.
- Высокая цена простоя (финансовая, репутационная).

### Итог

SRE — это:
- **Инженерия**, а не администрирование.
- **Баланс** между инновациями и стабильностью.
- **Прогнозируемость** через метрики.
- **Готовность к сбоям**, а не попытка их избежать.

- **Культура обучения** на ошибках.

Цель SRE — не «идеальная безотказность», а **управляемая надёжность**, позволяющая бизнесу развиваться без критических рисков.
