### Паттерн Stand‑in (заместитель, подставной компонент)

**Суть паттерна**  
Stand‑in — это компонент‑заместитель, временно принимающий на себя функции основного сервиса/системы. Его цель — обеспечить непрерывность работы при недоступности или перегрузке «оригинала».

### Ключевые цели

- **Обеспечение отказоустойчивости**: поддержание работы системы при сбоях основного компонента.  
- **Снижение нагрузки**: разгрузка основного сервиса в периоды пиков.  
- **Плавный деплой**: возможность обновления без простоя.  
- **Тестирование в продакшене**: проверка новых версий на реальном трафике.  

### Как работает

1. **Обнаружение проблемы**  
   Система мониторинга фиксирует:  
   - сбой основного сервиса;  
   - превышение нагрузки;  
   - плановое обслуживание.

2. **Переключение на stand‑in**  
   Трафик перенаправляется на заместитель (через балансировщик, DNS, сервис‑меш).

3. **Выполнение функций**  
   Stand‑in обрабатывает запросы одним из способов:  
   - возвращает **заранее заготовленные ответы** (кэш, заглушки);  
   - использует **упрощённую логику** (минимальный функционал);  
   - делегирует часть задач другим сервисам.

4. **Возврат к основному сервису**  
   После восстановления оригинала трафик переключается обратно.

### Типы stand‑in

1. **Кэширующий заместитель**  
   - Хранит копии ответов основного сервиса.  
   - Пример: CDN для статического контента.

2. **Заглушка (stub)**  
   - Возвращает фиксированные ответы (например, HTTP 200 OK или шаблонный JSON).  
   - Используется для тестирования или временного поддержания «жизни» системы.

3. **Упрощённый сервис**  
   - Реализует только критический функционал.  
   - Пример: режим «только чтение» при перегрузке БД.

4. **Резервный экземпляр**  
   - Полная копия основного сервиса, но с ограниченными ресурсами.  
   - Пример: вторичный сервер в другом регионе.

5. **Прокси‑заместитель**  
   - Принимает запросы, но выполняет лишь базовую валидацию, откладывая полную обработку.  
   - Пример: очередь сообщений, аккумулирующая запросы до восстановления сервиса.

### Примеры реализации

1. **Веб‑приложение**  
   - Основной сервис упал → stand‑in показывает страницу «Сервис временно недоступен» с кэшированным контентом.

2. **Микросервисная архитектура**  
   - Сервис заказов перегружен → stand‑in принимает запросы в очередь и возвращает «Ваш заказ в обработке».


3. **API**  
   - Версия 2 API недоступна → stand‑in перенаправляет запросы на версию 1 или возвращает заглушку.

4. **База данных**  
   - Реплика БД становится stand‑in при сбое мастера (режим чтения).

### Плюсы

- **Непрерывность сервиса**: минимизация простоев.  
- **Гибкость**: возможность поэтапного развёртывания.  
- **Контроль нагрузки**: предотвращение каскадных сбоев.  
- **Тестирование**: безопасный эксперимент с новыми версиями.

### Минусы и риски

- **Сложность**: требует настройки мониторинга и переключения.  
- **Согласованность данных**: возможны расхождения между stand‑in и основным сервисом.  
- **Ограниченный функционал**: пользователи получают урезанную версию сервиса.  
- **Задержки**: переключение и обработка через заместителя могут увеличивать latency.

### Когда применять

- **Критичные системы**, где недопустимы простои.  
- **Распределённые архитектуры** с множеством микросервисов.  
- **Плановые обновления** (zero‑downtime деплой).  
- **Защита от всплесков нагрузки** (DDoS, вирусный рост трафика).

### Важные нюансы

- **Автоматизация**: переключение должно быть максимально быстрым (желательно без ручного вмешательства).  
- **Мониторинг**: необходимо отслеживать состояние и производительность stand‑in.  
- **Тестирование**: регулярно проверять сценарии отказа и переключения.  
- **Документация**: пользователи должны понимать, что видят «упрощённую» версию сервиса.

---

**Итог**  
Stand‑in — это «страховой трос» для системы: он не заменяет основной сервис навсегда, но позволяет пережить сложные моменты с минимальными потерями.

### Stand‑in vs [[Resilience Patterns|Failover]]: ключевые различия

Хотя оба паттерна направлены на обеспечение отказоустойчивости, они различаются по **механизму работы**, **степени автоматизации** и **целям**.

---
## Stand‑in (заместитель)

**Суть:**  
Временный компонент‑заменитель, который *может* взять на себя функции основного сервиса — но не обязательно делает это автоматически.

**Как работает:**  
1. Stand‑in **готовится заранее** (например, развёртывается в инфраструктуре).  
2. При сбое основного сервиса **требуется ручное или полуавтоматическое переключение** трафика на stand‑in.  
3. Stand‑in обрабатывает запросы, имитируя функционал оригинала (полностью или частично).  
4. После восстановления основного сервиса трафик переключается обратно.

**Ключевые черты:**  
- **Не гарантирует мгновенного переключения** — может потребоваться вмешательство оператора.  
- Часто используется для **плановых работ** (обновление, миграция).  
- Может быть **упрощённой версией** сервиса (например, только чтение данных).  
- Подходит для сценариев, где допустимы **короткие простои**.

**Примеры:**  
- Резервный API‑сервис, который активируют вручную при сбое основного.  
- Временный статический сайт на CDN во время обновления основной версии.  
- Упрощённый микросервис, обрабатывающий критические запросы при перегрузке.

## Failover (автоматическое переключение)

**Суть:**  
Механизм **автоматического** перевода трафика на резервный компонент при обнаружении сбоя. Цель — минимизировать downtime без участия человека.


**Как работает:**  
1. Система **постоянно мониторит** состояние основного компонента.  
2. При обнаружении сбоя (тайм‑аут, ошибка, отсутствие ответа) **автоматически** переключает трафик на резерв.  
3. Резервный компонент (standby) уже запущен и синхронизирован с основным.  
4. После восстановления оригинала возможен **автоматический возврат** (в зависимости от настройки).

**Ключевые черты:**  
- **Полная автоматизация** — не требует ручного вмешательства.  
- Минимальное время простоя (секунды).  
- Требует **синхронизации данных** между основным и резервным компонентами.  
- Используется для **критичных систем** (платежи, медицина, телеком).

**Типы failover:**  
- **Active‑Passive:** основной компонент обрабатывает трафик, резервный ждёт в режиме standby.  
- **Active‑Active:** оба компонента активны, нагрузка распределяется между ними.  
- **Geographical:** переключение между дата‑центрами в разных регионах.

**Примеры:**  
- Автоматическое переключение на вторичный сервер БД при падении основного.  
- Перенаправление трафика в резервный дата‑центр при региональном сбое.  
- Переключение на реплику сервиса в Kubernetes при сбое пода.

## Сравнительная таблица


| Критерий | Stand‑in | Failover |
|--------|---------|--------|
| **Автоматизация** | Ручная/полуавтоматическая активация | Полностью автоматическая |
| **Время переключения** | Минуты/часы (зависит от действий оператора) | Секунды |
| **Синхронизация данных** | Не обязательна | Обязательна (для минимизации потерь) |
| **Ресурсы** | Может быть упрощённым или лёгким | Требует полных ресурсов (копия основного сервиса) |
| **Сценарии** | Плановые работы, временные замены | Критичные сбои, аварийное восстановление |
| **Сложность настройки** | Низкая | Высокая (нужен мониторинг, синхронизация, тестирование) |
| **Пример** | Временный статический сайт | Реплика БД в Active‑Passive конфигурации |

---

## Когда что применять

**Используйте Stand‑in, если:**  
- Допустимы короткие простои для ручного переключения.  
- Нужно временно заменить сервис на период обновления.  
- Нет ресурсов для полноценной репликации данных.  
- Требуется упрощённый функционал на время ремонта.

**Используйте Failover, если:**  
- Необходим нулевой или минимальный downtime.  
- Система критична для бизнеса (например, платежи).  
- Есть инфраструктура для синхронизации и мониторинга.  
- Важно автоматическое восстановление без участия человека.

## Комбинирование паттернов


На практике их часто **сочетают**:  
1. **Failover** срабатывает мгновенно при критичном сбое (переключение на реплику).  
2. Если основной сервис долго не восстанавливается, **stand‑in** используется как временная замена с упрощённым функционалом.  
3. После ремонта основного сервиса трафик возвращается, а stand‑in отключается.


**Пример:**  
- Основной сервис упал → failover автоматически переключает трафик на реплику.  
- Реплика перегружена → активируется stand‑in с кэшированными данными.  
- После восстановления → трафик возвращается на основной сервис.

---

## Вывод

- **Stand‑in** — «запасной игрок», которого выводят на поле вручную. Подходит для управляемых сценариев.  
- **Failover** — «автопилот», который мгновенно подхватывает управление при аварии. Критичен для высокодоступных систем.  

Выбор зависит от:  
- допустимого времени простоя;  
- критичности сервиса;  
- доступных ресурсов;  
- необходимости автоматизации.
