## Метрики нагрузки для high‑load приложений

Метрики нагрузки — это количественные показатели, позволяющие оценивать состояние системы под высокой нагрузкой, выявлять узкие места и принимать решения о масштабировании или оптимизации.

### Основные категории метрик

1. **Ресурсы сервера (инфраструктурные)**
	- ⭐**CPU usage** (% загрузки процессора) — перегрузка CPU ведёт к задержкам обработки запросов.
	- ⭐**Memory usage** (потребление ОЗУ) — утечки памяти или нехватка ресурсов вызывают сбои.
	- **Disk I/O** (операции ввода‑вывода) — медленные диски замедляют работу БД и кэша.
	- **Network throughput** (пропускная способность сети) — перегрузка каналов приводит к таймаутам.

2. **Производительность приложения**
	- ⭐**RPS (Requests Per Second)** — количество запросов в секунду. Ключевой показатель масштабируемости.
	- ⭐**Response time** (время ответа) — среднее/максимальное время обработки запроса. Критично для UX.
	- **Latency** (задержка) — время между отправкой запроса и получением ответа (включая сетевые задержки).
	- ⭐**Error rate** (% ошибочных запросов) — рост ошибок сигнализирует о перегрузке или багах.

3. **Состояние сервисов**
	- ⭐**Queue length** (длина очереди запросов) — если растёт, система не успевает обрабатывать нагрузку.
	- **Thread/connection pool usage** — переполнение пула потоков/соединений вызывает блокировки.
	- **Garbage Collection (GC) pauses** (паузы сборщика мусора) — в JVM/Go влияют на latency.

4. **Работа с данными**
	- ⭐**DB query time** — медленные запросы к БД тормозят приложение.
	- ⭐**Cache hit rate** (% успешных обращений к кэшу) — низкий показатель означает неэффективное кэширование.
	- ⭐**QPS (Queries Per Second)** — количество запросов в секунду к базе данных.
	- **Replication lag** (задержка репликации) — расхождение данных между мастер‑ и слейв‑серверами.

5. **Бизнес‑метрики**
	- **Active users** (активные пользователи) — коррелирует с RPS.
		- ⭐**DAU (Daily Active Users)** — количество пользователей в день.
		- **MAU** — Monthly Active Users.
	- **Transaction success rate** (% успешных операций) — важно для платёжных систем.
	- **Conversion rate** (конверсия) — падение может быть следствием деградации производительности.

### Ключевые метрики для мониторинга

1. **RPS**
	- *Почему важно*: показывает реальную нагрузку на систему.
	- *Пороговые значения*: зависят от архитектуры (например, 1 000 RPS для небольшого API vs 100 000 RPS для соцсети).
	- *Действия при росте*: вертикальное/горизонтальное масштабирование, оптимизация кода.

2. **Response time (95‑й перцентиль)**
	- *Почему важно*: средние значения скрывают «длинные хвосты» (редкие, но долгие запросы).
	- *Пример*: 95 % запросов обрабатываются за <200 мс, 5 % — за 2 с.
	- *Действия*: поиск узких мест (БД, сеть, код).

3. **Error rate**
	- *Критично для*: платёжных систем, API внешних интеграций.
	- *Типичные ошибки*: 500 (серверная), 503 (перегрузка), 429 (rate limiting).
	- *Действия*: авто‑рестарт сервисов, троттлинг, эскалация в техподдержку.

4. **Cache hit rate**
	- *Норма*: >80–90 % для высоконагруженных систем.
	- *Низкий показатель*: значит, кэш не используется эффективно (неверные TTL, частые инвалидации).
	- *Действия*: пересмотр стратегий кэширования.

5. **Queue length**
	- *Почему важно*: очередь растёт — система не справляется.
	- *Действия*: увеличение числа воркеров, оптимизация обработки задач.

6. **DB query time**
	- *Критичные значения*: >100 мс для OLTP‑систем.
	- *Действия*: оптимизация запросов, индексация, шардирование.

7. **Memory/CPU spikes**
	- *Причины*: утечки памяти, неоптимальные алгоритмы, DDoS.
	- *Действия*: профилирование кода, ограничение ресурсов (cgroups/Docker).

### Инструменты сбора метрик
- **Prometheus + Grafana** — сбор и визуализация метрик.
- **ELK Stack (Elasticsearch, Logstash, Kibana)** — анализ логов и метрик.
- **Datadog/New Relic** — коммерческие платформы мониторинга.
- **cAdvisor/Node Exporter** — мониторинг ресурсов контейнеров/серверов.
- **Jaeger/Zipkin** — распределённая трассировка запросов (для микросервисов).

### Как работать с метриками

1. **Установите пороговые значения** (thresholds) для каждой метрики.
2. **Настройте алерты** (оповещения) на критические отклонения (например, RPS > 10 000 или error rate > 5 %).
3. **Анализируйте тренды** — рост latency за неделю может указывать на скрытую проблему.
4. **Коррелируйте метрики** — например, рост CPU + падение cache hit rate могут означать неэффективное кэширование.
5. **Проводите нагрузочное тестирование** (load testing) для прогнозирования поведения системы.

### Типичные проблемы и решения

- **Рост RPS → падение response time**
	- *Решение*: горизонтальное масштабирование, кэширование, CDN.
- **Высокий error rate → переполненная очередь**
	- *Решение*: троттлинг запросов, авто‑масштабирование воркеров.
- **Низкий cache hit rate → высокая нагрузка на БД**
	- *Решение*: пересмотр TTL, стратегии инвалидации, увеличение размера кэша.
- **Memory leaks → перезапуск сервисов**
	- *Решение*: профилирование памяти, исправление кода.

### Вывод
Для high‑load систем критически важно:
- отслеживать метрики **в реальном времени**;
- настраивать **автоматические алерты**;
- регулярно проводить **нагрузочное тестирование**;
- использовать **распределённые системы мониторинга** (особенно для микросервисов).

Без системного мониторинга невозможно гарантировать стабильность и масштабируемость приложения под высокой нагрузкой.

## USE и RED — две ключевые модели мониторинга систем

Это не конкурирующие, а **взаимодополняющие** модели: 
* USE фокусируется на *ресурсах инфраструктуры*
* RED — на *производительности сервисов*.

---

### Модель USE (Brendan Gregg)

**Цель**: выявить «узкие места» на уровне аппаратных ресурсов.
**Формула**: для каждого ресурса измеряем три метрики:
- **U**tilization (загрузка);
- **S**aturation (насыщение/очередь);
- **E**rrors (ошибки).

Примеры по ресурсам

1. **CPU**
	- *Utilization*: % времени в режиме работы (не idle).
	- *Saturation*: длина очереди задач (например, `runqlen` в Linux).
	- *Errors*: аппаратные ошибки (редко; чаще — ошибки планировщика).

2. **Память**
	- *Utilization*: использованная ОЗУ (GB или %).
	- *Saturation*: своп‑активность (чтение/запись в swap).
	- *Errors*: OOM‑киллы, page faults.

3. **Диск**
	- *Utilization*: % времени занятости диска (iowait).
	- *Saturation*: очередь операций ввода‑вывода (`avgqu-sz`).
	- *Errors*: I/O‑ошибки, timeouts.

4. **Сеть**
	- *Utilization*: загрузка интерфейса (Mbps/Gbps).
	- *Saturation*: очереди пакетов, отбрасывание (drop rate).
	- *Errors*: [[CRC‑ошибки]], потерянные пакеты.

**Когда применять USE**:
	- диагностика «железных» проблем;
	- планирование масштабирования инфраструктуры;
	- анализ утилизации ресурсов.

---

### Модель RED (Tom Wilkie)

**Цель**: измерить производительность сервисов (особенно микросервисов).

**Три метрики**:
1. **R**equests (запросы) — количество HTTP/RPC‑запросов в секунду (RPS).
2. **E**rrors (ошибки) — % или число неудачных запросов (коды 5xx, таймауты).
3. **D**uration (длительность) — время обработки запроса (латентность).

Детализация

- **Requests**:
	- разбивка по endpoint’ам, методам (GET/POST), сервисам;
	- тренды RPS во времени.
- **Errors**:
	- типы ошибок (500, 503, 429 и др.);
	- корреляция с нагрузкой.
- **Duration**:
	- средние/медианные значения;
	- перцентили (p90, p95, p99) — показывают «длинные хвосты»;
	- разбивка по стадиям запроса (сеть, БД, бизнес‑логика).

**Когда применять RED**:
- мониторинг API и микросервисов;
- [[SLI|SLA/SLI]] для клиентских сервисов;
- выявление деградации производительности.

---

### Как сочетать USE и RED

1. **Шаг 1: RED — диагностика симптомов**
	- Вырос error rate? Падает RPS? Растёт latency?
	- Пример: p99 latency API подскочила до 5 с.

2. **Шаг 2: USE — поиск причины**
	- Проверяем ресурсы:
	- CPU загружен на 95 %?
	- Диск в saturation (длинная очередь I/O)?
	- Память уходит в swap?
	- Находим «узкое место».

3. **Шаг 3: действия**
	- Если проблема в CPU — оптимизируем код или масштабируем инстансы.
	- Если диск в saturation — добавляем SSD или шардируем БД.

---

### Примеры сценариев

**Сценарий 1: Рост latency API (RED)**
- *RED*: p99 duration = 3 с (норма — 200 мс).
- *USE*:
	- CPU utilization = 98 %;
	- runqlen = 10 (очередь задач).
	- *Вывод*: перегрузка CPU.
	- *Решение*: добавить инстансы или оптимизировать код.

**Сценарий 2: Ошибки 503 (RED)**
- *RED*: error rate = 15 % (503 Service Unavailable).
- *USE*:
	- Memory utilization = 100 %;
	- swap активность высокая.
	- *Вывод*: нехватка памяти, OOM‑киллы.
	- *Решение*: увеличить RAM или исправить утечки.

**Сценарий 3: Падение RPS (RED)**
- *RED*: RPS упал на 40 %.
- *USE*:
	- Disk I/O saturation (очередь 20 операций);
	- iowait = 30 %.
	- *Вывод*: медленные диски тормозят БД.
	- *Решение*: перейти на SSD или реплицировать БД.

---

### Инструменты

- **USE**:
	- `vmstat`, `iostat`, `sar` (Linux);
	- Prometheus node‑exporter + Grafana dashboards.
- **RED**:
	- Prometheus (метрики приложений);
	- Grafana (визуализация p99, error rate);
	- OpenTelemetry/Jaeger (трассировка запросов).

---

### Итог

- **USE** отвечает на вопрос *«Что сломалось на уровне железа?»*.
- **RED** отвечает на вопрос *«Как это влияет на сервис?»*.
- **Вместе** они дают полную картину: от аппаратных ограничений до пользовательского опыта.
- **Рекомендация**: стройте дашборды, где USE и RED‑метрики видны рядом — это ускорит диагностику.

## Four Golden Signals
**«Четыре золотых сигнала» (Four Golden Signals)** — это набор ключевых метрик мониторинга, предложенный Google в рамках практики [[SRE|Site Reliability Engineering]] (SRE). Они позволяют **быстро оценить здоровье системы** и выявить 90 % проблем в production‑среде.
* Google проанализировал тысячи инцидентов и обнаружил: отслеживая всего 4 параметра, можно диагностировать большинство сбоев. Это «минимально достаточный набор» для первичного мониторинга.
### Четыре сигнала

1. **Latency (задержка)**  
   - **Что измеряет**: время от отправки запроса до получения ответа.  
   - **Примеры**:  
     - время обработки HTTP‑запроса;  
     - отклик базы данных на запрос;  
     - задержка между сервисами в микросервисной архитектуре.  
   - **Важное**:  
     - смотрите на **процентили** (p95, p99), а не на среднее значение — они выявляют «длинные хвосты»;  
     - разделяйте успешные и ошибочные запросы (медленная ошибка хуже быстрой).  
   - **Пример проблемы**: latency вырос с 100 мс до 2 с → вероятна перегрузка БД или сервера.

2. **Traffic (трафик/нагрузка)**  
   - **Что измеряет**: объём запросов, которые система обрабатывает в единицу времени.  
   - **Примеры**:  
     - HTTP‑запросы в секунду (RPS);  
     - транзакции в БД в секунду;  
     - активные соединения;  
     - объём передаваемых данных (МБ/с).  
   - **Зачем**:  
     - прогнозировать масштабирование;  
     - выявлять аномальные всплески (DDoS, баги клиента).  


3. **Errors (ошибки)**  
   - **Что измеряет**: долю неудачных запросов.  
   - **Примеры**:  
     - HTTP‑коды 5xx (серверные ошибки);  
     - таймауты;  
     - некорректные ответы (например, HTTP 200 с битым JSON).  
   - **Важно**:  
     - считайте **процент ошибок** от общего числа запросов;  
     - отслеживайте динамику (резкий рост — сигнал проблемы).  


4. **Saturation (насыщение)**  
   - **Что измеряет**: степень использования ресурсов относительно их лимитов.  
   - **Примеры**:  
     - загрузка CPU (%);  
     - использование памяти (%);  
     - заполненность диска (%);  
     - длина очереди запросов;  
     - число активных соединений.  
   - **Ключевая идея**:  
     - система часто деградирует **до** достижения 100 % утилизации (обычно на 75–85 %);  
     - рост latency — ранний индикатор saturation.  


**Как применять на практике**

1. **Выберите критически важный сервис** и настройте сбор 4 сигналов.  
2. **Определите базовые пороги** (например: p99 latency < 500 мс, error rate < 0,5 %, saturation < 80 %).  
3. **Создайте дашборд** с 4 панелями (по одной на каждый сигнал).  
4. **Настройте алерты** на выход за пороги (но не слишком чувствительные, чтобы избежать «alert fatigue»).  
5. **Коррелируйте сигналы**:  
   - высокий saturation + рост latency → нехватка ресурсов;  
   - рост errors + нормальный traffic → баг в коде;  
   - резкий спад traffic + рост errors → проблема на стороне клиента.  


**Важные оговорки**

- Это **стартовая точка**, а не исчерпывающий мониторинг. Для глубокого анализа нужны дополнительные метрики (например, GC pauses, DB query time).  
- Для batch‑систем (обработка данных) важнее throughput и durability, чем latency.  
- Для ML‑систем добавляют метрики качества (accuracy, bias).
