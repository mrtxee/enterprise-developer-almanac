**IAM (Identity and Access Management)** — это набор технологий, политик и процессов для управления **идентификацией пользователей** и **контролем доступа** к ресурсам в информационных системах.

### Основная цель IAM
Обеспечить, чтобы:
* нужный человек (или сервис) получил доступ к нужным ресурсам;
* ненужные люди (и злоумышленники) не получили доступ ни к чему;
* все действия были зафиксированы и поддавались аудиту.

### Ключевые компоненты IAM

1. **Идентификация**  
   * Присвоение уникального идентификатора (логина, email, ID).  
   * Проверка подлинности пользователя (аутентификация).

2. **Аутентификация**  
   * Подтверждение, что пользователь — это действительно он.  
   * Методы: пароль, OTP, биометрия, смарт‑карта, FIDO2‑ключи.

3. **Авторизация**  
   * Определение, какие ресурсы и действия доступны пользователю.  
   * Реализация через роли, группы, политики доступа.

4. **Управление учётными записями**  
   * Создание, изменение, блокировка, удаление аккаунтов.  
   * Синхронизация между системами.

5. **Аудит и мониторинг**  
   * Журналирование действий пользователей.  
   * Отчёты о доступе и изменениях.

### Как это работает на практике

1. Пользователь пытается войти в систему (например, в корпоративную почту).  
2. Система запрашивает идентификатор (логин) и средство аутентификации (пароль + OTP).  
3. IAM‑система проверяет данные и «узнаёт» пользователя.  
4. Система сверяет права пользователя (роли/политики) и решает, какие функции ему доступны.  
5. Все действия пользователя записываются в журнал аудита.

### Основные модели управления доступом

* **RBAC (Role-Based Access Control)** — доступ по ролям (например, «менеджер», «бухгалтер»).  
* **ABAC (Attribute-Based Access Control)** — доступ по атрибутам (отдел, время суток, устройство).  
* **DAC (Discretionary Access Control)** — владелец ресурса сам назначает права.  
* **MAC (Mandatory Access Control)** — жёсткие политики безопасности (часто в госсекторе).

### Где применяется IAM

* Корпоративные сети и облачные сервисы (AWS IAM, Azure AD, Google Cloud IAM).  
* Банковские и финансовые системы.  
* Государственные информационные системы.  
* SaaS‑платформы и веб‑приложения.  
* Системы контроля физического доступа (пропускные пункты).


### Преимущества IAM

* **Безопасность** — минимизация рисков утечек и взломов.  
* **Удобство** — единый вход ([[SSO]]) для множества сервисов.  
* **Соответствие нормам** — выполнение требований регуляторов (GDPR, ФЗ‑152, PCI DSS).  
* **Эффективность** — автоматизация управления учётными записями.  
* **Прозрачность** — полный аудит действий пользователей.

### Примеры реализаций

* **Microsoft Azure Active Directory (Azure AD)** — для облачных и гибридных сред.  
* **AWS IAM** — управление доступом в инфраструктуре Amazon.  
* **Okta, OneLogin** — сторонние IDP (Identity Providers) для SSO.  
* **FreeIPA, [[Keycloak]]** — открытые решения для Linux‑окружений.

### Важные термины

* **[[SSO]] (Single Sign-On)** — единый вход в несколько систем.  
* **MFA/2FA** — многофакторная/двухфакторная аутентификация.  
* **IdP (Identity Provider)** — поставщик идентификационных данных.  
* **SP (Service Provider)** — сервис, предоставляющий ресурсы.  
* **[[SAML]], [[OAuth]], [[OIDC|OpenID Connect]]** — протоколы обмена идентификационными данными.

### Итог
IAM — это «цифровой пропуск» и «система охраны» для информационных ресурсов. Она гарантирует, что:
* только авторизованные пользователи получат доступ;  
* каждый пользователь будет иметь ровно те права, которые ему нужны;  
* все действия будут зафиксированы и проверены при необходимости.

| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **On-premise**  | - **Высокая степень контроля** Организация полностью контролирует инфраструктуру и данные, система почти не зависит от внешних факторов <br>- **Возможность кастомизации** Можно учесть специфические требования к безопасности или предписания регуляторов                                                                                                                                            | - **Высокая стоимость** Работа физических машин, на которых работает такая система, стоит очень дорого <br>- **Сложно масштабировать** Решения ограничены наличием ресурсов у компании <br>- **Трудоёмкость** Потребуется разобраться в работе системы, научиться настраивать и поддерживать её |
| **Cloud-based** | - **Легко масштабировать** Сервисы автоматически масштабируются, если меняется нагрузка <br>- **Низкая стоимость** Оплата обычно привязана к количеству пользователей, поэтому для маленьких компаний сервис стоит недорого <br>- **Доступность** Облачные решения проще настраивать и поддерживать <br>- **Единая инфраструктура** Возможна интеграция в единую систему с другими облачными сервисами | - **Высокая зависимость** На доступность и работоспособность системы влияют внешние риски. Под эти риски сейчас попадают практически все иностранные облачные IAM <br>- **Слабый контроль** Данные хранятся на облачных серверах, а значит, есть риски утечек                                   |

## RBAC vs ABAC

| **Характеристика**      | **RBAC (Role-Based Access Control)**                                                              | **ABAC (Attribute-Based Access Control)**                                                                 |
| ----------------------- | ------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| **Основной принцип**    | Доступ определяется на основе ролей пользователей                                                 | Доступ определяется на основе атрибутов субъекта, объекта и среды                                         |
| **Гранулярность**       | Средняя. Доступ группируется по ролям                                                             | Высокая. Можно создавать очень детальные правила                                                          |
| **Сложность внедрения** | Низкая или средняя. Относительно просто определить и назначить роли                               | Высокая. Нужно тщательно планировать атрибуты и правила                                                   |
| **Масштабируемость**    | Средняя — при росте организации может потребоваться создание множества ролей                      | Высокая — легко адаптируется к новым условиям за счёт гибкости атрибутов                                  |
| **Гибкость**            | Ограниченная. Модель привязана к предопределённым ролям                                           | Высокая. Можно учитывать любые атрибуты и их комбинации                                                   |
| **Администрирование**   | Простое. Управление происходит через назначение ролей                                             | Сложное. Нужно постоянно настраивать правила и атрибуты                                                   |
| **Производительность**  | Высокая. Можно быстро проверить принадлежности к роли                                             | Средняя или низкая. Необходимо проверять множество атрибутов                                              |
| **Аудит**               | Простой. Легко отследить, кому какие роли выданы                                                  | Сложный. Необходимо анализировать множество параметров                                                    |
| **Применимость**        | Подходит небольшим и средним организациям с чёткой структурой                                     | Подходит крупным организациям со сложными политиками доступа                                              |
| **Типичные атрибуты**   | — Должность — Отдел — Уровень доступа                                                             | — Время доступа — Местоположение — Устройство — Уровень риска — Состояние системы                         |
| **Пример**              | У всех бухгалтеров есть доступ к финансовой системе                                               | У бухгалтера есть доступ к финансовой системе только в рабочее время из офиса с корпоративного устройства |
| **Недостатки**          | — «Взрыв ролей» при масштабировании — Недостаточная гибкость — Сложно временно делегировать права | — Сложность реализации — Повышенные требования к ресурсам — Сложность первоначальной настройки            |
