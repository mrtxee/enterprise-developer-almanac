**Security Contexts** и **Scope‑based Authorization** решают смежные задачи контроля доступа, но принципиально различаются по механизму и уровню детализации. Разберём оба понятия и их ключевые отличия.


### Security Contexts (контексты безопасности)

**Что это:** набор динамических атрибутов, описывающих *текущую среду* запроса. Это «окружение», в котором выполняется действие.


**Из чего состоит** (примеры атрибутов):
* идентификатор пользователя/службы;
* IP‑адрес клиента;
* время суток/дата;
* геолокация;
* тип устройства (мобильное/десктоп);
* состояние сессии (аутентифицирован/аноним);
* роли пользователя в текущей сессии;
* уровень доверия устройства;
* сетевой сегмент (VPN, корпоративная сеть).

**Как работает:**  
При запросе система собирает все доступные атрибуты контекста и на их основе принимает решение о доступе. Например:  
> «Разрешить чтение документа, только если запрос идёт из корпоративной сети (IP 192.168.0.0/16) *и* пользователь имеет роль „редактор“ *и* время между 9:00–18:00».

**Где применяется:**  
* ABAC (Attribute‑Based Access Control);
* политики сетевого доступа (firewall, VPN);
* динамическая авторизация в микросервисах.


### Scope‑based Authorization (авторизация на основе скопов)

**Что это:** статический набор *разрешений*, явно присвоенных пользователю/приложению. Скопы — это «билеты» на конкретные действия.


**Примеры скопов:**  
* `read:documents`
* `write:reports`
* `delete:temp_files`
* `admin:users`
* `openid` (специальный скоп для OpenID Connect)


**Как работает:**  
1. При аутентификации сервис выдаёт токен с перечнем скопов.  
2. При запросе система проверяет: есть ли нужный скоп в токене.  
3. Если скоп присутствует — доступ разрешён; если нет — отклонён.  


**Где применяется:**  
* OAuth 2.0 / OpenID Connect;
* API‑шлюзы;
* делегированный доступ приложений к ресурсам пользователя.


### Ключевые отличия


| Критерий | Security Contexts | Scope‑based Authorization |
|----------|------------------|-------------------------|
| **Природа данных** | Динамические атрибуты среды (меняются от запроса к запросу) | Статические разрешения (задаются при выдаче токена) |
| **Детализация** | Очень тонкая (можно учитывать десятки параметров) | Грубая (скоп покрывает группу действий) |
| **Гибкость** | Высокая: правила адаптируются к контексту | Низкая: скопы фиксированы до перевыпуска токена |
| **Сложность правил** | Поддерживает сложные логические условия («И», «ИЛИ», «НЕ») | Простые проверки на наличие скопа |
| **Типичные сценарии** | «Доступ только из офиса в рабочее время» | «Приложение может читать почту, но не удалять» |
| **Интеграция** | Требует развитой системы оценки атрибутов | Встроена в OAuth 2.0, легко внедряется |

| **Аудит** | Фиксирует полный контекст запроса | Фиксирует только использованные скопы |



### Как они взаимодействуют

На практике часто используют **комбинированный подход**:  
1. **Скопы** задают *базовый уровень доступа* (что пользователь/приложение *может* делать).  
2. **Контексты** накладывают *дополнительные ограничения* (при каких условиях это разрешено).  


**Пример:**  
- Скоп: `write:reports` (пользователь *может* редактировать отчёты).  
- Контекст: «но только если запрос идёт с корпоративного устройства *и* в рабочие часы».  


### Вывод
- **Security Contexts** — это «умные» правила, учитывающие *обстоятельства* запроса. Подходят для тонкой настройки доступа.  
- **Scope‑based Authorization** — это «пропуск» с заранее оговоренными правами. Прост в реализации, но менее гибок.  


Выбор между ними (или их комбинация) зависит от требований к безопасности и сложности сценариев доступа.




### Кратко: в чём разница

**Security Contexts** — это *набор данных* (атрибутов), описывающих обстоятельства запроса (кто, где, когда, с какого устройства и т. п.).

**Contextual Access** (Context‑Based Access Control, CAC) — это *модель управления доступом*, которая *использует* security contexts для принятия решений «разрешить/запретить».


Иначе говоря:  
- **security contexts** — «сырые данные» о ситуации;  
- **contextual access** — логика, которая на основе этих данных выдаёт вердикт.

### Security Contexts: что входит

Это динамические атрибуты, собираемые в момент запроса:
- **пользователь**: ID, роль, группа, история действий;
- **устройство**: тип (ПК/смартфон), ОС, статус антивируса, доверенность устройства;
- **сеть**: IP‑адрес, геолокация, тип сети (корпоративная/публичная);
- **сессия**: время начала, число параллельных сессий, смена IP в ходе сессии;
- **время**: текущее время, день недели;
- **ресурс**: путь/объект, к которому идёт запрос;
- **действие**: тип операции (чтение, запись, удаление).


*Пример контекста:*  
```json
{
  "user_id": "alice",
  "role": "editor",
  "device_type": "laptop",
  "os": "Windows 11",
  "ip": "203.0.113.45",
  "location": "Moscow",
  "time": "2025-11-03T10:15:00Z",
  "resource": "/docs/confidential-report.pdf",
  "action": "read"
}
```

### Contextual Access (CAC): как работает


Система берёт security contexts и по правилам решает, разрешить ли доступ. Ключевые черты:
- **Динамичность**. Правила применяются в реальном времени для каждого запроса.
- **Многофакторность**. Учитывается комбинация атрибутов (например, «роль + геолокация + время»).
- **Гибкость**. Можно задавать сложные условия:  
  - «Разрешить чтение, если пользователь — редактор, устройство доверенное И запрос идёт из офиса между 9:00–18:00».  
  - «Запретить запись, если устройство не в реестре корпоративных активов».
- **Адаптивность**. При изменении контекста (например, пользователь вышел из офисной сети) доступ может быть немедленно ограничен.


---

### Примеры сценариев


1. **Безопасный удалённый доступ**  
   - *Контекст*: пользователь подключается из дома (`location: "home"`), время — 22:00.  
   - *Решение CAC*: разрешить просмотр документов, но запретить изменение критически важных данных.


2. **Защита от скомпрометированных учётных записей**  
   - *Контекст*: логин с нового устройства и необычного IP.  
   - *Решение CAC*: запросить дополнительную аутентификацию (MFA) или ограничить доступ до подтверждения.


3. **Контроль мобильных устройств**  
   - *Контекст*: запрос с смартфона, на котором нет корпоративного MDM‑профиля.  
   - *Решение CAC*: запретить скачивание конфиденциальных файлов.


---


### Чем отличается от статических моделей


- **RBAC** (Role‑Based Access Control): доступ только по роли (без учёта контекста).  
  *Пример*: «редактор может читать все документы».  
- **ABAC** (Attribute‑Based Access Control): ближе к CAC, но часто использует статические атрибуты (например, департамент пользователя), а не динамический контекст сессии.  
- **CAC**: явно учитывает *текущие* обстоятельства запроса (геолокация, устройство, время).


---


### Итог


- **Security Contexts** — это «данные о ситуации» (кто/где/когда/с чего запрашивает ресурс).  
- **Contextual Access** — это механизм, который *на основе* этих данных принимает решение о доступе.  


**Практический вывод**:  
Чтобы внедрить contextual access, нужно:  
1. Собирать security contexts (через агенты, логи, API).  
2. Задать правила, связывающие контексты с разрешениями.  
3. Интегрировать движок правил в точку принятия решений (шлюз, приложение, IAM‑систему).
