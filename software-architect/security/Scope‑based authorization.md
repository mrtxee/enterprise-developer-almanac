**Scope‑based authorization** (авторизация на основе областей/скопов) — это модель контроля доступа, где права пользователя определяются через **назначенные ему «скопы»** (scopes) — логические группы разрешений, описывающие, *какие действия* и *к каким ресурсам* он может выполнять.

### Суть подхода

Вместо детального перечисления прав для каждого объекта (например, «пользователь A может редактировать документ X») системе присваивают **набор скопов** — кратких меток‑разрешений типа:
- `read:documents`
- `write:reports`
- `delete:temporary_files`
- `admin:users`

При запросе к ресурсу система проверяет: есть ли у пользователя нужный скоп в его текущем наборе. Если есть — доступ разрешён; если нет — отклонён.

### Как это работает (упрощённо)

1. **Определение скопов**  
   Администратор задаёт именованные скопы, каждый из которых кодирует определённый тип доступа к ресурсу (например, `view:finance_data`, `edit:profile`).

2. **Назначение скопов пользователю**  
   При аутентификации сервис выдаёт пользователю токен (например, OAuth 2.0), в котором перечислены его скопы.  
   *Пример токена:*  
   ```json
   {
     "user_id": "123",
     "scopes": ["read:docs", "write:notes", "print:any"]
   }
   ```

3. **Проверка при запросе**  
   Когда пользователь пытается выполнить действие (например, «сохранить заметку»), сервер:
   - извлекает скопы из токена;
   - сверяет их с требуемым скопом для операции (`write:notes`);
   - разрешает или запрещает действие.

4. **Динамическая смена прав**  
   Скопы могут меняться в зависимости от контекста:  
   - время суток;  
   - устройство (мобильное/десктоп);  
   - IP‑адрес;  
   - роль в текущем сеансе (например, «модератор» в чате).

### Где применяется

- **OAuth 2.0 / OpenID Connect** — стандартно используют скопы для ограничения доступа приложений к API (например, приложение просит скоп `mail:send`, но не получает `mail:delete`).  
- **Микросервисы** — каждый сервис проверяет скопы в токене, чтобы решить, выполнять ли запрос.  
- **SaaS‑платформы** — предоставление разным клиентам разных наборов функций через комбинацию скопов.  
- **API‑гейтвеи** — фильтрация запросов на уровне шлюза по скопам.

### Плюсы

- **Простота управления** — вместо тысячи правил достаточно назначить/отозвать скопы.  
- **Масштабируемость** — легко добавлять новые скопы без переписания логики доступа.  
- **Гибкость** — скопы можно комбинировать и накладывать условия.  
- **Стандартизация** — интеграция с OAuth 2.0 делает подход универсальным.  
- **Аудиторность** — в токене явно видны все разрешённые действия.

### Минусы и ограничения

- **Грубость гранулярности** — скопы часто покрывают группы действий, а не индивидуальные объекты (нельзя сказать «только к документу X»).  
- **Риск избыточных прав** — если скоп слишком широкий (`admin:*`), пользователь получает больше, чем нужно.  
- **Сложность проектирования** — нужно заранее продумать семантику скопов, чтобы избежать конфликтов.  
- **Зависимость от токена** — если токен украден, злоумышленник получит все скопы из него.

### Пример

**Сценарий:** веб‑приложение позволяет пользователям:
- читать свои документы (`read:my_docs`);
- редактировать общие заметки (`write:shared_notes`);
- печатать любые файлы (`print:any`).

**Процесс:**
1. Пользователь логинится, система выдаёт токен со скопами:  
   ```json
   "scopes": ["read:my_docs", "write:shared_notes"]
   ```
2. Пользователь пытается распечатать файл — система видит, что скопа `print:any` нет, и отказывает.  
3. Администратор добавляет скоп `print:any` — в следующем сеансе печать становится доступна.

### Отличие от других моделей

- **RBAC (Role‑Based Access Control)** — права даются через роли («менеджер», «бухгалтер»), а не через скопы.  
- **ABAC (Attribute‑Based Access Control)** — доступ зависит от атрибутов (время, местоположение), а не от фиксированных меток.  
- **ACL (Access Control List)** — права прописываются для каждого объекта отдельно, а не через общие скопы.

### Итог

Scope‑based authorization — это **удобный и стандартизированный способ ограничить, что пользователь может делать в системе**, используя набор именованных «разрешений» (скопов). Он особенно популярен в API и облачных сервисах благодаря простоте интеграции с OAuth 2.0, но требует аккуратного проектирования скопов, чтобы избежать избыточных прав.
